# 1과목 1장: 전사아키텍처 개요

## 1. 전사아키텍처 정의

**전사아키텍처(Enterprise Architecture, EA)** 는 조직의 비즈니스 목표를 달성하기 위해 업무, 데이터, 애플리케이션, 기술 등 전사 구성 요소와 이들 간의 관계를 체계적으로 정의·관리하는 프레임워크이다.

| 구분 | 설명 |
|------|------|
| 목적 | 비즈니스-IT 정렬(Alignment), AS-IS → TO-BE 전환 계획 수립 |
| 범위 | 전사(Enterprise) 수준의 모든 IT 및 비즈니스 자원 |
| 핵심 산출물 | 아키텍처 뷰, 원칙, 표준, 로드맵 |

### EA의 5대 아키텍처 도메인

전통적인 4대 도메인(BA·DA·AA·TA)에 **보안 아키텍처(SA)** 를 더해 5대 도메인으로 구성한다. 위협 증가와 개인정보보호법 강화로 보안은 사후 부가활동이 아닌, 전략 수립 단계부터 고려할 독립 도메인으로 격상되었다.

| 도메인 | 약어 | 주요 내용 | 산출물 예시 |
|--------|------|---------|----------|
| 비즈니스 아키텍처 | BA | 전략, 프로세스, 조직 — 모든 아키텍처의 출발점 | 업무 기능 분류체계, 업무 흐름도 |
| 데이터 아키텍처 | DA | 데이터 구조, 표준, 흐름 | 개념/논리 데이터 모델, 데이터 표준 |
| 애플리케이션 아키텍처 | AA | 응용 시스템 구조·관계 | 응용 기능 분류체계, 인터페이스 목록 |
| 기술 아키텍처 | TA | 하드웨어, 소프트웨어, 네트워크 | 기술 참조 모델, 시스템 구성도 |
| 보안 아키텍처 | SA | 접근통제·암호·개인정보·위협모델 — 전 계층을 관통하는 보호막 | 보안 정책, 접근통제 체계, 재해복구 체계 |

> **핵심**: EA는 단순 IT 계획이 아닌 비즈니스-IT 정렬이 핵심 목표이다. BA가 방향을 정의하고 DA·AA가 정보시스템으로 구체화하며 TA가 물리적 기반을 제공하고, SA는 전 영역을 감싸 보호한다.

## 1-1. EA를 이해하는 공식 — RMP(규칙·모델·계획)

EA를 가장 체계적으로 이해·기억하는 공식은 **RMP**: 규칙(Rule) 아래 모델(Model)이라는 청사진을 그리고, 이를 현실로 만드는 계획(Plan)을 세운다.

| 관점 | 정의 | 예시 |
|---|---|---|
| R — 규칙(Rule) | IT 의사결정 시 반드시 준수해야 하는 원칙·기준 | EA 원칙, 기술표준, 보안정책, 데이터 명명규칙 |
| M — 모델(Model) | 현행/목표를 정형화된 표기법으로 구조화한 청사진 | BPMN, ERD, 구성도, 네트워크 토폴로지 |
| P — 계획(Plan) | 현행에서 목표로 가기 위한 실행 가능한 이행계획 | Gap 분석 → 과제 도출 → 우선순위 → 전환 아키텍처 |

> 규칙은 기준, 모델은 그림, 계획은 그에 이르는 길이다.

## 1-2. 전사(Enterprise) 범위 판단 4대 기준

"전사"는 물리적 회사 전체가 아니라 **동일한 의사결정 권한과 통합된 자원 관리가 적용되는 경계**를 뜻한다.

| # | 기준 | 판단 질문 |
|---|------|---------|
| 1 | 지배구조(Governance) | 원칙·표준을 강제할 단일 의사결정 기구(ARB)가 있는가? |
| 2 | 예산·투자(PPM) | IT 투자예산을 통합 기획·통제하는 주체가 명확한가? |
| 3 | 데이터 공유 | 핵심 마스터 데이터를 공동으로 정의·소유·책임지는가? |
| 4 | IT 관리(ITSM·CMDB) | 인프라·보안정책·운영표준을 공통 적용·관리하는가? |

> 네 질문에 모두 '그렇다'고 답할 수 있는 가장 큰 조직 단위가 전사의 범위다.

## 1-3. 추적성(Traceability)과 영향분석

**추적성**이란 요구사항부터 구현 구성요소까지 인과·의존 관계를 양방향으로 추적하는 능력이다.

| 유형 | 정의 | 검증하는 것 |
|------|------|-----------|
| 수직적 추적성(Vertical) | 동일한 뷰(열) 안에서 관점(행)이 다른 산출물 간 연결 (예: 핵심정보목록→개념모델→논리모델→물리스키마) | 비즈니스 전략이 시스템 구현까지 왜곡 없이 반영되었는지 |
| 수평적 추적성(Horizontal) | 동일한 관점(행) 안에서 뷰(열)가 다른 산출물 간 연결 (예: 논리모델↔애플리케이션 기능↔배포 서버) | 아키텍처의 완전성·일관성 |

**영향분석(Impact Analysis)**: 특정 요소의 변경이 어떤 산출물·업무·비즈니스 목표까지 파급되는지 역추적하는 것 — 추적성이 만들어내는 핵심 실무 가치.

## 1-4. EA 거버넌스 원칙과 ARB

원칙은 선언이 아니라 측정 가능한 지표와 예외절차를 갖춘 실행 지침이어야 한다.

**5대 거버넌스 원칙**: ① 표준 준수, ② 변경 관리, ③ 품질·보안 내재화, ④ 재사용·공유, ⑤ 메타데이터 우선

**원칙 정의 템플릿 6항목**

| 항목 | 정의 내용 |
|---|---|
| 원칙 | 핵심 개념의 간결한 기술 |
| 의미 | 구체적 의미와 적용 범위 |
| 배경 | 원칙이 필요한 비즈니스·기술적 이유 |
| 기대효과 | 준수 시 기대되는 긍정적 결과 |
| 지표 | 준수 여부를 측정하는 KPI |
| 예외처리 | 미준수 시 ARB 심의·승인 절차 |

**ARB(Architecture Review Board, 아키텍처 리뷰보드)**: 표준을 따르지 못할 때 공식 승인·이력관리를 담당하는 의사결정 기구.

## 1-5. 레퍼지토리(Repository) — 단일 진실 공급원

레퍼지토리는 단순 파일 폴더가 아니라, 모든 도메인 산출물·메타데이터·개체 간 링크·버전·변경이력을 통합 관리하는 **단일 진실 공급원(Single Source of Truth, SSoT)** 이다. TOGAF·ADM 같은 방법론이 무엇을 어떤 순서로 만들지 규정하고, 사용자는 레퍼지토리를 통해 필요한 아키텍처 정보를 조회한다.

## 2. 전사아키텍처 프레임워크

EA 프레임워크는 아키텍처를 개발·관리하기 위한 체계적 방법론과 구조를 제공하는 틀이다.

### 2.1 Zachman Framework

존 재크만(John Zachman, 1987). **6 관점 × 6 역할 = 36개 셀** 구조.

**6가지 관점(Column):**

| 관점 | 키워드 | 아키텍처 요소 |
|------|--------|------------|
| What | 무엇을 | 데이터 |
| How | 어떻게 | 기능/프로세스 |
| Where | 어디서 | 네트워크/위치 |
| Who | 누가 | 사람/조직 |
| When | 언제 | 시간/이벤트 |
| Why | 왜 | 동기/목표/업무규칙 |

**6가지 역할(Row):**

| 행 | 역할 |
|----|------|
| 1 | 기획자(Planner)/범위 |
| 2 | 소유자(Owner)/기업 모델 |
| 3 | 설계자(Designer)/시스템 모델 |
| 4 | 구현자(Builder)/기술 모델 |
| 5 | 하도급자(Subcontractor)/세부 표현 |
| 6 | 운영자(User)/실제 시스템 |

> **Zachman 원형(6×6)**: 위 36개 셀 구조는 Zachman Framework 고유의 분류체계이며, 실무에서 쓰이는 아래 "아키텍처 매트릭스(4×6)"와는 별개 개념이므로 구분해서 기억한다.

### 2.1a 실무 아키텍처 매트릭스 (관점×뷰, 4행×6열)

Zachman의 아이디어에서 유래했으나, 실무에서는 이해관계자 4단계(행) × 육하원칙 6열로 단순화한 매트릭스를 사용한다.

| 관점 \ 뷰 | 데이터(What) | 프로세스(How) | 네트워크(Where) | 사람(Who) | 시간(When) | 동기(Why) |
|---|---|---|---|---|---|---|
| 계획자(Planner) | 핵심 정보목록 | 핵심 성공요인 | 사업장 위치 | 조직도 | 연간 사업계획 | 비즈니스 전략 |
| 책임자(Owner) | 개념 데이터모델 | 업무 프로세스 모델 | 업무 지역 분포 | 역할 정의 | 이벤트 목록 | 업무 규칙 |
| 설계자(Designer) | 논리 데이터모델 | 앱 기능 설계서 | 시스템 배치도 | 권한 모델 | 처리 주기 정의 | 시스템 제약조건 |
| 개발자(Builder) | 물리 DB 스키마 | 소스 코드 | 서버·장비 위치 | 사용자 계정 | 배치 스케줄 | 구현 규칙 |

> 행(관점)은 위→아래로 추상→구체, 열(뷰)은 What·How·Where·Who·When·Why. Zachman 원형(6×6)과 혼동하지 말 것 — 실무 매트릭스는 행 4개(계획자/책임자/설계자/개발자)만 사용한다.

### 2.2 TOGAF (The Open Group Architecture Framework)

The Open Group이 개발한 EA 방법론. **ADM(Architecture Development Method을 핵심으로 한다.

**ADM 순환 단계:**

```
예비 단계 → A(아키텍처 비전) → B(비즈니스 아키텍처) → C(정보시스템 아키텍처)
→ D(기술 아키텍처) → E(기회·해결방안) → F(이전계획) → G(구현거버넌스)
→ H(아키텍처 변경 관리) → (A로 순환)
```

| 단계 | 주요 산출물 |
|------|---------|
| A. 아키텍처 비전 | 이해관계자 분석, 비전 문서 |
| B. 비즈니스 아키텍처 | 비즈니스 프로세스 모델 |
| C. 정보시스템 아키텍처 | 데이터 모델, 애플리케이션 목록 |
| D. 기술 아키텍처 | 기술 표준, 플랫폼 명세 |
| E. 기회·해결방안 | 갭 분석, 후보 솔루션 |
| G. 구현 거버넌스 | 준수 여부 감독 |
| H. 변경 관리 | 변경 요청 처리 |

**TOGAF 아키텍처 리포지터리** 구성: 메타모델, 역량, 랜드스케이프, 표준 정보 기반

### 2.3 FEA (Federal Enterprise Architecture)

미국 연방정부 EA 체계. **5개 참조 모델** 구성:

| 약어 | 참조 모델 |
|------|---------|
| PRM | 성과 참조 모델 |
| BRM | 비즈니스 참조 모델 |
| SRM | 서비스 컴포넌트 참조 모델 |
| TRM | 기술 참조 모델 |
| DRM | 데이터 참조 모델 |

### 2.4 국내 ITA/EA 프레임워크

「전자정부법」에 근거한 국내 공공기관 EA 체계. 도메인 구성은 위 "EA의 5대 아키텍처 도메인"(BA/DA/AA/TA/SA)과 동일하며, 별도의 "성과 아키텍처" 도메인은 존재하지 않는다.

## 3. 전사아키텍처 참조 모델

**EA 참조 모델(Reference Model)** 은 아키텍처 구성 요소를 표준화된 방식으로 분류·정의한 모델로, 기관 간 아키텍처 정보 공유와 재사용을 위한 공통 언어를 제공한다.

### 3.1 참조 모델의 역할

| 역할 | 설명 |
|------|------|
| 표준화 | 아키텍처 구성 요소의 공통 분류 체계 제공 |
| 재사용 | 기관 간 공통 서비스·컴포넌트 재사용 촉진 |
| 비교·평가 | AS-IS와 TO-BE 아키텍처 비교 기준 |
| 거버넌스 | 아키텍처 표준 준수 여부 판단 기준 |

### 3.2 국내 IT 참조 모델 (ITA)

| 참조 모델 | 내용 |
|---------|------|
| BRM (비즈니스 참조 모델) | 정부 업무 기능 분류체계 |
| SRM (서비스 참조 모델) | 공통 IT 서비스 분류 |
| TRM (기술 참조 모델) | 표준 기술 컴포넌트 분류 |
| DRM (데이터 참조 모델) | 데이터 항목·표준 분류 |

### 3.3 AS-IS / TO-BE 아키텍처

| 구분 | 설명 |
|------|------|
| AS-IS (현재 아키텍처) | 현재 운영 중인 IT 환경 |
| TO-BE (목표 아키텍처) | 미래 달성 목표 상태 |
| 전환 계획 (Transition Plan) | AS-IS → TO-BE 단계별 로드맵 |

## 4. 전사아키텍처 프로세스

EA 프로세스는 전사아키텍처를 수립·유지하는 단계적 활동 체계이다.

### 4.1 EA 수명주기 5단계

EA는 일회성 구축이 아니라, 평가 결과가 다시 계획으로 환류되는 순환 활동이다.

```
① 계획(Plan) → ② 설계(Design) → ③ 구현(Implement) → ④ 운영(Operate) → ⑤ 평가(Evaluate) → (①로 환류)
```

| 단계 | 내용 |
|------|------|
| ① 계획(Plan) | 전략 분석, 목표 아키텍처 정의 (산출: 아키텍처 비전) |
| ② 설계(Design) | Gap 분석, 이행과제 도출 (산출: 이행 로드맵) |
| ③ 구현(Implement) | 이행 프로젝트 착수·감독, 구현 거버넌스 수행 |
| ④ 운영(Operate) | 성능·가용성 모니터링, 변경관리 상시 운영 |
| ⑤ 평가(Evaluate) | ROI·품질·준수율 측정, 성숙도 진단 후 환류 |

#### (참고) EA 준비·방향수립 초기 활동 (수명주기 ①계획 단계의 세부 활동)

```
EA 준비 → EA 방향 수립 → AS-IS 현황 파악 → TO-BE 목표 수립 → 이행 계획 수립 → 관리·유지
```

| 단계 | 주요 활동 |
|------|---------|
| EA 준비 | 조직·방법론 수립, 범위 정의 |
| 방향 수립 | 비전, 원칙, 목표 정의 |
| AS-IS 현황 파악 | 현행 아키텍처 정보 수집·문서화 |
| TO-BE 목표 수립 | 목표 아키텍처 설계 |
| 이행 계획 | 갭 분석, 프로젝트 로드맵 |
| 관리·유지 | 아키텍처 최신화, 거버넌스 운영 |

#### 변경관리 6단계와 RACI

운영 단계에서 변화가 발생하면 통제된 변경 관리 프로세스를 거쳐야 하며, 추적성 기반 영향분석이 선행되어야 한다.

| 단계 | 내용 |
|------|------|
| ① 요구 식별 | 변경요청서 접수 |
| ② 영향 분석 | 추적성 기반 파급효과 분석 |
| ③ 표준·모델 변경 | 변경 초안·리스크 검토 |
| ④ 승인 | ARB·운영위 심의 |
| ⑤ 교육·배포 | 공지·교육·포털 게시 |
| ⑥ 효과 측정 | 기대효과 검증·피드백 |

**RACI**: CIO/EDA = **A**(최종 승인·공표), DA·EA팀 = **R**(프로세스 운영·영향분석·조율), User = **C/I**(검토 의견·교육 참여).

### 4.2 EA 성숙도 모델 (5단계)

| 단계 | 명칭 | 특징 |
|------|--------|------|
| 1 | 초기(Initial) | 인식 부족, 비공식·비정기 활동 |
| 2 | 반복(Developing) | 일부 영역 시작, 전사 확산·일관성 부족 |
| 3 | 정의(Defined) | 전사 표준·프로세스 문서화, 거버넌스 수립 |
| 4 | 관리(Managed) | KPI로 정량 측정·관리, 성과 기반 개선 |
| 5 | 최적화(Optimizing) | 조직문화로 내재화, 혁신 주도 — **최고 수준** |

> 시험에서는 3(표준 정의)·4(정량화 관리)·5(자동화·최적화) 단계가 주로 출제된다.

### 4.3 EA 원칙 특성

| 특성 | 의미 |
|------|------|
| 보편성 | 전사 적용 가능한 일반 원칙 |
| 명확성 | 모호하지 않은 표현 |
| 안정성 | 자주 변경되지 않아야 함 |
| 완전성 | EA 전 영역 커버 |

## 5. 데이터 아키텍처(DA) 심화

### 5.1 아키텍처의 3가지 구성요소

| 구성요소 | 설명 |
|---------|------|
| Rule(규칙) | 조직의 전략·원칙·지침으로 아키텍처 설계의 기준 확립 |
| Plan(계획) | 현재와 목표 아키텍처를 정의하여 이행·구축 계획 수립 |
| Model(모델) | 참조모델/비즈니스/데이터/애플리케이션/기술 아키텍처 수립 |

### 5.2 효과적인 데이터 아키텍처의 특징

| 특징 | 설명 |
|------|------|
| 현행 비즈니스 지원 | 현행 비즈니스를 지원하면서 미래 변화에 유연하게 대응 |
| 핵심 데이터 집중 | 필수·핵심 데이터에 집중 (불필요한 모든 데이터 포함 지양) |
| Actionable(실행가능성) | 명확한 활동과 마일스톤 정의로 실행 가능해야 함 |
| Evolutionary(진화성) | 변화하는 요구사항과 기술에 대응 가능한 유연성 |

### 5.3 데이터 아키텍처 실패 요인

1. 불필요한 모든 데이터와 정보를 포함하려는 시도
2. 구조 설계에 대한 전문성 부족
3. IT 부서의 독점적 소유 (이해관계자 참여 필요)
4. 단계적 성과 미확인 (진행 중 검증 필요)

### 5.4 데이터 아키텍처 모델 계층

```
전사 데이터 영역 모델 → 개념 데이터 모델 → 논리 데이터 모델 → 물리 데이터 모델
     (주제 영역 분류)       (핵심 엔터티 도출)    (속성·관계 상세화)   (물리 DB 설계)
```

### 5.4a DRM(데이터 참조 모델)의 4계층 구조

| 계층 | 정의 | 예시 |
|---|---|---|
| 주제영역(Subject Area) | 가장 상위의 데이터 분류 | 고객·상품·계약·재무·인사 |
| 개체(Entity)/데이터세트 | 구체적인 개체 | 고객기본정보·고객등급정보 |
| 속성(Attribute) | 개체의 특징 | 고객번호·고객명·생년월일 |
| 코드·도메인(Code/Domain) | 값의 허용 범위 통제 | 성별코드 M/F, 일자 도메인 YYYY-MM-DD |

**DRM 관리 체크리스트 6항목**: ① 표준 용어(사전 등록 명칭 준수), ② 정의(오해 없는 의미 기술), ③ 형식·값범위(타입·길이·도메인·코드), ④ 관리자·소유자(현업/IT 지정), ⑤ 버전(변경 이력·사유·일자), ⑥ 출처(원본 시스템 명시).

### 5.5 데이터 참조모델 구축 방법

1. 동종·유사 업종의 선진 참조모델 활용
2. 상위 및 연계 대상의 참조모델 활용
3. 외부(국외) 표준 활용
4. 현행 데이터 구조 참고
5. 외부 데이터 전문 인력을 통한 정의

### 5.6 데이터 참조모델 지속적 유지관리 기준

| 기준 | 설명 |
|------|------|
| 범용성 | 다양한 업무 영역에서 참조 가능 |
| 단순성 | 복잡하지 않은 단순한 모델 |
| 표준성 | 일반적인 표준 용어 사용 |
| 정확성 | 반드시 정확한 내용 |
| 정보 이용성 | 엔터티 정의·관계·규칙 등 포함 |
| 분류성 | 업무 영역과 업종별 분류 가능 |

### 5.7 데이터 참조모델 기대효과

1. 데이터 표준화 및 재사용 환경 구축
2. 이식성 및 확장성 향상
3. 조직 및 시스템 간 상호 운용성 향상
4. 데이터 품질 향상 및 생산성 증대
5. 중복 투자 방지 및 비용 절감

### 5.8 기술 참조모델(TRM)의 특징

1. 구축하기 쉽고 활용 효과가 커서 **가장 먼저 적용**되는 참조모델
2. 개별 기업에서도 기술 참조모델을 별도 정의하여 사용하는 것이 일반적
3. 기업에 적합한 DBMS 선택 기준 제공
4. 시스템 구축에 사용할 기술의 표준 프로파일 분류 기준 제공

## 출제 포인트

1. EA 5대 도메인: BA·DA·AA·TA·SA (보안 아키텍처 포함, "국내 6대 도메인/성과 아키텍처"는 존재하지 않음)
2. 국내 ITA 법적 근거: 「전자정부법」, 도메인 구성은 국제 표준과 동일한 5대 도메인
3. Zachman 원형: 6×6 = 36개 셀, 분류 체계 중심 / 실무 아키텍처 매트릭스: 4행(계획자·책임자·설계자·개발자)×6열(What~Why) — 두 개념 구분 필수
4. Zachman 6관점(열): What/How/Where/Who/When/Why
5. TOGAF: ADM 방법론, 예비+A~H 단계 순환 (예비 단계 포함 9단계)
6. FEA 5대 참조 모델: PRM/BRM/SRM/TRM/DRM
7. EA 참조 모델 역할: 표준화·재사용·비교평가·거버넌스
8. EA 성숙도 5단계: 초기(Initial)→반복(Developing)→정의(Defined)→관리(Managed)→최적화(Optimizing), 최고 = 최적화
9. EA 원칙 4특성: 보편성·명확성·안정성·완전성
10. AS-IS = 현재, TO-BE = 목표, 전환계획 = 로드맵
11. EA 수명주기 5단계: 계획(Plan)→설계(Design)→구현(Implement)→운영(Operate)→평가(Evaluate), 환류형 순환
12. RMP: 규칙(Rule)·모델(Model)·계획(Plan) — EA를 이해하는 핵심 공식
13. 전사 범위 판단 4대 기준: 지배구조(ARB)·예산투자(PPM)·데이터공유·IT관리(ITSM·CMDB)
14. 추적성: 수직적(같은 뷰, 다른 관점)/수평적(같은 관점, 다른 뷰) → 영향분석의 기반
15. EA 거버넌스 5대 원칙: 표준준수·변경관리·품질보안내재화·재사용공유·메타데이터우선
16. 원칙 정의 템플릿 6항목: 원칙·의미·배경·기대효과·지표·예외처리
17. ARB: 표준 예외 승인 등 아키텍처 준수를 심의하는 공식 기구
18. 레퍼지토리(Repository) = 단일 진실 공급원(SSoT)
19. DRM 4계층: 주제영역→개체/데이터세트→속성→코드·도메인
20. 변경관리 6단계: 요구식별→영향분석→표준·모델변경→승인→교육·배포→효과측정, RACI(CIO/EDA=A, DA·EA팀=R, User=C/I)
21. EA 프로세스 초기 활동: 준비→방향수립→AS-IS→TO-BE→이행계획→관리유지
