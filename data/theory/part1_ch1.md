# 1과목 1장: 데이터 모델링의 이해

## 1. 모델링의 정의와 특징

### 모델링의 정의
- 복잡한 **현실세계를 단순화**시켜 표현하는 것
- 사물 또는 사건에 관한 양상이나 관점을 명확하게 하는 것
- 현실 세계의 **추상화된 반영**

> **핵심**: 모델링 = "현실세계를 추상화, 단순화, 명확화 하기 위해 일정한 표기법에 의해 표현하는 기법"

```
현실세계 → [추상화, 단순화, 명확화] → 데이터 모델
```

### 모델링의 세 가지 특징

| 특징 | 설명 |
|------|------|
| 추상화 (모형화) | 현실세계를 일정한 형식에 맞추어 표현 |
| 단순화 | 약속된 규약에 의해 제한된 표기법이나 언어로 표현 |
| 명확화 | 애매모호함을 제거하고 정확하게 현상을 기술 |

### 모델링의 세 가지 관점

| 관점 | 영문 | 설명 |
|------|------|------|
| 데이터 관점 | Data, What | 업무가 어떤 데이터와 관련이 있는지, 데이터간의 관계 |
| 프로세스 관점 | Process, How | 업무가 실제하고 있는 일은 무엇인지, 무엇을 해야 하는지 |
| 상관 관점 | Data vs Process | 업무가 처리하는 일의 방법에 따라 데이터는 어떻게 영향을 받는지 |

## 2. 데이터 모델링의 정의와 중요성

### 데이터 모델링의 정의
1. 정보 시스템을 구축하기 위한 **데이터 관점의 업무 분석 기법**
2. 현실세계의 데이터에 대해 **약속된 표기법에 의해 표현**되는 과정
3. **데이터베이스를 구축**하기 위한 분석/설계의 과정

### 데이터 모델이 제공하는 기능
1. 시스템을 현재 또는 원하는 모습으로 **가시화**
2. 시스템의 구조와 행동을 **명세화**
3. 시스템을 구축하는 **구조화된 틀**을 제공
4. 시스템을 구축하는 과정에서 결정한 것을 **문서화**
5. 다양한 영역에 집중하기 위해 다른 영역의 세부 사항은 숨기는 **다양한 관점** 제공
6. 특정 목표에 따라 **구체화된 상세 수준의 표현방법** 제공

### 데이터 모델링의 중요성 및 유의점

| 중요성 | 설명 |
|--------|------|
| 파급효과 (Leverage) | 다른 어떤 설계 과정보다 **데이터 설계가 중요** |
| 복잡한 정보 요구사항의 간결한 표현 (Conciseness) | 가장 명확하고 간결하게 표현할 수 있는 도구 |
| 데이터 품질 (Data Quality) | 데이터의 중복, 비 유연성, 비 일관성이 발생할 수 있음 |

## 3. 데이터 모델링의 3단계

```
현실세계 → [개념 데이터 모델링] → 개념적 구조
         → [논리 데이터 모델링] → 논리적 구조
         → [물리 데이터 모델링] → 물리 구조(데이터베이스)
```

| 단계 | 설명 |
|------|------|
| **개념적 데이터 모델링** | 추상화 수준이 높고 업무 중심적이고 포괄적인 수준의 모델링. 전사적 데이터 모델링, EA수립 시 사용 |
| **논리적 데이터 모델링** | Key, 속성, 관계 등을 정확하게 표현. 재사용성이 높음 |
| **물리적 데이터 모델링** | 실제 데이터베이스에 이식할 수 있도록 성능, 저장 등 물리적인 성격 고려 |

### 프로젝트 생명주기에서 데이터 모델링

```
정보전략계획 → 분석 → 설계 → 개발 → 테스트 → 전환/이행
   ↑             ↑      ↑
개념적 모델링  논리적  물리적 모델링
```

## 4. 데이터 독립성

### 데이터 독립성 필요성
- 유지보수 비용 증가, 데이터 중복성 증가, 데이터 복잡도 증가, 요구사항 대응 저하 → 데이터 독립성 확보

> **핵심**: 각 View의 독립성을 유지하고 계층별 View에 영향을 주지 않고 변경 가능

### 데이터베이스 3단계 구조 (ANSI/SPARC)

| 단계 | 스키마 | 설명 | 관점 |
|------|--------|------|------|
| 외부 단계 | 외부 스키마 | 개개 사용자가 보는 개인적 DB 스키마 | 사용자 관점 |
| 개념적 단계 | 개념 스키마 | 모든 사용자 관점을 통합한 조직 전체의 DB | 통합 관점 |
| 내부적 단계 | 내부 스키마 | 물리적으로 저장된 형식, 실제 저장 방법 | 물리적 관점 |

### 데이터 독립성 2가지

| 독립성 | 설명 |
|--------|------|
| **논리적 독립성** | 개념 스키마가 변경되어도 외부 스키마에는 영향을 미치지 않도록 지원 |
| **물리적 독립성** | 내부 스키마가 변경되어도 외부/개념 스키마는 영향을 받지 않도록 지원 |

## 5. 엔터티 (Entity)

### 엔터티의 개념
- 사람, 장소, 물건, 사건, 개념 등의 **명사**에 해당
- 업무상 관리가 필요한 **관심사**에 해당
- **저장이 되기 위한 어떤 것(Thing)**

> **핵심**: 엔터티 = "업무에 필요하고 유용한 정보를 저장하고 관리하기 위한 집합적인 것(Thing)"

### 엔터티의 특징

| 특징 | 설명 |
|------|------|
| 업무에서 필요로 하는 정보 | 반드시 업무에서 필요하고 관리하고자 하는 정보여야 함 |
| 식별이 가능해야 함 | 인스턴스 각각을 구분하기 위해 유일한 **식별자**가 존재해야 함 |
| 인스턴스의 집합 | **"한 개"가 아니라 "두 개 이상"** 이라는 집합 개념 (중요!) |
| 업무프로세스에 의해 이용 | Business Process가 그 엔터티를 반드시 이용해야 함 |
| 속성을 포함 | 반드시 **속성(Attributes)** 이 포함되어야 함 |
| 관계의 존재 | 다른 엔터티와 **최소 한 개 이상의 관계**가 존재해야 함 |

### 엔터티의 분류

**유무(有無)형에 따른 분류**

| 유형 | 예시 | 설명 |
|------|------|------|
| 유형 엔터티 | 사원, 물품, 강사 | 물리적인 형태가 있고 안정적이며 지속적으로 활용 |
| 개념 엔터티 | 조직, 보험상품 | 물리적 형태는 없고 관리해야 할 개념적 정보 |
| 사건 엔터티 | 주문, 청구, 미납 | 업무 수행에 따라 발생, 발생량이 많음 |

**발생시점(發生時點)에 따른 분류**

| 유형 | 예시 | 설명 |
|------|------|------|
| 기본(키) 엔터티 | 고객, 상품 | 다른 엔터티와 관계 없이 독립적으로 생성. 타 엔터티의 부모 역할 |
| 중심(메인) 엔터티 | 주문, 배송 | 기본 엔터티로부터 발생. 업무의 중심적 역할 |
| 행위(액션) 엔터티 | 주문변경이력 | 두 개 이상의 부모 엔터티로부터 발생. 자주 내용이 바뀜 |

### 엔터티의 명명
1. 가능하면 **현업업무에서 사용하는 용어** 사용
2. **약어를 사용하지 않는다**
3. **단수 명사** 사용
4. 모든 엔터티에서 **유일하게** 이름 부여
5. 엔터티 **생성 의미대로** 이름 부여

## 6. 속성 (Attribute)

### 속성의 개념
속성은 업무에서 필요로 하는 인스턴스에서 관리하고자 하는 **의미상 더 이상 분리되지 않는 최소의 데이터 단위**

조건:
1. 업무에서 필요로 한다
2. **의미상 더 이상 분리되지 않는다**
3. 엔터티를 설명하고 인스턴스의 구성요소가 된다

### 엔터티/인스턴스/속성/속성값의 관계
1. 한 개의 엔터티는 **두 개 이상**의 인스턴스의 집합이어야 한다
2. 한 개의 인스턴스는 **두 개 이상**의 속성을 갖는다
3. 한 개의 속성은 **한 개**의 속성값을 갖는다

### 속성의 분류 - 특성에 따른 분류

| 유형 | 설명 | 예시 |
|------|------|------|
| **기본 속성** (Basic Attribute) | 업무 분석을 통해 바로 정의한 속성 | 제품명, 판매금액 |
| **설계 속성** (Designed Attribute) | 원래 업무에는 없지만 설계하면서 도출 | 제조사코드 |
| **파생 속성** (Derived Attribute) | 다른 속성으로부터 계산이나 변형으로 생성 | 판매금액합계 |

> **핵심**: 파생속성은 없어도 다른 속성으로 결과를 도출할 수 있다

### 속성의 분류 - 엔터티 구성방식에 따른 분류

| 유형 | 설명 |
|------|------|
| **PK 속성** | 엔터티를 식별할 수 있는 속성 |
| **FK 속성** | 다른 엔터티와의 관계에서 포함된 속성 |
| **일반 속성** | PK, FK에 포함되지 않은 속성 |

### 도메인 (Domain)
각 속성이 가질 수 있는 **값의 범위**를 정의한 것
- 예) 학점 속성의 도메인: 0.00~4.50 사이의 실수
- 각 속성은 도메인 이외의 값을 갖지 못한다

## 7. 관계 (Relationship)

### 관계의 정의
- 상호 연관성이 있는 상태
- **엔터티 간 논리적인 연관성**
- 존재에 의한 관계와 **행위에 의한 관계**로 구분

### 관계의 분류

| 분류 | 예시 | 설명 |
|------|------|------|
| **존재에 의한 관계** | 사원 → 부서에 소속 | 존재의 형태에 의해 관계 형성 |
| **행위에 의한 관계** | 고객 → 주문한다 | 행위에 의한 이벤트로 발생 |

### 관계의 표기법

| 개념 | 설명 |
|------|------|
| **관계명** (Membership) | 관계의 이름 |
| **관계차수** (Cardinality) | 1:1, 1:M, M:M |
| **관계선택사양** (Optionality) | 필수관계, 선택관계 |

### 관계 차수

| 차수 | 설명 |
|------|------|
| **1:1** | 각 엔터티가 관계를 맺는 다른 엔터티에 대해 단지 하나의 관계만 가짐 |
| **1:M** | 한 명의 사원은 한 부서에 소속되고 한 부서에는 여러 사원을 포함 |
| **M:M** | 각각의 엔터티가 하나 혹은 그 이상의 수와 관계를 가짐 |

### 관계 읽기
1. 기준(Source) 엔터티를 **한 개(One) 또는 각(Each)** 으로 읽는다
2. 대상(Target) 엔터티의 관계 참여도(**개수**)를 읽는다
3. **관계선택사양(필수/선택)** 과 관계명을 읽는다

예) "각각의 고객은 여러 개의 주문을 때때로 주문한다."

## 8. 식별자 (Identifier)

### 식별자의 개념
엔터티 내의 각 인스턴스를 **개별적으로 식별**하기 위해 사용되는 구분자

### 식별자의 특징

| 특징 | 내용 |
|------|------|
| **유일성** | 주식별자에 의해 엔터티 내 모든 인스턴스들이 유일하게 구분 |
| **최소성** | 주식별자 구성 속성 수는 유일성을 만족하는 **최소의 수** |
| **불변성** | 지정된 주식별자의 값은 **자주 변하지 않아야** 함 |
| **존재성** | 주식별자가 지정되면 반드시 데이터 값이 존재 (**Null 불가**) |

### 식별자 분류

| 분류 기준 | 식별자 | 설명 |
|-----------|--------|------|
| 대표성 여부 | **주식별자** | 타 엔터티와 참조관계 연결 가능 (예: 사원번호) |
| | **보조식별자** | 각 행을 구분할 수는 있지만 대표성 없음 (예: 주민등록번호) |
| 생성 여부 | **내부식별자** | 엔터티 내부에서 스스로 만들어지는 식별자 |
| | **외부식별자** | 타 엔터티와의 관계를 통해 받아오는 식별자 (FK) |
| 속성의 수 | **단일식별자** | 하나의 속성으로 구성 |
| | **복합식별자** | 둘 이상의 속성으로 구성 |
| 대체 여부 | **본질식별자** | 업무에 의해 만들어지는 식별자 |
| | **인조식별자** | 원조식별자가 복잡하여 인위적으로 만든 식별자 |

### 식별자 관계 vs 비식별자 관계

| 항목 | 식별자 관계 | 비식별자 관계 |
|------|-------------|---------------|
| 목적 | **강한** 연결 관계 표현 | **약한** 연결 관계 표현 |
| 자식 주식별자 영향 | 자식 주식별자의 구성에 **포함** | 자식 **일반 속성**에 포함 |
| 연결 고려사항 | 반드시 부모 엔터티 종속 | 약한 종속관계 |

> **핵심**: 식별자 관계로만 연결하면 PK속성이 지속적으로 증가하여 개발의 복잡성과 오류 가능성이 커진다

## 출제 포인트

1. **모델링 3단계**: 개념적(추상적, EA수립) → 논리적(Key/속성/관계) → 물리적(성능/저장)
2. **엔터티 특징 6가지**: 업무필요, 식별가능, 집합(2개이상), 업무프로세스이용, 속성포함, 관계존재
3. **엔터티 분류**: 유무형(유형/개념/사건) vs 발생시점(기본/중심/행위)
4. **속성 분류**: 기본/설계/파생 속성 — 파생속성은 다른 속성으로 계산 가능
5. **관계차수**: 1:1, 1:M, M:M — 관계선택사양(필수/선택)
6. **식별자 특징**: 유일성, 최소성, 불변성, 존재성(Null불가)
7. **식별자 분류**: 대표성(주/보조), 생성(내부/외부), 수(단일/복합), 대체(본질/인조)
8. **비식별자 관계 선택**: 약한 관계, 독립 PK 필요, SQL 복잡성 증가 시 고려
9. **데이터베이스 3단계**: 외부스키마(사용자), 개념스키마(통합), 내부스키마(물리)
10. **논리적 독립성**: 개념 스키마 변경 → 외부 스키마 영향 없음
