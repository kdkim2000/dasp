# 1과목 2장: 전사아키텍처 구축

### EA 구축 3대 마일스톤

| 단계 | 명칭 | 내용 |
|---|---|---|
| 1단계 | 방향 수립 | 환경분석 → 비전 → 원칙, 범위·우선순위·로드맵 수립 |
| 2단계 | 정보 구성 정의 | 메타모델(객체·속성·관계) 설계, 도메인별 관리 정보 정의 |
| 3단계 | 정보 구축 및 이행 계획 | As-Is/To-Be/Gap 분석, 레퍼지토리·포탈·품질·보안 |

## 1. 전사아키텍처 방향 수립

EA 방향 수립은 조직의 비즈니스 전략에서 EA 비전·원칙·목표를 정의하는 단계이다. EA 구축 전 반드시 선행되어야 한다.

### 1.0 환경분석 5요소

| # | 구분 | 내용 |
|---|---|---|
| 1 | 비즈니스 내·외부 환경 | 중장기 비전·경영방침 등 경영이념 이해 |
| 2 | 외부 환경 | 법·제도 변화, 기술 트렌드, 시장 경쟁 구도 |
| 3 | 내부 환경 | 데이터 정책·현황, 기술 도입 동향, 내부 이슈 |
| 4 | 이해관계자 | 경영진·현업·개발자·사용자의 불만·요구·기대사항 |
| 5 | 시사점 종합 | 경영전략을 지원할 EA 방향성 정의 → 비전·원칙의 근거 |

> 원칙: EA 구축의 첫 걸음은 기술 도입이 아니라 환경 분석·진단이며, 순서는 언제나 "진단 후 비전"이다.

### 1.1 EA 비전 및 목표 수립

**EA 비전의 3요소**: ① 핵심 목표(무엇을 어느 수준까지 달성할 것인가), ② 핵심 가치(어떤 원칙을 고수할 것인가), ③ 전략 방향(어떤 기술적·조직적 접근법을 취할 것인가). 세 요소가 "무엇을(목표)·어떤 원칙으로(가치)·어떻게(방향)"의 한 문장으로 이어져야 한다.

| 항목 | 내용 |
|------|------|
| EA 비전 | EA를 통해 달성하고자 하는 미래 모습 |
| EA 목표 | 비전을 구체화한 측정 가능한 목표 |
| EA 범위 | 아키텍처 적용 대상 조직·시스템 범위 |
| EA 전략 | 목표 달성을 위한 접근 방법 |

### 1.2 EA 원칙 정의

EA 원칙은 아키텍처 수립·운영 시 준수해야 하는 고수준 지침이다. 원칙들을 체계적으로 모아둔 문서를 **원칙 카탈로그(Principle Catalog)** 라 하며, 조직 IT 거버넌스의 헌법 역할을 한다.

**좋은 원칙의 4가지 요건**: ① 명확성(뜻이 분명), ② 의사결정 유용성(실제 결정에 도움), ③ 전사 준수(모두가 지켜야 함), ④ 비충돌(다른 원칙과 충돌 금지).

**EA 원칙 템플릿 6항목** (기존 원칙명/설명/근거/영향의 4항목을 확장):

| 항목 | 정의 내용 |
|------|------|
| 원칙 | 핵심 개념의 간결한 기술 |
| 의미 | 구체적 의미와 적용 범위 |
| 배경 | 원칙이 필요한 비즈니스·기술적 이유 |
| 기대효과 | 준수 시 기대되는 긍정적 결과 |
| 지표 | 준수 여부를 측정하는 KPI |
| 예외처리 | 미준수 시 ARB 심의·승인 절차 |

**5개 원칙 유형 예시**

| 원칙 유형 | 핵심 의미 | 측정 지표 예시 |
|---|---|---|
| 데이터 자산화 원칙 | 데이터를 전략 자산으로 취급 | 표준 준수율, 중복 테이블 수 |
| 보안 내재화 원칙 | 설계 초기부터 보안 요건 반영 | 보안 점검 통과율, 사고 건수 |
| 표준·재사용 우선 원칙 | 신규 개발보다 표준 컴포넌트 재사용 | 재사용률 |
| 클라우드 네이티브 우선 원칙 | 신규 시스템은 클라우드 우선 설계 | 클라우드 전환율 |
| 개방형 상호운용성 원칙 | 표준 API·개방형 인터페이스 채택 | 표준 API 적용률 |

### 1.3 접근 방식 결정

| 방식 | 설명 | 장점 | 단점 |
|------|------|------|------|
| Top-Down | 전략 → 아키텍처 순 | 비즈니스 정렬성 높음 | 시간·비용 소요 |
| Bottom-Up | 현행 시스템 분석 → 아키텍처 도출 | 현실 반영도 높음 | 비즈니스 정렬성 부족 |
| Hybrid | Top-Down + Bottom-Up 결합 | 균형적 접근 | 조정 복잡 |

### 1.4 범위 한정 4단계와 PPM

한정된 예산·시간 안에서 전사 전체를 한 번에 구축하려 하면 실패하기 쉽다.

| 단계 | 내용 |
|---|---|
| 1단계 | 조직 범위 설정 — 우선 적용할 사업부·부문 선정 |
| 2단계 | 도메인 범위 설정 — BA·DA·AA·TA·SA 중 이번 단계 도메인 한정 |
| 3단계 | 산출물 수준 설정 — 개념·논리·물리 수준 중 상세화 범위 결정 |
| 4단계 | 과제 우선순위 확정 — PPM 5대 평가기준으로 실행 순서 확정 |

**PPM(Project Portfolio Management) 5대 평가기준**: 전략적 적합성 / 리스크·복잡도 / 투자 대비 효과 / 규제 대응 / 시급성

### 1.5 로드맵과 전환 아키텍처

**로드맵 3요소**: ① 단계 구분(As-Is→Phase1→Phase2→...→To-Be), ② 프로그램 정의(단계별 사업 단위 과제), ③ 전환 아키텍처 정의(각 단계 종료 시점의 안정적 중간 상태 명세).

**전환 아키텍처(Transition Architecture)**: As-Is에서 To-Be로 한 번에 도달할 수 없으므로, 그 사이 안정적으로 운영 가능한 중간 정거장을 정의한 것.

## 2. 전사아키텍처 정보 구성 정의

EA 정보 구성 정의는 어떤 아키텍처 정보를 어떻게 구조화할지를 결정하는 단계이다.

### 2.1 아키텍처 뷰와 뷰포인트

| 개념 | 설명 |
|------|------|
| 아키텍처 뷰(View) | 특정 관심사에 따른 시스템의 표현 |
| 뷰포인트(Viewpoint) | 특정 역할(이해관계자)이 관심 갖는 관점 |
| 아키텍처 산출물(Artifact) | 뷰를 구체화한 문서·모델 |

### 2.2 EA 산출물 체계 정의

| 도메인 | 주요 산출물 |
|--------|---------|
| BA | 업무 기능 분류체계, 업무 흐름도, 조직도 |
| DA | 개념/논리/물리 데이터 모델, 데이터 표준, 데이터 흐름도 |
| AA | 응용 기능 분류체계, 인터페이스 목록, 응용 구성도 |
| TA | 기술 참조 모델, 시스템 구성도, 네트워크 구성도 |

### 2.3 아키텍처 메타모델(Metamodel)

아키텍처 요소와 이들 간의 관계를 정의한 모델로, EA 리포지터리의 기반이 된다. 메타모델은 데이터를 담기 위한 틀이며 **OAR 3요소**로 구성된다.

```
비즈니스 프로세스 ──지원── 애플리케이션 ──사용── 데이터
        │                      │
      수행                    실행
        │                      │
      조직                   기술 플랫폼
```

| 요소 | 의미 | 예시 |
|---|---|---|
| Object(객체) | 관리할 대상 | 업무 프로세스, 애플리케이션, 데이터 엔티티, 서버 장비 |
| Attribute(속성) | 객체의 고유 특성 | 서버 IP, 소유 부서, 담당자 연락처 |
| Relationship(관계) | 객체 간 연결 고리 | "이 애플리케이션은 저 서버 위에서 구동된다" |

**애플리케이션 속성의 4범주** (예시)

| 범주 | 질문 | 예시 |
|---|---|---|
| 기본 정보 | 이게 무엇인가? | 시스템 ID, 명칭, 버전, 운영 상태 |
| 거버넌스 정보 | 누가 책임을 지는가? | 소유 부서, 관리 책임자, 보안 등급 |
| 기술 정보 | 어떤 기술로 만들어졌는가? | 개발 언어, 프레임워크, DBMS |
| 관계 정보 | 어디에 연결되는가? | 지원 프로세스, 입출력 데이터, 연계 인터페이스(FK 역할) |

### 2.4 EA 정보 표현 원칙

| 원칙 | 내용 |
|------|------|
| 일관성 | 동일 개념을 동일 방식으로 표현 |
| 완전성 | 필요한 모든 정보 포함 |
| 정확성 | 현실을 올바르게 반영 |
| 추적성 | 요소 간 연결 관계 명확화 |

### 2.5 데이터 원칙 8가지

| # | 원칙 | 한 줄 의미 |
|---|---|---|
| 1 | 자산성 | 데이터는 조직의 전략적 자산으로 관리한다 |
| 2 | 주체자 정의 | 모든 데이터에는 책임지는 소유자(Data Owner)가 있다 |
| 3 | 표준 준수 | 정의된 데이터 표준과 명명 규칙을 따른다 |
| 4 | 원자성 | 더 이상 쪼갤 수 없는 최소 단위로 정의한다 |
| 5 | 중복 최소화 | 동일 데이터를 여러 곳에 중복 저장하지 않는다 |
| 6 | 보안 | 민감도에 따라 접근을 통제·보호한다 |
| 7 | 통합 | 부서 간 데이터를 상호 연계·통합할 수 있도록 설계한다 |
| 8 | 품질 | 완전성·정확성 등 품질 기준을 지속 관리한다 |

**데이터 품질 6요소**: 완전성·유일성·유효성·일관성·정확성·적시성

### 2.6 데이터 모델 변경 관리 6단계

① 요청(현업/개발팀) → ② 검토(DA가 준수 여부 검토) → ③ 승인(거버넌스 기구) → ④ 배포(레퍼지토리) → ⑤ 이행(DBA가 DB 반영) → ⑥ 검증(DA가 모델-실제 DB 일치 확인). 검증 단계가 생략되면 문서와 현실이 괴리된다.

## 3. 전사아키텍처 정보 구축

EA 정보 구축은 정의된 구성 체계에 따라 실제 아키텍처 정보를 수집·분석·문서화하는 단계이다.

### 3.1 현행(AS-IS) 아키텍처 정보 수집

| 수집 방법 | 내용 |
|---------|------|
| 인터뷰 | 현업·IT 담당자 면담으로 현황 파악 |
| 문서 검토 | 기존 설계서·운영 매뉴얼 분석 |
| 설문 | 다수 이해관계자 대상 현황 조사 |
| 자동화 도구 | EA 관리 도구로 시스템 정보 자동 수집 |

### 3.2 현행 아키텍처 분석 항목

| 분석 항목 | 내용 |
|---------|------|
| 중복 시스템 식별 | 동일 기능을 수행하는 중복 시스템 파악 |
| 인터페이스 현황 | 시스템 간 데이터 교환 현황 |
| 기술 표준 현황 | 현재 사용 중인 기술 표준 |
| 데이터 현황 | 주요 데이터 항목과 흐름 |

### 3.3 목표(TO-BE) 아키텍처 수립

| 구분 | 내용 |
|------|------|
| 목표 아키텍처 설계 | 비즈니스 전략과 AS-IS 갭 기반으로 목표 상태 설계 |
| 이행 계획 수립 | 단계별(Phase) 전환 계획과 우선순위 결정 |
| 아키텍처 검토 | ARB 검토·승인 |

### 3.4 갭(Gap) 분석

| 절차 | 내용 |
|------|------|
| AS-IS 파악 | 현행 아키텍처 요소 목록화 |
| TO-BE 정의 | 목표 아키텍처 요소 정의 |
| 갭 식별 | 차이 분석: 추가·변경·제거 요소 |
| 이행 방안 | 갭 해소를 위한 프로젝트·조치 도출 |

### 3.5 EA 구축 산출물 검증

| 검증 항목 | 방법 |
|---------|------|
| 완전성 | 모든 도메인 산출물 존재 여부 확인 |
| 일관성 | 도메인 간 산출물 연계 관계 확인 |
| 정확성 | 현업 검토를 통한 내용 정확성 확인 |
| 추적성 | 비즈니스 요구 → 기술까지 연결 가능 여부 |

## 4. 데이터 아키텍처 방향 수립 심화

### 4.1 데이터 아키텍처 환경분석 (5요소)

EA 구축 전 내·외부 환경을 분석하여 구축 방향의 근거를 마련한다. (1장의 환경분석 5요소와 동일 체계)

| # | 분석 요인 | 주요 내용 |
|---|---------|---------|
| 1 | 비즈니스 내·외부 환경 | 중장기 비전·경영방침 등 경영이념 |
| 2 | 외부 환경 | 기술 이슈·트렌드, 법제도 변화 |
| 3 | 내부 환경 | 데이터 정책·현황, 내부 시스템·조직 동향 |
| 4 | 이해관계자 | 데이터 관련 현업의 불만·요구사항 |
| 5 | 시사점 종합 | 분석 결과를 EA 방향성으로 종합 |

### 4.2 아키텍처 매트릭스(Architecture Matrix)

2차원 매트릭스로 의사결정 유형(행)과 정보 유형(열)을 구성하며, 각 셀에서 필요한 산출물을 정의한다. 열(정보 유형)은 1장에서 확정한 육하원칙 6열 체계와 일치시킨다(업무/데이터/응용/기술 4열 축소본은 오류).

| 구성 축 | 세부 유형 |
|--------|---------|
| 의사결정 유형 (행) | 계획자, 책임자(소유자), 설계자, 개발자 |
| 정보 유형 (열) | 데이터(What), 프로세스(How), 네트워크(Where), 사람(Who), 시간(When), 동기(Why) — 6열 |

**아키텍처 매트릭스 정의 시 고려사항:**
- 모든 이해관계자의 동의 필수
- 선진 모범 사례 참조 및 조직에 맞게 조정
- 아키텍처 원칙 및 표준 준수성 강화
- 타 도메인(BA/DA/AA/TA)과의 상호 연계성 고려

### 4.3 현행 데이터 분석 4가지 방법

현행 데이터아키텍처 정보를 구축할 때 수행하는 분석:

| 분석 방법 | 주요 내용 |
|---------|---------|
| 1. 데이터 현황 분석 | DB 개체 및 스토리지 사용 현황 파악, 완전성·우선순위·정합성·유효성 분석 |
| 2. 데이터 표준화 현황 분석 | 명칭·도메인·코드 사용의 일관성 파악 |
| 3. 문서화 현황 및 정합성 분석 | 설계 문서와 실제 DB 개체의 일치성 확인 |
| 4. 설계 및 관리 현황 분석 | 현행화 상태 확인 및 데이터 관리 체계 파악 |

## 5. AS-IS 상향식 / TO-BE 하향식 구축

> 핵심 원칙: **현행(As-Is)은 상향식(Bottom-up), 목표(To-Be)는 하향식(Top-down)**으로 구축한다. 혼동하면 구축 프로젝트는 실패한다.

### 5.1 현행(As-Is) 구축 5단계 (상향식)

| 순서 | 단계 | 내용 |
|---|---|---|
| 1 | 자료 수집·분석 | 모델·테이블 정의서 수집, DB 현황의 완전성·정합성·유효성 분석 |
| 2 | 현행 물리 데이터모델 | 운영 DB 개체정보로부터 역공학(Reverse Engineering)으로 생성 |
| 3 | 현행 논리 데이터모델 | 물리 모델을 비즈니스 관점으로 한글화, 엔터티·속성·관계로 전환 |
| 4 | 현행 개념·주제영역 | 유사 엔터티 그룹핑, 고객·상품·계약 등 최상위 집합 분류 |
| 5 | 문제점·개선방향 도출 | 중복·비일관성·비표준 등 구조상 문제 분석 → 개선 방향 |

### 5.2 목표(To-Be) 구축 5단계 (하향식)

| 순서 | 단계 | 내용 |
|---|---|---|
| 1 | 설계 3대 고려요소 | 전략 정렬·성숙도 목표·표준 및 보안 요구 반영 |
| 2 | 목표 데이터 표준·프로세스 | 개선된 용어·도메인·코드 표준, 모델/품질/요구사항 관리 프로세스 정의 |
| 3 | 목표 주제영역·개념모델 | 통합 분류체계와 목표 데이터 구조의 골격 정의 |
| 4 | 목표 논리·물리 모델 | 비즈니스 규칙을 구체화한 논리 모델, DBMS에 맞춘 물리 모델 |
| 5 | 목표 데이터 흐름 | 시스템 간 데이터 교환의 미래 모습을 통합 흐름도로 정의 |

### 5.3 Gap → 과제 평가 매트릭스

갭 분석의 결과는 신규개발/통합/폐기 등 구체적 이행 과제로 전환되며, 5개 기준으로 점수화하여 우선순위를 정한다.

| 평가 기준 | 설명 |
|---|---|
| 비즈니스 영향 | 과제가 핵심 업무에 미치는 영향도 |
| 기술적 난이도 | 구현의 기술적 복잡성 |
| 타 시스템 파급 | 연관 시스템에 미치는 영향 범위 |
| 규제 시급성 | 법규·컴플라이언스 대응 긴급도 |
| 기대 가치 | 투자 대비 기대 효과 |

> 5점 척도로 점수화 후 종합점수 산정, 프로그램 단위로 묶어 로드맵 단계에 배치한다.

## 6. EAMS(전사 아키텍처 관리 시스템)

| 영역 | 내용 |
|---|---|
| 정의(Definition) | 모델링 도구로 아키텍처 산출물을 직접 생성 |
| 관리(Management) | 중앙 레퍼지토리에서 버전 관리·접근제어·메타데이터·링크 통제 |
| 활용(Utilization) | 포탈을 통해 임직원·개발자가 카탈로그를 조회·분석·활용 |

> 세 영역은 API로 유기적으로 연동되어 정보의 생성-관리-활용이 끊기지 않아야 한다.

## 7. 데이터 품질 관리 사이클과 보안 정책

### 7.1 데이터 품질 관리 사이클 6단계

핵심 데이터 선정 → 품질 지표 정의 → 품질 측정 → 원인 분석 → 개선 → 재평가 (순환 구조)

### 7.2 데이터 보안 정책 6요소

| 요소 | 내용 |
|---|---|
| 데이터 자산 분류 | 중요도·민감도 등급별 보호대책 차등 적용 |
| 접근 권한 관리 | 최소 권한 원칙, 역할 기반 부여·정기 검토 |
| 개인식별정보(PII) 보호 | 수집~파기 전 과정 법규 준수, 가명·익명처리 |
| 암호화 및 마스킹 | 저장·전송 시 암호화, 개발·테스트 환경 마스킹 |
| 감사 및 이력 관리 | 접근·변경 이력 기록, 이상행위 탐지 |
| 보안 교육 | 전 임직원 정기 교육 |

> 품질은 계속 측정·개선을 반복하고, 보안은 설계 단계부터 내재화한다.
