# 1과목 2장: 데이터 모델과 성능

## 1. 성능 데이터 모델링 개요

### 성능 데이터 모델링의 정의
성능 데이터 모델링이란 **데이터베이스 성능 향상을 목적**으로 설계 단계부터 정규화, 반정규화, 테이블 통합/분리, 조인 구조, PK/FK 설계 등 여러 가지 성능과 관련된 사항을 데이터 모델링에 반영하는 것을 말한다.

> **핵심**: 성능 문제는 데이터 모델이 결정되고 나서 SQL이 작성되는 과정에서 발생하기 때문에, 데이터 모델 단계에서 성능을 고려해야 한다.

### 성능 데이터 모델링 수행 시점
- 성능 데이터 모델링은 **분석/설계 단계**에서 수행하는 것이 가장 좋다
- 프로젝트 후반부에 성능 문제가 발생하면 재작업 비용이 크게 증가한다

### 성능 데이터 모델링 절차

| 순서 | 단계 | 내용 |
|------|------|------|
| 1 | 정규화 | 데이터 중복 제거, 데이터 모델의 독립성 확보 |
| 2 | 용량 산정 | 각 엔터티에 저장될 데이터 양 예측 |
| 3 | 트랜잭션 유형 분석 | 데이터 처리의 유형 파악 |
| 4 | 반정규화 적용 | 조회 성능 개선을 위한 역정규화 |
| 5 | 이력/이력 모델링 | 이력관리 방법 결정 |
| 6 | PK/FK 조정 | 조인 성능, 클러스터링 고려 |

## 2. 정규화 (Normalization)

### 정규화의 개념
정규화란 데이터의 **중복을 최소화**하고 **데이터 무결성**을 보장하기 위해 데이터를 구조화하는 프로세스이다.

> **핵심**: 정규화는 데이터의 일관성, 최소한의 데이터 중복, 최대한의 데이터 유연성을 위한 것이며, 데이터를 분해하는 과정이다.

### 이상 현상 (Anomaly)
정규화가 제대로 되지 않으면 이상 현상이 발생한다.

| 이상 현상 | 설명 |
|-----------|------|
| **삽입 이상** (Insertion Anomaly) | 데이터를 삽입할 때 원하지 않는 다른 데이터가 함께 삽입되어야 하는 현상 |
| **삭제 이상** (Deletion Anomaly) | 데이터 삭제 시 필요한 다른 데이터가 함께 삭제되는 현상 |
| **갱신 이상** (Update Anomaly) | 중복된 데이터 중 일부만 변경되어 데이터 불일치가 발생하는 현상 |

### 함수적 종속성 (Functional Dependency)
- X → Y : X가 Y를 **함수적으로 결정**한다 (X가 Y를 결정한다)
- X: **결정자** (Determinant), Y: **종속자** (Dependent)
- 예) 학번 → 학생명 (학번이 학생명을 결정)

### 정규화 단계

#### 제1정규형 (1NF)
**조건**: 모든 속성값이 **원자값(Atomic Value)** 이어야 한다. 즉, 반복 그룹이나 다중값 속성이 없어야 한다.

```
[위반 예시]
학번 | 이름 | 수강과목
001  | 김철수 | 데이터베이스, 알고리즘  ← 다중값 위반

[1NF 만족]
학번 | 이름 | 수강과목
001  | 김철수 | 데이터베이스
001  | 김철수 | 알고리즘
```

#### 제2정규형 (2NF)
**조건**: 1NF를 만족하고, **기본키에 완전 함수 종속**이어야 한다. 즉, 부분 함수 종속을 제거한다.

> **핵심**: 부분 함수 종속 = 복합 기본키에서 일부 키만으로도 결정되는 속성이 있는 경우

```
[위반 예시] 기본키: (학번, 과목코드)
학번+과목코드 → 성적  (완전 종속)
학번 → 학생명       (부분 종속 - 위반!)
과목코드 → 과목명   (부분 종속 - 위반!)

[2NF 만족] 테이블 분리
수강 테이블: (학번, 과목코드, 성적)
학생 테이블: (학번, 학생명)
과목 테이블: (과목코드, 과목명)
```

#### 제3정규형 (3NF)
**조건**: 2NF를 만족하고, **이행적 함수 종속**을 제거한다.

> **핵심**: 이행적 종속 = A → B이고 B → C이면 A → C가 되는 관계

```
[위반 예시]
학번 → 학과코드 → 학과명  (이행적 종속 위반!)

[3NF 만족] 테이블 분리
학생 테이블: (학번, 학생명, 학과코드)
학과 테이블: (학과코드, 학과명)
```

#### BCNF (Boyce-Codd Normal Form)
**조건**: 3NF를 만족하고, **모든 결정자가 후보키**여야 한다.

```
[위반 예시] 교수-학생-과목 관계에서
(학번, 과목명) → 교수명
교수명 → 과목명  (교수명이 결정자이지만 후보키가 아님 - 위반!)
```

#### 제4정규형 (4NF), 제5정규형 (5NF)
- 4NF: **다치 종속(Multi-Valued Dependency)** 제거
- 5NF: **조인 종속(Join Dependency)** 제거

### 정규화 단계 요약

| 정규형 | 제거 대상 | 핵심 조건 |
|--------|-----------|-----------|
| 1NF | 반복 그룹, 다중값 | 원자값만 허용 |
| 2NF | 부분 함수 종속 | 기본키에 완전 종속 |
| 3NF | 이행적 함수 종속 | 직접 종속만 허용 |
| BCNF | 결정자가 후보키가 아닌 경우 | 모든 결정자 = 후보키 |
| 4NF | 다치 종속 | 다치 종속 제거 |
| 5NF | 조인 종속 | 조인 종속 제거 |

## 3. 반정규화 (De-Normalization)

### 반정규화의 개념
반정규화란 정규화된 데이터 모델을 **성능 향상 및 개발 편의를 위해** 의도적으로 정규화 원칙에 위배되도록 설계하는 것이다.

> **핵심**: 반정규화는 데이터 무결성 위험을 감수하면서 조회 성능을 향상시키는 기법이다. 정규화된 모델에서 중복/통합/분리를 통해 성능을 개선한다.

### 반정규화 적용 기준

반정규화 적용 시 반드시 **정규화된 상태에서 성능 문제를 확인**한 후 적용해야 한다.

| 반정규화 적용 시점 | 내용 |
|-------------------|------|
| 자주 사용되는 테이블에 ACCESS가 많고 시스템 부하가 클 때 |
| 경미한 성능 저하를 감수하여 개발 편의를 높일 때 |
| 테이블 간 M:M 관계로 조인이 빈번할 때 |
| 특정 범위 데이터만 자주 처리될 때 |

### 반정규화 기법

#### 테이블 반정규화

| 기법 | 내용 |
|------|------|
| **테이블 병합** | 1:1 관계나 1:M 관계 테이블을 하나로 합침 |
| **테이블 분리** | 자주 사용하는 컬럼과 그렇지 않은 컬럼을 분리 (수직/수평 분할) |
| **테이블 추가** | 집계/합계 데이터를 위한 별도 테이블 생성 |

#### 컬럼 반정규화

| 기법 | 내용 |
|------|------|
| **중복 컬럼 추가** | 조인 감소를 위해 다른 테이블의 컬럼을 복사 |
| **파생 컬럼 추가** | 자주 사용하는 집계값을 별도 컬럼으로 저장 |
| **이력 테이블 컬럼 추가** | 최신값을 조회하기 쉽도록 추가 컬럼 |
| **PK에 의한 컬럼 추가** | 복합의미의 PK에서 의미를 분리하여 컬럼 추가 |

#### 관계 반정규화

| 기법 | 내용 |
|------|------|
| **중복 관계 추가** | 여러 경로를 통해 접근하는 경우 직접 관계 추가 |

## 4. 대용량 데이터에 따른 성능

### 로우 체이닝과 로우 마이그레이션

| 현상 | 설명 | 발생 원인 |
|------|------|-----------|
| **로우 체이닝** (Row Chaining) | 한 행의 데이터가 블록 한 개에 저장되지 못해 두 개 이상의 블록에 걸쳐 저장 | 행 길이가 블록 크기보다 큰 경우 |
| **로우 마이그레이션** (Row Migration) | 수정 데이터가 크기 증가로 인해 원래 블록에 저장 못하고 다른 블록으로 이동 | UPDATE로 인한 컬럼 크기 증가 |

> **핵심**: 로우 체이닝과 로우 마이그레이션은 디스크 I/O 증가를 유발하여 성능 저하의 원인이 된다.

### 파티셔닝 (Partitioning)
대용량 테이블을 물리적으로 분리하여 성능을 향상시키는 기법

| 파티셔닝 종류 | 설명 |
|--------------|------|
| **범위 파티셔닝** (Range) | 날짜, 숫자 범위로 분리 (예: 월별 데이터) |
| **목록 파티셔닝** (List) | 특정 값 목록으로 분리 (예: 지역별) |
| **해시 파티셔닝** (Hash) | 해시 함수로 균등 분리 |
| **복합 파티셔닝** (Composite) | 두 가지 이상의 파티셔닝 방법 혼합 |

## 5. 데이터베이스 구조와 성능

### 슈퍼타입/서브타입 모델

슈퍼타입/서브타입 관계는 공통 속성을 슈퍼타입에, 서브타입별 고유 속성을 서브타입에 두는 구조이다.

```
[슈퍼타입/서브타입 예시]
     [고객]         ← 슈퍼타입 (공통: 고객번호, 이름)
    /       \
[개인고객] [법인고객] ← 서브타입 (고유: 주민번호 / 사업자번호)
```

### 슈퍼타입/서브타입 변환 방법

| 변환 방법 | 특징 | 적합 트랜잭션 |
|-----------|------|--------------|
| **1: All in One** (단일 테이블) | 모든 속성을 하나의 테이블로 통합, NULL 많이 발생 | 슈퍼+서브 통합 조회 빈번 |
| **2: All in Each** (서브타입별 테이블) | 서브타입별 테이블, 슈퍼타입 속성 중복 | 서브타입별 단독 처리 빈번 |
| **3: Plus** (슈퍼+서브 분리) | 슈퍼타입 + 서브타입 테이블 분리 유지 | 슈퍼타입/서브타입 각각 처리 |

## 6. 인덱스 (Index)와 성능

### 인덱스의 개념
인덱스는 데이터를 **빠르게 조회**하기 위해 별도로 만든 데이터 구조이다.

> **핵심**: 인덱스는 조회 성능을 향상시키지만, INSERT/UPDATE/DELETE 시 인덱스도 갱신해야 하므로 DML 성능은 저하될 수 있다.

### 인덱스 종류

| 종류 | 설명 |
|------|------|
| **B-Tree 인덱스** | 가장 일반적. 범위 검색, 정렬에 유리 |
| **비트맵 인덱스** | 카디널리티 낮은 컬럼에 적합 (성별, 지역 등) |
| **함수기반 인덱스** | 함수나 수식에 의한 인덱스 |
| **클러스터드 인덱스** | 물리적 데이터 순서와 인덱스 순서 일치 |

### 인덱스 적용 기준

**인덱스 생성 적합 컬럼**
- WHERE 조건절에 자주 사용되는 컬럼
- 조인 조건에 자주 사용되는 컬럼
- ORDER BY, GROUP BY에 자주 사용되는 컬럼
- 카디널리티(중복도)가 낮은 컬럼 (= 유일한 값이 많은 컬럼)

**인덱스 생성 부적합 컬럼**
- DML 작업이 빈번한 컬럼
- 카디널리티가 매우 높은 컬럼 (성별, Y/N 등)
- 테이블이 매우 작은 경우

## 7. 분산 데이터베이스

### 분산 데이터베이스의 개념
여러 곳으로 분산된 데이터베이스를 **하나의 가상 시스템**으로 관리하는 데이터베이스

> **핵심**: 분산 데이터베이스는 데이터의 물리적 위치에 관계없이 논리적으로 하나의 데이터베이스처럼 사용할 수 있도록 한다.

### 분산 데이터베이스 투명성 (Transparency)

| 투명성 종류 | 설명 |
|-------------|------|
| **분리 투명성** (Fragmentation) | 하나의 릴레이션이 여러 단편(Fragment)으로 분리되어 저장되어도 사용자는 하나의 릴레이션처럼 사용 |
| **위치 투명성** (Location) | 데이터가 어느 위치에 있더라도 동일한 명령으로 접근 가능 |
| **지역사상 투명성** (Local Mapping) | 지역 DBMS와의 사상을 사용자가 알 필요 없음 |
| **중복 투명성** (Replication) | 동일 데이터가 여러 곳에 있어도 사용자는 하나처럼 사용 |
| **장애 투명성** (Failure) | 구성 요소 장애에도 트랜잭션이 정확하게 실행 |
| **병행 투명성** (Concurrency) | 여러 트랜잭션이 동시에 실행되어도 결과의 일관성 유지 |

### 분산 데이터베이스 장단점

| 구분 | 내용 |
|------|------|
| **장점** | 지역 자치성, 신뢰성/가용성 향상, 데이터 공유 확장, 통신 비용 절감 |
| **단점** | 소프트웨어 개발 복잡성, 처리 비용 증가, 설계 복잡성, 데이터 무결성 관리 어려움 |

### 분산 데이터베이스 적용 기준

| 적합 | 부적합 |
|------|--------|
| 업무 데이터가 지역 단위로 발생 | 대부분의 처리가 중앙에서 이루어질 때 |
| 여러 지역에서 동일 데이터 참조 | 보안이 엄격히 필요할 때 |
| 지역별 처리 요구가 상이 | 데이터 무결성 관리가 중요할 때 |

## 8. 이력 데이터 모델링

### 이력 데이터 관리의 필요성
시간에 따라 변하는 데이터를 추적하고 관리하기 위한 모델링 방법

### 이력 관리 유형

| 유형 | 설명 |
|------|------|
| **점 이력** | 특정 시점의 값만 관리 (가장 최신 값 유지) |
| **선분 이력** | 변경 시작일자와 종료일자로 기간을 관리 |

```sql
-- 선분이력 예시
CREATE TABLE 급여이력 (
    사원번호  VARCHAR2(10),
    시작일자  DATE,
    종료일자  DATE,    -- 현재 유효하면 '9999-12-31'
    급여액   NUMBER,
    CONSTRAINT PK_급여이력 PRIMARY KEY (사원번호, 시작일자)
);
```

> **핵심**: 선분이력은 기간 관리가 가능하여 특정 시점의 데이터를 쉽게 조회할 수 있다. 현재 유효한 데이터는 종료일자를 '9999-12-31'로 관리하는 것이 일반적이다.

## 9. 조인 성능 고려사항

### 조인 방식과 성능

| 조인 방식 | 특징 | 적합 상황 |
|-----------|------|-----------|
| **Nested Loop Join** | 외부 테이블의 각 행에 대해 내부 테이블 반복 스캔 | 소량 데이터, 인덱스 활용 가능 시 |
| **Sort Merge Join** | 양쪽 테이블 정렬 후 병합 | 정렬 가능, 범위 조인 |
| **Hash Join** | 해시 테이블 생성 후 조인 | 대용량 데이터, 동등 조인 |

### PK/FK 설계와 성능

```sql
-- 주문 테이블에서 고객번호가 FK인 경우
-- 고객번호에 인덱스가 없으면 조인 시 전체 스캔 발생
SELECT O.주문번호, C.고객명
FROM 주문 O, 고객 C
WHERE O.고객번호 = C.고객번호;  -- 고객번호 인덱스 필요!
```

> **핵심**: FK 컬럼에는 인덱스를 생성하는 것이 조인 성능에 유리하다. 단, DML이 빈번한 경우 트레이드오프를 고려해야 한다.

## 출제 포인트

1. **정규화 목적**: 데이터 중복 최소화, 이상 현상 제거, 데이터 무결성 보장
2. **이상 현상 3가지**: 삽입/삭제/갱신 이상
3. **정규형 조건**: 1NF(원자값), 2NF(완전함수종속), 3NF(이행적종속 제거), BCNF(결정자=후보키)
4. **반정규화 적용**: 성능 개선 목적, 조회 빈번 시, 데이터 중복 허용
5. **반정규화 기법**: 테이블 병합/분리/추가, 컬럼 중복 추가, 파생 컬럼 추가
6. **슈퍼/서브타입 변환**: 단일테이블(통합조회), 서브타입별(단독처리), 슈퍼+서브분리
7. **인덱스**: 조회 성능 향상, DML 성능 저하 유발
8. **분산DB 투명성 6가지**: 분리/위치/지역사상/중복/장애/병행
9. **이력 관리**: 점이력(최신값), 선분이력(시작/종료일자로 기간관리)
10. **로우체이닝/마이그레이션**: 디스크 I/O 증가 → 성능 저하
