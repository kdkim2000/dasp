# 2과목 1장: 정보 요구 사항 개요

## 1. 정보 요구 사항 정의

**정보 요구 사항(Information Requirement)** 은 조직의 업무 목표를 달성하기 위해 필요한 정보의 내용, 구조, 품질, 타이밍에 관한 요구를 체계적으로 정의한 것이다.

### 1.1 정보 요구 사항의 개념

| 구분 | 설명 |
|------|------|
| 정의 | 업무 수행에 필요한 정보의 요구를 체계적으로 기술한 것 |
| 목적 | 데이터 아키텍처·시스템 설계의 기반 마련 |
| 범위 | 데이터 항목, 관계, 규칙, 품질, 보안 등 |

### 1.2 정보 요구 사항의 유형 — 기능(동사) vs 비기능

정보 요구사항은 최상위에서 **기능 요구사항(동사)** 과 **비기능 요구사항** 두 갈래로 분류한다. "기능은 동사, 데이터는 명사"라는 프레임으로 이해하면 쉽다 — 예: "고객을 **등록한다**"에서 등록한다(행위)=기능, 고객(대상)=데이터.

| 유형 | 설명 | 예시 |
|------|------|------|
| 기능적 요구(동사) | 업무 기능 수행에 필요한 정보·행위 | "주문을 처리한다" — 고객·상품 정보 필요 |
| 비기능적 요구 | 정보 품질·성능·보안 등 기능 수행의 조건 | 응답시간 3초, 데이터 암호화 |

**비기능 요구의 대표 하위 예시** (상세는 2장에서 다룸): 데이터 표준 요구(예: 표준 날짜 형식 YYYY-MM-DD), 데이터 품질 요구(예: 주요 필드 NULL 허용 불가)

### 1.3 정보 요구 사항과 다른 요건의 관계

| 요건 유형 | 관계 |
|---------|------|
| 기능 요건(FR) | 정보 요구 사항과 긴밀히 연계 — 기능 수행에 필요한 정보 도출 |
| 비기능 요건(NFR) | 정보의 품질·성능·보안 요구 포함 |
| 업무 규칙 | 정보 생성·변경·삭제 조건 정의 → 데이터 요건 도출 근거 |

### 1.4 요구사항의 중요성 — CHAOS 보고서

스탠디시 그룹(Standish Group) CHAOS 보고서 통계:

| 수치 | 내용 |
|---|---|
| 16.2% | 1994년 IT 프로젝트 성공률 |
| 31.1% | 완료 못하고 중도 취소된 비율 |
| TOP 2 (2004년) | 실패 주요 원인 — ① 불완전한 요구사항, ② 사용자 참여 부족 |

### 1.5 불명확한 요구사항의 6단계 연쇄반응

① 불명확한 요구사항 → ② 잦은 변경(Scope Creep) → ③ 재작업 증가 → ④ 일정지연·예산초과 → ⑤ 품질 저하 → ⑥ 프로젝트 실패

> **차단 지점은 ②번**이다. 변경 자체는 막을 수 없으나, ②단계에 체계적 변경 관리 프로세스(기준선+CCB+RTM)를 두면 연쇄 반응을 끊을 수 있다.

### 1.6 정보 요구 사항 생명주기 4단계

| 단계 | 내용 |
|---|---|
| 수집(Elicitation) | 인터뷰·설문·워크숍, 현행 문서 분석으로 요구를 이끌어냄 |
| 분석·정의(Analysis) | 타당성 검토, 중복 통합, 상충 해결, 우선순위·기능/비기능 분류 |
| 상세화(Specification) | 명확·완전·일관된 형태로 공식 문서화 (산출물: 요구사항 정의서) |
| 검증(Validation) | 동료 검토·프로토타입 시연으로 "올바른 제품을 만드는가" 확인 |

> 폭포수형 단방향이 아니라 피드백을 통해 반복(iterative)되는 순환 구조다.

## 2. 정보 요구 사항 관리

정보 요구 사항 관리는 수집된 요구 사항을 체계적으로 저장·추적·변경·검증하는 활동이다.

### 2.1 정보 요구 사항 관리의 필요성

| 이유 | 내용 |
|------|------|
| 일관성 유지 | 여러 시스템 간 정보 요구의 일관성 확보 |
| 변경 통제 | 요구 사항 변경 시 영향 분석·승인 체계 |
| 추적성 확보 | 요구 사항 → 설계 → 구현 연결 관계 관리 |
| 품질 보증 | 도출된 정보 요구 사항의 정확성·완전성 검증 |

### 2.2 정보 요구 사항 관리 항목

| 관리 항목 | 설명 |
|---------|------|
| 요구 사항 ID | 고유 식별자 |
| 요구 사항 명칭 | 간결한 명칭 |
| 요구 사항 설명 | 상세 내용 |
| 우선순위 | 중요도 (High/Medium/Low) |
| 출처 | 요구 사항 제시자·근거 문서 |
| 상태 | 검토 중/승인/구현/완료 |
| 검증 기준 | 충족 여부 확인 방법 |

### 2.3 정보 요구 사항 추적성(Traceability)

요구 사항이 설계·구현·테스트 등 개발 산출물과 어떻게 연결되는지 관리하는 것.

```
정보 요구 사항 → 데이터 모델(ERD) → 물리 테이블 → 테스트 케이스
```

| 추적 방향 | 목적 |
|---------|------|
| 순방향(Forward) | 요구 사항이 올바르게 구현되었는지 확인 |
| 역방향(Backward) | 설계·구현 요소의 근거 요구 사항 파악 |

**RTM(Requirements Traceability Matrix) 예시**

| 요구사항 ID | 요구사항 설명 | 설계 문서 | 소스코드 모듈 | 테스트 케이스 | 결과 |
|---|---|---|---|---|---|
| REQ-FUN-001 | 사용자는 키워드로 상품을 검색할 수 있다 | DES-PROD-01 | ProductSearch.java | TC-SEARCH-001 | Pass |
| REQ-NF-PER-002 | 검색 응답은 평균 3초 이내 | DES-PROD-01 | ProductSearch.java | TC-PERF-002 | Pass |

### 2.3a 기준선(Baseline)과 CCB

**기준선(Baseline)**: 특정 시점에 이해관계자가 합의한 요구사항 상태를 고정한 것 — 변경 전후 비교의 통제탑(척도) 역할.

**CCB(Change Control Board, 변경통제위원회) 3역할**: ① 단일 통제 창구(임의 수용 차단), ② 객관적 의사결정(일정·예산·품질 관점, 골드플레이팅 방지), ③ 공식적 기록과 소통(회의록·변경관리대장).

**골드플레이팅(Gold Plating)**: 요청받지 않은 과잉 기능을 임의로 추가하는 것 — 지양 대상.

**변경 요청 5단계 절차**: ① 변경요청 → ② 접수 및 검토 → ③ 영향도 분석(핵심) → ④ 공식화·결정 → ⑤ 반영 계획 수립

### 2.3b R&R (역할과 책임) 7역할

| 역할 | 주요 책임 | 산출물 |
|---|---|---|
| 사용자 | 업무 요건 제시, 검증·최종 확인 | 정보 요구사항 정의서 |
| 현업 분석가 | 요구 수렴·비즈니스 분석, IT-현업 중재 | 요구사항 목록 |
| DA | 전사 데이터 표준 부합 검토, 모델 영향도 분석 | 개념/논리 데이터 모델 |
| AA | AP 컴포넌트·인터페이스 영향도 분석 | 인터페이스 정의서 |
| DBA | 성능·안정성 영향 분석, 물리 모델 변경 | 물리 데이터 모델 |
| PM | 관리 프로세스 총괄, CCB 운영 | 변경관리대장 |
| QA | 명확성·검증가능성 검토, 추적성 관리 | RTM, 테스트 계획서 |

### 2.4 정보 요구 사항 우선순위 결정 기법

**MoSCoW 기법:**

| 구분 | 의미 |
|------|------|
| Must Have | 반드시 구현해야 하는 필수 요구 사항 |
| Should Have | 중요하지만 없어도 운영 가능 |
| Could Have | 있으면 좋은 요구 사항 |
| Won't Have | 이번 범위에서 제외 (미래 고려) |

### 2.5 좋은 요구사항이 갖추어야 할 8가지 특성

| # | 특성 | 설명 |
|---|------|------|
| 1 | 명확성(Unambiguous) | 모호하지 않고 단일한 해석 가능 |
| 2 | 완전성(Complete) | 정상 시나리오 + 예외 처리까지 포함 |
| 3 | 일관성(Consistent) | 다른 요구 사항과 충돌 없음 |
| 4 | 검증가능성(Verifiable) | 충족 여부를 테스트로 확인 가능 |
| 5 | 추적가능성(Traceable) | 고유 ID 부여, 출처-구현까지 추적 |
| 6 | 수정용이성(Modifiable) | 독립적 기술로 변경 영향 최소화 |
| 7 | 원자성(Atomic) | 하나의 요구사항에 하나의 내용만 |
| 8 | What not How | 구현 방법이 아닌 기능(What)에 집중 |

## 출제 포인트

1. 정보 요구 사항 최상위 분류: 기능(동사) vs 비기능 — 데이터표준·데이터품질은 비기능의 하위 예시
2. 정보 요구 사항 관리 항목: ID·명칭·설명·우선순위·출처·상태·검증기준
3. 추적성(Traceability): 요구사항↔설계↔구현↔테스트 연결 관계, RTM으로 관리
4. 순방향 추적: 요구사항이 올바르게 구현되었는지 확인
5. CHAOS 보고서: 1994년 성공률 16.2%, 31.1% 중도취소, 2004 TOP2 실패원인(불완전한 요구사항·사용자 참여 부족)
6. 6단계 연쇄반응: 불명확요구사항→잦은변경(Scope Creep)→재작업증가→일정지연예산초과→품질저하→프로젝트실패, 차단지점 ②
7. 요구사항 생명주기 4단계: 수집(Elicitation)→분석·정의(Analysis)→상세화(Specification)→검증(Validation)
8. 기준선(Baseline): 합의된 상태를 고정한 통제탑 / CCB 3역할: 단일창구·객관적의사결정·공식기록소통
9. 골드플레이팅(Gold Plating): 요청받지 않은 과잉 기능 개발
10. 변경 요청 5단계: 변경요청→접수및검토→영향도분석→공식화결정→반영계획수립
11. R&R 7역할: 사용자·현업분석가·DA·AA·DBA·PM·QA
12. RTM: 요구사항ID-설계문서-소스코드-테스트케이스-결과 매핑표
13. 좋은 요구사항 8대 특성: 명확성·완전성·일관성·검증가능성·추적가능성·수정용이성·원자성·What not How
14. 역방향 추적: 설계·구현 요소의 근거 요구 사항 파악
15. MoSCoW: Must/Should/Could/Won't Have 4단계 우선순위
16. 업무 규칙이 데이터 요건 도출 근거
17. 정보 요구 관리 필요성: 일관성·변경통제·추적성·품질보증
18. 요구 사항 상태 관리: 검토 중→승인→구현→완료
