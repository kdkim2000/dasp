# 2과목 2장: 정보 요구 사항 조사

## 0. 조사의 위치 — CSF → CIR 흐름

**경영환경·정보환경 분석 → CSF(핵심성공요소, Critical Success Factor) → CIR(핵심정보요구, Critical Information Requirement)** 로 구체화되어 내려온다. "조사"는 CIR(전략에서 도출된 핵심정보요구)과 현장의 목소리를 잇는 다리 역할을 한다.

수집 → 정리 → 통합은 엄격한 선형이 아니라 **반복적(iterative)·비선형적** 구조다. 예: 통합 단계에서 상충을 발견하면 다시 수집 단계로 돌아가 조정 워크숍을 재실시한다.

## 1. 정보 요구 사항 수집

정보 요구 사항 수집은 이해관계자로부터 업무 요구 정보를 획득하는 활동이다.

### 1.0a 3대 수집 접근법 — 하향식·상향식·혼합형

| 구분 | 하향식(Top-Down) | 상향식(Bottom-Up) | 혼합형(Hybrid) |
|---|---|---|---|
| 방법 | 비전·전략에서 구체적 데이터 요건으로 분해 | 현행 시스템에서 상위 요건을 역으로 도출 | 하향식 방향설정 + 상향식 현황분석 병행 |
| 장점 | 전사 일관성, 비즈니스 전략과 직접 연계 | 현실 반영도 높음, 암묵적 업무규칙 발견 | 상호 검증으로 완전성 극대화 |
| 단점 | 목표가 추상적이면 구체성 부족 | 혁신적 미래 요건 도출 어려움 | — |

> **혼합형이 가장 이상적인 전략**으로 제시된다 — 전략적 방향성과 현실 기반 구체성을 동시에 확보.

### 1.0 정보 요구사항 유형 (4가지)

| 유형 | 설명 | 예시 |
|------|------|------|
| 외부 인터페이스 요건 | 시스템 송수신 간 요구사항 | 타 시스템 연계·API |
| 기능개선 요건 | 시스템 내 프로세스에 대한 요구 | 업무 처리 기능 추가 |
| 성능개선 요건 | 성능 관련 요구 (트랜잭션 시간, 동시 사용자 수 등) | 응답 시간 개선 |
| 보안개선 요건 | 보안 요소 관련 요구 (인증, 암호화, 방화벽 등) | 접근 권한 강화 |

### 1.1 이해관계자(Stakeholder) 식별

정보 요구 조사의 첫 단계는 요구 사항에 영향을 주거나 받는 모든 이해관계자를 식별하는 것이다.

| 유형 | 예시 |
|------|------|
| 내부 이해관계자 | 현업 담당자, IT 부서, 경영진 |
| 외부 이해관계자 | 고객, 파트너사, 규제 기관 |

### 1.2 수집 기법

| 기법 | 특징 | 적합 상황 |
|------|------|---------|
| 인터뷰(Interview) | 1:1 또는 소그룹, 심층 정보 수집 | 핵심 이해관계자 의견 파악 |
| 워크숍(Workshop) | 다수 참여, 합의 도출 | 여러 이해관계자 의견 통합 |
| JAD(Joint Application Development) | 사용자·개발자·관리자 집중 워크숍 | 빠른 요건 도출·합의 |
| 설문(Survey) | 대규모, 정량적 데이터 수집 | 많은 이해관계자 의견 취합 |
| 관찰(Observation) | 현장 업무 직접 관찰 | 실제 업무 방식 파악 |
| 문서 검토 | 기존 문서·시스템 분석 | 현행 업무 현황 파악 |
| 브레인스토밍 | 자유로운 아이디어 제시 | 창의적 요구 발굴 |
| 포커스 그룹 | 소그룹 토론, 의견·태도 수집 | 특정 주제 깊이 있는 탐색 |
| 프로토타입 | 시각적 요건 확인·피드백 | 요건 명확화·조기 검증 |

### 1.1a 핵심기법 vs 보조기법

**핵심기법**: 문서 분석, 사용자 면담, 워크숍/JAD — 대부분의 프로젝트에서 기본적으로 수행.
**보조기법**: 설문조사, 관찰, 프로토타이핑, **벤치마킹(Benchmarking)** — 상황에 따라 조합.

| 기법 | 설명 | 단점 |
|---|---|---|
| 설문조사 | 지리적 분산·다수 대상, 정량+정성 데이터 신속 수집 | 심층 정보 한계, 낮은 응답률 |
| 관찰 | 실제 업무 환경에서 직접 관찰, 암묵적 요구 발견 | 호손 효과, 시간 소모 |
| 프로토타이핑 | 시제품으로 피드백 수집, 조기 문제 발견 | 초기 비용 증가, 범위 만연 위험 |
| 벤치마킹 | 경쟁사·동종업계 선진 사례 분석, 시장표준·경쟁우위 요건 도출 | — |

### 1.1b 문서 분석(Document Analysis) — 모든 조사의 출발점

**4대 문서 범주**

| 범주 | 예시 |
|---|---|
| 전략/기획 문서 | 중장기 경영전략, 사업계획서, RFP |
| 업무 관련 문서 | 업무 매뉴얼·흐름도, 직무 기술서 |
| 시스템 관련 문서 | ERD·테이블 명세서, 인터페이스 정의서 |
| 규제/법규 문서 | 개인정보보호법, 사내 데이터 표준 지침 |

**4단계 절차**: ① 자료 수집 목록 작성 → ② 자료 수집(공식 요청) → ③ 내용 분석·요약 → ④ 보안 관리(문서 관리자 지정, 접근 통제)

> 단점: 문서가 최신이 아니거나 문서화되지 않은 암묵지는 파악 불가 → 반드시 면담·관찰로 교차 검증.

### 1.2a 면담(Interview) 심화

**면담 역할 분담:**

| 역할 | 책임 |
|------|------|
| **면담자** | 실질적 면담 진행, 대상자 질문 |
| **기록자** | 면담 내용을 있는 그대로 기록하고, 종료 후 재확인 |
| **관찰자** | 주제 이탈 시 주의, 보충 질문, 종료 여부 판단 |

**면담 진행 과정:**
```
대상자 선정 → 일정 수립 → 면담 준비 → 면담 진행 → 결과 분석 → 결과 피드백
```

| 단계 | 주요 내용 |
|------|---------|
| 대상자 선정 | 관련 업무를 명확히 이해하는 사람 (필수), 후원자·사용자 추천 (선택) |
| 일정 수립 | 프로젝트 목적과 범위 전달, 관련 문서 자료 요청 |
| 면담 준비 | 대상자 파악(업무·성향), 시나리오 준비, 30분 전 최종 점검 |
| 면담 진행 | 준비 내용 기반 진행, 필요시 질문 수정 |
| 결과 분석 | 팀 전원 참석, 이슈 정리, 필요시 추가 면담 |
| 결과 피드백 | **반드시** 면담 대상자 본인에게 결과지 승인 |

**면담 구조 유형:**

| 유형 | 특징 | 적합 상황 |
|------|------|---------|
| **피라미드** | 구체적 → 일반적 질문 순 | 아이디어 발굴, 구체적 사항 확인 |
| **퍼널** | 일반적 → 구체적 질문 순 | 기존 아이디어 발전, 범위 좁히기 |
| **다이아몬드** | 피라미드 + 퍼널 결합 | 균형 있는 심층 탐색 |

**면담 시간 기준:**
- 상위 관리자: 1.5시간 이내
- 실무자: 3시간 이내

**워크숍 목적:**
- 경영층·현업 부서장의 공통된 의견 도출
- 유사 업무 부서 간 면담 시간 절감
- 전문가 판단력으로 최적의 결론 도출

#### (교재 병기) 면담 3단계 절차와 질문 유형

교재 기준 면담은 아래 3단계 절차로도 설명된다 — 위 6단계(진행과정)와 상충하지 않는 보완적 관점이다.

| 단계 | 내용 |
|---|---|
| 계획 및 준비 | 주제·목표 설정, 핵심 실무자 선정, '면담 요지'를 최소 1주일 전 전달 |
| 수행 | 2인 1조(진행자+기록자), 동의를 얻어 녹음, 기록 누락 방지 |
| 결과 분석 및 정리 | 직후 면담록 작성 → 대상자에게 재송부하여 사실 확인(피드백) |

**질문 유형 3가지**: 폐쇄형("하루 몇 건 처리되나요?" — 사실관계 확인) / 개방형("가장 어려운 점은?" — 심층정보·근본원인) / 유도형("이 기능이 추가되면 효율이 오를까요?" — 의견·동의 확인)

**성공을 위한 5가지 고려사항**: ① 시간 준수·비밀보장으로 신뢰 형성, ② 기대수준 설정(지금은 '파악' 단계), ③ 범위 준수, ④ 실질적 권한을 가진 실무 전문가 선정, ⑤ 사전 자료 배포로 준비된 면담 진행

### 1.2b 워크숍/JAD 3단계 절차

| 단계 | 내용 |
|---|---|
| 계획 | 목표 설정, 핵심 이해관계자 선정, 중립적 촉진자·기록자 지정, 자료 사전 배포 |
| 수행 | 의제에 따라 진행, 브레인스토밍·다이어그램, 실시간 정리·공유 |
| 종료 및 정리 | 도출 요구사항·미해결 과제·결정사항을 보고서화, 회람·확인 후 공식 산출물 확정 |

**장점**: 단기간 집중 수렴·빠른 합의, 충돌·모호성 조기 발견, 참여자 주인의식 형성
**단점**: 핵심 인력 장시간 참여 부담, 촉진자 역량에 성패 좌우, 의견 독점 가능성

### 1.3 수집 시 주요 확인 사항

| 확인 항목 | 내용 |
|---------|------|
| 현재 업무 프로세스 | 현업이 수행하는 실제 업무 흐름 |
| 데이터 항목 | 업무에서 사용하는 데이터 목록 |
| 문제점·개선 요구 | 현재 시스템의 불편사항과 개선 필요 사항 |
| 법규·컴플라이언스 | 반드시 준수해야 하는 법규·정책 |

### 1.4 비기능 요구 4대 중요영역과 데이터 품질 요구 예문

데이터 아키텍처 설계 시 특히 중요한 비기능 요구 4대 영역과 구체적 요구사항 문장 예시:

| 영역 | 요구사항 문장 예시 |
|---|---|
| 표준 | "고객 코드는 전사 표준 코드(영문 약어)를 따른다" |
| 품질 | "고객 등록 시 이름과 연락처는 필수 입력(완전성)" |
| 성능 | "일일 매출 통계는 10초 이내 생성, 피크 시 동시 1,000명 지연 없이 조회" |
| 보안 | "비밀번호는 복호화 불가능한 방식으로 해싱 저장" |

**데이터 품질 5대 기준을 요구사항 문장으로 표현**

| 기준 | 요구사항 문장 |
|---|---|
| 완전성 | 고객 등록 시 이름과 연락처는 필수 입력 |
| 유일성 | 동일 주민등록번호 고객 중복 등록 금지 |
| 유효성 | 이메일은 @를 포함한 유효 형식 |
| 일관성 | 주문 시스템과 배송 시스템의 고객 주소는 항상 동일 |
| 정확성 | 상품 재고 수량은 실제 창고 재고와 일치 |

## 2. 정보 요구 사항 정리

수집된 정보 요구 사항을 구조화·표준화하여 체계적으로 정리하는 활동이다.

### 2.0 정리의 5대 목표

| # | 목표 | 설명 |
|---|---|---|
| 1 | 명확성 확보 | 모호·다의적 표현 제거 |
| 2 | 완전성 검토 | 필요한 정보 누락 여부 1차 검토 |
| 3 | 일관성 유지 | 동일 용어·형식으로 표준화 |
| 4 | 구조화 | 체계적 분류 + 고유 ID 부여 |
| 5 | 우선순위화 | 제한된 자원의 효율적 배분 |

### 2.0a 아키텍처 계층 매핑 규칙

정리된 요구사항은 데이터 아키텍처 계층에 매핑되어 이후 설계 단계와의 추적성을 확보한다: **비즈니스 요구 → 개념 데이터모델**, **기능 요구 → 논리 데이터모델**, **성능 요구 → 물리 데이터모델**.

### 2.1 정보 요구 사항 분류

수집된 요구 사항을 주제·기능·데이터 영역 등 기준으로 분류한다.

| 분류 기준 | 예시 |
|---------|------|
| 업무 기능별 | 주문 관리, 재고 관리, 고객 관리 |
| 데이터 주제 영역별 | 고객, 상품, 주문, 재고 |
| 요구 유형별 | 기능적/비기능적/데이터 표준/품질 |
| 우선순위별 | 필수/중요/선택 |

### 2.2 정보 요구 사항 정규화(Normalization)

유사하거나 중복된 요구 사항을 통합하고 표준 형식으로 기술하는 작업.

| 정규화 방법 | 내용 |
|---------|------|
| 유사 요구 통합 | 같은 의미의 요구 사항을 하나로 통합 |
| 중복 제거 | 동일 요구 사항 제거 |
| 표준 형식 기술 | 통일된 형식으로 재기술 |
| 모호한 표현 명확화 | 구체적이고 측정 가능한 표현으로 수정 |

### 2.3 정보 요구 사항 명세서 작성

| 항목 | 내용 |
|------|------|
| 요구 ID | 고유 식별자 (예: 기능 REQ-FUN-001, 비기능-성능 REQ-NF-PER-002) |
| 요구 명칭 | 간결한 명칭 |
| 요구 설명 | 상세한 내용 기술 |
| 출처 | 이해관계자 및 근거 문서 |
| 우선순위 | Must/Should/Could/Won't |
| 관련 업무 | 연관된 업무 기능 |
| 검증 기준 | 충족 여부 확인 방법 |

### 2.4 정보 요구 분류 체계

수집된 정보 요구를 데이터 아키텍처 관점에서 분류:

```
주제 영역(Subject Area)
  └── 핵심 엔터티 후보
        └── 데이터 항목(Attribute)
              └── 업무 규칙(Business Rule)
```

## 3. 정보 요구 사항 통합

여러 이해관계자·부서·시스템에서 수집된 정보 요구 사항을 하나의 일관된 체계로 통합하는 활동이다.

### 3.1 통합의 필요성

| 이유 | 내용 |
|------|------|
| 불일치 해소 | 부서별로 다르게 정의된 요구 사항의 불일치 해결 |
| 중복 제거 | 동일한 요구 사항의 중복 기술 제거 |
| 일관성 확보 | 전사 단일 정보 요구 사항 체계 수립 |
| 누락 보완 | 개별 수집 시 놓친 요구 사항 발굴 |

### 3.2 통합 절차

```
1. 수집된 요구 사항 목록화
2. 동의어·유사어 그룹화
3. 불일치·충돌 식별
4. 이해관계자 협의·조정
5. 통합 요구 사항 확정
6. 전사 정보 요구 사항 명세서 완성
```

### 3.3 이해관계자 간 충돌 조정

| 유형 | 해결 방법 |
|------|---------|
| 용어 불일치 | 표준 용어 선정·용어 사전 등록 |
| 요구 사항 충돌 | 우선순위 기준 또는 조정 회의로 결정 |
| 범위 불일치 | 프로젝트 범위 명확화 |

### 3.4 통합 결과물

| 산출물 | 내용 |
|--------|------|
| 통합 정보 요구 사항 명세서 | 전사 관점의 정보 요구 목록 |
| 데이터 주제 영역 목록 | 정보 분류 체계 |
| 업무 규칙 목록 | 정보 생성·변경·삭제 규칙 |
| 이해관계자 매트릭스 | 요구 사항별 이해관계자 책임 매핑 |

### 3.5 우선순위 결정 방법 — 4개 기법군

**방법 1: 화폐가치 산출**
1. 기업 차원의 중요성 평가 (1~3점)
2. 시스템 차원의 중요성 평가 (1~3점)
3. 다른 요구사항 영향 정도 평가 (1~5점)
4. 전체 점수 합산 후 백분율 환산
5. 백분율을 금액으로 환산하여 우선순위 배정

**방법 2: 상대적 중요도 산정**
1. 업무 기여도 평가 (1~5점)
2. 현행 정보시스템 충족 정도 평가 (1~3점)
3. 요구사항 간 연관성 평가 (최고 9점)
4. 평가 점수 기준으로 가중치 결정

**방법 3: MoSCoW** — Must-have(필수)/Should-have(중요)/Could-have(있으면 좋음)/Won't-have(제외). 애자일·MVP 범위 정의에 적합.

**방법 4: Kano 모델** — 기본적 품질(없으면 불만, 있어도 당연)/성과적 품질(충족될수록 만족 선형 증가)/매력적 품질(기대 안 했으나 큰 기쁨). 신제품 기획·차별화 포인트 발굴에 적합.

**방법 5: RICE 점수** — Reach(도달범위)×Impact(영향력)÷Effort(노력)×Confidence(확신도)로 계산: **점수 = R×I×C÷E**, 높을수록 우선순위 상위.

> 우선순위 기법은 정답을 알려주는 계산기가 아니라, 서로 다른 관점을 공통 언어로 테이블에 올려 합의를 돕는 협상 도구다.

### 3.6 이음동의어 통합 예시

부서 간 동일 대상을 다르게 부르는 경우를 표준 용어로 통합한다.

| 부서 | 표현 | → 통합 |
|---|---|---|
| 영업팀 | 거래처 정보 관리 | |
| 구매팀 | 공급사 정보 관리 | → **"파트너 정보 관리"** (단일 표준 요구사항) |
| 재무팀 | 지급처 정보 관리 | |

### 3.7 분할(Decomposition) vs 통합(Composition)

| 구분 | 설명 | 예시 |
|---|---|---|
| 분할 | 하나의 큰 요구사항을 세부 요구사항으로 나눔 | "영업 활동 지원 시스템 구축" → 고객정보관리·일일활동보고·실적통계조회 |
| 통합 | 여러 세부 요구사항이 하나의 상위 목표를 위한 것임이 명확할 때 묶음 | 세 부서의 파트너 정보 요구를 하나로 묶음 |

### 3.8 상충 요구사항 해결 5단계

| # | 단계 | 설명 |
|---|---|---|
| 1 | 갈등 식별·문서화 | 상충 요구사항과 각 소유자를 공식 문서화 |
| 2 | 근본 원인 분석 | 심층 인터뷰로 진짜 비즈니스 목표 파악 |
| 3 | 우선순위 재조정 | RICE·화폐가치 등으로 가치·긴급성·위험도 재평가 |
| 4 | 대안 탐색·타협안 도출 | 양측을 만족시킬 제3의 대안 모색 |
| 5 | 이해관계자 워크숍 | 촉진자 주도로 최종 합의 |

**사례**: 보안팀("모든 개인정보 필드 강력 암호화") vs 분석팀("대용량 집계 쿼리 성능 보장") → 타협안: 자주 조회되는 일부 필드는 암호화 완화, 민감 핵심 정보만 강력 암호화.

### 3.9 기준선(Baseline) 예시

| 요구사항 ID | 요구사항명 | 우선순위 | 상태 | 비고 |
|---|---|---|---|---|
| REQ-FUN-021 | 고객 등급별 할인율 자동 적용 | Must-have | 수용 | 관리자 화면에서 변경 가능 |
| REQ-NF-SEC-007 | 개인정보 조회 이력 기록 | Must-have | 수용 | 로그 최소 2년 보관 |
| REQ-FUN-088 | 상품 추천 알고리즘 고도화 | Could-have | 보류 | 2단계 사업에서 검토 |

## 출제 포인트

1. CSF→CIR 흐름: 경영환경·정보환경분석 → 핵심성공요소(CSF) → 핵심정보요구(CIR), 조사는 CIR과 현장을 잇는 다리
2. 수집→정리→통합은 반복적(iterative)·비선형적 구조
3. 3대 수집 접근법: 하향식/상향식/혼합형 — 혼합형이 가장 이상적
4. 문서 분석 4대 문서범주: 전략기획/업무관련/시스템관련/규제법규, 4단계 절차
5. 면담 3단계(교재): 계획및준비→수행→결과분석정리, 질문유형 3종(폐쇄형/개방형/유도형)
6. JAD 3단계: 계획→수행→종료및정리, 사용자·개발자·관리자가 함께 참여하는 집중 워크숍
7. 핵심기법(문서분석·면담·워크숍JAD) vs 보조기법(설문·관찰·프로토타이핑·벤치마킹)
8. 인터뷰 장점: 심층 정보 수집, 단점: 많은 시간 소요
9. 설문 장점: 대규모 정량적 데이터 수집, 단점: 심층 정보 한계
10. 관찰: 현장의 실제 업무 방식 파악에 적합, 단점은 호손 효과
11. 정리의 5대 목표: 명확성·완전성·일관성·구조화·우선순위화
12. 아키텍처 계층 매핑: 비즈니스요구→개념모델, 기능요구→논리모델, 성능요구→물리모델
13. 요구사항 ID 형식: REQ-FUN-001(기능), REQ-NF-PER-002(비기능-성능)
14. 정보 요구 분류 기준: 업무기능별·주제영역별·요구유형별·우선순위별
15. 정규화: 유사 통합·중복 제거·표준 형식·모호한 표현 명확화
16. 우선순위 결정 4기법군: 화폐가치산출·상대적중요도산정·MoSCoW·Kano모델·RICE점수(R×I×C÷E)
17. 이음동의어 통합: 거래처/공급사/지급처 → "파트너 정보 관리"
18. 분할(Decomposition) vs 통합(Composition) — 서로 다른 두 가지 통합 작업
19. 상충 요구사항 해결 5단계: 갈등식별문서화→근본원인분석→우선순위재조정→대안탐색타협안도출→이해관계자워크숍
20. 통합 필요성: 불일치 해소·중복 제거·일관성·누락 보완
21. 이해관계자 충돌 해결: 표준 용어 선정, 조정 회의, 범위 명확화
22. 통합 산출물: 통합 정보 요구 명세서·주제영역 목록·업무규칙·이해관계자 매트릭스, 최종 산출물은 기준선(Baseline)
