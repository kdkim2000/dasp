# 2과목 3장: 정보 요구 사항 분석

## 1. 분석 대상 정의

분석 대상 정의는 통합된 정보 요구 사항 중 실제 데이터 모델링·시스템 개발 대상이 될 요구 사항의 범위를 결정하는 단계이다.

### 1.1 분석 대상 선정 기준

| 기준 | 내용 |
|------|------|
| 비즈니스 가치 | 업무 목표 달성에 핵심적인 정보 |
| 우선순위 | MoSCoW 기법으로 결정된 Must Have 중심 |
| 실현 가능성 | 기술적·예산적으로 구현 가능한 범위 |
| 데이터 주제 영역 | EA 데이터 아키텍처의 주제 영역과 연계 |

### 1.2 분석 제외 기준

| 제외 기준 | 이유 |
|---------|------|
| 중복 요구 사항 | 통합 단계에서 이미 처리됨 |
| 시스템 외부 영역 | 프로젝트 범위 밖의 요구 사항 |
| 현행 유지 영역 | 변경이 필요 없는 현행 기능 |

### 1.3 분석 대상 데이터 영역 분류

정보 요구 사항을 데이터 관점에서 분류:

| 분류 | 설명 |
|------|------|
| 마스터 데이터 | 변경이 적은 기준 정보 (고객, 상품, 조직) |
| 트랜잭션 데이터 | 업무 처리 결과 데이터 (주문, 결제, 배송) |
| 이력 데이터 | 시간에 따른 변경 이력 관리 데이터 |
| 참조 데이터 | 코드, 분류 체계 등 참조용 데이터 |

### 1.4 현행 업무 분석 기법 (As-Is 진단)

#### SWOT 분석 (데이터 관점)

| 구분 | 예시 |
|------|------|
| 강점(S) | 경쟁사 대비 정확성·최신성이 높은 고객 데이터, 잘 구축된 데이터 표준 체계 |
| 약점(W) | 부서 간 데이터 단절(데이터 사일로), 데이터 품질 관리 조직 부재 |
| 기회(O) | 빅데이터·AI 기반 신규 서비스, 데이터 기반 마케팅을 통한 점유율 확대 |
| 위협(T) | 강화되는 개인정보보호 규제, 경쟁사의 데이터 기반 신규 비즈니스 |

**약점+기회 → 구체적 요구사항 전환**: '데이터 사일로'(W)를 극복하고 '빅데이터 분석'(O)을 활용 → "전사 데이터 통합 플랫폼 구축"이라는 구체적 정보 요구사항 도출.

#### 가치사슬(Value Chain) 분석

기업 활동을 **본원적 활동**(입고물류·운영/생산·출고물류·마케팅/영업·서비스)과 **지원 활동**(인사관리·재무/회계 등)으로 나누어 데이터 관점에서 매핑한다.

| 본원적 활동 | 관련 데이터 |
|---|---|
| 입고 물류 | 공급업체 정보, 원자재 입고 데이터, 재고량 데이터 |
| 운영/생산 | 생산 계획, 공정·품질 검사, 생산 실적 데이터 |
| 출고 물류 | 주문, 창고 관리, 배송 추적 데이터 |
| 마케팅/영업 | 고객 정보, 프로모션 반응, 영업 활동·계약 데이터 |
| 서비스 | 고객 문의(VOC), A/S 처리 이력, 만족도 데이터 |

**데이터 흐름 단절 발견**: '서비스' 단계 VOC 데이터가 '운영/생산' 단계 품질 개선에 활용되지 않는 경우 → 실시간 연계 요구사항 도출. 가치사슬 분석은 아키텍처의 데이터 흐름 단절 구간을 찾는 지도 역할을 한다.

#### 리버스 모델링(Reverse Engineering)

산출물(문서) 분석이 부실하거나 신뢰할 수 없을 때, **DDL·데이터 카탈로그 정보를 역분석**하여 물리 데이터 모델(PDM)·논리 데이터 모델(LDM)을 역생성하는 기법. 비정규화·데이터 타입 불일치·잘못된 관계 설정 등 현행 구조의 문제점을 진단할 수 있다.

### 1.5 Gap 발견 4단계 프로세스

| # | 단계 | 내용 |
|---|------|------|
| 1 | 업무 분석 | SWOT 등으로 이상적 업무 목표·데이터 요건 정의 |
| 2 | 시스템 분석 | 업무 영역/현행 시스템 매트릭스로 현재 지원 기능·구조 파악 |
| 3 | Gap 발견 | ERD·테이블 정의서 분석 결과와 이상적 요건 간 괴리 진단 |
| 4 | 요구사항 도출 | Gap을 메우는 신규 기능·데이터 구조 변경 요건 정의 |

**업무 영역/현행 시스템 매트릭스**: 전사 비즈니스 프로세스가 어떤 레거시 시스템에 의해 지원되는지 행렬로 조망하여 기능 중복과 지원 공백(사각지대)을 파악한다.

**사용자 뷰(View) 분석**: 화면·보고서·수작업 양식은 사용자가 데이터를 어떻게 조합해 보는지 보여주는 직접적 증거다. 한 보고서에 '고객 정보'+'주문 내역'+'A/S 이력'이 함께 나오면 → 엔티티 간 연관 관계의 단서. 수기로 계산해 기입하는 항목이 있으면 → 시스템이 제공 못 하는 잠재적 요구사항(추출 속성) 가능성.

## 2. 정보 요구 사항 상세화

분석 대상으로 확정된 정보 요구 사항을 구체적이고 측정 가능하게 상세히 기술하는 단계이다.

### 2.1 상세화 활동

| 활동 | 내용 |
|------|------|
| 데이터 항목 도출 | 요구 사항에서 필요한 데이터 항목(속성) 목록화 |
| 데이터 관계 정의 | 데이터 항목·엔터티 간의 관계 파악 |
| 업무 규칙 명세 | 데이터 생성·변경·삭제에 관한 규칙 정의 |
| 데이터 품질 요건 | 정확성·완전성·일관성·적시성 요건 정의 |

### 2.2 업무 규칙 명세

업무 규칙(Business Rule)은 정보 요구 사항 상세화의 핵심 활동이다.

| 규칙 유형 | 설명 | 예시 |
|---------|------|------|
| 정의 규칙 | 용어의 의미·범위 정의 | "고객 = 1회 이상 구매한 자" |
| 사실 규칙 | 개념 간 구조·관계 기술 | "주문은 하나 이상의 주문항목 포함" |
| 제약 규칙 | 데이터·프로세스 제약 조건 | "잔액 >= 0", "주문 시 고객 존재 필수" |
| 파생 규칙 | 기존 데이터에서 새 값 계산 | "세금 = 금액 × 세율" |

### 2.3 프로세스 분해와 계층도

| 단계 | 설명 |
|------|------|
| ① 단위 업무 기능 | 예) '주문 관리' |
| ② 기본 프로세스로 분해 | '신규 주문 접수'·'주문 내역 변경'·'주문 취소' — 하나의 사건으로 시작되어 중단 없이 수행되고 측정 가능한 결과를 산출하는 업무 단위 |
| ③ 프로세스 계층도 작성 | 높은 응집도(Cohesion)·낮은 결합도(Coupling) 원칙으로 계층화 |
| ④ 정보 항목 도출 | 각 프로세스의 입력·출력 정보를 **명사형**으로 식별·목록화 (도출 즉시 표준 단어·용어·도메인과 대조하여 명칭·타입·길이 일관화) |

> 상위 프로세스 1개 → 하위 7개 내외로 분해하는 것이 인지적으로 효과적. 하위 프로세스 7개 초과 시 상위 프로세스 분리 고려.

### 2.4 데이터 흐름 분석

데이터가 시스템 내에서 어떻게 생성·처리·출력되는지 분석.

**DFD(Data Flow Diagram) 구성 요소:**

| 기호 | 명칭 | 의미 |
|------|------|------|
| ○ | 프로세스 | 입력 데이터를 가공하여 새 데이터를 출력하는 활동. '동사+명사'로 표기(예: 고객 정보 등록) |
| → | 데이터 흐름 | 데이터의 이동 경로와 방향 |
| ▤ | 데이터 저장소 | 데이터가 저장되는 장소(파일·테이블) |
| □ | 외부 개체(엔티티) | 시스템과 데이터를 주고받는 외부 주체(예: 고객, 세무 시스템) |

#### DFD 레벨링(Leveling)

| 레벨 | 설명 |
|------|------|
| 레벨 0 (배경도/Context Diagram) | 전체 시스템을 단 하나의 프로세스로 보고, 외부 엔티티와의 주요 입출력만 표현 → 시스템의 범위와 외부 인터페이스 정의 |
| 레벨 1 | 레벨 0의 단일 프로세스를 주요 기능으로 분해, 데이터 흐름과 주요 저장소 식별 → 핵심 내부 구조 |
| 레벨 2 이상 | 각 프로세스를 더 상세한 하위 프로세스로 분해해 구체적 처리 로직 표현 → 충분히 상세화될 때까지 반복 |

#### DFD 작성 규칙과 검증 — 블랙홀·미라클

**데이터 보존의 원칙**: 프로세스는 입력 데이터 없이 출력 데이터를 생성할 수 없다. 모든 출력 데이터 흐름은 반드시 입력 데이터 흐름이 변환된 결과여야 한다.

| 오류 유형 | 설명 |
|------|------|
| 블랙홀(Blackhole) | 입력 데이터 흐름은 있으나 출력 데이터 흐름이 없는 프로세스 → 데이터가 소멸되는 논리적 오류 |
| 미라클(Miracle) | 입력 데이터 흐름 없이 출력 데이터 흐름만 생성하는 프로세스 → 데이터가 무(無)에서 창조되는 논리적 오류 |
| 직접 연결 금지 | 데이터 저장소 ↔ 데이터 저장소, 외부 엔티티 ↔ 외부 엔티티 간 직접 흐름 불가 → 모든 흐름은 반드시 프로세스를 거쳐야 함 |

### 2.5 유스케이스 모델링

**구성 요소**: 액터(Actor, 시스템과 상호작용하는 사람·외부 시스템 등), 유스케이스(Use Case, 액터가 목표를 달성하는 일련의 상호작용, '동사+명사'로 표기), 시스템 경계(개발 대상 시스템의 범위)

**관계(Relationship)**

| 관계 | 설명 | 예 |
|------|------|------|
| 포함(Include) | 반드시 포함하여 수행 | '게시글 작성'·'게시글 수정' 모두 '사용자 인증'을 포함 |
| 확장(Extend) | 조건 만족 시 선택적으로 수행 | '상품 결제'가 '쿠폰 사용'으로 확장 |
| 일반화(Generalization) | 공통 특징을 상위 유스케이스로 추상화, 하위가 상속 | — |

**시나리오 흐름 3종**: ① 정상 흐름(Basic Flow) — 예외 없이 성공적으로 완료되는 주된 경로 / ② 대안 흐름(Alternative Flow) — 분기 가능한 또 다른 정상 경로(예: 소셜 로그인) / ③ 예외 흐름(Exception Flow) — 오류·비정상 상황으로 실패하는 경우(예: 비밀번호 5회 오류)

### 2.6 클래스 다이어그램 도출 규칙

유스케이스 명세서는 개념 데이터 모델링의 기초 입력 자료가 된다.

| # | 변환 규칙 | 예시 |
|---|------|------|
| 1 | 명사 → 엔티티 클래스 | "고객이 상품을 주문한다" → '고객'·'상품'·'주문' |
| 2 | 형용사·소유격 → 속성 | "고객'의' '이름'·'주소'" → 속성(Attribute) 후보 |
| 3 | 동사 → 관계 | "'고객'과 '주문'의 '주문하다'" → 클래스 간 관계(Association) |

### 2.7 비기능 요구사항(NFR) 정량화와 FURPS+

비기능 요구사항은 반드시 **정량화**해야 한다. 예) ✕ "응답 속도가 빨라야 한다" → ○ "동시 사용자 1,000명 환경에서 95%의 경우 2초 이내에 응답해야 한다" (데이터 양·처리 속도·보안 수준이 물리 데이터 모델의 인덱싱·파티셔닝·반정규화를 결정)

| 구분 | 항목 | 세부 내용 |
|------|------|------|
| F | Functionality (기능성) | 기능 범위·정확성·상호운용성 |
| U | Usability (사용성) | 학습·사용 용이성 — 심미성·일관성·도움말 |
| R | Reliability (신뢰성) | 안정성 — MTBF·가용성·장애 복구 능력 |
| P | Performance (성능) | 응답 시간·TPS·자원 사용 효율 |
| S | Supportability (지원성) | 유지보수성·이식성·확장성·테스트 용이성 |
| + | Constraints (제약) | 설계·구현·인터페이스·물리적 제약 |

### 2.8 DFD vs 유스케이스 — 상호 보완과 교차 검증

DFD는 데이터의 정적 구조와 흐름의 논리적 무결성(완전성)을 보증하고, 유스케이스는 사용자 목표 달성 시나리오와 상호작용의 완전성을 보증한다. 두 관점을 교차 검증할 때 숨겨진 요구사항이 드러난다. 예) 유스케이스 시나리오에는 "포인트로 결제" 단계가 있으나 DFD의 '결제 처리' 프로세스에는 '회원' 저장소로부터 '포인트 정보'가 입력되는 경로가 없다면 → 요구사항의 불일치·누락 발견.

### 2.9 상세화 산출물

| 산출물 | 내용 |
|--------|------|
| 상세 정보 요구 사항 명세서 | 데이터 항목·규칙·품질 요건 포함 |
| 개념 데이터 모델(초안) | 주요 엔터티와 관계를 도식화한 초안 ERD |
| 업무 규칙 목록 | 유형별 업무 규칙 목록 |
| 데이터 흐름도(DFD) | 데이터 처리 흐름 시각화 |

## 3. 정보 요구 사항 확인

상세화된 정보 요구 사항을 이해관계자와 함께 검토·확인하는 단계이다.

### 3.1 확인 목적

| 목적 | 내용 |
|------|------|
| 정확성 검증 | 이해관계자의 실제 요구와 일치하는지 확인 |
| 완전성 검증 | 누락된 요구 사항이 없는지 확인 |
| 일관성 검증 | 요구 사항 간 충돌·모순이 없는지 확인 |
| 실현가능성 검증 | 기술적으로 구현 가능한지 확인 |

### 3.2 확인 기법 3종 (형식성 증가 순: 동료검토 → 워크스루 → 인스펙션)

교재 기준 정보 요구 사항 확인 기법은 **동료검토(Peer Review)·워크스루(Walkthrough)·인스펙션(Inspection)** 3종이며, 이 순서로 형식성(공식성)이 높아진다. (프로토타입 검토·체크리스트 검토는 이를 보조하는 도구로 활용될 뿐 별도의 정식 기법은 아님)

| 구분 | 동료 검토 (Peer Review) | 워크스루 (Walkthrough) | 인스펙션 (Inspection) |
|------|---------|---------|---------|
| 목적 | 비공식 의견 교환, 초기 결함 발견 | 작성자 주도 설명 후 피드백으로 오류 조기 발견 | 훈련된 전문가 팀이 절차·역할에 따라 결함을 발견·기록하는 공식 검증 |
| 절차 | 비공식 — 동료에게 검토 요청 후 자유 토론 | 준공식 — ①자료 배포 ②작성자 주도 회의 ③결함 목록화 | 공식 — ①계획 ②사전 준비 ③검토 회의 ④재작업 ⑤후속 조치 |
| 참여자 역할 | 작성자, 동료 검토자 | 작성자(발표자), 참석자(검토자) | 사회자·작성자·발표자·기록자·검토자 등 명확한 역할 분담 |
| 장점 | 비용이 적고 신속, 협업 문화 증진 | 교육 효과가 크고 오류 조기 발견에 효과적 | 결함 발견율 최고, 통계 수집·프로세스 개선에 활용 |
| 단점 | 검토 깊이가 얕고 감정 개입 가능 | 작성자 발표 능력에 의존, 해결보다 발견에 집중 | 준비·수행에 많은 시간과 비용 소요 |
| 적합한 상황 | 초기 아이디어·초안 검토 | 팀 내부 중간 산출물 검토 | 안정성·품질이 매우 중요한 핵심 산출물(최종 SRS) |

**보조 도구**: 프로토타입 검토(시각적 시제품으로 이해관계자 피드백 수집), 체크리스트 검토(사전 정의된 점검 항목으로 보완) — 위 3대 기법 수행 시 함께 활용하는 보조 수단.

※ 검토 기준(체크리스트): 완전성·정확성·일관성·명확성·검증 가능성·추적성

### 3.4 확인 결과 처리

| 상태 | 처리 |
|------|------|
| 승인 | 다음 단계(분석) 진행 |
| 수정 필요 | 해당 요구 사항 수정 후 재확인 |
| 추가 발견 | 신규 요구 사항 등록 |
| 제외 결정 | 범위 외로 분류 |

### 3.5 CRUD 매트릭스로 요구사항의 논리적 완전성 검증

> 행 = 업무 기능/프로세스, 열 = 데이터 집합(엔티티)

| 업무 기능 ↓ / 정보 항목 → | 고객 | 상품 | 주문 | 재고 |
|---|---|---|---|---|
| 회원 가입 | C | | | |
| 상품 정보 조회 | | R | | |
| 주문 접수 | R | R | C | U |
| 결제 처리 | | | U | |
| 배송 처리 | | | U | |
| 회원 탈퇴 | D | | | |

**CRUD 검증 6가지 규칙** (part2_ch4.md의 CRUD 매트릭스 규칙과 동일하게 통일)

| 규칙 | 검증 항목 | 설명 |
|---|---|---|
| 규칙1 | 생성(C)의 존재 여부 | 모든 정보 항목(행)은 반드시 하나 이상의 'C'를 가져야 한다 |
| 규칙2 | 활용(R/U)의 존재 여부 | 'C'로 생성된 항목은 최소 한 번 이상 조회·수정되어야 한다 |
| 규칙3 | 소멸(D)의 존재 여부 | 비즈니스 규칙상 소멸이 필요한 항목은 'D' 프로세스를 가져야 한다(영구 보존 데이터는 예외) |
| 규칙4 | 프로세스의 역할 존재 | 모든 기본 프로세스(열)는 하나 이상의 C·R·U·D를 수행해야 한다 |
| 규칙5 | 생성(C)의 유일성 | 'C'를 수행하는 프로세스가 둘 이상이면 업무 역할 중복·오너십 충돌 위험 신호 |
| 규칙6 | 과도한 CRUD 집중 | 한 엔티티에 대한 C/U/D 프로세스 수가 비정상적으로 많으면(예 7개 초과) 세분화 검토 |

**분석 결과 → 도출된 요구사항 예시**: 위 표에서 '상품' 엔티티에 C·U·D가 없음(규칙2 위반 가능성) → "상품 등록/수정/삭제 프로세스" 신규 요구사항 도출.

### 3.6 검증(Verification)과 확인(Validation) — 두 개의 관문

- **검증(Verification)**: 명세서 자체의 논리적 정확성 확인 — "제품을 올바르게(right) 만들고 있는가?" (인스펙션, CRUD 매트릭스 등으로 수행)
- **확인(Validation)**: 사용자의 실제 의도 충족 여부 확인 — "올바른(right) 제품을 만들고 있는가?"
- 두 관문을 모두 통과해야 흔들림 없는 요구사항 기준선(Baseline)이 완성된다.

### 3.7 4대 핵심 산출물 (분석 단계 완료 시)

| 산출물 | 설명 |
|---|---|
| ① 요구사항 명세서 | 도출된 모든 요구사항을 공식 기록한 문서. 향후 설계·테스트의 절대적 기준점 |
| ② 업무 영역 및 현행 시스템 매트릭스 | 비즈니스 프로세스별 지원 시스템 조망 → 아키텍처 사각지대 제거 |
| ③ CRUD 매트릭스 | 프로세스-데이터 상호작용 규명 → 데이터 모델의 논리적 완전성 검증 도구 |
| ④ 분석 모델(DFD·유스케이스) | 추상적 요건을 시각화하여 모델링의 직접적 기반 제공 |

## 4. 정보 요구사항 상세화 심화

### 4.1 분석 대상 자료 평가 기준

현행 시스템 관련 자료 수집 시 4가지 기준으로 평가:

| 기준 | 설명 |
|------|------|
| **유용성** | 문서를 분석 활동에 활용할 수 있는가 |
| **완전성** | 문서에 누락된 내용이 없는가 |
| **정확성** | 현재 운영 중인 시스템과 일치하는가 |
| **유효성** | 최신 문서인가 (구버전 아닌지 확인) |

### 4.2 프로세스 관점의 요구사항 상세화

**프로세스의 특징:**
- 실제 업무가 수행되는 행위로 시작·종료 시점이 명확
- 실행 횟수를 셀 수 있음
- 더 이상 분해할 수 없는 시점 = 기본 프로세스

**프로세스 도출 시 중요 원칙:**

| 원칙 | 설명 |
|------|------|
| 높은 응집도(Cohesion) | 하나의 프로세스는 단일 목적 수행 |
| 낮은 결합도(Coupling) | 프로세스 간 의존성 최소화 |

> 하위 프로세스 7개 초과 시 상위 프로세스 분리 고려

### 4.3 정보 요구사항 재검토 4가지 확인 기준

재검토(Review) 단계에서 산출물 누락·보완 사항을 도출하는 기준:

| 확인 기준 | 설명 |
|---------|------|
| **완전성** | 요구사항 누락 여부 확인 |
| **정확성** | 정확하게 표현되었는지 확인 |
| **일관성** | 표준화 준수 여부 확인 |
| **안정성** | 다른 업무 영역에 미치는 영향 여부 확인 |

### 4.4 재검토 절차

```
재검토 계획 수립 → 재검토 실시 → 보완 결과 확인
```

| 단계 | 주요 내용 |
|------|---------|
| 계획 수립 | 일자·장소·시간·참석대상·준비물 계획, 재검토 업무와 세부 시간 계획 |
| 재검토 실시 | 담당자별 업무 숙지, 배포된 산출물 **반드시 예습**, 해당 업무 관련자가 진행 |
| 보완 결과 확인 | 재검토 결과·보완목록 배포, 모두 반영되면 재검토 종료 |

## 출제 포인트

1. 분석 대상 선정 기준: 비즈니스 가치·우선순위·실현가능성·주제영역
2. 마스터 데이터: 기준 정보(고객·상품), 트랜잭션 데이터: 업무 처리 결과
3. 업무 규칙 4가지: 정의·사실·제약·파생 규칙
4. DFD 4개 구성 요소: 프로세스·데이터 저장소·외부 개체·데이터 흐름, 레벨링(레벨0 배경도/레벨1/레벨2 이상)
5. 정보 요구 상세화: 데이터 항목 도출→관계 정의→업무 규칙→품질 요건
6. 확인 기법 3종(형식성 증가 순): 동료검토→워크스루→인스펙션 (프로토타입·체크리스트 검토는 보조 도구)
7. SWOT(약점+기회→구체적 요구사항), 가치사슬 분석(데이터 흐름 단절 발견), 리버스 모델링(DDL→PDM/LDM 역생성)
8. Gap 발견 4단계: 업무 분석→시스템 분석→Gap 발견→요구사항 도출
9. 확인 4대 목적: 정확성·완전성·일관성·실현가능성
10. 확인 결과 처리: 승인/수정 후 재확인/추가 등록/제외
11. 블랙홀(출력 없음)·미라클(입력 없음) — 데이터 보존의 원칙 위반, 저장소↔저장소·외부엔티티↔외부엔티티 직접 연결 금지
12. 유스케이스 관계: 포함(Include)·확장(Extend)·일반화(Generalization), 시나리오 3종(정상/대안/예외)
13. 클래스 도출 규칙: 명사→엔티티, 형용사→속성, 동사→관계
14. FURPS+: 기능성·사용성·신뢰성·성능·지원성·제약 — 비기능 요구사항 정량화 프레임워크
15. CRUD 검증 6가지 규칙: 생성/활용/소멸/프로세스역할/생성유일성/과도한CRUD집중 (part2_ch4.md와 동일)
16. 검증(Verification, 올바르게 만드는가) vs 확인(Validation, 올바른 것을 만드는가)
17. 4대 핵심 산출물: 요구사항 명세서·업무영역/현행시스템 매트릭스·CRUD 매트릭스·분석 모델
18. 상세화 산출물: 상세 명세서·개념 데이터 모델·업무규칙 목록·DFD
