# 2과목 4장: 정보 요구 검증

## -1. 결함 수용 비용 곡선 — 검증의 경제학

요구사항 분석 단계의 수정 비용을 1이라 할 때, 단계가 늦어질수록 결함 수정 비용은 기하급수적으로 증가한다.

| 단계 | 상대 비용 |
|---|---|
| 요구사항 분석 | 1 |
| 설계 | 3~6배 |
| 코딩 | 10배 |
| 테스트 | 20~50배 |
| 운영(상용 이후) | 100~200배 |

→ 정보 요구 검증은 단순 오류 색출이 아니라 프로젝트의 예산·일정·품질을 담보하는 경제적 활동이다.

## 0. 정보 요구사항 생명주기와 명세화

### 0.1 정보 요구사항 생명주기

```
도출 → 분석/정의 → 명세화 → 검증 → 승인
  ↑                              ↓
  └──── 추적·변경 요청·영향 분석·승인/기각 ────┘
```

### 0.2 정보 요구 명세서의 역할

| 역할 주체 | 활용 목적 |
|---------|---------|
| **사용자** | 개발 완료 판단의 기준 |
| **개발자** | 분석·설계·코딩의 기초 문서 |
| **테스터** | 테스트 케이스 작성 기준 |

> **핵심**: 정보 요구 명세서는 "사용자와 개발자를 연결하는 문서"이다.

### 0.3 명세서 작성 시 주의사항

1. 사용자 이해도 중심의 명확한 작성
2. 개발 가능성을 고려한 기술
3. **정량적** 테스트 기준 제시
4. 비기능 요구(성능·보안·가용성) 명시
5. 품질 우선순위 명확화

### 0.4 정보 요구 검증의 6가지 목적

| 목적 | 설명 |
|---------|------|
| **완전성 (Completeness)** | 누락 없이 요구사항이 포함되었는가 |
| **정확성 (Correctness)** | 사용자 의도와 업무 규칙이 올바르게 기술되었는가 |
| **일관성 (Consistency)** | 요구사항 간 상충·모순이 없는가 |
| **명확성 (Clarity)** | 모호한 표현이 제거되었는가 |
| **검증 가능성 (Verifiability)** | 테스트로 충족 여부를 확인할 수 있는가 |
| **실현 가능성 (Feasibility)** | 예산·기술·일정 내에 구현 가능한가 |

### 0.5 상관분석 수행 주체 비교

| 수행 주체 | 장점 | 단점 |
|---------|------|------|
| **요구사항 분석가** | 업무 이해도 높음 | 객관성 저하 우려 |
| **품질보증팀(QA)** | 인터페이스 검증 용이 | 업무 이해도 낮음 |
| **외부 감리** | 제3자 객관성 극대화 | 업무 파악 한계 |

## 1. 정보 요구 사항 상관분석 기법

정보 요구 사항 상관분석은 여러 정보 요구 사항 간의 관계·연관성·충돌을 체계적으로 분석하는 기법이다.

### 1.1 상관분석의 목적

| 목적 | 내용 |
|------|------|
| 충돌 식별 | 서로 모순되거나 충돌하는 요구 사항 발견 |
| 의존성 파악 | 요구 사항 간 선후 관계·의존 관계 파악 |
| 중복 탐지 | 유사하거나 동일한 요구 사항 중복 확인 |
| 누락 발견 | 다른 요구 사항에서 유추 가능한 누락 요건 도출 |

### 1.2 CRUD 매트릭스 기반 상관분석

정보 요구 사항 상관분석은 정보 요구사항을 프로세스·업무 기능·조직 구조와 2차원 매트릭스로 교차 분석하는 기법이다. (참고: 유사 기법으로 요구사항 간 관계를 ◎강한상관/○약한상관/×충돌 기호로 표현하는 상관 행렬(Correlation Matrix)식 접근도 있으나, 본 교재의 핵심 기법은 아래 CRUD 매트릭스 기반 상관분석이다.)

**CRUD 매트릭스 작성 3단계**

| # | 단계 | 설명 |
|---|------|------|
| 1 | 행(Row) 정의 | 정보 항목(데이터 모델의 핵심 엔티티) 목록 |
| 2 | 열(Column) 정의 | 단위 업무 기능(기본 프로세스) 목록 |
| 3 | 셀(Cell) 값 정의 | 교차 지점에 C·R·U·D 표기 |

표기 우선순위(한 프로세스가 한 항목에 여러 작업을 하는 경우): **C → D → U → R** 순으로 영향이 큰 것을 우선 표기(또는 모두 표기).

#### ① 정보요구/업무 기능 상관분석

- 목적: 데이터와 비즈니스의 전략적 정렬(Strategic Alignment) 검증
- 열 = 비즈니스 아키텍처(BA)의 최하위 업무 기능
- 체크포인트: 열 전체가 비어 있음(순수 오프라인 활동 또는 정보 항목 누락) / 행 전체가 비어 있음(어떤 업무 기능도 지원하지 않는 데이터 → 삭제 대상) / 'C'는 있으나 'U'가 없음(존재 가치 재검토)

#### ② 정보요구/조직 기능 상관분석

- 목적: 데이터 오너십(Ownership)과 스튜어드십 정의 — 셀 값: **C(주도적 생성·변경) / U(단순 참조·활용)**
- 열 = 조직도상의 조직 단위(본부·팀·부서)
- 체크포인트: 'C'가 표시된 조직은 데이터 오너 후보 / 'C'가 여러 조직에 나타나면 **오너십 충돌** / 'U'가 다수 조직에 분포하면 전사 공유 기준 정보(Master Data)

**오너십 충돌 해결**: 오너십 충돌이 발견되면 반드시 데이터 거버넌스 협의체를 통해 유일한 생성·관리 주체(Single Source of Truth)를 공식적으로 결정해야 한다. 단, 비즈니스 특성상 복수 생성 주체가 타당한 경우(예: 영업사원 등록=인사팀, 파트너사 직원 등록=사업개발팀)도 있으므로 기계적 통합이 아니라 담당자와의 협의를 거쳐야 한다.

### 1.3 CRUD 검증 체크리스트 — 6가지 규칙

| 규칙 | 검증 항목 | 설명 |
|---|---|---|
| 규칙1 | 생성(C)의 존재 여부 | 모든 정보 항목(행)은 반드시 하나 이상의 'C'를 가져야 한다 |
| 규칙2 | 활용(R/U)의 존재 여부 | 'C'로 생성된 항목은 최소 한 번 이상 조회·수정되어야 한다 |
| 규칙3 | 소멸(D)의 존재 여부 | 비즈니스 규칙상 소멸이 필요한 항목은 'D' 프로세스를 가져야 한다(영구 보존 데이터는 예외) |
| 규칙4 | 프로세스의 역할 존재 | 모든 기본 프로세스(열)는 하나 이상의 C·R·U·D를 수행해야 한다 |
| 규칙5 | 생성(C)의 유일성 | 'C'를 수행하는 프로세스가 둘 이상이면 업무 역할 중복·오너십 충돌 위험 신호 |
| 규칙6 | 과도한 CRUD 집중 | 한 엔티티에 대한 C/U/D 프로세스 수가 비정상적으로 많으면(예 7개 초과) 세분화 검토 |

(part2_ch3.md의 CRUD 검증 규칙과 동일하게 통일된 6가지 규칙이다.)

### 1.4 이상 징후(Anomaly) → 조치(Action) 프레임워크

| # | 점검 내용(Anomaly) | 분석 결과 | 조치 사항(Action) |
|---|---|---|---|
| 1 | 생성(C) 프로세스 없음 | 데이터 생성 로직 누락 | 생성 프로세스 요구사항 도출 / 불필요 시 정보 항목 삭제 |
| 2 | 생성만 되고 활용(R·U) 안 됨 | 불필요 데이터 또는 활용 로직 누락 | 활용 프로세스·리포트 요구사항 도출 / 정보 항목 삭제 |
| 3 | 생성(C) 주체가 둘 이상 | 업무 역할 중복 또는 오너십 충돌 | 중복 프로세스 통합·역할 재정의 / 거버넌스 협의로 단일 오너 지정 |
| 4 | 업무 기능·조직이 사용하는 정보 항목 없음 | 기능 정의 오류 또는 데이터 누락 | 업무 기능 역할 재점검 / 신규 정보 요구사항 도출 |
| 5 | 삭제(D) 프로세스 없음(영구 보존 제외) | 데이터 생명주기 관리 누락 | 보관 정책 확인 후 삭제·비활성화 프로세스 도출 |
| 6 | 기본 프로세스가 조회(R)만 함 | 상태 변경 없는 프로세스일 가능성 | 단순 조회인지 상태 변경 프로세스인지 재검토 |
| 7 | 너무 많은 프로세스에서 사용(7개 이상) | 책임·역할 과대, 응집도 낮음 | 더 작은 단위로 세분화 검토 |

### 1.5 사례 연구 — 온라인 서점 주문관리 CRUD 매트릭스

| 정보 항목 ↓ / 프로세스 → | 회원가입 | 상품조회 | 주문하기 | 결제처리 | 배송정보입력 | 회원탈퇴 |
|---|---|---|---|---|---|---|
| 고객 | C | | R | | | D |
| 상품 | | R | R | | | |
| 주문 | | | C | R | U | |
| 결제 | | | | C | | |

**발견된 이상 징후 3건**

| Anomaly | 위배 규칙 | 도출된 요구사항 |
|---|---|---|
| 1 | 규칙2 | '상품'이 조회(R)만 존재 → 상품 등록/수정/삭제 프로세스 + '공급사' 정보 항목 추가 |
| 2 | 규칙3 | '주문'에 D가 없음 → 주문 취소 프로세스 추가 |
| 3 | 규칙2 | '결제'가 생성(C)만 있고 활용 없음 → 결제 내역 조회, 결제 취소/환불 프로세스 추가 |

### 1.6 RTM vs 상관분석 — 혼동 주의

| 구분 | RTM (요구사항 추적성 매트릭스) | 상관분석 (Correlation Analysis) |
|---|---|---|
| 범위 | 요구사항-설계-구현-테스트 등 SDLC 전반의 폭넓은 추적성 도구 | 데이터(정보 요구)와 비즈니스 컨텍스트(업무·조직) 간 논리적 정합성 보장에 특화된 도구 |
| 초점 | 개발 산출물 간 연결 관계 추적 | 데이터 오너십·완전성·일관성 검증 |

## 2. 추가 및 삭제 정보 요구 사항 도출

검증 과정에서 새롭게 추가해야 할 요구 사항과 제거해야 할 불필요한 요구 사항을 도출하는 단계이다.

### 2.1 추가 정보 요구 사항 도출

상관분석 결과, 기존 요구 사항에서 암묵적으로 필요하지만 명시되지 않은 요구 사항을 발굴한다.

| 도출 방법 | 내용 |
|---------|------|
| 상관분석 결과 활용 | 상관 관계에서 유추 가능한 누락 요구 사항 |
| 업무 흐름 검토 | 업무 흐름도 검토 시 발견되는 누락 단계 |
| 법규·컴플라이언스 검토 | 법적 요건에서 도출되는 추가 요구 사항 |
| 데이터 품질 요건 보완 | 주요 데이터 항목의 품질 요건 누락 확인 |

**추가 요구 사항 발굴 시 확인 질문:**
- "이 데이터는 어디서 생성되는가?"
- "이 프로세스의 예외 처리는 어떻게 되는가?"
- "해당 데이터의 보존 기간은 얼마인가?"
- "이 데이터에 접근할 수 있는 권한은 누구에게 있는가?"

### 2.2 삭제 정보 요구 사항 도출

중복, 범위 외, 비현실적인 요구 사항을 식별하여 제거하는 활동.

| 삭제 기준 | 내용 |
|---------|------|
| 중복 요구 사항 | 통합 과정에서 누락된 중복 요구 사항 |
| 범위 외 요구 사항 | 프로젝트 범위 밖의 요구 사항 |
| 비실현 가능 요구 사항 | 기술적·비용적으로 구현 불가한 요구 사항 |
| 이미 구현된 기능 | 현행 시스템에 이미 존재하는 기능 |

### 2.3 요구 사항 변경 관리

추가·삭제 결정 시 공식적인 변경 관리 절차를 따른다.

```
변경 요청 제출 → 영향 분석 → 이해관계자 검토·승인 → 요구 명세서 업데이트 → 추적성 매트릭스 업데이트
```

| 관리 항목 | 내용 |
|---------|------|
| 변경 이력 | 언제, 누가, 무엇을 변경했는지 기록 |
| 영향 분석 | 변경 시 다른 요구 사항에 미치는 영향 분석 |
| 승인 이력 | 이해관계자 승인 기록 |

## 3. 정보 요구 보완 및 확인

검증 결과를 토대로 정보 요구 사항을 최종 보완하고 이해관계자의 최종 확인을 받는 단계이다.

### 3.1 보완 활동

| 활동 | 내용 |
|------|------|
| 누락 요구 사항 추가 | 상관분석·검토에서 발견된 누락 요구 추가 |
| 불명확한 요구 수정 | 모호한 표현을 구체적으로 수정 |
| 충돌 요구 조정 | 상충하는 요구 사항 중재·조정 |
| 우선순위 재조정 | 변경된 요구 사항 반영하여 우선순위 재설정 |

### 3.1a 형상 관리 3원칙

도출된 모든 추가·수정·삭제 사항은 공식 산출물에 체계적으로 반영되어야 한다.

| # | 원칙 | 설명 |
|---|------|------|
| 1 | 고유 ID 부여 | 모든 요구사항(신규 포함)은 전사 규칙에 따라 고유 ID 부여(예: DAR-016) |
| 2 | 버전 관리 | 요구사항 목록은 변경될 때마다 버전 번호 부여 |
| 3 | 변경 이력 기록 | 변경 일자·변경자·변경 사유·승인자를 상세히 기록 |

### 3.1b 재검토 세션(Review Session) — 워크스루 vs 인스펙션 선택 기준

| 검토 방식 | 설명 |
|------|------|
| 워크스루(Walkthrough) | 작성자가 문서를 설명하고 참석자가 질문·의견을 제시하는 비공식적 검토 |
| 인스펙션(Inspection) | 사회자·기록자·검토자의 역할과 체크리스트에 따라 공식 절차로 오류를 찾는 가장 엄격한 방식 |

**선택 기준**: 프로젝트 공식도(formality) 수준에 따라 선택 — **중간 산출물은 워크스루**, **최종 요구사항 명세서(SRS)처럼 품질이 결정적인 산출물은 인스펙션**.

### 3.2 최종 확인 절차

| 단계 | 내용 |
|------|------|
| 검토 회의 준비 | 보완된 정보 요구 사항 명세서 배포 |
| 이해관계자 검토 | 현업·IT·관리자 등 검토 |
| 의견 수렴 | 이견 조정 및 합의 도출 |
| 최종 승인 | 이해관계자 서명·승인 |
| 기준선(Baseline) 설정 | 승인된 요구 사항을 기준선으로 확정 |

### 3.3 기준선(Baseline) 관리

**기준선(Configuration Baseline)** 은 공식적으로 검토·승인된 정보 요구 사항의 확정 버전이다.

| 특성 | 설명 |
|------|------|
| 변경 통제 대상 | 기준선 변경 시 공식 변경 요청 필요 |
| 추적성 기준 | 이후 설계·구현의 참조 기준 |
| 버전 관리 | 버전 번호로 변경 이력 관리 |

**기준선의 두 가지 성격**

| 구분 | 설명 |
|------|------|
| ① 공식적인 계약 | 비즈니스 요구 부서와 IT 개발 부서 간의 공식 '계약' — 이후 모든 설계·개발·테스트는 이 기준선을 근거로 수행 |
| ② 범위 통제의 기준 | 기준선 설정 이후 합의되지 않은 신규 요구·변경은 반드시 공식 변경 통제 프로세스를 거쳐야 함 → 범위 만연(Scope Creep) 방지 |

**변경통제위원회(CCB: Change Control Board)**: PM과 핵심 이해관계자로 구성되어 기준선 설정 이후의 변경 요청을 승인·기각·보류하는 심의 기구. 변경 관리 절차(요청→영향분석→이해관계자 검토·승인→명세서 업데이트→추적성 매트릭스 업데이트)의 '검토·승인' 단계는 CCB의 심의로 이루어진다.

### 3.4 최종 산출물

| 산출물 | 내용 |
|--------|------|
| 확정 정보 요구 사항 명세서 | 승인된 최종 요구 사항 문서 |
| 요구 사항 추적성 매트릭스(RTM) | 요구 사항 ↔ 설계 ↔ 구현 추적 매핑 |
| 변경 요청 목록 | 추가·삭제 변경 이력 |

### 3.5 요구 사항 추적성 매트릭스(RTM: Requirements Traceability Matrix)

| 요구 ID | 요구 명칭 | 설계 산출물 | 구현 모듈 | 테스트 케이스 |
|--------|---------|---------|---------|------------|
| IR-001 | 고객 정보 관리 | ERD: 고객 엔터티 | 고객관리 모듈 | TC-001 |
| IR-002 | 주문 처리 | ERD: 주문 엔터티 | 주문관리 모듈 | TC-002 |

1. 결함 수용 비용 곡선: 분석(1)→설계(3~6배)→코딩(10배)→테스트(20~50배)→운영(100~200배)
2. 검증의 6가지 목적: 완전성·정확성·일관성·명확성·검증가능성·실현가능성
3. CRUD 매트릭스 3단계: 행(정보항목) 정의→열(프로세스) 정의→셀 값 정의, 표기 우선순위 C→D→U→R
4. CRUD 검증 6가지 규칙: 생성/활용/소멸/프로세스역할/생성유일성/과도한CRUD집중 (part2_ch3.md와 동일)
5. 정보요구/업무기능 상관분석 vs 정보요구/조직기능 상관분석(오너십, C/U 표기)
6. 오너십 충돌: 'C'가 여러 조직에 나타남 → 거버넌스 협의체를 통한 Single Source of Truth 결정
7. 이상 징후(Anomaly)→조치(Action) 7종 프레임워크
8. RTM vs 상관분석: RTM은 SDLC 전반 추적성 도구, 상관분석은 데이터-업무맥락 정합성 도구
9. 형상 관리 3원칙: 고유 ID 부여(예 DAR-016)·버전 관리·변경 이력 기록
10. 재검토 세션 선택 기준: 중간 산출물=워크스루, 최종 SRS=인스펙션
11. 기준선(Baseline)의 두 성격: 공식 계약 + 범위 통제(Scope Creep 방지) 기준
12. 변경통제위원회(CCB): 변경 요청 승인·기각·보류를 결정하는 심의 기구
13. 변경 관리 절차: 요청→영향분석→승인(CCB)→명세서 업데이트→추적성 업데이트
14. 기준선(Baseline): 공식 승인된 요구 사항의 확정 버전, 이후 설계의 참조 기준
15. RTM(요구 사항 추적성 매트릭스): 요구 ↔ 설계 ↔ 구현 ↔ 테스트 연결 추적
16. 최종 확인: 검토 회의→이해관계자 검토→합의→승인→기준선 설정
17. 보완 활동: 누락 추가·불명확 수정·충돌 조정·우선순위 재조정
