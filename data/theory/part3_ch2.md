# 3과목 2장: 데이터 표준 수립

## 0. 데이터 표준화 정책 문서화 6요소

정책은 표준화 활동의 방향을 제시하고 이해관계자의 참여·준수를 이끌어내는 최상위 지침이다.

| # | 요소 | 설명 |
|---|------|------|
| ① | 목적 및 목표 | 달성할 비즈니스 목표를 수치로 명시 |
| ② | 적용 범위 | 대상 시스템·데이터·조직 정의 |
| ③ | 데이터 표준의 정의 | 관리할 표준의 종류 명시 — 단어·용어·도메인·코드 |
| ④ | 표준화 원칙 | 유일성·업무적 보편성·의미 전달의 충분성 + 명명/정의/형식 규칙 |
| ⑤ | 조직 및 R&R | 데이터 관리자·데이터 스튜어드, 협의체 구성과 책임 정의 |
| ⑥ | 프로세스 | 신청 → 심의 → 확정 → 변경 → 폐기의 전체 관리 프로세스 |

## 1. 데이터 명칭 표준

데이터 명칭 표준은 조직 내 데이터 항목의 이름을 일관되게 부여하기 위한 규칙 체계이다.

> **핵심**: 데이터 명칭 표준은 표준 단어 → 표준 용어 → 표준 도메인 → 표준 코드의 **4단계 계층 구조**로 구성되며(part3_ch1.md와 동일한 4단계), 이를 조합하여 일관된 데이터 항목명·형식·규칙을 생성한다.

### 데이터 표준 3대 핵심 원칙

| # | 원칙 | 설명 |
|---|------|------|
| ① | 유일성(Uniqueness) | 하나의 개념에는 하나의 표준 명칭만 존재 |
| ② | 업무적 보편성 | 현업 사용자가 직관적으로 이해할 수 있는 용어 채택 |
| ③ | 의미 전달의 충분성 | 명칭만으로 의미·범위가 파악되도록 구체화 |

| 원칙 | 위반 사례 | 적용 결과 |
|---|---|---|
| 유일성 | 고객 계좌번호 / 고객 구좌번호 혼용 | '고객 계좌번호' 단일 표준, 나머지는 금칙어 등록 |
| 의미 전달의 충분성 | '금액' — 세전/세후 불명확 | '주문세후할인후금액'으로 구체화 |

### 단어 표준(Word Standard)

- **정의**: 데이터 항목명에 사용되는 개별 단어(최소 의미 단위)의 표준
- **구성**: 한글명, 영문명, 약어, 설명
- **목적**: 임의 약어 사용 방지, 일관된 영문명 부여

| 단어(한글) | 영문명 | 표준 약어 | 설명 |
|---------|------|--------|-----|
| 고객 | CUSTOMER | CUST | 상품·서비스를 구매하는 주체 |
| 번호 | NUMBER | NO | 식별을 위한 고유 번호 |
| 금액 | AMOUNT | AMT | 화폐 단위의 수치 |
| 날짜 | DATE | DT | 특정 일자 |
| 이름 | NAME | NM | 사람·사물의 호칭 |
| 코드 | CODE | CD | 표준화된 분류 값 |

**표준 단어 정의 프로세스 4단계**

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 현행 용어 수집 | 데이터 모델·테이블 정의서에서 한글명·영문명 전수 수집 |
| 2 | 단어 분할 | 최소 의미 단위로 분할(고객주문일자 → 고객·주문·일자) |
| 3 | 정제 및 표준화 | 이음동의어 통합, 동음이의어 분리, 영문 전체명·약어 표준화 |
| 4 | 사전 등록 | 한글명·영문명·약어 등록, 공식 표준 단어 사전 확정 |

**이음동의어 통합 vs 동음이의어 분리 (Worked Example)**

- 이음동의어 통합: '고객'과 '손님' → 빈도·보편성 기준으로 '고객' 선정, '손님'은 금칙어로 등록
- 동음이의어 분리: '주소'가 거주지와 IP를 함께 가리키면 → '거주지주소', 'IP주소'로 분리해 별도 표준어로 정의

### 용어 표준(Term Standard)

- **정의**: 비즈니스에서 사용하는 용어(단어의 조합)를 표준화한 것
- **구성**: 용어명(한글), 영문명, 용어 설명, 관련 용어
- **단어 표준과의 차이**: 단어 표준이 개별 단어라면, 용어 표준은 비즈니스 의미를 가진 합성 용어

| 용어(한글) | 영문명 | 도메인 | 설명 |
|---------|------|------|-----|
| 고객번호 | CUSTOMER_NO | 일반번호 | 고객 식별 고유번호 |
| 주문금액 | ORDER_AMOUNT | 금액 | 주문의 총 금액 |
| 가입일자 | JOIN_DATE | 일반날짜 | 서비스 가입 날짜 |
| 상품코드 | PRODUCT_CODE | 일반코드 | 상품 식별 코드 |

**표준 용어 정의 프로세스 4단계**

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 개념 명확화 | 담당자(재무·영업·물류 등) 인터뷰로 암묵적 비즈니스 규칙 확인 |
| 2 | 비즈니스 규칙 합의 | 조건·범위(포함/제외 항목)를 전사 합의로 확정 |
| 3 | 표준 용어 생성 | 후보 명칭 검토 후 최종 표준 용어 확정 |
| 4 | 단어 조합 및 등록 | 표준 단어를 조합해 영문명 생성, 정의서 작성 후 사전 등록 |

**Worked Example — '주문금액' → '주문총금액'**: "주문금액이 부가세·배송비·할인을 포함하는가?"를 둘러싼 이견을 조정한 결과, "모든 할인 적용 후 부가세·배송비를 포함한 최종 결제 금액"으로 합의하고 '주문총금액'(ORD_TOT_AMT)으로 표준 용어를 확정. → 표준 정의는 이름표를 붙이는 일이 아니라 암묵적 비즈니스 규칙을 발굴해 공식화하는 분석 활동이다.

### 도메인 표준(Domain Standard)

- **정의**: 데이터 항목이 가질 수 있는 값의 범위·형식·유형을 정의한 표준
- **목적**: 동일한 성격의 데이터에 동일한 물리적 형식 적용

| 도메인명 | 데이터유형 | 길이/정밀도 | 설명 |
|--------|---------|-----------|-----|
| 일반번호 | VARCHAR | 20 | 일반적인 번호 유형 |
| 금액 | DECIMAL | 15,2 | 화폐 금액 |
| 일반날짜 | DATE | - | 표준 날짜 (YYYY-MM-DD) |
| 일반코드 | VARCHAR | 10 | 분류 코드 |
| 이메일주소 | VARCHAR | 100 | 이메일 형식 |
| 전화번호 | VARCHAR | 20 | 전화번호 형식 |
| 사용여부 | CHAR | 1 | Y/N 이진 값 |
| 장문텍스트 | VARCHAR | 4000 | 설명·비고 텍스트 |

**표준 도메인 정의 프로세스 4단계**

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 현행 컬럼 분석 | 타입·길이·제약 조건 수집 |
| 2 | 도메인 그룹화 | 비즈니스 의미·성격별로 분류(고객명·직원명·상품명 → '명칭') |
| 3 | 표준 도메인 정의 | 대표 타입·길이 확정, 확장성 고려해 여유 설정 |
| 4 | 도메인 사전 등록 | 이름·타입·길이·허용값·형식 규칙 등록 |

**표준 도메인의 추상화(abstraction) 가치**: 원화 금액 컬럼 500개의 소수점 자릿수를 2자리→4자리로 바꿔야 할 때, 도메인이 없으면 500개 컬럼을 일일이 수정해야 하지만(며칠 소요), 도메인이 있으면 중앙 도메인 사전의 '금액_KRW' 정의 하나만 수정하면 상속받는 500개 컬럼 전체에 자동·일관 전파된다(몇 분 소요). 표준 도메인의 진짜 가치는 타입 통일이 아니라 데이터 아키텍처에 추상화 계층을 제공하는 것이다.

> **핵심**: 표준 단어(원자 단위) → 표준 용어(비즈니스 합성 단위) → 표준 도메인(물리적 형식) → 표준 코드(허용값)의 **4계층**이 데이터 명칭 표준의 핵심이다(part3_ch1.md와 동일한 4단계).

## 2. 데이터 형식 표준

### 데이터 유형 표준

각 데이터 유형별로 사용 기준을 표준화:

| 데이터 유형 | 사용 기준 | 예시 |
|---------|--------|-----|
| VARCHAR | 가변 길이 문자열 | 이름, 주소, 설명 |
| CHAR | 고정 길이 코드값 | 성별코드(M/F), 사용여부(Y/N) |
| INTEGER | 정수 | 수량, 순번 |
| DECIMAL(p,s) | 소수점 있는 수치 | 금액, 비율 |
| DATE | 날짜 (시간 없음) | 가입일, 생년월일 |
| TIMESTAMP | 날짜+시간 | 거래일시, 수정일시 |
| CLOB | 대용량 텍스트 | 상품 상세 설명 |
| BLOB | 대용량 바이너리 | 첨부 파일 |

### 날짜·시간 형식 표준

```
날짜: YYYY-MM-DD (예: 2025-01-15)
시간: HH:MM:SS (예: 14:30:00)
날짜+시간: YYYY-MM-DD HH:MM:SS (예: 2025-01-15 14:30:00)
연도: YYYY (예: 2025)
연월: YYYY-MM (예: 2025-01)
```

### 수치 형식 표준

```
금액: 소수점 2자리, 천 단위 구분자 없음 (예: 1500000.00)
비율: 소수점 2자리, 백분율 (예: 15.75)
좌표: 소수점 6자리 (예: 37.566535)
```

## 3. 코드 표준

### 코드 정의(Code Definition)

코드(Code)는 특정 도메인의 값을 약속된 기호·숫자로 표현한 것으로, 데이터의 표준화와 효율화를 위해 사용된다.

#### 코드의 특성

| 특성 | 설명 |
|-----|------|
| 유일성 | 하나의 코드값은 하나의 의미만 가짐 |
| 포괄성 | 해당 도메인의 모든 가능한 값을 포함 |
| 안정성 | 코드값이 자주 변경되지 않음 |
| 간결성 | 코드값은 최대한 간결하게 |

### 코드 설계(Code Design)

#### 코드 체계 유형

| 코드 유형 | 설명 | 예시 |
|--------|-----|------|
| 순번 코드 | 단순 일련번호 | 001, 002, 003... |
| 약자 코드 | 의미 있는 약자 | M(남성), F(여성) |
| 분류 코드 | 계층적 분류 체계 | 1=식품, 11=과일, 111=열대과일 |
| 블록 코드 | 그룹별 번호 범위 | 100-199: 한국, 200-299: 미국 |
| 복합 코드 | 여러 코드의 조합 | 지역코드 + 구분코드 |

#### 코드 설계 원칙

1. 확장성: 새로운 코드값 추가를 고려한 여유 공간
2. 유추 가능성: 코드값에서 의미를 일부 유추 가능하면 좋음
3. 비어있는 범위: 미래 추가를 위한 예약 범위 설정

**표준 코드 정의 프로세스 4단계**

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 코드성 데이터 수집 | 성별·직급·주문상태 등, 하드코딩된 값까지 발굴 |
| 2 | 통합 및 표준화 | 표현 방식 통일('1','M','남'→'M'), 행정표준코드·ISO 코드 재사용 |
| 3 | 코드 오너십 정의 | 직급코드 오너=인사팀, 상품분류코드 오너=상품기획팀 등 지정 — 현행성 유지의 핵심 |
| 4 | 코드 사전 등록 | 분류명·코드값·코드명·설명·데이터 오너 등록 |

### 코드 관리(Code Management)

```
코드 관리 절차:

1. 코드 등록 요청 (업무 담당자)
   ↓
2. 코드 검토 (데이터 스튜어드)
   - 기존 코드와 중복 여부 확인
   - 코드 설계 기준 적합성 검토
   ↓
3. 코드 승인 (데이터 관리자)
   ↓
4. 코드 사전 등록 (데이터 표준팀)
   ↓
5. 시스템 적용 (개발팀)
   ↓
6. 코드 변경/폐기 관리
   - 변경: 이력 관리, 영향 분석 필수
   - 폐기: 사용 여부 코드(Y/N)로 관리, 물리 삭제 지양
```

## 4. 메타데이터 표준

### 메타데이터의 정의

메타데이터(Metadata)란 "데이터에 대한 데이터"로, 데이터를 설명하고 관리하기 위한 구조화된 정보이다.

> **핵심**: 메타데이터는 기술적 메타데이터(물리적 구조), 관리적 메타데이터(관리 정보), 구조적 메타데이터(논리적 구조)의 3가지 유형으로 분류된다.

### 메타데이터 유형

#### 기술적 메타데이터(Technical Metadata)

- **정의**: 데이터의 물리적 저장 구조와 기술적 속성 정보
- **예시**:
  - 테이블명, 컬럼명, 데이터 유형, 길이
  - 인덱스, 파티션 정보
  - 저장 위치 (데이터베이스, 테이블스페이스)
  - 데이터 볼륨 (행 수, 크기)

#### 관리적 메타데이터(Administrative Metadata)

- **정의**: 데이터 자산의 관리와 거버넌스에 필요한 정보
- **예시**:
  - 데이터 오너 (부서, 담당자)
  - 생성일, 최종 수정일
  - 접근 권한 (보안 등급)
  - 보관 기간 및 폐기 규칙
  - 출처 (Source System)

#### 구조적 메타데이터(Structural Metadata)

- **정의**: 데이터 개체 간의 논리적 구조와 관계 정보
- **예시**:
  - 엔터티-관계 정보 (ERD)
  - 참조 무결성 관계 (PK-FK)
  - 비즈니스 규칙과 제약 조건
  - 데이터 계보(Data Lineage)

| 메타데이터 유형 | 핵심 내용 | 주요 사용자 |
|------------|---------|-----------|
| 기술적 | 물리적 구조, DB 정보 | DBA, 개발자 |
| 관리적 | 소유권, 보안, 이력 | 데이터 관리자, 감사 |
| 구조적 | 논리 구조, 관계, 계보 | 데이터 아키텍트, 분석가 |

### 메타데이터 관리 시스템(MDR: Metadata Registry)

- **기능**: 메타데이터 등록, 검색, 버전 관리
- **ISO 11179**: 메타데이터 레지스트리 국제 표준
- **구성 요소**: 데이터 요소 개념, 데이터 요소, 값 도메인, 표현 클래스

## 5. 데이터 표준화 산출물

### 주요 산출물 목록

| 산출물 | 내용 | 형식 |
|------|-----|------|
| 데이터 표준화 지침서 | 표준화 원칙, 명명 규칙 전반 | 문서 |
| 단어 사전 | 표준 단어 목록 (한글명, 영문명, 약어) | 엑셀/DB |
| 용어 사전 | 표준 용어 목록 (비즈니스 의미 포함) | 엑셀/DB |
| 도메인 사전 | 도메인 목록 (유형, 형식, 규칙) | 엑셀/DB |
| 코드 사전 | 코드 목록 및 코드값 정의 | 엑셀/DB |
| 데이터 사전 | 전체 데이터 항목 메타데이터 | DB |
| 표준 ERD | 개념/논리 데이터 모델 표준 | 다이어그램 |

### 데이터 표준화 산출물 간의 관계

```
단어 사전 ──→ (단어 조합) ──→ 용어 사전
                                   │
                          도메인 사전 ←─ 연결 ─→ 용어 사전
                                   │
                            데이터 사전 (용어 + 도메인 조합)
                                   │
                             코드 사전 ←─ 참조 ─→ 데이터 사전
```

## 6. 데이터 표준 정의 심화 (고려사항)

### 표준 단어 고려사항

1. 일반적인 업무용 단어 선정 (누구나 동일하게 이해)
2. 동의어 중 대표 단어 하나만 선정
3. 접두어·접미어 같은 한 자리 단어 배제
4. 높은 빈도로 조합되는 단어는 하나의 표준 단어로 정의 가능
5. 발음식 단어 지양 (영문명 작성 기준)
6. 한글명당 하나의 영문명만 허용 (동음이의어 불가)
7. 영문명당 복수의 한글명 허용 가능 (이음동의어)

### 표준 코드 고려사항

1. 표준기구·정부에서 정의한 표준 코드 우선 사용
2. 텍스트 직접 입력 최소화 (코드 체계로 대체)
3. 엄격한 기준으로 관리 (사용자 임의 수정 금지)
4. 코드 값 변경 시 기존 코드는 사용 중지 처리
5. **표준 코드 - 현행 코드 변환 매핑 정보** 반드시 기록
6. 코드 통합 대상 파악 및 단일화 작업 수행

### 담당자별 표준 관리 업무 역할

| 담당자 | 담당 업무 |
|--------|---------|
| 데이터 관리자(DA) | 표준 단어·용어·도메인·코드 신규 생성 및 변경 요청, **신규·변경 사항 검토, 표준 준수 체크, 영향도 분석, 메타 DB 등록** |
| 전사 데이터 관리자 | 변경 사항 영향도 파악, 평가서 작성, 테스트 및 검증 |
| 데이터베이스 관리자(DBA) | 물리 DB 구현·성능 튜닝·백업·복구·보안 등 기술적·운영적 역할 (표준 검토·영향도 분석은 DA 업무이며 DBA 업무가 아님에 유의) |
| 자문 역할 | 전사 관점에서의 표준 가이드 제시 |

> **정정 포인트**: "신규·변경 사항 검토, 표준 준수 체크, 영향도 분석, 메타 DB 등록"은 데이터베이스 관리자(DBA)가 아니라 **데이터 관리자(DA)**의 업무이다. DBA는 물리적·기술적 구현과 운영(성능·백업·보안)을 담당한다.

## 6a. 표준 검토·승인과 공표·전파

### 표준 검토·승인 5단계

| # | 단계 | 설명 |
|---|------|------|
| 1 | 검토 계획 수립 | 검토 대상 범위와 기준 정의, 이해관계자 선정 |
| 2 | 검토 자료 준비 및 배포 | 표준안과 체크리스트를 사전 배포해 숙지 |
| 3 | 검토 회의 진행 | 각 안이 기준을 충족하는지 검증, 이견은 별도 이슈 목록 관리 |
| 4 | 검토 결과 정리 및 보완 | 검토 결과서 작성, 보완 목록 반영(단어·도메인·코드 변경의 파급 효과 기록) |
| 5 | 최종 승인 | 재검토 또는 서면 합의, 거버넌스 협의체(또는 CDO)의 공식 승인 |

**검토 체크리스트 6항목**: 유일성 · 범용성 · 명확성 · 정의의 완전성 · 타당성 · 오너 지정 여부

### 공식 공표 및 전파 전략 4가지

| # | 전략 | 설명 |
|---|------|------|
| ① | 중앙 저장소 등록·공개 | 확정 표준을 메타데이터 시스템에 등록 — 단일 진실 공급원(SSoT), 웹 포털로 검색·조회 |
| ② | 공식 커뮤니케이션 | 전사 공지·이메일·게시판, 변경 요약+배경+시스템 링크 포함 |
| ③ | 사용자 교육 및 훈련 | 모델러·개발자·분석가·현업 대상 정기 교육 |
| ④ | 개발 환경으로의 통합 | 모델링 도구 플러그인, IDE에서 표준 컬럼 조회 지원 |

## 7. 출제 포인트

1. **명칭 표준 4계층**: 표준 단어(원자) → 표준 용어(합성) → 표준 도메인(형식) → 표준 코드(허용값) (part3_ch1.md와 동일)
2. **도메인 표준**: 동일 성격 데이터에 동일 물리 형식 적용, 예) 금액 도메인: DECIMAL(15,2). 추상화 가치: 도메인 정의 1곳 수정으로 상속받는 전 컬럼에 일괄 전파
3. **메타데이터 3가지 유형**: 기술적(물리구조), 관리적(소유권·보안), 구조적(논리구조·관계)
4. **코드 체계 유형**: 순번, 약자, 분류, 블록, 복합 코드
5. **코드 폐기 원칙**: 물리 삭제 대신 사용여부 코드(Y/N)로 관리
6. **ISO 11179**: 메타데이터 레지스트리 국제 표준
7. **단어 사전 구성**: 한글명, 영문명, 약어, 설명의 4요소
8. **CHAR vs VARCHAR**: CHAR는 고정 길이 코드값, VARCHAR는 가변 길이 문자열
9. **데이터 계보(Data Lineage)**: 구조적 메타데이터의 일종, 데이터 흐름·변환 이력
10. **표준화 산출물 체계**: 지침서 → 단어/용어/도메인/코드 사전 → 데이터 사전 → 표준 ERD
11. **정책 문서화 6요소**: 목적및목표·적용범위·데이터표준의정의·표준화원칙·조직및R&R·프로세스
12. **표준 단어/용어/도메인/코드 정의 프로세스**: 각 4단계 — 수집(분석)→분할(그룹화/합의)→정제(정의/생성)→등록
13. **이음동의어 통합**('고객'/'손님'→'고객') **vs 동음이의어 분리**('주소'→거주지주소/IP주소)
14. **DA vs DBA 역할 정정**: 표준 신규·변경 검토, 준수 체크, 영향도 분석, 메타 DB 등록은 **DA** 업무 — DBA는 물리 DB·성능·백업·보안 담당(단골 오답 포인트)
15. **검토·승인 5단계**: 계획수립→자료준비배포→회의진행→결과정리보완→최종승인, 체크리스트 6항목(유일성·범용성·명확성·정의완전성·타당성·오너지정여부)
16. **공표·전파 4전략**: 중앙저장소등록공개·공식커뮤니케이션·사용자교육훈련·개발환경통합
