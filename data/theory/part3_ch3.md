# 3과목 3장: 데이터 표준 관리

## 1. 데이터 표준 관리 체계

데이터 표준 관리 체계란 수립된 데이터 표준이 지속적으로 유지·발전될 수 있도록 하는 조직, 프로세스, 도구의 종합 체계이다.

> **핵심**: 데이터 표준은 한 번 수립하면 끝나는 것이 아니라, 비즈니스 변화에 맞게 지속적으로 관리·진화해야 한다.

### 데이터 표준 관리의 주요 영역

| 관리 영역 | 내용 |
|--------|-----|
| 표준 유지 관리 | 표준 사전의 지속적 갱신 |
| 표준 준수 관리 | 시스템이 표준을 준수하는지 모니터링 |
| 표준 변경 관리 | 표준 변경 절차 및 영향 관리 |
| 표준 배포 관리 | 표준 공표·교육·공유 |

### 데이터 표준 관리 시스템(메타데이터 관리 시스템)

- **목적**: 데이터 표준 사전을 시스템으로 관리하여 접근성·일관성 향상
- **주요 기능**:
  1. 표준 사전 등록·조회·수정
  2. 버전 관리 및 변경 이력
  3. 표준 준수 자동 검사
  4. 이해관계자 접근 통제

## 2. 데이터 품질 관리

### 데이터 품질의 개념

데이터 품질(Data Quality)은 데이터가 정의된 요건을 충족하는 정도로, 데이터 관리의 핵심 성과 영역이다.

### 데이터 품질 측정 항목

#### 완전성(Completeness)

- **정의**: 필수 데이터 항목이 빠짐없이 존재하는 정도
- **측정 공식**: 완전성 = (값이 있는 건수 / 전체 건수) × 100
- **예시**: 고객 테이블에서 이메일 항목의 채움률

#### 정확성(Accuracy)

- **정의**: 데이터 값이 실제 세계의 참 값과 일치하는 정도
- **측정 방법**: 표준 원천과 대조, 현장 확인
- **예시**: 고객 주소가 실제 주소와 일치하는 비율

#### 일관성(Consistency)

- **정의**: 동일한 데이터가 여러 시스템에서 동일한 값을 가지는 정도
- **측정 방법**: 시스템 간 데이터 비교
- **예시**: ERP와 CRM 시스템의 고객 정보 일치율

#### 유효성(Validity)

- **정의**: 데이터 값이 정의된 도메인·형식·규칙을 준수하는 정도
- **측정 방법**: 도메인 규칙 위반 건수 집계
- **예시**: 날짜 형식 위반, 코드값 범위 이탈

#### 유일성(Uniqueness)

- **정의**: 데이터 개체가 중복 없이 단 한 번만 존재하는 정도
- **측정 방법**: 기본키 중복 검사, 비즈니스 키 중복 검사
- **예시**: 동일 고객이 두 개 이상의 레코드로 존재하는 비율

#### 적시성(Timeliness)

- **정의**: 데이터가 필요한 시점에 최신 상태를 반영하는 정도
- **측정 방법**: 데이터 지연 시간 측정
- **예시**: 주문 상태 변경 후 화면 반영까지 소요 시간

```
데이터 품질 지표 산출 예시:

완전성:  (1000 - 50) / 1000 × 100 = 95%
정확성:  (1000 - 8) / 1000 × 100 = 99.2%
일관성:  (500 - 12) / 500 × 100 = 97.6%
유효성:  (1000 - 30) / 1000 × 100 = 97%
유일성:  (1000 - 5) / 1000 × 100 = 99.5%
```

### 데이터 품질 관리 프레임워크

```
계획(Plan)
  - 품질 목표 설정
  - 측정 항목 정의
  - 측정 주기 결정
    ↓
측정(Do)
  - 데이터 프로파일링
  - 품질 지표 산출
  - 문제 데이터 식별
    ↓
분석(Check)
  - 품질 목표와 비교
  - 근본 원인 분석
  - 개선 우선순위 결정
    ↓
개선(Act)
  - 데이터 정제(Data Cleansing)
  - 프로세스 개선
  - 입력 통제 강화
```

## 3. 데이터 표준 준수 관리

### 준수 관리의 개념

데이터 표준 준수 관리는 시스템 개발 및 운영 단계에서 데이터 표준이 실제로 적용되는지를 검토하고 위반 사항을 개선하는 활동이다.

### 준수 검사 시점

| 검사 시점 | 내용 |
|--------|-----|
| 설계 단계 | ERD, 테이블 명세서의 표준 준수 검토 |
| 개발 단계 | 개발된 DB 스키마와 표준 자동 비교 |
| 운영 단계 | 주기적 표준 준수율 측정 및 보고 |

### 준수 감사 5단계

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 점검 대상 선정 | 대상 스키마·모델 범위 확정 |
| 2 | 자동 스캔 | 메타데이터 시스템으로 테이블명·컬럼명·타입·길이 자동 추출 |
| 3 | 표준과 비교 | 중앙 저장소 표준과 대조해 불일치 항목 자동 식별 |
| 4 | 보고서 생성 | 전체 준수율 산출, 미준수 유형별 통계·상세 목록 |
| 5 | 개선·추적 | 담당자와 개선 계획 수립, 신규 등록 또는 시스템 수정 |

### 미준수(위반) 3대 유형 (교재 기준 — 부정형 프레이밍)

- **미등록 용어 사용**: 표준 용어 사전에 없는 용어를 테이블명·컬럼명으로 사용
- **도메인 불일치**: 컬럼의 데이터 유형·길이가 표준 도메인과 상이
- **명명 규칙 위반**: 표준 영문 약어 미사용, 단어 조합 규칙 위반

(참고 — 무결성 준수: 필수 항목에 NOT NULL·FK 제약이 설정되어 있는가는 별도 참고 점검 항목으로 활용 가능)

### 표준 준수율 측정

```
표준 준수율 = (표준 준수 항목 수 / 전체 항목 수) × 100

예시:
- 전체 컬럼 수: 500개
- 표준 준수 컬럼 수: 470개
- 표준 준수율: 470 / 500 × 100 = 94%
```

## 4. 데이터 표준 변경 관리

### 변경 관리의 필요성

데이터 표준은 비즈니스 환경 변화, 법규 개정, 새로운 서비스 출시 등으로 변경이 발생한다. 변경 관리가 미흡하면 시스템 오류, 데이터 불일치가 발생할 수 있다.

### 변경 관리 프로세스 (교재 기준 4단계)

```
1. 요청
   - 변경 요청자: 업무 담당자, 개발자, DA
   - 요청 내용: 변경 이유, 변경 내용, 긴급도
     ↓
2. 영향도 분석
   - 접수 즉시 파급 효과 분석을 의무적으로 수행
   - 변경 시 영향받는 시스템·테이블·프로그램 목록 작성
     ↓
3. 심의·승인
   - 데이터 스튜어드 검토, 관련 부서 협의
   - 거버넌스 협의체 심의 — 타당성·시급성·소요 비용 종합 검토(신규 등록보다 엄격)
     ↓
4. 변경 실행·공표
   - 표준 사전 갱신, 시스템 변경 계획 수립·작업 완료
   - 관련 이해관계자에게 공식 공표, 변경 이력 기록
```

### 표준 폐기 프로세스 (별도 3단계)

```
1. 요청 및 분석
   - 단종 상품 코드 등 미사용 표준의 폐기 요청 접수
   - 데이터·프로그램·보고서에서 참조 여부를 시스템적으로 검증
     ↓
2. 심의 및 승인
   - 어떤 자산에도 영향이 없음이 확인되면 공식 승인
     ↓
3. 폐기 처리
   - '사용 중지' 또는 '폐기' 상태로 변경 (물리 삭제 대신 이력 보존)
```

### 변경 유형별 관리

| 변경 유형 | 예시 | 관리 포인트 |
|--------|-----|----------|
| 용어 추가 | 새 비즈니스 용어 등록 | 중복 여부 검토 |
| 용어 수정 | 의미 변경, 영문명 변경 | 기존 사용처 영향 분석 |
| 용어 폐기 | 더 이상 사용하지 않는 용어 | 물리 삭제 대신 폐기 이력 관리 |
| 코드 추가 | 새 코드값 등록 | 기존 범위와 충돌 여부 |
| 도메인 변경 | 데이터 유형·길이 변경 | DB 스키마 변경 영향 분석 |

## 5. 데이터 거버넌스

### 데이터 거버넌스의 정의

데이터 거버넌스(Data Governance)란 조직 전체의 데이터 자산에 대한 의사결정 권한, 책임, 프로세스를 정의하고 실행하는 체계이다.

> **핵심**: 데이터 거버넌스는 "누가 데이터에 대해 책임을 지고, 어떤 규칙으로 데이터를 관리하는가"를 정의하는 종합 체계이다.

### 거버넌스 조직의 4대 역할 (교재 기준)

효과적인 표준 관리는 '누가(조직)'와 '무엇을(프로세스)' 책임지고 수행할지 명확히 정의하는 데서 시작된다. (참고: 일부 조직에서는 "데이터 오너 → 데이터 스튜어드 → 데이터 쿠스토디언 → DBA"라는 유사한 4단계 오너십 체계를 쓰기도 하나, 본 교재의 핵심 프레임워크는 아래 4대 역할이다.)

| # | 역할 | 설명 |
|---|------|------|
| ① | 데이터 거버넌스 협의체 | 최고데이터책임자(CDO)와 주요 비즈니스·IT 리더로 구성된 최상위 의사결정 기구 — 표준화 정책 최종 승인, 부서 간 분쟁 조정 |
| ② | 전사 데이터 관리자(DA) | 표준 관리 실무 총괄 — 원칙·절차 수립, 신규/변경 표준안 검토, 관리 시스템 운영 |
| ③ | 데이터 스튜어드 | 특정 데이터 영역(고객·상품·재무 등)을 위임받은 현업 전문가 — 표준 용어·비즈니스 규칙 정의, '데이터 콘텐츠'의 전문가 |
| ④ | 데이터베이스 관리자(DBA) | 물리적 저장을 책임지는 기술 전문가 — DA가 정의한 논리 표준을 물리 객체로 구현, 성능·백업·보안 운영 |

**한 문장 정리**: 협의체는 '결정'하고, DA는 '조정'하며, 스튜어드는 '정의'하고, DBA는 '구현'한다.

### 역할과 책임 매트릭스 (RACI)

R(실무 책임자)·A(최종 책임자)·C(협의 대상)·I(통보 대상)로 업무 중복과 책임 공백을 막는 도구. **핵심 원칙: A(최종 책임)는 반드시 한 역할에만 부여**된다.

| 주요 활동 | 거버넌스 협의체 | 전사 DA | 데이터 스튜어드 | DBA | 현업 사용자 |
|---|---|---|---|---|---|
| 전사 데이터 표준 정책 승인 | A | R | C | I | I |
| 신규 비즈니스 용어 정의 | I | C | A, R | I | C |
| 표준 도메인(논리적 형식) 정의 | I | A, R | C | C | I |
| 데이터베이스 물리적 성능 튜닝 | I | C | I | A, R | I |
| 표준 변경 요청에 대한 영향도 분석 | I | A, R | C | C | C |
| 표준 관련 부서 간 분쟁 조정 | A | R | I | I | I |

> 표준 도메인 정의의 A는 DA, 물리적 성능 튜닝의 A는 DBA — 특정 활동의 A/R 주체를 묻는 문제가 자주 출제된다.

### 표준 신규 등록 프로세스 5단계

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 요청 | 현업·개발자가 신규 개념 필요 시 등록 요청서 제출 |
| 2 | 검토 | DA가 기존 표준과의 중복 여부·표준화 필요성 1차 검토 |
| 3 | 정의 | 담당 데이터 스튜어드가 비즈니스 관점의 명확한 정의 작성 |
| 4 | 심의·승인 | DA가 전사 원칙에 맞게 완성해 거버넌스 협의체에 공식 심의·승인 요청 |
| 5 | 공표 | 표준 관리 시스템에 등록, 관련자에게 공식 공표 |

> **핵심**: DA가 정의를 직접 쓰지 않는다 — 의미의 주인은 현업(데이터 스튜어드)이기 때문이다.

### 데이터 오너십(Data Ownership) — 참고 개념

일부 조직에서는 데이터 자산에 대한 책임을 아래와 같이 세분화하기도 한다(교재의 4대 역할 체계와 병행 참고).

| 역할 | 수준 | 주요 책임 |
|-----|-----|---------|
| 데이터 오너 | 비즈니스 (임원) | 데이터 정책 결정, 최종 책임 |
| 데이터 스튜어드 | 비즈니스 (실무자) | 일상적 품질·표준 관리 |
| 데이터 쿠스토디언(일부 조직에서 사용하는 유사 개념) | IT (DBA/개발자) | 물리적 저장·보안·백업 |

### 데이터 거버넌스 프레임워크

```
비전 및 전략
  └→ 데이터 원칙 정의
       └→ 데이터 정책 수립
            └→ 표준 및 절차 정의
                 └→ 실행 및 모니터링
```

### 데이터 거버넌스 핵심 구성 요소

| 구성 요소 | 설명 |
|--------|-----|
| 조직(People) | 거버넌스 협의체, DA, 데이터 스튜어드, DBA |
| 프로세스(Process) | 표준 관리, 품질 관리, 변경 관리 절차 |
| 기술(Technology) | 메타데이터 관리 시스템, 품질 측정 도구 |
| 정책(Policy) | 데이터 사용 정책, 보안 정책, 보관 정책 |

## 6. 변경 영향도 분석과 사례 연구

### 변경 영향도 분석 3단계

| # | 단계 | 설명 |
|---|------|------|
| ① | 영향 대상 식별(Identification) | 메타데이터 시스템의 'Where-Used' 질의로 해당 표준을 사용하는 모든 데이터 자산 목록화 |
| ② | 영향 내용 분석(Analysis) | 기술적 영향(비정상 종료·ETL 실패·데이터 잘림?)과 비즈니스적 영향(보고서 오류·법규 문제?) 분석 |
| ③ | 대응 계획 수립(Planning) | 수정 대상 프로그램·담당자·일정, 테스트 방안·배포 순서 수립 |

**영향 대상 자산 6종**: 데이터 모델(논리·물리) / 데이터베이스 객체(테이블·컬럼·뷰·프로시저) / ETL 스크립트 및 변환 로직 / 애플리케이션 소스 코드 / 보고서 및 BI 대시보드 / 데이터 인터페이스 전문

### 사례 연구 — '상품코드' 길이 변경

CHAR(10) → VARCHAR2(12) 변경 하나가 165개 자산(DB 25개 테이블, 애플리케이션 80개 화면, ETL 15개 작업, 보고서·BI 45개)에 영향을 미친 사례 — 데이터베이스 25개 테이블은 데이터 잘림 위험은 없으나 성능 변화 가능성, 애플리케이션 80개 화면은 12자리 입력 불가 위험, ETL 15개 작업은 타겟 컬럼이 여전히 10자면 적재 실패, 보고서·BI 45개는 UI 깨짐 위험. → 사소해 보이는 변경 하나가 연쇄 반응을 일으킬 수 있으므로 변경 영향도 분석은 표준 관리에서 가장 중요한 활동이다.

## 7. 데이터 표준 관리 시스템과 성숙도 모델

### 데이터 표준 관리 시스템 5대 핵심 기능

| # | 기능 | 설명 |
|---|------|------|
| ① | 중앙 리포지토리 | 단어·용어·도메인·코드의 단일 저장소(SSoT) |
| ② | 워크플로우 엔진 | 등록·변경·폐기의 신청·검토·승인 자동화 |
| ③ | 모델링 도구 통합 | ERwin·ER-Studio 연동 — 모델링 중 실시간 표준 조회·적용 |
| ④ | 변경 영향도 분석 엔진 | 자산 간 연관 관계(Lineage) 자동 분석, 영향 객체 목록 제공 |
| ⑤ | 준수율 점검 및 리포팅 | 물리 스키마 주기적 추출·비교, 준수율 현황 대시보드 시각화 |

### 데이터 표준화 성숙도 모델 5단계

| 단계 | 상태 | 특징 |
|---|---|---|
| 1단계 초기(Initial) | 공식 표준 전혀 없음, 명칭은 개발자 임의 부여 | 중복·불일치 만연, 구두 확인 의존 |
| 2단계 관리(Managed) | 부서·프로젝트별 비공식 표준(엑셀 용어집) 존재 | 일부 영역만 일관, 수동·비정기 관리 |
| 3단계 정의(Defined) | 전사 표준 공식 정의·문서화, 조직(DA·스튜어드)·프로세스·중앙 시스템 도입 | 신규 개발 시 표준 준수 의무화 |
| 4단계 정량적 관리 | 준수율 정기 측정·KPI화, 변경 영향도 분석 의무 수행 | 준수 여부가 객관적 데이터로 관리 |
| 5단계 최적화 | 정량 분석 결과가 프로세스 개선에 지속 피드백 | 거버넌스가 조직 문화로 정착 |

**자가진단 체크리스트 (6문항)**
1. 표준의 최종 승인권자가 문서로 지정되어 있는가?
2. DA와 DBA의 책임이 RACI로 정의되어 있는가?
3. 긴급 상황에서도 공식 변경 관리 프로세스를 우회하지 않는가?
4. 준수율을 정기 측정하고 KPI로 관리하는가?
5. 변경 영향도 분석이 의무로 규정되어 있는가?
6. 메타데이터 시스템으로 데이터 계보를 자동 추적할 수 있는가?

→ 4개 이상 'Yes'면 4단계(정량적 관리) 수준.

### 메타데이터 드리프트(Metadata Drift)

긴급 변경이라는 이유로 공식 변경 관리 프로세스를 우회해 컬럼을 즉시 수정하면, 중앙 표준 관리 시스템·데이터 모델에는 반영되지 않아 문서와 실제 시스템 간 불일치가 발생하는 현상. 성숙한 조직은 아무리 긴급해도 공식 프로세스를 강제하는 것이 유일한 방어책이다.

## 8. 출제 포인트

1. **데이터 품질 6대 측정 항목**: 완전성, 정확성, 일관성, 유효성, 유일성, 적시성 — 각 정의와 측정 방법
2. **거버넌스 조직 4대 역할**: 거버넌스 협의체(결정)·전사 DA(조정)·데이터 스튜어드(정의)·DBA(구현)
3. **RACI 매트릭스**: R(실무책임)·A(최종책임, 한 역할에만 부여)·C(협의)·I(통보) — 표준도메인 정의 A=DA, 성능튜닝 A=DBA
4. **표준 신규 등록 5단계**: 요청→검토→정의→심의승인→공표 — DA는 정의를 직접 쓰지 않음(의미의 주인은 스튜어드)
5. **표준 변경 관리 4단계**: 요청 → 영향도 분석 → 심의·승인 → 변경 실행·공표
6. **표준 폐기 프로세스 3단계**: 요청 및 분석 → 심의 및 승인 → 폐기 처리 (물리 삭제 대신 사용 중지)
7. **준수 관리 3가지 시점**: 설계 단계, 개발 단계, 운영 단계
8. **표준 준수 감사 5단계**: 점검대상선정→자동스캔→표준과비교→보고서생성→개선추적
9. **미준수 3대 유형**: 미등록 용어 사용·도메인 불일치·명명 규칙 위반 (참고: 무결성 준수도 점검 항목으로 활용 가능)
10. **변경 영향도 분석 3단계**: 식별(Where-Used)→분석(기술적·비즈니스적)→계획, 영향 자산 6종
11. **데이터 표준 관리 시스템 5대 기능**: 중앙리포지토리·워크플로우엔진·모델링도구통합·변경영향도분석엔진·준수율점검리포팅
12. **데이터 표준화 성숙도 모델 5단계**: 초기→관리→정의→정량적관리→최적화, 자가진단 체크리스트 6문항
13. **메타데이터 드리프트**: 공식 프로세스 우회로 인한 문서-실제 시스템 간 불일치
14. **데이터 거버넌스 구성 요소**: 조직(People), 프로세스, 기술, 정책의 4요소
15. **품질 관리 PDCA**: Plan(목표 설정) → Do(측정) → Check(분석) → Act(개선)
16. **코드 폐기 원칙**: 물리 삭제 금지, 사용여부 플래그로 폐기 관리
17. **완전성 공식**: (값이 있는 건수 / 전체 건수) × 100으로 수치 계산 문제 출제
