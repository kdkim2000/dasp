# 4과목 1장: 데이터 모델링 이해

## 1. 데이터 모델링 개요

### 1.1 데이터 모델링 정의

**데이터 모델링(Data Modeling)** 은 현실 세계의 데이터를 추상화하여 컴퓨터에서 처리 가능한 형태로 표현하는 과정이다.

| 구분 | 설명 |
|------|------|
| 목적 | 업무에서 필요한 데이터를 체계적으로 정의 |
| 결과 | 데이터 모델(ERD 등) 산출 |
| 활용 | 데이터베이스 설계의 기반 |

**정의의 3키워드**: ① 정보와 관계의 표현, ② 업무 규칙의 식별, ③ 컴퓨터가 처리할 수 있는 형태로의 변환. 이 중 "업무 규칙의 식별"이 누락되면 서술형에서 오답으로 처리되는 경우가 많다.

### 1.1a 스토브파이프(Stovepipe) 시스템과 등장 배경

초창기 정보 시스템은 프로세스(기능) 중심으로 설계되어 인사·회계·영업 시스템이 각각 독립된 굴뚝(난로 연통)처럼 데이터를 보유했다. 이 **스토브파이프 시스템**은 다음 3가지 문제를 낳았다.

| 문제 | 내용 |
|------|------|
| 정보의 고립화(Information Silos) | 시스템 간 데이터가 단절되어 전사적 통합·공유 불가 |
| 데이터 중복(Data Redundancy) | 동일 정보(예: 사원 정보)가 여러 시스템에 각기 다른 형태로 중복 |
| 무결성 훼손(Data Integrity) | 한 곳의 변경이 다른 곳에 반영되지 않아 정확성·일관성 훼손 |

해법은 기술적 혁신(찰스 바크만, IDS — 최초의 상용 DBMS)과 방법론적 혁신(에드거 커드, 1970년 관계형 모델 발표)으로 나타났다.

### 1.1b 왜 모델링을 반드시 해야 하는가 — "파·간·품"

| 근거 | 내용 |
|------|------|
| ① 파급 효과 | 후반 단계의 구조 변경은 응용 프로그램 수정·테스트·이관까지 연쇄적으로 유발 |
| ② 간결한 표현 | 수백 페이지 문서보다 ERD 한 장이 명확 — 공통 언어로 소통 |
| ③ 데이터 품질 | 구조 결함은 오래 쌓인 데이터를 신뢰할 수 없는 자산으로 만듦 |

### 1.2 데이터 모델링의 3가지 특징

| 특징 | 설명 |
|------|------|
| 추상화(Abstraction) | 현실 세계를 일정한 형식으로 표현 |
| 단순화(Simplification) | 약속된 표기법으로 간결하게 표현 |
| 명확화(Clarity) | 애매모호함을 제거하고 명확히 기술 |

### 1.3 데이터 모델링 3단계

```
1. 개념 데이터 모델링  →  2. 논리 데이터 모델링  →  3. 물리 데이터 모델링
(주제 영역·핵심 엔터티)   (엔터티·속성·관계 상세화)   (테이블·컬럼·인덱스 설계)
```

| 단계 | 목적 | 산출물 | 특징 |
|------|------|--------|------|
| 개념 | 핵심 데이터 개념 정의 | 개념 ERD | DBMS 독립적 |
| 논리 | 업무 규칙·속성 상세화 | 논리 ERD | DBMS 독립적 |
| 물리 | DB 구현을 위한 설계 | 테이블 명세서 | DBMS 종속적 |

### 1.4 전사 아키텍처(EA)와의 관계

| 프레임워크 | 데이터 모델링과의 연결 |
|------|------|
| 자크만 프레임워크(Zachman) | 육하원칙(열)×관점(행) 6×6 매트릭스. '데이터(What)' 열의 관점이 모델링 3단계와 대응: 계획자(Planner)=핵심 데이터 목록, 소유자(Owner)=개념 데이터 모델, 설계자(Designer)=논리 데이터 모델, 구축자(Builder)=물리 데이터 모델(DDL) |
| 토가프(TOGAF) | 비즈니스·데이터·애플리케이션·기술 4대 아키텍처 도메인. 데이터 아키텍처가 논리·물리 데이터 자산의 구조를 다룸 |

## 2. 데이터 모델링 기법 이해

### 2.1 엔터티-관계(ER) 모델링

**ERD(Entity-Relationship Diagram)** 은 엔터티와 이들 간의 관계를 도식화한 모델링 기법이다.

**핵심 구성 요소 — 문법 비유:**

| 요소 | 문법 비유 | 정의 | ERD 표현 |
|------|------|------|---------|
| 엔터티(Entity) | 명사 | 업무에서 관리해야 할 독립적 관심 대상 | 사각형 |
| 속성(Attribute) | 형용사 | 엔터티의 특성을 나타내는 데이터 항목 | 타원형 (원래 표기법) |
| 관계(Relationship) | 동사 | 엔터티 간의 연관 | 마름모 (원래 표기법) |
| 식별자(Identifier) | 주어 | 인스턴스를 유일하게 구별하는 속성(집합) | 밑줄 |

"학생이 과목을 수강한다"라는 문장 하나에 개체·관계·개체가 모두 담긴다.

**좋은 개체의 5가지 조건**: ① 관리 대상일 것, ② 식별 가능할 것, ③ 인스턴스의 집합일 것(2개 이상), ④ 속성을 포함할 것, ⑤ 관계를 형성할 것. **"홍길동"은 인스턴스이지 엔티티가 아니다** — 엔티티는 2개 이상의 인스턴스를 갖는 집합("학생")이어야 한다.

**강한 개체 vs 약한 개체**

| 구분 | 정의 | 예시 |
|------|------|------|
| 강한 개체(Strong Entity) | 다른 개체와 무관하게 독립적으로 존재 가능 | 학생, 과목, 상품 |
| 약한 개체(Weak Entity) | 강한 개체가 존재해야만 의미를 갖는 종속적 개체 | 수강신청내역 |

**엔터티 유형:**

| 유형 | 설명 | 예시 |
|------|------|------|
| 유형(Tangible) 엔터티 | 물리적 형태가 있는 대상 | 고객, 직원, 상품 |
| 개념(Conceptual) 엔터티 | 추상적 개념 대상 | 보험 상품, 서비스 |
| 사건(Event) 엔터티 | 업무 행위·사건으로 생성 | 주문, 거래, 계약 |

**속성 분류 — 특성 기준 vs 구성 기준:**

| 특성 기준 | 설명 | 예 |
|------|------|------|
| 기본 속성(Basic) | 업무 분석을 통해 직접 도출된 일반 속성 | 학생이름, 주문일자 |
| 설계 속성(Designed) | 유일성 부여·코드화를 위해 인위적으로 생성 | 학생ID, 학과코드 |
| 파생 속성(Derived) | 다른 속성으로 계산·유도 | 생년월일→나이 |

| 구성 기준 | 설명 | 예 |
|------|------|------|
| 단순 속성(Simple) | 더 이상 분해 불가 | 성별 |
| 복합 속성(Composite) | 여러 의미 단위로 분해 가능 | 주소→시/구/동 |
| 다중값 속성(Multi-valued) | 한 인스턴스가 여러 값을 가짐 | 취미 |

**식별자(Identifier) 4기준 분류 프레임워크:**

| 기준 | 구분 | 예 |
|------|------|------|
| 대표성 | 주식별자 / 보조식별자 | 사원번호(주) ↔ 주민등록번호(보조) |
| 생성 위치 | 내부식별자 / 외부식별자 | 사원번호(내부) ↔ 관계로 상속된 FK(외부) |
| 속성 개수 | 단일식별자 / 복합식별자 | 학번(단일) ↔ (학번,과목코드)(복합) |
| 업무 의미 | 본질식별자 / 인조식별자 | 주민번호(본질) ↔ 순차 일련번호(인조) |

인조 식별자는 복합 식별자가 너무 길고 복잡할 때 단순화를 위해 사용한다.

**식별자 특성:**

| 특성 | 의미 |
|------|------|
| 유일성(Uniqueness) | 각 인스턴스를 유일하게 식별 |
| 최소성(Minimality) | 식별에 필요한 최소 속성으로 구성 |
| 불변성(Immutability) | 값이 변경되지 않아야 함 |
| 존재성(Not Null) | 반드시 값이 존재해야 함 |

### 2.1a 관계의 3요소, 슈퍼타입/서브타입, M:N 해소

**관계의 3요소 ("차·기·선")**

| 요소 | 정의 | 유형/예 |
|------|------|------|
| 차수(Degree) | 관계에 참여하는 개체 수 | 이항(Binary, 학생↔과목) / 순환(Unary·Recursive, 사원 내 상사-부하) / 삼항(Ternary, 교수·강의실·과목) |
| 대응수/기수성(Cardinality) | 몇 개까지 관계를 맺는가 | 1:1(학생-사물함), 1:N(지도교수-학생), M:N(학생-과목) |
| 참여도/선택성(Optionality) | 반드시 관계를 맺어야 하는가 | 필수(모든 학생은 반드시 학과 소속), 선택(사원은 프로젝트 참여 안 할 수도 있음) |

**슈퍼타입/서브타입 (개요)**: 공통 속성을 가진 상위 개체(슈퍼타입)와 고유 속성을 가진 하위 개체(서브타입)의 'is-a' 계층 구조. 배타적 관계(한 인스턴스가 서브타입 중 하나에만 속함) vs 포괄적 관계(여러 서브타입에 동시 속할 수 있음)로 나뉜다. 상세 내용은 4과목 2장(개념 모델링)·3장(논리 모델링)에서 다룬다.

**M:N 관계 해소 4단계 (개념적 요약)** — 관계형 DB는 M:N을 직접 구현할 수 없으므로 연관 개체(Associative Entity)를 두어 두 개의 1:N으로 분해한다.

| 단계 | 내용 |
|------|------|
| ① M:N 식별 | 두 개체 사이의 M:N 관계 파악 (예: 학생↔과목의 '수강한다') |
| ② 연관 개체 생성 | 행위 자체를 표현하는 새 개체 생성 (예: 수강신청) |
| ③ 1:N 분해 | 학생-수강신청, 과목-수강신청의 두 관계로 분해 |
| ④ 식별자 상속 | 학번·과목코드를 FK로 상속받아 복합 주식별자 구성, 관계 고유 속성(수강일자·성적) 추가 |

> 이 4단계는 개념적 요약이며, 논리 모델링 단계의 상세 절차는 5단계(4과목 3장)로 더 세분화된다 — 관점의 상세도 차이일 뿐 서로 모순되지 않는다.

### 2.1b ERM 바깥의 패러다임 — 객체지향, NoSQL, UML

| 구분 | ERM | 객체지향 모델링(OOM) |
|------|------|------|
| 핵심 단위 | 개체(Entity) | 객체(Object) — 데이터+행위 포함 |
| 관계 | 관계(Relationship) | 연관(Association), 상속(Inheritance) |
| 핵심 개념 | 데이터 구조 중심 | 캡슐화(Encapsulation) |
| 산출물 | ERD | UML 클래스 다이어그램 |

객체지향 애플리케이션 데이터를 관계형 DB에 저장할 때 발생하는 패러다임 차이를 **임피던스 불일치(Impedance Mismatch)** 라 하며, ORM으로 완화하지만 근본적 차이는 남는다.

> **RDBMS vs NoSQL**: RDBMS는 데이터 중심·정규화 지향, NoSQL은 쿼리 결과 지향·비정규화 지향(조회 형태에 최적화된 형태로 중복 허용 저장).

> UML 클래스 다이어그램도 데이터 모델링 도구다 — 클래스↔개체, 속성↔속성, 연관↔관계. 집합(Aggregation, 빈 마름모)과 복합(Composition, 채운 마름모)으로 ERM보다 풍부한 전체-부분 관계를 표현한다.

### 2.2 정규화(Normalization)

데이터 중복과 이상 현상(Anomaly)을 제거하기 위한 테이블 분해 과정.

**이상 현상 유형:**

| 이상 유형 | 설명 |
|---------|------|
| 삽입 이상(Insertion Anomaly) | 불필요한 데이터 없이 삽입 불가 |
| 수정 이상(Update Anomaly) | 중복 데이터 일부만 수정 시 불일치 |
| 삭제 이상(Deletion Anomaly) | 하나의 데이터 삭제 시 다른 데이터도 삭제 |

**정규형 단계:**

| 정규형 | 조건 |
|--------|------|
| 제1정규형(1NF) | 모든 속성이 원자값(Atomic Value) |
| 제2정규형(2NF) | 1NF + 부분 함수 종속 제거 |
| 제3정규형(3NF) | 2NF + 이행 함수 종속 제거 |
| BCNF | 3NF + 모든 결정자가 후보 키 |

## 3. 데이터 모델링 표기법 이해

### 3.1 IE 표기법 (Information Engineering)

현재 가장 널리 사용되는 ERD 표기법. 관계선 끝에 기호로 카디널리티를 표현한다.

**카디널리티 기호:**

| 기호 | 의미 |
|------|------|
| `│` (수직선) | 1 (반드시 하나) |
| `O` (원) | 0 (없을 수도 있음, Optional) |
| `<` (까마귀 발) | 多 (하나 이상) |

**관계 표현 예시:**

| 관계 | 기호 조합 |
|------|---------|
| 1:1 (필수) | `│──│` |
| 1:M (선택, 필수) | `O──<` |
| 1:M (필수, 선택) | `│──O<` |
| M:N | `>O──O<` |

**참여도(Participation):**

| 구분 | 의미 |
|------|------|
| 필수 참여 | 반드시 관계에 참여해야 함 (NOT NULL FK) |
| 선택 참여 | 관계에 참여하지 않을 수도 있음 (NULL 허용 FK) |

### 3.2 Barker 표기법

Richard Barker가 제안한 표기법. Oracle에서 많이 사용된다.

**주요 특징:**

| 요소 | 표현 |
|------|------|
| 엔터티 | 모서리가 둥근 사각형 |
| 속성 | 엔터티 내부에 나열, 필수 속성 `*`, 선택 속성 `o` |
| 식별자 | `#` 기호 |
| 관계 | 실선(필수), 점선(선택) |

### 3.3 IE 표기법 vs Barker 표기법 비교

| 구분 | IE 표기법 | Barker 표기법 |
|------|---------|------------|
| 엔터티 모양 | 직사각형 | 둥근 직사각형 |
| 관계 카디널리티 | 까마귀 발 기호 | 실선·점선 |
| 사용 환경 | 범용 | Oracle 중심 |
| 속성 표현 | 별도 나열 | 박스 내 표현 |
| 서브타입 표기 | 슈퍼타입-서브타입을 별도 사각형으로 그리고 관계로 연결 | 슈퍼타입 사각형 내부에 중첩 상자로 표현 |

**부서-사원 구체 예시**: IE 기준 부서→사원 관계선 양 끝은 까마귀발+원(0..N, 신설 부서는 사원이 없을 수 있음), 사원→부서 방향은 이중 수직선(1..1, 모든 사원은 반드시 하나의 부서에 소속).

### 3.4 식별 관계 vs 비식별 관계

| 구분 | 설명 | IE 표기 |
|------|------|---------|
| 식별 관계 | 부모 PK가 자식 PK의 일부 구성 | 실선 |
| 비식별 관계 | 부모 PK가 자식의 일반 속성(FK) | 점선 |

## 4. 관계형 데이터 모델 심화

### 4.1 릴레이션(Relation)의 특성 6가지

**열(Column)의 특징:**
1. 각 열은 하나의 값만 보유 (원자성)
2. 동일한 종류의 값만 포함 (동질성)
3. 유일한 이름 보유
4. 열의 순서는 무의미

**행(Row)의 특징:**
5. 테이블 내 각 행은 유일해야 함 (중복 행 없음)
6. 행의 순서는 무의미

### 4.2 관계 연산자(Relational Algebra)

수학의 집합 이론을 배경으로 데이터를 집합 단위로 처리:

| 연산자 | 설명 |
|--------|------|
| Select(σ) | 조건에 맞는 행 선택 |
| Project(π) | 특정 열 선택 |
| Product(×) | 두 릴레이션의 카티션 곱 |
| Join(⋈) | 공통 속성으로 두 릴레이션 결합 |
| Union(∪) | 두 릴레이션의 합집합 |
| Intersection(∩) | 두 릴레이션의 교집합 |
| Difference(−) | 두 릴레이션의 차집합 |
| Division(÷) | 나눗셈 연산 |

**처리 연산자:** Insert / Update / Delete

### 4.3 관계형 모델의 무결성 규칙

| 무결성 종류 | 설명 |
|---------|------|
| **엔터티 무결성** | 기본키(PK)는 NULL 값을 포함할 수 없음 |
| **참조 무결성** | 외래키(FK) 값은 반드시 참조 테이블의 PK 값으로 존재해야 함 (NULL 허용) |
| **도메인 무결성** | 컬럼 값은 정의된 데이터 타입·길이·허용값 제약을 준수 |
| **연쇄 작용** | 입력·삭제·수정·조회 작업 시 관련 테이블에 미치는 영향 규칙 |

## 5. 좋은 데이터 모델의 6가지 조건

| # | 조건 | 설명 |
|---|------|------|
| 1 | 완전성(Completeness) | 업무에 필요한 모든 데이터를 빠짐없이 담아냄 |
| 2 | 중복 배제(Non-Redundancy) | 동일한 사실은 단 한 곳에서만 관리 |
| 3 | 업무 규칙 표현(Business Rules) | 비즈니스 중요 규칙을 모델에 명시적으로 담음 |
| 4 | 데이터 재사용성(Data Reusability) | 특정 애플리케이션에 종속되지 않고 전사적으로 재사용 |
| 5 | 안정성·확장성(Stability & Flexibility) | 미래 업무 변화에 유연하게 대응 |
| 6 | 의사소통(Communication) | 모든 이해관계자가 모델을 통해 명확하게 소통 |
