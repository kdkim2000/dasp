# 4과목 2장: 개념 데이터 모델링

## 1. 개념 데이터 모델링 이해

**개념 데이터 모델링(Conceptual Data Modeling)** 은 업무에서 관리해야 할 핵심 데이터 개념과 이들 간의 관계를 비즈니스 관점에서 정의하는 단계이다. DBMS 독립적이며, 전사 관점의 데이터 구조를 파악하는 것이 목적이다.

| 특징 | 설명 |
|------|------|
| 관점 | 비즈니스·현업 관점 |
| 수준 | 높은 추상화 수준 |
| DBMS 독립성 | DBMS 기술에 무관 |
| 대상 독자 | 비즈니스 이해관계자·현업 담당자 |
| 산출물 | 개념 ERD, 주제 영역 정의서 |

### 1.1 데이터 아키텍처 4계층 내 위상

| 관점 | 개괄(Contextual) | 개념(Conceptual) | 논리(Logical) | 물리(Physical) |
|------|------|------|------|------|
| 핵심 질문 | 범위가 무엇인가 | 무엇(What)이 필요한가 | 어떻게(How) 구조화되는가 | 어디에 어떻게 저장되는가 |
| 주요 구성요소 | 전략적 도메인 | 핵심 엔티티, 주요 관계 | 모든 엔티티·속성·관계·식별자·서브타입 | 테이블, 칼럼, 데이터타입, 제약조건, 인덱스 |
| 기술 독립성 | 완전 독립 | 완전 독립 | DBMS 독립적 | 특정 DBMS 종속적 |
| 주요 사용자 | 경영진 | 현업 전문가, 비즈니스 분석가, DA | 데이터 모델러, 비즈니스 분석가, DBA | DBA, 개발자 |

### 1.2 개념모델링 3대 목표 — 위험 관리 전략

| 목표 | 설명 |
|------|------|
| 의사소통(Communication) | 비즈니스 사용자·분석가·개발자가 데이터 요구사항을 발견·검증하는 토론의 장 |
| 안정성(Stability) | 데이터 정의를 프로세스로부터 분리해 프로세스 변화에 흔들리지 않는 구조 확보 |
| 통찰력(Insight) | 구축 과정에서 숨겨진 가정·명문화되지 않은 규칙이 드러남 |

> **위험 관리 프레이밍**: 오류는 발견 시점이 빠를수록 수정 비용이 기하급수적으로 감소한다. 개념 모델은 코드 작성 전, 상세 스키마 설계 전에 오해를 표면화하는 가장 비용 효율적인 품질보증 활동이다.

## 2. 주제 영역 정의

**주제 영역(Subject Area)** 은 비즈니스 관점에서 유사한 데이터를 그룹화한 상위 분류 체계이다.

### 2.1 주제 영역의 특징

| 특징 | 설명 |
|------|------|
| 업무 기능과 유사 | 주요 업무 영역과 대응 |
| 3~10개 내외 | 너무 많거나 적지 않게 정의 |
| 배타적·완전 분류 | 엔터티는 하나의 주제 영역에만 속함 |

### 2.1a 주제 영역 정의의 4대 목적

① 전사적 데이터 조망, ② 의사소통의 기준(공통 언어), ③ 데이터 통합의 기반(데이터 웨어하우스 주제 지향성과 연결), ④ 데이터 거버넌스 단위(주제 영역별 데이터 오너 지정).

### 2.1b 주제 영역 명명 3원칙

① 실무 업무 용어 사용(○고객·상품, ×고객마스터), ② 유일한 단수형 명사(○고객, ×고객들), ③ 데이터 그룹명(명사·What) 부여(○고객·주문, ×고객관리·주문처리 — 동사·How는 프로세스로 자주 바뀌므로 금지).

### 2.1c 계층적 분할 3단계

| 단계 | 내용 |
|------|------|
| 1차 분류 | 주체(관계자·조직·직원), 대상(상품·자산·자재), 행위(계약·주문·결제), 자원·장소(채널·창고), 기준·공통(기준정보·회계) |
| 2차 분류 | 업무 활동에 필요한 데이터의 기능적 세분화 (예: 고객 기본, 고객 상세, 고객 관계, 고객 거래 이력) |
| 3차 분류 | 세부 주제 영역 — 핵심 엔티티와 거의 1:1 대응 (예: 관계자기본→개인고객·법인고객·협력사) |

### 2.2 주제 영역 도출 방법

| 방법 | 내용 |
|------|------|
| 업무 기능 분석 | 비즈니스 기능을 기준으로 주제 영역 도출 |
| 정보 흐름 분석 | 데이터 흐름을 기준으로 관련 데이터 그룹화 |
| 조직 구조 분석 | 조직 단위·부서 기반으로 주제 영역 도출 |

**하향식·상향식·혼합형 접근법**

| 접근법 | 시작점 | 장단점 |
|------|------|------|
| 하향식(Top-Down) | 비즈니스 전략에서 추상적 개념→구체적 데이터로 | 전사 일관성↑ / 분석 기간 김 |
| 상향식(Bottom-Up) | 기존 DB 스키마·업무 양식에서 구체적 데이터→추상적 개념으로 | 현업 요구 충실 반영·빠름 / 전사 일관성 확보 어려움 |
| 혼합형(Hybrid) | Top-Down 전략 수립→Bottom-Up 현실 분석(CRM·ERP 리버스엔지니어링)→검증 및 상세화 | 가장 현실적·실용적 |

**주제 영역 예시 (유통 기업):**

| 주제 영역 | 포함 엔터티 |
|---------|---------|
| 고객 | 고객, 고객 등급, 회원 |
| 상품 | 상품, 카테고리, 브랜드 |
| 주문 | 주문, 주문항목, 결제 |
| 재고 | 재고, 창고, 입출고 이력 |
| 마케팅 | 캠페인, 쿠폰, 이벤트 |

## 2a. 엔터티 분류 체계

블로그 교재에서는 엔터티를 3가지 관점으로 분류한다.

### 유형별 분류 (업무적 성격)

| 유형 | 설명 | 예시 |
|------|------|------|
| **유형(Tangible) 엔터티** | 물리적 형태가 있는 대상 | 고객, 직원, 상품 |
| **활동(Event) 엔터티** | 업무 행위나 사건으로 생성 | 주문, 계약, 접속 기록 |
| **개념(Conceptual) 엔터티** | 무형의 개념적 대상 | 계정과목, 보험상품, 성적 |

### 의존성에 따른 분류

| 유형 | 설명 |
|------|------|
| **독립(Fundamental) 엔터티** | 다른 엔터티에 의존하지 않고 독립적으로 존재 |
| **종속(Dependent) 엔터티** | 다른 엔터티의 존재에 의존하여 식별됨 |

### 발생 시점에 따른 분류

| 유형 | 설명 | 예시 |
|------|------|------|
| **키(Key) 엔터티** | 부모 엔터티 없음, 독립적으로 생성 | 상품, 고객 |
| **메인(Main) 엔터티** | 중심 업무를 수행하는 엔터티 | 주문 |
| **액션(Action) 엔터티** | 키·메인 엔터티의 행위 결과로 생성 | 주문 상세, 배송 |

### 관계 명칭 선정 기준

1. 현업에서 사용하는 간결한 **동사형** 사용
2. **현재 시제** 적용
3. 두 엔터티 간의 **업무적 연관성** 표현

### 속성 도출 방법

1. 현행 시스템 문서(화면, 보고서, 장표) 참고
2. 현업 장표 및 보고서 수집·분석
3. 현업 담당자 협의를 통한 도출

### 식별자 유형 (키의 종류)

| 유형 | 설명 |
|------|------|
| **후보키(Candidate Key)** | 유일성과 최소성을 모두 만족하는 키 |
| **기본키(Primary Key)** | 후보키 중 실제 튜플 식별에 사용되는 키 |
| **대체키(Alternate Key)** | 후보키 중 기본키로 선택되지 않은 키 |
| **외래키(Foreign Key)** | 다른 테이블의 기본키를 참조하는 키 |

## 3. 후보 엔터티 선정

**후보 엔터티(Candidate Entity)** 는 정보 요구 사항 분석에서 도출된 데이터 항목 중 독립적으로 존재할 수 있는 것들을 선별한 목록이다.

### 3.0 엔터티 선정 4단계 생명주기

| 단계 | 내용 |
|------|------|
| ① 수집(Collection) | 잠재 후보를 빠짐없이 찾아내는 탐색("판단하지 말고 일단 모아라") |
| ② 식별(Identification) | 진정한 엔터티 자격 검증 |
| ③ 분류(Classification) | 중요도·업무 영역에 따라 구조화 |
| ④ 검증(Validation) | 업무 프로세스를 온전히 지원하는지 CRUD로 최종 확인 |

**수집 방법 6가지**: 기존 시스템 문서(설계서·DB 스키마), 현업 장표·보고서(가공된 결과물이므로 근원 데이터를 역추적), 현업 사용자 인터뷰(암묵적 규칙 발견에 최적), 관련 전문 서적(선진 사례 참고), DFD 데이터 저장소(훌륭한 엔터티 후보), 타 시스템·현장 조사.

### 3.0a 3단계 심사 (순차 필터링)

| 단계 | 내용 |
|------|------|
| ① 개념의 명확한 정립 | 후보 단어가 의미하는 진정한 집합을 업무 맥락에서 구체적으로 정의 |
| ② 관리 대상 여부 판정 | 현재뿐 아니라 앞으로 관리해야 할 필요성까지 포함한 전략적 판단 |
| ③ 집합의 요건 확인 | 2개 이상의 인스턴스, 2개 이상의 속성, 유일한 식별자 — "가로(속성)와 세로(인스턴스)를 가진 면적" |

> **본질 순수성 원칙**: 엔터티는 순수한 객체(사람·상품) 또는 순수한 행위(입금·계약) 중 하나여야 한다. '납입자·수강생'처럼 개체+행위가 혼합된 형태는 엔터티가 아니라 숨은 M:N 관계의 신호다.

**3대 설계 안티패턴**: ① 프로세스 중심 모델링(화면 흐름 따라 엔터티 분리→데이터 중복), ② EAV(Entity-Attribute-Value, 속성명·값을 행으로 저장→무결성 제약 불가), ③ 갓 오브젝트(God Object, 여러 개념을 하나로 뭉쳐 모든 로직이 의존).

### 3.1 후보 엔터티 도출 방법

| 방법 | 내용 |
|------|------|
| 명사 분석 | 업무 설명에서 명사로 표현된 개념 추출 |
| 정보 요구 사항 분석 | 정보 요구 사항의 데이터 항목에서 도출 |
| 장표·화면 분석 | 업무 장표·화면에 반복 등장하는 개념 추출 |
| 인터뷰 결과 분석 | 이해관계자 인터뷰에서 언급된 주요 개념 |

### 3.2 엔터티 선정 기준

| 기준 | 설명 |
|------|------|
| 독립 존재성 | 다른 것에 의존하지 않고 독립적으로 존재 |
| 식별 가능성 | 고유하게 식별할 수 있는 속성 존재 |
| 2개 이상의 속성 | 단 하나의 속성만 있다면 엔터티가 아닐 가능성 |
| 업무 관련성 | 업무에서 실제로 관리·추적하는 대상 |

### 3.2a 검증 4대 기둥

| 기둥 | 질문 |
|------|------|
| 제1: 관리적 중요성 | 비즈니스가 시간·자원을 들여 추적·관리할 가치가 있는가 |
| 제2: 집합 무결성 | 가로(속성)와 세로(인스턴스)를 가진 면적 집합인가 |
| 제3: 동질성 및 독립성 | 모든 인스턴스가 동일한 본질·속성 공유(동질성), 다른 엔터티와 개념적으로 구분(독립성) |
| 제4: 본질 순수성 | 개체 집합 또는 행위 집합이어야 하며 혼합되면 안 됨 |

### 3.2b 본질 식별자 vs 인조 식별자, 엔터티 정제 고급 기법

| 구분 | 정의 |
|------|------|
| 본질 식별자(Essential) | 엔터티의 비즈니스적 정의에 내재된 속성·관계로 구성, 업무 규칙을 담음 |
| 인조 식별자(Artificial) | 비즈니스 의미 없이 시스템이 생성한 값 (조인 성능·복합키 단순화 목적) |

개념·논리 단계에서는 본질 식별자 규명에 집중하고, 인조 식별자 채택 여부는 물리 모델링의 구현 편의에 따른 결정이다.

**엔터티 정제 고급 기법**: ① 통합(Integration, 개인고객+법인고객→'고객'+고객유형), ② 분할(Division, 본질 식별자가 근본적으로 다르면 분리), ③ 서브타입 활용(슈퍼타입(계약)+서브타입(대출계약·예금계약)), ④ 코드성 엔터티 판단 3질문(자체 속성을 가지는가/다른 엔터티의 부모가 되는가/여러 엔터티와 관계를 맺는가 — 하나라도 해당하면 엔터티로 승격).

### 3.3 엔터티 후보 목록 관리

| 항목 | 내용 |
|------|------|
| 후보 엔터티명 | 한글·영문 명칭 |
| 설명 | 엔터티의 정의 |
| 출처 | 도출 근거 (어떤 요구 사항에서 나왔는가) |
| 포함 여부 | 채택/제외 결정 |

## 4. 핵심 엔터티 정의

후보 엔터티 중 업무에서 가장 중요한 **핵심 엔터티(Core Entity)** 를 선별하고 상세히 정의한다.

### 4.1 핵심 엔터티 선별 기준

| 기준 | 설명 |
|------|------|
| 비즈니스 핵심 | 주요 업무 기능에 필수적인 데이터 |
| 높은 활용도 | 여러 업무 영역에서 공통으로 사용 |
| 독립 존재 | 다른 엔터티에 종속되지 않음 |

### 4.2 엔터티 정의서

핵심 엔터티를 확정한 후 엔터티 정의서를 작성한다.

| 항목 | 내용 |
|------|------|
| 엔터티명 | 한글명, 영문명 |
| 정의 | 업무 관점의 의미 설명 |
| 식별자(후보) | 엔터티를 유일하게 구분하는 속성 |
| 주제 영역 | 속하는 주제 영역 |
| 관련 요구 사항 | 도출 근거 정보 요구 사항 ID |

## 5. 관계 정의

엔터티 간의 **관계(Relationship)** 를 정의하고 카디널리티·참여도를 결정한다.

### 5.0 관계 정의 3요소와 관계 구문

| 요소 | 정의 |
|------|------|
| 관계 차수 | 한 엔터티 인스턴스가 상대방 몇 개와 연결되는가 (단수/다수) |
| 관계 선택성 | 반드시 참여해야 하는가 (필수: 실선 / 선택: 점선) — 1:M에서 자식(M쪽)을 필수로 설계해 고아 데이터 방지 |
| 관계명 | 간결한 현재 시제 동사('소속된다'·'주문한다'), 모호한 표현 금지, 순환·다항 관계에서는 필수 |

**관계 구문(Relationship Syntax) 템플릿**: "[엔터티1]의 임의의 한 개체는 [관계 형태]의 [엔터티2]와 [관계명] 관계를 [선택 사양] 가진다." — 예: "사원의 임의의 한 개체는 단 하나의 부서와 소속된다 관계를 반드시 가진다."

**관계의 두 가지 성격**: 존재에 의한 관계(정적, 예: 사원은 부서에 소속된다) vs 행위에 의한 관계(동적, 예: 고객은 상품을 주문한다).

### 5.1 관계 도출 방법

| 방법 | 내용 |
|------|------|
| 동사 분석 | 업무 설명에서 엔터티 간 연결 동사 추출 |
| 업무 규칙 분석 | 엔터티 간 관계를 정의하는 업무 규칙 |
| 정보 흐름 분석 | 데이터 흐름에서 연관 관계 파악 |

### 5.2 카디널리티(Cardinality) 심화

| 관계 유형 | 설명 | 예시 |
|---------|------|------|
| 1:1 | 하나 대 하나. 드물게 나타나며, 필수-필수 1:1이 나오면 두 엔터티가 사실상 하나의 논리 집합일 가능성을 의심 | 직원:사원증 |
| 1:M | 하나 대 다수. 가장 흔한 형태 — 필수(M)-선택(1)이 기본형(사원-부서), 필수-필수는(주문-주문항목) | 고객:주문 |
| M:N | 다수 대 다수 | 학생:강좌 |

**순환관계(Recursive)**: 하나의 엔터티가 자기 자신과 관계 (사원의 상사-부하, BOM처럼 M:M 순환도 가능). **배타적 관계(Arc)**: 여러 엔터티 중 단 하나와만 관계 (결제수단이 카드 또는 계좌 중 하나).

### 5.2a 개념 vs 논리/물리 단계의 M:N 취급 차이 (중요 정정)

**개념 단계에서는 M:N을 그대로 유지하는 것이 권장된다.** 개념 모델의 목적은 이해관계자와의 직관적 소통이며, '학생-과목'처럼 M:N을 있는 그대로 보여주는 것이 가장 이해하기 쉽다. 중간(연결) 엔터티를 개념 단계에서 미리 보여주면 오히려 소통을 방해한다. M:N 해소는 **논리 단계**에서 비로소 수행하며(연결 테이블 도입, 1:M×M:1 분해), 이는 기술적 변환이 아니라 업무 규칙(신청일자·성적 등 관계 고유 속성)을 발견하는 과정이다.

| 단계 | M:N 취급 |
|------|------|
| 개념 | 그대로 유지 (권장) — 의사소통 목적 |
| 논리 | 반드시 해소 — 연결 엔터티 도입, 두 개의 1:M 식별 관계로 분해 |
| 물리 | 해소된 상태로 연결 테이블(교차 테이블) 구현 |

```
[개념] 학생 ──M:N── 강좌   (그대로 표현)
[논리] 학생 ──1:M── 수강신청 ──M:1── 강좌   (해소)
```

### 5.3 참여도(Participation)

| 구분 | 의미 | DB 구현 |
|------|------|---------|
| 필수(Mandatory) | 반드시 관계에 참여 | NOT NULL FK |
| 선택(Optional) | 관계에 참여 안 할 수도 있음 | NULL 허용 FK |

### 5.4 식별 관계 vs 비식별 관계 비교

| 구분 | 식별 관계 | 비식별 관계 |
|------|------|------|
| 표기법 | 실선(Solid Line) | 점선(Dashed Line) |
| 자식의 존재 | 부모에 강하게 종속, 부모 없이 존재 불가 | 부모와 독립적으로 존재 가능 |
| 데이터 무결성 | DB 스키마 수준에서 강력하게 강제 | 애플리케이션 로직·추가 제약 필요 |
| 모델 유연성 | 낮음(부모 변경이 연쇄 영향) | 높음(수정·확장 용이) |
| 사용 사례 | '~의 일부이다'(주문-주문항목) | 단순 참조(사원-부서) |

식별 관계는 정합성을 최우선하는 **'보수적' 전략**(부모와의 관계가 존재의 본질일 때 적합), 비식별 관계는 변화 적응성을 중시하는 **'민첩한' 전략**이다.

## 6. 개념 데이터 모델 작성

### 6.1 개념 ERD 작성 절차

```
1. 주제 영역 결정
2. 후보 엔터티 도출
3. 핵심 엔터티 확정
4. 관계 정의
5. 개념 ERD 작성
6. 검토 및 확인
```

### 6.1a 개념 모델 구축 3대 방법론

| 방법론 | 흐름 | 적합 상황 |
|------|------|------|
| 하향식(Forest to Trees) | 비즈니스 전략→주제 영역→핵심 엔터티→핵심 관계 | EA 수립·차세대 시스템 구축 (전사 일관성↑, 분석 기간 김) |
| 상향식(Trees to Forest) | 요구사항·자료 수집→후보 엔터티→정제·관계→추상화 | 부서 업무 개선·프로토타이핑 (빠른 산출물, 전사 관점 부족) |
| 리버스엔지니어링(Product to Blueprint) | 물리 스키마 추출→논리화→개념화 | 레거시 현대화·데이터 마이그레이션 (나쁜 설계 답습 위험) |

### 6.1b CRUD 매트릭스 검증 규칙

| 규칙 | 의미 |
|------|------|
| C(Create)가 없는 엔터티 | 생성 프로세스 누락 또는 엔터티 자체가 불필요 |
| R(Read)이 없는 엔터티 | 생성만 되고 활용되지 않음, 저장 가치 재검토 필요 |
| CRUD가 전혀 없는 프로세스 | 프로세스 분석 오류 또는 관련 엔터티 누락 |

### 6.1c 이해관계자 검토 워크숍 3단계

① 사전 준비(목표·범위 설정, ERD·정의서를 2~3일 전 배포), ② 워크숍 진행(배경 공유→주제 영역 단위 순차 설명, 일방적 발표 금지), ③ 사후 조치(논의 결과 반영·모델 수정, 공식 합의 도출).

### 6.2 개념 데이터 모델 검토 기준

| 검토 항목 | 확인 내용 |
|---------|---------|
| 엔터티 완전성 | 중요한 업무 데이터가 빠짐없이 정의되었는가 |
| 관계 정확성 | 엔터티 간 관계가 업무 규칙과 일치하는가 |
| 비즈니스 이해 용이성 | 현업 담당자가 이해할 수 있는 수준인가 |
| 주제 영역 일관성 | 모든 엔터티가 적절한 주제 영역에 속하는가 |

## 출제 포인트

1. 개념 데이터 모델링 목적: 핵심 데이터 개념·관계 정의, 완전 기술 독립적(위험 관리 전략)
2. 데이터 아키텍처 4계층: 개괄(What범위)→개념(What)→논리(How-구조)→물리(How-저장)
3. 개념모델링 3대 목표: 의사소통·안정성·통찰력
4. 주제 영역 4대 목적: 전사적 조망·의사소통 기준·데이터 통합 기반(DW 주제지향성)·거버넌스 단위
5. 주제 영역 명명 3원칙: 실무 업무 용어·유일한 단수형 명사·명사(동사 금지)
6. 계층적 분할 3단계: 1차(주체/대상/행위/자원장소/기준공통)→2차(기능적 세분화)→3차(세부 주제영역)
7. 주제 영역 도출: 하향식·상향식·혼합형(CRM/ERP 리버스엔지니어링) / 업무기능·정보흐름·조직구조 분석
8. 엔터티 선정 4단계 생명주기: 수집→식별→분류→검증, 수집 방법 6가지
9. 3단계 심사: 개념정립→관리대상판정→집합요건확인(2개 이상 인스턴스/속성, 유일 식별자)
10. 본질 순수성 원칙: 개체+행위 혼합('납입자'·'수강생')은 숨은 M:N 신호
11. 3대 설계 안티패턴: 프로세스 중심 모델링·EAV·God Object
12. 검증 4대 기둥: 관리적 중요성·집합 무결성·동질성 및 독립성·본질 순수성
13. 본질 식별자(업무 규칙 내재) vs 인조 식별자(시스템 생성), 개념·논리 단계는 본질 식별자 집중
14. 엔터티 정제 기법: 통합·분할·서브타입 활용·코드성 엔터티 판단 3질문
15. 관계 정의 3요소: 관계 차수·관계 선택성·관계명(현재시제 동사)
16. **[중요]** M:N은 개념 단계에서 그대로 유지(권장, 의사소통 목적), 논리 단계에서 반드시 해소(연결 엔터티+1:M 식별관계)
17. 1:1(희소, 논리집합 통합 의심)/1:M(필수-선택 기본형)/순환관계(Recursive, BOM)/배타적 관계(Arc)
18. 식별관계(실선, 부모종속, 보수적 전략) vs 비식별관계(점선, 독립존재, 민첩한 전략)
19. 개념 모델 구축 3대 방법론: 하향식(Forest to Trees)·상향식(Trees to Forest)·리버스엔지니어링(Product to Blueprint)
20. CRUD 매트릭스 검증: C없음(불필요 엔터티)/R없음(활용안됨)/CRUD없는 프로세스(분석오류)
21. 이해관계자 검토 워크숍 3단계: 사전준비·워크숍진행·사후조치
22. 필수 참여 = NOT NULL FK, 선택 참여 = NULL 허용 FK
23. 개념 ERD 작성 순서: 주제영역→후보엔터티→핵심엔터티→관계→ERD→검토
