# 4과목 3장: 논리 데이터 모델링

## 0. 논리 데이터 모델링의 기능 4가지

논리 데이터 모델링이 조직에 제공하는 핵심 기능:

1. **전사적 통합 데이터 체계 구축**: 조직 전체의 일관된 데이터 구조 정립
2. **데이터 일관성 및 정확성 규칙 도출**: 업무 규칙과 무결성 조건 명세화
3. **사용자와의 명확한 의사소통 수단**: 비즈니스 언어로 표현된 논리 ERD로 현업과 소통
4. **안정적인 데이터베이스 설계 토대**: 물리 모델링의 기반이 되는 논리 구조 수립

---

## 1. 논리 데이터 모델링 이해

**논리 데이터 모델링(Logical Data Modeling)**은 개념 데이터 모델을 기반으로 속성, 엔터티 관계, 이력 관리 등을 상세히 정의하는 단계이다. DBMS에 독립적이며, 데이터베이스 설계를 위한 논리적 구조를 결정한다.

| 특징 | 설명 |
|------|------|
| 관점 | 데이터 관리 관점 (중간 수준 추상화) |
| DBMS 독립성 | DBMS 기술에 무관 |
| 표현 | IE 또는 Barker 표기법의 ERD |
| 대상 독자 | DA, 시스템 설계자 |
| 산출물 | 논리 ERD, 엔터티 정의서, 속성 정의서 |

**개념 → 논리 모델링 전환:**

| 개념 모델 | 논리 모델 |
|---------|---------|
| 엔터티(개략적) | 엔터티(상세, 정규화된) |
| 관계(선택적 기술) | 관계(카디널리티·참여도 상세화) |
| 핵심 속성 일부 | 모든 속성 완전 정의 |
| 식별자(후보) | 기본 키, 외래 키 확정 |

## 2. 속성 정의

**속성(Attribute)** 은 엔터티의 특성을 나타내는 데이터 항목이다. 논리 모델링에서 모든 속성을 빠짐없이 정의해야 한다.

### 2.0 속성의 4대 본질적 특징

| 특징 | 설명 |
|------|------|
| 귀속성 | 속성은 독립적으로 존재하지 않고 반드시 특정 엔터티에 귀속(할당)된다 |
| 집합성 | 속성은 유효한 모든 값의 집합(도메인)을 표현 |
| 관계의 이중성 | 논리 모델의 관계는 물리 세계에서 외래키 속성으로 구현됨 ("소속된다"→FK 컬럼) |
| 독립성 | 일반 속성은 주 식별자에만 완전히 종속되어야 함, 일반 속성끼리 종속되면 이행적 종속(갱신 이상의 원인) |

### 2.0a 속성 후보 도출 6대 수집처와 선정 원칙

| 수집처 | 설명 |
|------|------|
| 구 시스템 문서 | 테이블 정의서·화면 설계서·COBOL COPYBOOK 등 |
| 현업 장표·보고서 | 최종 결과값이 아니라 원천 데이터를 역추적 |
| 사용자 협의 | "시간이 지나며 변경될 수 있는 것은?" → 이력 관리 설계로 연결 |
| DFD·데이터 사전 | DFD 데이터 저장소는 훌륭한 속성 후보 |
| 전문서적·표준 모델 | BIAN·ISO 20022 등 산업 표준 모델의 체크리스트 |
| 타 시스템 인터페이스 | 외부 API가 요구하는 속성 참고 |

**후보 선정 2대 원칙**: ① 원시 속성을 버리지 않는다 — '나이'(파생)만 저장하고 '생년월일'(원시)을 버리면 생일 마케팅 같은 미래 요건을 충족할 수 없음, ② 소그룹 후보군→엔터티 할당 — 유사 속성을 후보군(Pool)으로 묶은 뒤 가장 적합한 엔터티에 할당.

**속성의 3대 기본 구성요소**: 속성명(업무 용어, 명확한 상태), 도메인(타입·길이·허용값·기본값·NULL 허용 여부), 선택성(필수 Mandatory/선택 Optional).

### 2.1 속성 유형

| 유형 | 설명 | 예시 |
|------|------|------|
| 기본 속성 | 업무에서 자연스럽게 도출된 속성 | 고객명, 전화번호 |
| 설계 속성 | 모델링·설계 과정에서 필요로 추가된 속성 | 코드 컬럼 |
| 파생 속성 | 다른 속성 값으로 계산·유도 | 나이(생년월일로 계산), 총액 |

### 2.2 속성 정의서 작성

| 항목 | 내용 |
|------|------|
| 속성명 | 한글명, 영문명 |
| 속성 설명 | 업무 의미 |
| 도메인 | 데이터 타입, 길이, 형식 |
| NULL 여부 | 필수(NOT NULL) / 선택(NULL) |
| 기본값 | Default 값 |
| 업무 규칙 | 허용 값, 유효성 규칙 |

### 2.3 도메인(Domain) 정의

속성이 가질 수 있는 값의 범위·타입·형식을 정의한 표준. 도메인은 단순 기술 명세가 아니라 **데이터 품질의 첫 방어선**이다 — 논리 단계에서 도메인을 명확히 정의하면 이후 물리 DB의 CHECK 제약으로 구현되어 오입력을 원천 차단한다. 기업은 개별 정의보다 표준 도메인 라이브러리를 구축하는 것이 효과적이다.

| 도메인 | 데이터 타입 | 길이 | 형식 |
|--------|---------|------|------|
| 날짜 | DATE | — | YYYY-MM-DD |
| 금액 | NUMBER | 15,2 | 소수점 2자리 |
| 코드 | VARCHAR | 10 | 영숫자 |
| 이름 | VARCHAR | 100 | 한글 허용 |

### 2.4 복합 속성(Composite Attribute) 처리

여러 값을 포함하는 복합 속성은 개별 원자 속성으로 분해해야 한다 (1NF 조건).

```
주소 → 우편번호 + 시도 + 시군구 + 상세주소
```

## 3. 엔터티 상세화

개념 모델의 엔터티를 논리 모델에서 완전하게 상세화하는 단계이다.

### 3.0 식별자 확정 절차 (본질 → 후보 → 대체 → 인조)

| 유형 | 정의 |
|------|------|
| 본질 식별자(Essential) | 엔터티가 생성되기 위해 근본적으로 필요한 '의미상의 주어'. 키 엔터티는 자체 생성, 행위 엔터티는 부모로부터 상속 |
| 후보 식별자(Candidate) | 아래 5조건을 모두 만족해야 함 |
| 대체/보조 식별자(Alternate) | 후보 중 주 식별자로 선정되지 않은 것 (물리 단계에서 Unique Constraint/Index로 구현) |
| 인조 식별자(Artificial) | 본질·후보 식별자가 부적합할 때 임의로 부여하는 새 식별자(일련번호 등) |

**후보 식별자의 5가지 조건**: ① 유일성, ② 최소성(직접적 속성으로 식별), ③ NULL 불허, ④ 개념적 유일성(향후 데이터까지 보장 — 동명이인이 있으면 '부서명+사원명'은 후보가 될 수 없음), ⑤ 변경 가능성 최소. 뒤의 두 조건이 자주 누락된다.

**종속 관계의 두 축**: 절대 종속(부모 없이 자식이 논리적으로 생성될 수 없음, 예: 주문 없는 주문항목 불가) vs 상대 종속(부모 없이도 생성 가능, 예: 사원은 부서 배정 전에도 생성 가능) / 직접 종속(1촌 관계) vs 간접 종속(조부모 등 1촌 이상을 통한 종속).

### 3.1 슈퍼타입/서브타입 모델링

공통 속성을 상위 엔터티(슈퍼타입)에, 특수 속성을 하위 엔터티(서브타입)에 정의하는 방식.

```
직원(슈퍼타입)
  ├── 정규직(서브타입)
  ├── 계약직(서브타입)
  └── 파견직(서브타입)
```

| 개념 | 설명 |
|------|------|
| 슈퍼타입(Super Type) | 공통 속성을 가진 상위 엔터티 |
| 서브타입(Sub Type) | 특수 속성을 가진 하위 엔터티 |
| 배타적(Exclusive) | 하나의 서브타입에만 속함 |
| 포함적(Inclusive) | 여러 서브타입에 동시 속함 가능 |

### 3.2 관계 상세화

개념 모델의 관계를 논리 모델에서 외래 키(FK)로 구현:

| 관계 유형 | 구현 방법 |
|---------|---------|
| 1:1 | FK를 어느 한쪽 테이블에 추가 |
| 1:M | 다(Many) 쪽에 FK 추가 |
| M:N | 연결 테이블(교차 엔터티) 추가 |

### 3.3 식별 관계 vs 비식별 관계

| 구분 | 설명 | 특징 |
|------|------|------|
| 식별 관계 | 부모 PK → 자식 PK 일부 구성 | 자식이 부모 없이 존재 불가 |
| 비식별 관계 | 부모 PK → 자식 일반 속성(FK) | 자식이 독립적 존재 가능 |

## 3a. 정규화 심화 (4NF·5NF)와 M:N 해소

### 3a.0 정규화 1NF~5NF

논리 모델링에서는 일반적으로 3NF까지 수행하는 것을 목표로 하되, 특수한 경우 BCNF~5NF까지 진행한다.

| 단계 | 조건 | 예 |
|------|------|------|
| 1NF | 모든 속성이 원자값 | 다중값(취미) 분리 |
| 2NF | 1NF + 부분 함수 종속 제거 (복합키에서만 발생) | (학번,과목코드) PK에서 과목명 분리 |
| 3NF | 2NF + 이행 함수 종속 제거 | 고객명을 고객 엔터티로 분리 |
| BCNF | 3NF + 모든 결정자가 후보키 | 복합 후보키가 겹치는 특수 케이스 |
| **4NF** | BCNF + 다가 종속(MVD) 제거 | 사원이 여러 자격증·여러 취미를 독립적으로 가질 때, (사원,자격증)과 (사원,취미)로 무손실 분해 |
| **5NF** | 4NF + 모든 조인 종속이 후보키를 통해서만 성립 | 후보키가 아닌 조인 종속이 있으면 최소 릴레이션으로 재분해 (위반 사례는 매우 드묾) |

**정규화의 5가지 장점**: ① 중복 감소, ② NULL 값 감소, ③ 무결성 강화, ④ **요구사항 발견 및 업무 규칙 명확화**(함수 종속 분석 중 몰랐던 업무 규칙을 발견), ⑤ 구조적 안정성 확보. 성능을 위해 정규화 수준을 의도적으로 낮추는 반정규화는 물리 모델링(4과목 4장) 단계의 활동이다.

### 3a.1 M:N 해소 이유와 절차 (논리 단계, 5단계)

**M:N을 반드시 해소해야 하는 3가지 이유**: ① 관계형 모델 구현 불가(표준 RDBMS는 M:N을 직접 지원하지 않음), ② 업무 규칙·속성 표현의 한계(관계 고유 정보를 담을 곳이 없음), ③ 모델의 불완전성(정규화되지 않았을 가능성, 누락 정보 파악 어려움).

| 단계 | 내용 |
|------|------|
| ① 관계 엔터티 생성 | 두 엔터티 사이에 새로운 관계(교차/연관) 엔터티 생성 |
| ② 1:M 식별 관계 | 관계 엔터티는 두 부모와 각각 1:M **식별** 관계를 맺음(단순 관계가 아님) |
| ③ 복합 식별자 구성 | 주 식별자는 두 부모로부터 상속받은 식별자의 조합 |
| ④ 관계 고유 속성 추가 | 신청일자·성적처럼 관계에서만 발생하는 속성 추가 |
| ⑤ 선택사양 반영 | 원래 M:N의 선택 사양·기수성을 분석해 새 1:M 관계에 정확히 반영 |

> **비교**: 4과목 1장의 M:N 해소 4단계(식별→연관개체생성→1:N분해→식별자상속)는 개념적 요약이며, 위 5단계는 논리 모델링 단계의 상세 절차다. 서로 다른 상세도의 절차일 뿐 모순되지 않는다.

## 3b. 참조 무결성 규칙 정의

부모-자식 관계 엔터티의 입력 및 삭제 시 적용할 규칙을 논리 모델링 단계에서 정의한다.

참조 무결성 규칙은 기술적 편의가 아니라 업무 규칙(Business Rule)에 근거해 결정한다. 교재 기준 입력 규칙과 삭제 규칙은 각각 **4종**이다 (일부 CASE 도구는 Customized·No Effect 같은 확장 옵션을 추가로 제공하기도 하나 시험 범위의 기본 규칙은 아래 4종이다).

### 입력 규칙 (자식 엔터티 데이터 입력 시) — 4종

| 규칙 | 설명 |
|------|------|
| **Dependent (기본 규칙)** | FK값이 부모 PK에 반드시 존재해야만 자식 입력 허용 |
| **Automatic** | 부모 인스턴스가 없으면 자동으로 부모를 생성(거의 미사용) |
| **Nullify** | 부모 인스턴스가 없으면 참조키를 NULL로 처리(선택 관계로 전환) |
| **Default** | 부모 인스턴스가 없으면 참조키를 사전 정의된 기본값으로 처리 |

### 삭제 규칙 (부모 엔터티 데이터 삭제 시) — 4종

| 규칙 | 설명 |
|------|------|
| **Restrict (기본 규칙)** | 참조하는 자식 인스턴스가 하나라도 있으면 부모 삭제·수정 불허 |
| **Cascade** | 부모 삭제 시 대응되는 자식도 자동으로 삭제(수정 시 FK도 함께 수정) |
| **Nullify** | 부모 삭제 시 자식의 참조키를 NULL로 처리 |
| **Default** | 부모 삭제 시 자식의 참조키를 기본값으로 처리 |

기본값 조합은 입력=Dependent, 삭제/수정=Restrict임을 반드시 기억한다.

## 4. 이력관리 정의

**이력 관리(History Management)** 는 데이터의 변경 내용을 시간 순으로 기록하여 과거 상태를 조회할 수 있게 하는 것이다. 모든 데이터에 일괄 적용하지 말고 비용(저장공간·설계복잡성·성능저하)과 편익(의사결정 지원·감사추적·복구능력)을 따져 **선별 적용**해야 한다.

### 4.0a 이력 관리 대상 선정 — 5대 요구사항 질문

① 변경 내역 감시("이전 값은 무엇이었고 언제 변경되었는가?"), ② 데이터의 시간적 변화("시간이 지나며 자연스럽게 변할 수 있는가?"), ③ 관계의 시간적 변화("담당자가 바뀌는 것처럼 관계가 변할 수 있는가?"), ④ As-of Query("과거 특정 시점 기준 상태를 조회해야 하는가?"), ⑤ 버전 보관("버전 자체를 보관·비교해야 하는가?").

### 4.0 이력 관리의 3가지 종류 (성격 × 시간 표현 2가지 방식)

"무엇을 기록하는가(성격)"와 "어떻게 시간을 표현하는가(형태)"의 매트릭스로 이해한다.

| 종류 | 설명 | 예시 |
|------|------|------|
| **발생 이력 데이터** | 데이터 발생 시마다 이력 기록 | 웹사이트 접속 기록, 로그 |
| **변경 이력 데이터** | 데이터 내용 변경 시마다 이력 기록 | 주문 정보 변경 이력 |
| **진행 이력 데이터** | 업무 진행 과정에 따라 이력 기록 | 주문 처리 진행 상황 |

### 4.1 이력 관리 방식

| 방식 | 설명 | 특징 |
|------|------|------|
| 선분 이력 | 시작일~종료일로 유효 기간(선분) 표현 | 기간 조회에 유리, 데이터량 적음 |
| 시점 이력 | 변경될 때마다 새 행으로 저장 | 변경 이력 추적에 유리, 데이터량 많음 |

**선분 이력 예시:**

```
고객ID | 등급 | 시작일     | 종료일
1001   | 일반 | 2024-01-01 | 2024-06-30
1001   | 우수 | 2024-07-01 | 9999-12-31 (현재)
```

**시점 이력 예시:**

```
고객ID | 등급 | 변경일시
1001   | 일반 | 2024-01-01 09:00:00
1001   | 우수 | 2024-07-01 14:30:00
```

> **트레이드오프**: 시점 이력은 입력(쓰기)이 단순(INSERT만) 하지만 조회(읽기)가 복잡(MAX() 서브쿼리 필요, 데이터가 늘수록 성능 저하). 선분 이력은 조회가 매우 효율적(BETWEEN, 인덱스 활용)이지만 입력 로직이 복잡(기존 레코드의 종료일자 마감 필요). 요약: **시점=쓰기 쉬움·읽기 어려움, 선분=읽기 쉬움·쓰기 어려움.**

### 4.1a 이력 설계 패턴 3종

| 패턴 | 설명 | 적합 |
|------|------|------|
| 인스턴스 레벨 | 속성 하나만 바뀌어도 레코드 전체를 새 이력으로 복사 | 스냅샷 조회 성능 최고, 저장 공간 낭비 심함 |
| 주제 레벨 | 연관성 높은 속성을 그룹으로 묶어 그룹 단위 스냅샷 저장 | 실무적 절충안 |
| 속성 레벨 | 변경된 속성 값만(개체ID·속성코드·속성값·변경시점) 기록 | 저장 효율 최고, 조회 로직 복잡(EAV 유사) |

### 4.1b 구현·성능 최적화 포인트

- **주식별자 설계**: 복합키(대상식별자+시작일자) vs 인조 식별자(단순 일련번호) — 조회 패턴과 함께 고려
- **종료일자 처리**: NULL 사용 vs 최댓값(9999-12-31) 사용 — 최댓값이 BETWEEN 조건·인덱스 활용에 유리
- **인덱스 전략**: 클러스터형 인덱스(물리 정렬), 현재 유효 건만 대상으로 하는 필터링 인덱스
- **SCD(Slowly Changing Dimension) 관리**: Type 2(이력 추적용 행 추가) / Type 4(현재 테이블은 최신만 유지, 이력은 별도 테이블로 분리)

### 4.1c Bitemporal 모델링 — 두 개의 시간 축

| 축 | 정의 | 예 |
|------|------|------|
| 유효 시간(Valid Time) | 현실 세계에서 사실이 유효한 기간(비즈니스 관점) | 2월 15일부로 급여 인상이 소급 확정 |
| 트랜잭션 시간(Transaction Time) | 그 사실이 DB에 기록되어 시스템이 인지한 기간 | 3월 15일에 담당자가 시스템에 등록 |

4개 타임스탬프(ValidFrom/To, TransactionFrom/To)로 구현하며, 물리적 UPDATE·DELETE 없이 INSERT와 TransactionTo 마감만으로 모든 변경을 불변의 기록(Immutable Log)으로 남긴다.

### 4.2 이력 관리 적용 기준

| 적용 기준 | 내용 |
|---------|------|
| 변경 빈도 | 자주 변경되는 중요 속성 |
| 조회 요건 | 과거 시점 데이터 조회 필요 |
| 감사 요건 | 데이터 변경 이력 감사 필요 |
| 법규 요건 | 데이터 보존 기간 법규 준수 |

## 5. 논리 데이터 모델 품질 검토

논리 모델 완성 후 품질 기준에 따라 검토한다.

### 5.1 데이터 모델 품질 6대 기준 ("정완준 최일활")

논리 모델 품질은 다음 6대 기준으로 검토한다 (물리 모델도 동일한 6기준을 대상만 바꾸어 적용 — 4과목 4장 참고).

| # | 기준 | 정의 |
|---|------|------|
| 1 | 정확성(Correctness) | 업무 규칙과 요구사항이 데이터 구조에 오류 없이 반영, 관계의 기수성·선택성이 실제 업무와 일치 |
| 2 | 완전성(Completeness) | 관리해야 할 데이터가 누락 없이 포함 — **동시에** 불필요한 요소가 없는가도 확인(완전성의 함정) |
| 3 | 준거성(Compliance) | 표준 단어·용어·도메인·명명 규칙 준수, 개인정보보호법 등 규제 요건 반영 |
| 4 | 최신성(Up-to-dateness) | '살아있는 문서'로서 현재 비즈니스 환경을 정확히 반영 |
| 5 | 일관성(Consistency) | 동일한 개념이 모델 전반에서 동일하게 표현됨 |
| 6 | 활용성(Usability & Flexibility) | 의사소통 도구로 충분한 설명·업무 규칙 기술, 안정성과 확장성 확보 |

> **주의**: 과거 "정확성·완전성·일관성·유연성·확장성·통합성"으로 암기하는 것은 오류다. 교재 기준 정식 6기준은 위 표의 "정확성·완전성·준거성·최신성·일관성·활용성"이다.

### 5.1a 품질검토 시점·관점·참여자

**검토 시점 4가지**: ① 주제영역별 초안 작성 후, ② 상세화 완료 후(가장 중요한 검토 시점), ③ 중요 변경 발생 시, ④ 물리 모델링 전환 직전(최종 검토).

**단계별 검토 관점 차이**: 개념=거시적 관계·핵심 주제영역/엔터티 식별 여부, 논리=업무 규칙이 데이터 구조에 정확·완전하게 표현되었는지, 물리=테이블·인덱스가 최적 설계되었는지.

**검토 참여자 역할**: 데이터 모델러/아키텍트(설계 의도 설명·기술적 무결성 책임), 현업 전문가(정확성·완전성의 최종 판단), DBA/개발자(구현 가능성·성능 조기 피드백).

### 5.2 논리 모델 검토 체크리스트

| 항목 | 확인 내용 |
|------|---------|
| 엔터티 | 엔터티명 명확성, 정의의 포함/제외 기준 명확화, 통합 수준 적절성, 서브타입 분류 기준의 배타성 |
| 속성 | 원자값 여부(1NF), 속성명이 의미를 정확히 설명, 도메인 정의 여부, 정규화로 중복·종속성 제거 |
| 식별자 | 유일성·최소성·불변성·존재성 만족, 인조 식별자 사용의 적절성 |
| 관계 | 업무 규칙과 일치, 카디널리티·참여도 정확, 참조 무결성 규칙이 업무 규칙에 근거 |
| 모델 전반 | 정규화 수행 여부(3NF 이상), M:N 관계가 모두 해소되었는가, 이력 관리 필요 엔터티 반영, 명명 규칙 준수 |

### 5.3 논리 모델 검토 방법

| 방법 | 설명 |
|------|------|
| 자동화 진단 | 데이터 모델 관리 도구를 통한 자동 오류 탐지 |
| 전문가 검토 | 데이터 아키텍트의 수동 검토 |
| 이해관계자 검토 | 현업 담당자와 함께 업무 일치성 확인 |

## 출제 포인트

1. **[중요/정정] 논리 모델 품질 6대 기준("정완준 최일활")**: 정확성(Correctness)·완전성(Completeness)·준거성(Compliance)·최신성(Up-to-dateness)·일관성(Consistency)·활용성(Usability & Flexibility) — "정확성·완전성·일관성·유연성·확장성·통합성"이 아님에 주의
2. **[중요/정정] 참조 무결성 입력 규칙은 4종**: Dependent(기본)·Automatic·Nullify·Default (6종 아님)
3. **[중요/정정] 참조 무결성 삭제 규칙은 4종**: Restrict(기본)·Cascade·Nullify·Default (6종 아님)
4. **[중요/정정] "시점 이력(Point-in-Time)"** — "점 이력"이 아닌 정식 용어. 시점=쓰기쉬움·읽기어려움, 선분=읽기쉬움·쓰기어려움
5. 속성 4대 본질 특징: 귀속성·집합성·관계의 이중성·독립성(이행적 종속 방지)
6. 속성 후보 6대 수집처, 후보 선정 2대 원칙(원시속성 보존/소그룹→엔터티 할당)
7. 도메인 = 데이터 품질의 첫 방어선(CHECK 제약 연계)
8. 식별자 확정 절차: 본질→후보→대체→인조, 후보 식별자 5조건(유일성·최소성·NULL불허·개념적유일성·변경최소)
9. 종속관계 2축: 절대종속/상대종속, 직접종속/간접종속
10. 정규화: 1NF(원자값)→2NF(부분종속제거)→3NF(이행종속제거)→BCNF(모든결정자=후보키)→**4NF(다가종속MVD 제거)**→**5NF(조인종속=후보키)**
11. 정규화 5대 장점(4번째: 요구사항 발견 및 업무규칙 명확화)
12. M:N 해소 이유 3가지(구현불가/속성표현한계/불완전성), 해소 절차 **5단계**(관계엔터티생성→1:M식별관계→복합식별자→관계고유속성추가→선택사양반영) — 4과목 1장의 개념적 4단계와는 상세도 차이
13. 이력관리 5대 요구질문(변경내역감시/시간적변화/관계의시간적변화/As-of Query/버전보관)
14. 이력 3유형(발생/변경/진행)×2형태(시점/선분) 매트릭스, 이력 설계 패턴 3종(인스턴스/주제/속성 레벨)
15. Bitemporal 모델링: 유효시간(Valid Time) vs 트랜잭션시간(Transaction Time), 4 timestamps
16. 슈퍼타입/서브타입: 공통 속성을 슈퍼타입에, 특수 속성을 서브타입에 / 배타적·포괄적 서브타입
17. 식별 관계: 부모 PK → 자식 PK 일부 구성 (실선) / 비식별 관계: 부모 PK → 자식 일반 FK (점선)
18. 품질검토 시점 4가지, 단계별 관점 차이(개념=거시적/논리=업무규칙표현/물리=최적화), 참여자 역할(모델러/현업/DBA)
19. 논리 모델 검토: 자동화 진단·전문가 검토·이해관계자 검토
