# 4과목 4장: 물리 데이터 모델링

## 1. 물리 데이터 모델링 이해

**물리 데이터 모델링(Physical Data Modeling)**은 논리 데이터 모델을 특정 DBMS에서 구현하기 위해 테이블, 컬럼, 인덱스, 파티션 등 물리적 요소를 설계하는 단계이다.

| 특징 | 설명 |
|------|------|
| 관점 | 데이터베이스 구현 관점 |
| DBMS 종속성 | 특정 DBMS에 최적화 |
| 성능 고려 | 인덱스·파티션 등으로 성능 최적화 |
| 대상 독자 | DBA, 개발자 |
| 산출물 | 테이블 명세서, DDL 스크립트 |

### 1.1 논리 vs 물리 모델 비교

| 구분 항목 | 논리 데이터 모델 | 물리 데이터 모델 |
|------|------|------|
| 핵심 목표 | 비즈니스 규칙·데이터 구조의 정확한 표현(정합성) | 성능 최적화 및 실제 시스템 구현 |
| 기본 관점 | 분석가·현업 전문가(Business-Centric) | 개발자·DBA(Technology-Centric) |
| 기술 종속성 | 기술 독립적 | 특정 DBMS·인프라에 종속적 |
| 주요 구성요소 | 엔터티·속성·관계·주/대체 식별자 | 테이블·칼럼·제약조건(PK/FK/UK/Check)·인덱스·뷰 |
| 표현 방식 | 비즈니스 용어, 정규화 원칙 엄격 준수 | DBMS 명명 규칙, 구체적 데이터 타입, 반정규화 |
| 추상화 수준 | 높음 | 낮음 |
| 주요 활동 | 정규화, 관계 정의, 엔터티 상세화 | 반정규화, 인덱스 설계, 파티셔닝, 데이터 타입 선정 |

물리 모델은 논리 모델을 '대체'하는 것이 아니라 '확장·구체화'한다 — 인덱스·파티셔닝·테이블스페이스 등은 논리 모델에 존재하지 않는 순수 물리 정보다.

### 1.2 물리적 스키마 구성 요소

**테이블 유형**

| 유형 | 특징 | 장/단점 |
|------|------|------|
| 힙 구성 테이블(Heap-Organized) | 입력 순서대로 정렬 없이 저장되는 일반적 형태 | 삽입 빠름 / 전체 스캔 필요할 수 있음 |
| 클러스터 인덱스 테이블(Index-Organized) | PK 등 인덱스 키 순서로 데이터 행 자체가 물리적으로 정렬 | 범위 조회 성능 뛰어남 / DML 시 재정렬 부하 |
| 파티션 테이블(Partitioned) | 날짜·지역 등 기준으로 여러 파티션으로 분할 저장 | 관리 용이성·쿼리 성능 개선 / 파티션 키 미사용 시 전체 스캔 |

**테이블스페이스(Tablespace)**: 하나 이상의 물리적 데이터 파일과 연결되어 논리적 설계와 물리적 저장을 분리하는 전략적 저장 단위. 테이블·인덱스 데이터를 서로 다른 디스크에 배치하면 디스크 경합이 줄고, 업무별 테이블스페이스 분리로 백업·복구 범위를 국한할 수 있다.

## 2. 물리 요소 조사 및 분석

논리 모델을 물리 모델로 변환하기 전, 물리적 환경을 분석하는 단계이다.

### 2.0 물리 데이터 모델링 전 조사 항목

실제 모델링 수행 전 반드시 조사해야 하는 사항:

1. 시스템 구축 관련 **명명 규칙**
2. 운영체제 및 DBMS 버전
3. **하드웨어 자원**: CPU, 메모리, 디스크, I/O 컨트롤러, 네트워크
4. DBMS 파라미터 정보
5. 데이터베이스 운영 관련 관리 요소 (사용자 관리, 백업, 복구, 보안)

### 2.1 DBMS 특성 분석

| 분석 항목 | 내용 |
|---------|------|
| DBMS 종류 | Oracle, MySQL, SQL Server 등 |
| 지원 데이터 타입 | VARCHAR2, NUMBER 등 DBMS별 타입 |
| 최대 컬럼 수 | DBMS별 테이블 최대 컬럼 수 제한 |
| 인덱스 지원 | 클러스터드, 논클러스터드, 비트맵 등 |
| 파티셔닝 지원 | 범위, 해시, 리스트 파티션 등 |

### 2.2 데이터 볼륨 분석

| 분석 항목 | 내용 |
|---------|------|
| 테이블별 행 수 | 현재 및 예상 데이터 건수 |
| 연간 증가율 | 데이터 증가 속도 예측 |
| 데이터 크기 | 테이블별 예상 저장 용량 |
| 조회 패턴 | 자주 실행되는 쿼리 유형 및 빈도 |

### 2.3 성능 요건 분석

| 요건 | 내용 |
|------|------|
| 응답 시간 | 쿼리별 허용 응답 시간 목표 |
| 처리량 | 동시 처리 가능한 트랜잭션 수 |
| 가용성 | 시스템 가동 시간 목표(99.9% 등) |

### 2.4 명명 규칙 3계층

| 계층 | 정의 | 예 |
|------|------|------|
| ① 표준 단어(Standard Word) | 최소 의미 단위, 업무 개념을 승인된 영문 약어로 매핑(동의어 통제) | 고객 → CUST |
| ② 표준 용어(Standard Term) | 표준 단어를 조합해 엔터티·속성 이름 생성(Self-describing) | 고객(CUST)+번호(NO) → CUST_NO |
| ③ 도메인(Domain) | 속성의 값 범위·타입·길이·NULL 허용 여부 정의(구조적 일관성 강제) | 고객번호는 어디서든 동일 타입·길이 |

**명명 패턴 예시**: 테이블은 [업무영역]_[주제어]_[분류어](예: SLS_ORD_HDR), 컬럼은 표준 용어 그대로(CUST_NO), 기본키는 [테이블명]_PK, 외래키는 [자식]_[부모][FK번호]. 표준 준수 여부를 자동 검증·영향도 분석하는 근거가 **데이터 용어 사전**이다.

### 2.5 하드웨어 성능 지표와 임계값

**높은 CPU 사용률은 원인이 아니라 증상일 수 있다** — 메모리·I/O를 먼저 확인한다.

| 자원 | 지표 | 임계값 |
|------|------|------|
| CPU | 전체 사용률 | 80~85% 지속 초과 → 병목 신호 |
| | 프로세서 대기열 | 코어 수의 2배 지속 초과 → CPU 모자람 |
| | %iowait | 20% 이상 → 디스크가 발목 잡는 CPU 병목 |
| 메모리 | Pages/sec | 초당 50회 초과 → 심각한 메모리 부족 |
| | Page Life Expectancy | 300초 미만 → 캐시 체류 시간 부족 |
| | Buffer Cache Hit Ratio | OLTP 95% 이상(이상적으로 99%+) |
| | swap in/out | DB 서버는 항상 0이어야 함 |
| 디스크 | Latency | OLTP 고성능 스토리지 10ms 미만, 20ms 초과 시 병목 |
| | %util | 80% 초과해 100% 근접 시 포화 |
| | 대기열 길이 | 스핀들 수의 2배 지속 초과 → 처리 지연 |

**"캐시 친화적" 설계**: 부적절한 인덱스로 인한 비효율적 쿼리 계획이 수백만 페이지를 읽어 CPU를 소모시키는 경우가 많다 — "CPU는 증상이지 원인이 아니다." 테이블 폭을 좁게 설계(Narrow Table)하고 선택도 높은 인덱스로 핵심 데이터가 메모리에 오래 머물게 한다.

## 3. 논리-물리 모델 변환

논리 ERD를 물리 테이블 구조로 변환하는 단계이다.

### 3.0 변환의 트릴레마 — 무결성·성능·확장성

기계적 치환이 아니라 상충하는 목표 사이에서 균형점을 찾는 의사결정 활동이다.

| 목표 | 설명 |
|------|------|
| 무결성(Integrity) | 반정규화로 계산된 컬럼을 추가했다면, 원본 변경 시 일관되게 갱신되는 동기화 메커니즘(트리거·애플리케이션 로직)을 반드시 함께 설계 — 동기화 설계 누락이 가장 흔한 사고 원인 |
| 성능(Performance) | 데이터 접근 경로 최소화·디스크 I/O 감소, 예상 데이터량·트랜잭션 부하 분석에 근거 |
| 확장성(Scalability) | 코드성 데이터를 별도 테이블로 분리해 신규 코드 추가 시 프로그램 수정 없이 데이터 추가만으로 대응 |

### 3.1 기본 변환 규칙

| 논리 모델 요소 | 물리 모델 요소 |
|------------|------------|
| 엔터티 | 테이블(Table) |
| 속성 | 컬럼(Column) |
| 기본 키(PK) | Primary Key 제약 |
| 보조 식별자(Alternate UID) | Unique Key 제약 |
| 외래 키(FK) | Foreign Key 제약 |
| 도메인 | 데이터 타입·길이·NOT NULL |
| 업무 제약(Business Constraints) | Check 제약 조건 |

### 3.2 테이블 설계 원칙

| 원칙 | 내용 |
|------|------|
| 컬럼 순서 | PK → 자주 사용하는 컬럼 → 나머지 |
| 이름 규칙 | 언더스코어 구분, 대문자 또는 소문자 일관성 |
| NOT NULL 최소화 | 필수 속성만 NOT NULL 지정 |

### 3.3 슈퍼타입/서브타입 변환 3전략 (교재 용어)

| 전략 | 방식 | 적합한 상황 | 단점 |
|------|------|------|------|
| ① 슈퍼타입 기준 통합(Single Table) | 슈퍼+서브를 하나의 테이블로 합치고 구분 컬럼(타입 코드) 추가 | 전체 통합 조회가 많고 고유 속성이 적을 때 | 고유 컬럼에 NULL 다수 발생(데이터 희소성) |
| ② 서브타입 기준 분할(Table per Subtype, "롤다운") | 각 서브타입을 별도 테이블로, 공통 속성도 각각 포함 | 서브타입별 접근이 빈번하고 고유 속성이 많을 때 | 전체 조회 시 UNION 필요 |
| ③ 개별 타입 기준 변환(Table per Type) | 슈퍼타입·서브타입을 모두 개별 테이블로 만들고 1:1 연결 | 전체 처리와 개별 처리가 모두 빈번할 때 | 조인이 항상 필요 |

> 기존에 통용되던 "One Table / One Per Type / Concrete Table" 명칭은 위 ①②③ 교재 용어에 각각 대응한다.

### 3.4 M:N 관계 변환

M:N 관계는 연결 테이블(교차 테이블)로 구현:

```sql
CREATE TABLE 수강 (
  학생ID   VARCHAR2(10) NOT NULL,
  강좌ID   VARCHAR2(10) NOT NULL,
  수강일자  DATE,
  PRIMARY KEY (학생ID, 강좌ID),
  FOREIGN KEY (학생ID) REFERENCES 학생(학생ID),
  FOREIGN KEY (강좌ID) REFERENCES 강좌(강좌ID)
);
```

### 3.5 무결성 제약 설계

| 제약 유형 | 설명 | SQL |
|---------|------|-----|
| 도메인 무결성 | 컬럼 값의 형식·범위 | CHECK 제약 |
| 개체 무결성 | PK는 NULL 불가·유일 | PRIMARY KEY |
| 참조 무결성 | FK 값은 부모 PK에 존재 | FOREIGN KEY |

### 3.6 데이터 타입 선택

**CHAR vs VARCHAR**: CHAR는 선언 길이만큼 고정 공간을 사용 — 주민번호·코드값처럼 길이가 고정된 데이터에 적합하고 파편화 방지에 유리. VARCHAR는 실제 데이터 길이만큼만 사용해 저장 효율적이나, 수정으로 길이가 변하면 **로우 마이그레이션(Row Migration)** 이 발생해 추가 I/O를 유발한다. 저장 효율뿐 아니라 수정 빈도도 함께 고려해야 한다.

> **[중요] 금융 데이터는 FLOAT/DOUBLE 금지**: 부동소수점형은 이진법 표현으로 정확한 십진수 계산에 오차가 발생한다. 금융(금액) 데이터에는 반드시 **DECIMAL/NUMERIC**을 사용해야 한다.

## 4. 반정규화(De-normalization)

정규화로 분리된 구조를 의도적으로 합치거나 중복을 허용하여 **조회 성능을 향상**시키는 기법.

### 4.0 반정규화 ≠ 비정규화, 부하의 이전

**반정규화(Denormalization)는 정규화를 전혀 하지 않은 '비정규화'와 다르다.** 반드시 잘 정립된 정규화 모델에서 출발해, 성능 저하가 예상되는 지점에 한정해 통제된 중복을 허용하는 최적화 전략이다. 정규화 없이 무분별하게 중복시키는 것은 그냥 잘못된 설계다.

정규화 모델에서는 여러 테이블에 나뉜 데이터를 조합·계산하는 작업이 모두 **조회 시점(Read Time)** 에 집중된다. 반정규화는 이 부하를 **조회 시점에서 입력·수정 시점으로 이전**시키는 전략이다 — 조회는 준비된 데이터를 읽기만 하면 되므로 빨라지고, 대신 입력·수정·삭제 시 중복 데이터의 일관성 유지 작업이 필요해 쓰기 성능은 저하된다.

| 관점 | 정규화(Normalization) | 반정규화(Denormalization) |
|------|------|------|
| 목표 | 데이터 일관성·무결성 확보, 중복 최소화 | 조회(Read) 성능 향상, 쿼리 단순화 |
| 데이터 중복성 | 최소화 | 의도적 허용 |
| 데이터 무결성 | 높음 | 저하 위험 존재 |
| 조회 성능 | 조인이 많으면 저하될 수 있음 | 빠름 |
| 입력/수정/삭제 | 빠름 | 중복 데이터 관리로 저하될 수 있음 |
| 사용 사례 | OLTP 시스템 | OLAP 시스템, 데이터 웨어하우스, 보고·통계 |

### 4.1 반정규화 적용 시점 / 효과적인 상황

**기존 적용 시점 기준**

| 기준 | 내용 |
|------|------|
| 조회 빈도 | 특정 JOIN이 매우 빈번하게 발생 |
| 성능 한계 | 정규화 상태에서 응답 시간 목표 미달성 |
| 데이터 안정성 | 참조 테이블 데이터가 거의 변경 안 됨 |

**반정규화가 효과적인 4가지 상황**: ① 과도한 조인으로 인한 성능 저하, ② 대용량 데이터 처리(대량 범위 조회·집계 쿼리 빈번), ③ 디스크 I/O 과부하, ④ 실시간 계산 부하(SUM·COUNT·AVG 등을 조회 시점에 반복 수행).

### 4.1a 왜 성능이 향상되는가 — I/O와 잠금의 원리

데이터는 8KB/16KB 고정 페이지 단위로 읽고 쓰이며, 버퍼 캐시에 재사용되면 캐시 히트로 빠르다. 반정규화는 관련 데이터를 물리적으로 같은/인접 페이지에 위치시켜(**데이터 지역성**) I/O를 최소화한다.

대규모 UPDATE·DELETE로 다수의 행 잠금이 페이지·테이블 잠금으로 자동 전환되는 것을 **잠금 에스컬레이션(Lock Escalation)** 이라 하며, 테이블 전체가 잠기면 무관한 트랜잭션까지 대기하는 심각한 블로킹이 발생한다. 자주 갱신되는 '동적(Hot)' 컬럼과 거의 변하지 않는 '정적(Cold)' 컬럼을 수직 분할로 분리하면 업데이트가 작은 테이블에만 국한된다 — 즉 **수직분할의 동기는 조인 감소가 아니라 동시성 보장**이다.

### 4.2 관점별 반정규화 기법 (테이블·컬럼·관계 관점)

| 관점 | 기법 | 설명 | 예시 |
|------|------|------|------|
| 테이블 | ① 테이블 병합 | 자주 JOIN되는 두 테이블을 하나로 합침(슈퍼/서브타입 통합 포함) | 주문+주문상세 병합 |
| 테이블 | ② 테이블 분할 | 수평 분할(행 기준)/수직 분할(컬럼 기준) | 연도별 거래 이력 분리, 기본정보·상세정보 분리 |
| 테이블 | ③ 테이블 추가(중복 테이블) | 집계/이력/부분 테이블을 새로 만들어 부하 분산 | 일별 매출 요약(집계) 테이블, 진행 테이블 |
| 컬럼 | ④ 중복 컬럼 추가 | 자주 JOIN해서 가져오는 컬럼을 현재 테이블에 추가 | 주문 테이블에 고객명 추가 |
| 컬럼 | ⑤ 파생/계산 컬럼 추가 | 집계 결과를 별도 컬럼으로 미리 계산 저장 | 주문항목 총액(수량×단가), 게시글 댓글수 |
| 관계 | ⑥ **중복 관계 추가** | 여러 단계를 거쳐야 도달하는 테이블 사이에 직접 관계(FK)를 추가해 조인 경로 단축 | 조인 경로 단축, 단 무결성 관리 부담 증가 |

> 6가지 기법의 공통 단점은 **데이터 불일치 위험**과 **쓰기 성능 저하**다. 중복 테이블은 인덱스 조정·클러스터링으로 해결 불가할 때 **최후의 방법**으로 사용한다.

### 4.3 반정규화 적용 절차 5단계 — "반정규화는 최후의 수단"

| 단계 | 내용 |
|------|------|
| 1. 성능 병목 지점 식별 | 추측이 아니라 측정(느린 쿼리 로그·모니터링)으로 특정 |
| 2. 실행 계획 분석 | 옵티마이저 실행 계획에서 Full Scan·비효율적 조인 순서 등 근본 원인 파악 |
| 3. 비침습적 최적화 우선 | 인덱스 튜닝, 쿼리 재작성, 커버링 인덱스 활용 — 실무는 대부분 이 단계에서 해결 |
| 4. DBMS 기능 활용 검토 | 물리적 파티셔닝, 클러스터링 등 검토 |
| 5. 반정규화 고려 및 기법 선택 | 위 대안이 부족할 때 비로소 최소한의 기법 선택·적용 |

### 4.4 과도한 반정규화의 함정과 문제점

| 문제점 | 설명 |
|--------|------|
| 유연성 저하 | 특정 조회 패턴에 과최적화되어 새 요구사항 변화에 대응하기 어려운 경직 구조 |
| 의미론적 무결성 훼손 | 중복 칼럼은 FK 제약의 보호를 받지 못해 모델의 업무 의미가 흐려짐 |
| 유지보수 복잡성 | 동기화 로직·트리거·배치의 복잡도 증가, 버그 시 데이터 신뢰성 붕괴 |
| 데이터 중복·수정삭제 이상 | 중복 데이터 동기화 필요, 이상 현상 재발 가능 |

### 4.5 반정규화 5대 핵심 원칙

① 정규화 먼저(Normalize First), ② 측정하고 증명하라(Measure, Don't Guess), ③ 대안 먼저 검토(Consider Alternatives), ④ 일관성 유지 전략 수립(항상 동기화 메커니즘 준비), ⑤ 모든 결정을 문서화(Document Everything) — 근거 기록이 없으면 후임자가 설계 오류로 오해할 수 있다.

## 5. 물리 데이터 모델 품질 검토

### 5.0 물리 데이터 모델 품질 6대 기준 ("정완준 최일활")

논리 모델(4과목 3장)과 **동일한 6대 기준**을 물리 개체에 적용한다.

| # | 기준 | 물리 모델에서의 검증 대상 |
|---|------|------|
| 1 | 정확성(Correctness) | PK·FK·CHECK 제약조건이 논리 모델의 업무 규칙을 정확히 강제하는가 |
| 2 | 완전성(Completeness) | 테이블·칼럼·인덱스·제약조건·코멘트가 누락 없이 정의되었는가 |
| 3 | 준거성(Compliance) | 표준 단어·용어·도메인·명명 규칙 준수, 개인정보 암호화 등 법적 요건 반영 |
| 4 | 최신성(Up-to-dateness) | 논리 모델 변경이 물리 모델에 반영되고 실제 운영 DB와 일치하는가 |
| 5 | 일관성(Consistency) | 유사한 상황에 동일한 설계 패턴(데이터 타입·인덱스 전략)이 적용되는가 |
| 6 | 활용성(Usability & Flexibility) | 사용 편의성·유연성·성능이 적합하고, 반정규화가 근거를 갖고 문서화되었는가 |

> 4과목 3장(논리 모델 품질)과 반드시 동일한 6개 축("정확성·완전성·준거성·최신성·일관성·활용성")이며, 차이는 검증 대상이 물리 개체(테이블·인덱스·제약조건)라는 점뿐이다. 아래 5.1~5.3의 체크리스트는 이 6대 기준의 세부 하위 항목이다.

### 5.1 인덱스(Index) 설계

| 구분 | 설명 |
|------|------|
| 클러스터드 인덱스 | 데이터가 인덱스 순서로 물리적 정렬 (테이블당 1개) |
| 논클러스터드 인덱스 | 별도 인덱스 구조로 데이터 위치 참조 (여러 개 가능) |
| 복합 인덱스 | 두 개 이상 컬럼으로 구성된 인덱스 |

**인덱스 설계 원칙:**

| 원칙 | 내용 |
|------|------|
| 분포도 높은 컬럼 우선 | 중복이 적은(선택성 높은) 컬럼 |
| WHERE 절 조건 컬럼 | 자주 검색 조건으로 사용되는 컬럼 |
| JOIN 컬럼 | 자주 JOIN에 사용되는 컬럼 |
| DML 부하 고려 | 인덱스가 많을수록 DML 성능 저하 |

### 5.2 파티셔닝(Partitioning) 설계

대용량 테이블을 관리 용이성과 성능 향상을 위해 물리적으로 분할.

| 파티션 유형 | 기준 | 예시 |
|---------|------|------|
| 범위(Range) | 값의 범위 | 날짜별 거래 이력 |
| 해시(Hash) | 해시 함수 결과 | 균등 분산 |
| 리스트(List) | 특정 값 목록 | 지역코드별 |
| 복합(Composite) | 두 기준 조합 | 날짜+해시 |

**파티션 프루닝(Partition Pruning)**: 쿼리 조건이 파티션 키와 일치할 때 해당 파티션만 스캔하여 성능 향상.

### 5.3 물리 모델 품질 검토 항목

| 검토 항목 | 내용 |
|---------|------|
| 테이블명·컬럼명 | 명명 규칙 준수 |
| 데이터 타입 | 업무 요건·도메인과 일치 |
| 인덱스 설계 | 조회 성능 요건 충족 |
| 반정규화 영향 | 무결성 관리 방안 마련 |
| 파티셔닝 적용 | 대용량 테이블 적절한 파티셔닝 |
| DDL 문법 | DBMS 문법·제약 준수 |

### 5.4 품질검토 프로세스 3단계와 상세 체크리스트

**프로세스 3단계**: ① 준비(체크리스트·모델 산출물 사전 배포), ② 수행(체크리스트 기반 검토 → 이슈 식별·토의 → 상충 요구사항 의사결정), ③ 후속 조치(검토 결과 보고서 작성 → 이슈 추적·해결 → 최종 모델 확정·공표).

**3영역 상세 체크리스트**

| 영역 | 점검 항목 |
|------|------|
| 테이블·칼럼 | 명칭이 명명 규칙·표준 용어를 준수하는가, 테이블/칼럼 설명(Comment)이 기술되었는가, 서브타입 변환 전략 선택 근거가 타당한가, 데이터 타입·길이가 도메인 정의를 따르는가 |
| 키·제약조건 | PK가 유일성·최소성·안정성을 만족하는가, UK가 대체 식별자에 정의되었는가, FK가 모든 관계에 정의되고 참조 행위 옵션이 업무 규칙에 부합하는가, CHECK 제약으로 도메인 규칙이 강제되는가 |
| 성능·확장성 | 반정규화의 정당성·트레이드오프가 문서화되었는가, 인덱스가 실제 조회 패턴에 근거해 설계되었는가, 대용량 테이블의 파티셔닝 전략이 수립되었는가 |

## 출제 포인트

1. **[중요/정정] 물리 모델 품질 6대 기준("정완준 최일활")**: 정확성·완전성·준거성·최신성·일관성·활용성 — 논리 모델(4과목 3장)과 **동일한 6개 축**, 검증 대상만 물리 개체로 다름
2. **[중요/정정] 서브타입 변환 3전략(교재 용어)**: ①슈퍼타입 기준 통합(Single Table, 구舊 "One Table") ②서브타입 기준 분할(Table per Subtype/"롤다운", 구 "One Per Type") ③개별 타입 기준 변환(Table per Type, 구 "Concrete Table")
3. 논리 vs 물리 모델 비교: 목표(정합성 vs 성능)·관점(Business-Centric vs Technology-Centric)·기술종속성
4. 물리적 스키마: 힙 구성 테이블·클러스터 인덱스 테이블·파티션 테이블, 테이블스페이스(물리적 구획화)
5. 명명 규칙 3계층: 표준 단어→표준 용어→도메인(구조적 일관성 강제)
6. 하드웨어 지표 임계값: CPU 80~85%, %iowait 20%↑, Buffer Cache Hit Ratio 95%↑, 디스크 Latency 10ms 미만(OLTP)
7. "CPU는 증상이지 원인이 아니다" — 인덱스 부재가 근본 원인일 수 있음, 캐시 친화적/Narrow Table 설계
8. 변환의 트릴레마: 무결성·성능·확장성의 균형(계산 컬럼 동기화 메커니즘 필요, 코드성 데이터 분리로 확장성 확보)
9. 논리→물리 변환: 엔터티→테이블, 속성→컬럼, PK/FK→제약
10. CHAR(고정길이) vs VARCHAR(가변길이, 로우 마이그레이션 위험) 선택 기준
11. **[중요] 금융 데이터는 FLOAT/DOUBLE 금지, DECIMAL/NUMERIC 사용** (정밀도 손실 방지)
12. 데이터 페이지/버퍼 캐시, 잠금 에스컬레이션(Lock Escalation), 수직분할의 동기는 조인감소가 아니라 동시성 보장
13. 반정규화 ≠ 비정규화 — 정규화된 모델에서 출발한 통제된 중복만 반정규화. 부하를 조회 시점에서 입력/수정 시점으로 이전
14. 정규화 vs 반정규화 비교: 목표·중복성·무결성·조회성능·입출력성능·OLTP(정규화) vs OLAP(반정규화)
15. 반정규화 효과적 4상황: 과도한조인·대용량데이터·디스크I/O과부하·실시간계산부하
16. 반정규화 3관점 6기법: 테이블(병합/분할/추가) · 컬럼(중복컬럼/파생컬럼) · 관계(**중복 관계 추가**)
17. 반정규화 적용 절차 5단계: 병목식별→실행계획분석→비침습적최적화우선→DBMS기능검토→반정규화(최후수단)
18. 과도한 반정규화 함정: 유연성저하·의미론적무결성훼손·유지보수복잡성
19. 반정규화 5대 원칙: 정규화먼저·측정하고증명·대안먼저검토·일관성유지전략·문서화
20. 인덱스 설계: 분포도 높은 컬럼·WHERE 조건·JOIN 컬럼 우선 / 클러스터드 인덱스는 테이블당 1개
21. 파티션 프루닝: 쿼리 조건과 파티션 키 일치 시 해당 파티션만 스캔 / 범위·해시·리스트·복합 파티션
22. 품질검토 프로세스 3단계(준비/수행/후속조치), 3영역 체크리스트(테이블·칼럼/키·제약조건/성능·확장성)
