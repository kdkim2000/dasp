> 정의와 범위 · 5대 도메인과 추적성 · 프레임워크와 참조모델 · EA 프로세스

## 0. 강의 도입 — 문제 제기(수강 신청 사례)

대학 수강 신청 때 대규모 접속과 시스템 마비 현상은 흔히 겪는 문제다. IT 담당자가 "서버 용량을 늘리면 해결된다"고 답하는 것은 잘못된 접근일 수 있다. 시스템 부하의 근본 원인은 서버 성능 부족이 아니라 다음과 같은 다양한 요인일 수 있다: ① 수강 신청을 처리하는 업무 프로세스의 비효율성, ② 학생·과목·수강신청 등 데이터 구조상의 문제, ③ 부서별로 제각각 구축되어 애플리케이션 간에 발생하는 시스템 병목, ④ 취약한 보안 정책.

결론적으로, 조직의 정보와 자원을 개별 시스템 단위로 나눠서 보지 않고 업무·데이터·애플리케이션·기술·보안 전체를 아우르는 하나의 거대한 유기체로 통합하여 거시적 관점에서 설계·통제하는 방법론 — 이것이 **EA(전사 아키텍처, Enterprise Architecture)**다.

### 이번 챕터에서 반드시 정복해야 할 4가지 핵심 질문

1. EA의 본질적인 정의와 역할은 무엇인가?
2. 조직에서 전사(Enterprise)의 경계와 범위를 설정하는 기준은 무엇인가?
3. 비즈니스·데이터·애플리케이션·기술·보안이라는 5대 도메인은 어떻게 톱니바퀴처럼 맞물려 돌아가는가?
4. 이 복잡한 청사진을 미완성이 아니라 지속적으로 관리 가능하게 해주는 체계는 무엇인가?

## SECTION 1. 전사 아키텍처 정의

### 1.1 EA는 조직의 '청사진'이다 — 전략과 IT 구현 사이의 교량

교과서적 정의로 EA는 **조직의 전략과 IT를 일치**시키고 **조직 자원의 최적화**를 달성하기 위한 전사적인 설계 동인(틀)으로 정의된다. 조금 더 풀어 쓰면, "조직의 비전과 전략을 달성하기 위해 비즈니스·데이터·애플리케이션·기술·보안 도메인을 통합 설계하고, 상호관계를 관리하며, 환경 변화 속에서 일관성을 유지·통제하는 거버넌스 활동과 그 결과물의 총체"다. 단일 정의로 요약되기보다 여러 층위를 함께 봐야 하는 다차원 개념이다.

**실무적 압축 — 3대 핵심 동사**

| 핵심 동사 | 의미 |
|---|---|
| 통합 설계 | 5개 도메인을 하나의 구조로 묶어 설계 |
| 관계 관리 | 도메인 간 상호관계를 체계화 |
| 일관성 통제(거버넌스) | 변화 속에서 표준·원칙을 일관되게 유지·통제 |

**왜 지금 EA인가**: 디지털 전환, 클라우드 네이티브, 생성형 AI가 동시에 도래하는 지금 시점에, 현재 상태(As-Is)를 객관적으로 진단하고 목표 상태(To-Be)를 설계하며 그 간극(Gap)을 메우는 이행계획(Roadmap)을 수립하는 전 과정을 EA가 포괄한다. 민첩성 확보, IT 투자 효율 극대화, 운영 리스크 선제 최소화가 EA가 답하려는 과제다.

### 1.2 도시 계획 비유

아무리 개별 건물을 세계 최고 수준으로 지어도, 건물과 건물을 잇는 도로가 끊겨 있거나 상하수도·전력망이 유기적으로 연결되지 않으면 도시는 기능을 상실한다. 기업·공공기관의 정보 시스템도 마찬가지다. EA는 개별 건물(시스템) 설계가 아니라 도로망·용도지역·개발순서를 정하는 '도시 마스터플랜'에 해당한다.

### 1.3 As-Is / To-Be / 로드맵

As-Is는 현재 아키텍처를 진단하는 것, To-Be는 조직이 지향해야 할 미래 목표 상태를 정의하는 것, 로드맵은 As-Is와 To-Be 사이의 격차를 메우기 위한 이행 계획을 체계적으로 수립하는 활동이다. 이 As-Is 진단 → To-Be 정의 → 로드맵 수립 활동 자체가 EA의 본질이다. 즉 EA는 단순한 IT 기술 문서가 아니라, 경영 전략을 실제 시스템 구현까지 연결시켜주는 전사적인 청사진이다.

## SECTION 1-1. EA를 이해하는 공식 — RMP(규칙·모델·계획)

가장 체계적으로 EA를 이해·기억하는 공식은 **RMP**, 즉 규칙(Rule), 모델(Model), 계획(Plan)이다. "규칙이라는 원칙 아래 모델이라는 청사진을 그리고, 이를 현실로 만드는 계획을 세운다"는 흐름으로 이해하면 된다.

| 관점 | 정의 | 세부 내용/예시 |
|---|---|---|
| R — 규칙(Rule) | 조직이 IT 의사결정을 내릴 때 반드시 준수해야 하는 원칙과 기준의 집합. 조직의 헌법·법률에 해당하며, 중복투자·데이터 사일로·연동 불가를 원천 차단 | EA 원칙, 기술표준(개발언어·DBMS), 보안정책, 데이터 명명규칙. 예: "클라우드 우선(Cloud-First)" |
| M — 모델(Model) | 현행(As-Is)과 목표(To-Be)를 정형화된 표기법으로 구조화한 시각적 청사진 | BPMN, ERD, 구성도, 네트워크 토폴로지 — 공통 이해와 소통의 기반, 문제점 분석·개선효과 예측의 기초자료 |
| P — 계획(Plan) | 현행에서 목표로 가기 위한 실행 가능한 이행계획 | Gap 분석 → 과제 도출 → 우선순위, 프로젝트를 프로그램으로 묶어 관리, 단계별 전환 아키텍처를 명확히 정의 |

**계획(Plan) 관점 3단계 예시**: 1단계 전사 데이터 표준 수립·데이터 거버넌스 확립 → 2단계 노후 기간계 시스템의 MSA 기반 차세대 전환 → 3단계 클라우드 기반 데이터 분석 플랫폼 구축.

부서별로 제각각 시스템을 구축하면 얼마나 무질서해질지 생각해보면, 규칙이 이런 문제를 방지해준다는 것을 알 수 있다. 요약하면 **규칙은 기준, 모델은 그림, 계획은 그에 이르는 길**이며, 이 세 가지 축이 결합해 EA를 현실로 만든다.

## SECTION 1-2. 전사(Enterprise)의 범위와 EA 5대 도메인

### 1) '전사'의 범위를 어떻게 정할 것인가

EA에서 다루는 "전사"는 무조건 기업의 법인 전체를 의미하는 것이 아니다. "전사"는 물리적인 회사 전체라기보다는, **동일한 의사결정 권한과 통합된 자원 관리가 적용되는 비즈니스·IT의 경계**를 뜻한다. 범위 설정의 실질 기준은 **의사결정의 경계 + 자원 관리의 경계**다.

**범위 판단을 위한 4가지 실질 기준**

| # | 기준 | 판단 질문 | 연결 개념 |
|---|---|---|---|
| 1 | 지배구조(Governance) | EA 원칙·표준·예외처리를 일관되게 강제할 단일 의사결정 기구(ARB)가 있는가? | CIO/ARB 통제 범위와 일치 |
| 2 | 예산·투자(Budget) | IT 투자예산을 통합 기획하고 부서 간 중복투자를 통제하는 주체가 명확한가? | IT 포트폴리오 관리(PPM) 대상 범위 |
| 3 | 데이터 공유(Data) | 고객·제품·직원 등 핵심 마스터 데이터를 공동으로 정의·소유·책임지는가? | 데이터 거버넌스 적용 경계 |
| 4 | IT 관리(IT Mgt.) | 인프라·공통 플랫폼·보안정책·운영표준을 공통으로 적용·관리하는가? | ITSM 및 CMDB 적용 범위 |

**판단 원칙**: 위 네 질문에 모두 '그렇다'고 답할 수 있는 가장 큰 조직 단위가 전사의 범위다. 너무 넓게 잡으면 관리가 불가능해지고 정보의 깊이가 저하되며, 너무 좁게 잡으면 전사 최적화에 실패한다. 예를 들어 이질적인 사업의 계열사는 각각을 '전사'로, 동일 CEO·공통 IT 정책을 쓰는 국내외 사업부는 기업 전체를 '전사'로 설정한다.

**구체적 예시**: 대학교 전체가 동일한 정보화 편성과 단일 학사 데이터 정책을 공유한다면 대학 전체가 하나의 "전사"다. 반면 대학 내 부속 병원이나 독립 법인 형태의 연구소가 예산·시스템·데이터를 완전히 독립적으로 운영하고 있다면, 별도의 전사 아키텍처 영역으로 분리해 관리하는 것이 타당하다.

### 2) EA 5대 도메인의 계층 구조

전통적 4개 도메인(BA·DA·AA·TA) + 보안(SA) 구조이며, 보안은 전 계층을 관통하는 보호막으로 별도 분리·관리한다. 조직 분석을 위해 EA는 다섯 가지 핵심 도메인으로 나눈다.

| 도메인 | 약어 | 내용 | 수강 신청 사례 |
|---|---|---|---|
| 비즈니스 아키텍처 | BA | 전략·목표·프로세스 — 모든 아키텍처의 출발점 | 누가, 언제, 어떤 목적과 규정에 따라 수강 신청 업무를 수행하는가 — 업무 프로세스와 조직 정책의 영역 |
| 데이터 아키텍처 | DA | 원칙·모델·거버넌스 | 학생·과목·성적 등 데이터의 정의·구조와 데이터 간 상호 관계 설계 |
| 애플리케이션 아키텍처 | AA | 포트폴리오·컴포넌트·인터페이스 | 수강 신청 포탈, 학사 관리 시스템 등 실제 업무를 처리하는 소프트웨어 응용 프로그램과 이들 간의 인터페이스 정의 |
| 기술 아키텍처 | TA | 플랫폼·네트워크·표준기술(TRM) — 안정적 구동 기반 | 애플리케이션이 구동되는 서버, DBMS, 네트워크, OS, 클라우드 인프라 등 기반 구축 |
| 보안 아키텍처 | SA | 접근통제·암호·개인정보·위협모델 — 전 계층 관통 | BA·DA·AA·TA 모든 도메인을 관통해 사용자 인증, 권한 통제, 개인정보 암호화 및 재해복구 체계를 수립 |

**읽는 법**: 위→아래로 전략이 정보시스템으로, 다시 인프라로 구체화된다. DA↔AA는 요구사항을 정보시스템으로 함께 구체화한다. SA는 전체를 감싸는 보호막(Security by Design)이다. 양방향 화살표는 추적성(Traceability)을 의미한다.

**왜 보안을 분리했나**: 위협 증가와 개인정보보호법 강화로, 보안은 구축 후 부가활동이 아니라 전략 수립 단계부터 고려할 독립 도메인이 되었다.

**구조적 이해**: BA가 비즈니스의 방향을 정의하고, DA와 AA가 정보 시스템으로 이를 구체화하며, TA가 안정적인 물리적 기반을 제공하고, SA가 전체 영역을 철저히 보호하는 형상으로 이해하면 된다.

**도메인별 대표 산출물(참고 — 암기보다 본질 이해 중요)**: 실무에서는 각 도메인별 산출물 목록(레퍼런스)이 존재하며, 모든 세부 문서를 암기할 필요는 없다. 각 산출물이 무엇을 설명하는지 본질을 파악하는 것이 중요하다. 예: API 명세 → AA 영역, DRM(데이터 참조 모델) → DA 영역, TRM(기술 참조 모델) → TA 영역. 문서의 목적을 먼저 이해하고, 어떤 도메인에 속하는지를 기억해 둔다.

## SECTION 1-3. 추적성과 거버넌스

### 1) 추적성(Traceability) — EA의 진짜 힘

조직이 EA 도입 시 가장 흔히 범하는 오류는 산출물 수십 개를 만들어 문서고에 쌓아두는 것이다. EA의 진정한 가치는 문서의 양이 아니라 **추적성**에 있다. 추적성이란 요구사항부터 구현 구성요소까지 인과·의존 관계를 양방향으로 추적하는 능력이며, 각 도메인의 산출물과 요소들이 논리적으로 강력하게 연결되어 있는 상태를 의미한다.

**추적 사슬 예시**: 비즈니스 목표(고객 이탈률 30%↓) → 업무 프로세스(고객 불만 처리) → 애플리케이션(CRM 시스템) → 데이터(고객 마스터 DB) → 기술 플랫폼(서버·DBMS)

| 유형 | 정의 | 예시 흐름 | 검증하는 것 |
|---|---|---|---|
| 수직적 추적성(Vertical) | 동일한 '뷰(열)' 안에서 '관점(행)'이 다른 산출물 간 연결 | 핵심 정보목록(계획자) → 개념 데이터모델(책임자) → 논리 데이터모델(설계자) → 물리 DB 스키마(개발자) | 비즈니스 전략이 시스템 구현까지 왜곡 없이 반영되었는지 보증 |
| 수평적 추적성(Horizontal) | 동일한 '관점(행)' 안에서 '뷰(열)'가 다른 산출물 간 연결 | 설계자 관점: 논리 데이터모델(What) ↔ 애플리케이션 기능(How) ↔ 배포 서버(Where) | 아키텍처의 완전성과 일관성을 검증 |

**추적성이 만들어내는 실무 가치 — 영향분석(Impact Analysis)**: "물리 DB 테이블의 컬럼 하나를 바꾸면, 어떤 애플리케이션과 업무 프로세스에 영향을 주고 최종적으로 어떤 비즈니스 목표와 연결되는가?"를 정확히 역추적할 수 있는 것 — 이것이 바로 영향 분석이며, 추적성은 이를 가능하게 해주는 핵심 동력이다.

### 2) EA 거버넌스 원칙과 원칙 정의 템플릿

원칙은 선언이 아니라, 측정 가능한 지표와 예외절차를 갖춘 실행 지침이어야 한다. 아무리 훌륭한 아키텍처 청사진과 매트릭스가 있어도 이를 통제·강제할 수 있는 거버넌스가 없으면 사문화된다.

**5대 거버넌스 원칙**: ① 표준 준수(기술 복잡성과 TCO 통제), ② 변경 관리(통제된 절차로만 아키텍처 변경), ③ 품질·보안 내재화(설계 단계부터 반영해 사후비용 절감), ④ 재사용·공유(개발 속도 향상과 전사 일관성), ⑤ 메타데이터 우선(정보자산의 검색 가능성·활용도 제고).

**원칙 템플릿 6항목**(예: 데이터는 전사 공유자산이다)

| 항목 | 정의 내용 |
|---|---|
| 원칙 | 핵심 개념의 간결한 기술 |
| 의미 | 구체적 의미와 적용 범위 |
| 배경 | 이 원칙이 필요한 비즈니스·기술적 이유 |
| 기대효과 | 준수 시 기대되는 긍정적 결과 |
| 지표 | 준수 여부를 측정하는 KPI(예: 데이터 중복률, 재사용률) |
| 예외처리 | 미준수 시 ARB 심의·승인 절차 |

불가피하게 표준을 따르지 못할 때는 **ARB(아키텍처 리뷰보드, Architecture Review Board)** 같은 공식 의사결정 기구의 승인을 거쳐 이력을 남겨야 한다.

## SECTION 2. EA 프레임워크

### 아키텍처 매트릭스 = 관점(Perspective) × 뷰(View)

추적성을 체계적인 격자 구조의 틀로 관리할 수 있도록 해주는 것이 아키텍처 매트릭스다. **자크만 프레임워크(Zachman Framework)**에서 유래했으며, 행은 이해관계자 시각, 열은 육하원칙 기반 아키텍처 질문으로 구성된다.

| 관점 \ 뷰 | 데이터(What) | 프로세스(How) | 네트워크(Where) | 사람(Who) | 시간(When) | 동기(Why) |
|---|---|---|---|---|---|---|
| 계획자(Planner) | 핵심 정보목록 | 핵심 성공요인 | 사업장 위치 | 조직도 | 연간 사업계획 | 비즈니스 전략 |
| 책임자(Owner) | 개념 데이터모델 | 업무 프로세스 모델 | 업무 지역 분포 | 역할 정의 | 이벤트 목록 | 업무 규칙 |
| 설계자(Designer) | 논리 데이터모델 | 앱 기능 설계서 | 시스템 배치도 | 권한 모델 | 처리 주기 정의 | 시스템 제약조건 |
| 개발자(Builder) | 물리 DB 스키마 | 소스 코드 | 서버·장비 위치 | 사용자 계정 | 배치 스케줄 | 구현 규칙 |

**행 = 관점**: 위→아래로 추상에서 구체로, 계획자·책임자·설계자·개발자 순. **열 = 뷰**: What·How·Where·Who·When·Why(정보·기능·위치·조직·이벤트·목표). **셀 = 연결**: 필수 산출물 + 메타데이터 속성 + 링크를 정의해야 '운영 테이블'이 된다.

**수직/수평 연결**: 수직적 연결은 예를 들어 데이터 관점의 최상단 개념 모델에서 시작해 하단의 물리 스키마까지 수직으로 내려가는 흐름이다. 수평적 연결은 특정 설계 단계에서 데이터와 애플리케이션·서버(배포 위치) 등을 횡으로 엮는 것이다. 매트릭스는 이 복잡한 자원 관계를 구조화하는 지도로 볼 수 있다.

### 프레임워크와 레퍼지토리(Repository)

프레임워크는 EA를 구축하고 운영하기 위한 문법이자 틀이다. 프레임워크의 중심에는 **레퍼지토리(Repository)**가 존재한다. 레퍼지토리는 단순한 파일 폴더가 아니라, 모든 도메인 산출물·메타데이터·개체 간 링크 관계·버전 관리·변경 이력 등을 통합적으로 관리하는 **단일 진실 공급원(Single Source of Truth)**이다. 바깥쪽에서는 **TOGAF, ADM** 같은 방법론이 전사 원칙을 무엇을, 어떤 순서로 만들 것인지 규정한다. 사용자는 이 레퍼지토리를 통해 필요한 아키텍처 정보를 조회할 수 있다.

## SECTION 3. EA 참조 모델

### 1) 참조모델 5종(FEA 기준)

참조 모델은 조직 전체가 공통으로 사용하는 표준 분류 사전이며, 전사 공통의 '표준 사전'이자 '품질 게이트'로서 상호운용성과 비교 가능성을 확보한다. 미 연방정부 기준(FEA)의 5대 참조 모델을 질문 형태로 기억해두면 좋다.

| 약어 | 명칭 | 핵심 질문 | 역할 |
|---|---|---|---|
| BRM | 업무 참조 모델 | "무엇을 하는가(What we do)" 관점에서 우리는 어떤 업무를 수행하는가? | 기능 중복 식별, 조직 간 협업, BPR 기초자료 |
| SRM | 서비스 참조 모델 | 어떤 서비스 구성 요소를 재사용할 수 있는가? | 서비스 재사용성 제고, SOA·MSA의 기반 |
| DRM | 데이터 참조 모델 | 데이터를 어떻게 표준화하고 공유하는가? | 데이터 공유·재사용 촉진, 품질 확보 기준 |
| TRM | 기술 참조 모델 | 어떤 기술과 표준 제품을 채택할 것인가? | 중복투자 방지, 상호운용성 극대화 |
| PRM | 성과 참조 모델 | 이 아키텍처의 성과를 무엇으로 측정할 것인가? | IT 투자 기여도 평가, 차기 투자계획 환류 |

**참조모델 = 품질 게이트**: 신규 프로젝트 착수 시 데이터는 DRM 표준용어와, 기술은 TRM 표준제품과, 서비스는 SRM 분류체계와 매핑을 의무화하고, 통과하지 못하면 다음 단계로 진행할 수 없도록 통제한다. 이 참조 모델들은 단순한 문서 보관용이 아니라, 신규 아키텍처가 기획 단계에서 표준 데이터와 표준 기술을 준수하고 있는지를 검증할 수 있는 품질 게이트로 활용되어야 실효성을 발휘할 수 있다.

**상위 참조모델과의 매핑은 필수**: 공공기관·그룹사의 자체 참조모델은 범정부/상위기관 참조모델과 매핑 관계를 설정·유지해야 한다. 기관 간 정보공유, 성과 비교분석, 정책 준수 및 감사 대응의 전제조건이다.

### 2) DRM의 계층 구조와 관리 체크리스트

주제영역에서 코드까지 — 계층별 명칭이 전사 표준 용어사전과 매핑되어야 의미적 일관성이 확보된다.

| 계층 | 정의 | 예시 |
|---|---|---|
| 주제영역(Subject Area) | 가장 상위의 데이터 분류 | 고객·상품·계약·재무·인사 |
| 개체(Entity)/데이터세트 | 구체적인 개체 | 고객기본정보·고객등급정보·고객계약정보 |
| 속성(Attribute) | 개체의 특징을 나타냄 | 고객번호·고객명·생년월일·성별코드 |
| 코드·도메인(Code/Domain) | 값의 허용 범위 — 코드는 어떤 값이 입력될 수 있는지, 도메인은 어떤 형식·데이터 타입이 되어야 하는지 통제 | 성별코드 M/F, 일자 도메인 YYYY-MM-DD |

관계(Relationship)는 카디널리티·옵셔널리티를 포함해 명확히 정의한다.

**DRM 관리 체크리스트 6항목**

| 항목 | 확인 내용 |
|---|---|
| 표준 용어 | 표준 용어사전 등록 명칭·명명규칙 준수 |
| 정의 | 누가 보아도 오해 없는 비즈니스 의미 기술 |
| 형식·값범위 | 타입·길이·도메인·코드 명시 |
| 관리자·소유자 | 현업 소유자와 IT 관리자 지정 |
| 버전 | 변경 이력·사유·일자 기록 |
| 출처 | 최초 생성·관리 기준 시스템(원본) 명시 |

> DRM의 품질 = 전사 데이터의 품질. 참조데이터(국가·부서·상품분류 코드)는 중앙 통합관리가 원칙이다. 이 체계가 무너지면 전사 데이터의 품질은 유지될 수 없다.

## SECTION 4. EA 프로세스

### 1) EA 수명주기와 변경관리 프로세스

EA는 일회성 구축이 아니라, 평가 결과가 다시 계획으로 환류되는 순환 활동이다. 한 번 구축하고 서랍에 넣어두는 정적인 것이 아니라 **계획 → 설계 → 구현 → 운영 → 평가**의 5단계를 거치며 끊임없이 순환하는 생명주기를 가진다.

| 단계 | 내용 | 산출/활동 |
|---|---|---|
| ① 계획(Plan) | 전략 분석, 목표 아키텍처 정의 | 산출: 아키텍처 비전 |
| ② 설계(Design) | Gap 분석, 이행과제 도출 | 산출: 이행 로드맵 |
| ③ 구현(Implement) | 이행 프로젝트 착수·감독 | 구현 거버넌스 수행 |
| ④ 운영(Operate) | 성능·가용성 모니터링 | 변경관리 상시 운영 |
| ⑤ 평가·개선 | ROI·품질·준수율 측정 | 성숙도 진단 후 환류 |

운영 단계에서 비즈니스 환경 변화나 시스템 개선 요구가 발생하면 반드시 통제된 변경 관리 프로세스를 거쳐야 한다. 이때 앞서 강조한 추적성 기반의 영향 분석이 선행되어야 하고, 아키텍처 위원회의 승인을 받아 레퍼지토리에 반영된다.

**변경관리 6단계와 RACI**

| 단계 | 내용 |
|---|---|
| ① 요구 식별 | 변경요청서 접수 |
| ② 영향 분석 | 추적성 기반 파급효과 |
| ③ 표준·모델 변경 | 변경 초안·리스크 |
| ④ 승인 | ARB·운영위 심의 |
| ⑤ 교육·배포 | 공지·교육·포털 게시 |
| ⑥ 효과 측정 | 기대효과 검증·피드백 |

RACI: **CIO/EDA = A(최종 승인·공표)**, **DA·EA팀 = R(프로세스 운영·영향분석·조율)**, **User = C/I(검토 의견·교육 참여)**.

**책임 구조**: 최종 책임은 CIO 또는 EDA(엔터프라이즈 데이터 아키텍트, Enterprise Data Architect)가 맡고, 실무 전담은 EA 전담 팀이 수행한다.

### 2) EA 성숙도 모델(1~5단계)

조직의 EA 역량이 어느 수준에 도달해 있는지를 평가하는 기준이다. 평가 영역은 자원관리·정보화 관리체계·활용성이며, 영역별 측정항목으로 수준을 판정한다.

| 단계 | 명칭 | 특징 |
|---|---|---|
| 1단계 | 초기(Initial) | 인식 부족, 비공식·비정기 활동. 담당자 개인의 역량에 의존해 절차가 매우 비체계적 |
| 2단계 | 반복(Developing) | 일부 영역 시작, 전사 확산·일관성 부족. 일부 프로젝트 단위로 EA 활동이 반복되기 시작 |
| 3단계 | 정의(Defined) | 전사 표준·프로세스 문서화, 거버넌스 수립. 공식 거버넌스가 문서화되어 정착 |
| 4단계 | 관리(Managed) | KPI로 정량 측정·관리, 성과 기반 개선. EA 활동과 성과가 정량적인 KPI를 통해 측정·통제 |
| 5단계 | 최적화(Optimizing) | 조직문화로 내재화, 혁신 주도. 측정된 피드백을 사용해 자동화와 지속적인 최적화가 일상화 |

**성숙도는 사업 생애주기와 연계될 때 효과적이다**: 사전검토 → 사업추진 → 이행점검 → 사후평가 → 환류의 선순환. 예) 변경관리 프로세스 측정지표: 3단계는 '표준 프로세스 준수율(%)', 4단계는 '변경 처리 평균 리드타임', 5단계는 '프로세스 자동화율·장애 감소율'.

시험이나 실무에서는 1~2단계보다 3, 4, 5단계가 주로 출제/언급된다 — 3단계는 표준 정의, 4단계는 정량화 관리, 5단계는 최적화로 핵심 키워드를 구분해 기억한다.

| EA = 규칙 + 모델 + 계획 | 원칙 아래 청사진을 그리고, 이를 실현하는 로드맵을 세운다 |
| 전사 = 의사결정·자원관리의 경계 | 지배구조·예산·데이터공유·IT관리 4개 기준으로 판단 |
| 5대 도메인과 추적성 | BA→DA·AA→TA, SA는 전 계층 관통 / 수직·수평 추적성으로 영향분석 |
| 프레임워크·참조모델 | 레퍼지토리(SSoT) 중심 + BRM·SRM·DRM·TRM·PRM |
| 프로세스·성숙도 | 계획-설계-구현-운영-평가의 환류 / 1~5단계 성숙도 진단 |

**자주 하는 실수 TOP 3**

1. 산출물을 '많이' 만들되 서로 연결하지 않는다 → 최소 핵심 산출물 세트 + 링크 강제가 필요하다.
2. BA/DA/AA 간 용어 불일치(고객·회원·사용자를 제각각 사용) → 용어 표준화가 선행되어야 한다.
3. 도구 없이 스프레드시트로 관리한다 → 레퍼지토리 도입과 온보딩이 우선되어야 한다.

## 자기 점검 Q&A

**Q1. EA를 규정하는 3대 관점은 무엇인가?**
A. 규칙(Rule), 모델(Model), 계획(Plan) — RMP.

**Q2. 전사의 범위를 확정하는 실질적 판단 기준은 무엇인가?**
A. 의사결정의 경계와 자원 관리의 경계다. 구체적으로는 지배구조(ARB 통제 범위), 예산·투자(IT 포트폴리오 관리 대상), 데이터 공유(데이터 거버넌스 적용 경계), IT 관리(ITSM·CMDB 적용 범위) 네 가지 기준에 모두 '그렇다'고 답할 수 있는 가장 큰 조직 단위가 전사의 범위가 된다.

**Q3. 5대 도메인 간의 유기적인 관계를 유지하는 핵심적인 힘은 무엇인가?**
A. 추적성(Traceability)이다. 수직적 추적성(같은 뷰 안에서 관점 간 연결)과 수평적 추적성(같은 관점 안에서 뷰 간 연결)으로 구성되며, 이를 통해 영향 분석이 가능해진다.

**Q4. 아키텍처 매트릭스의 행과 열은 각각 무엇을 의미하는가?**
A. 행(관점)은 위에서 아래로 갈수록 추상에서 구체로 내려가는 계획자·책임자·설계자·개발자 시각이고, 열(뷰)은 What·How·Where·Who·When·Why라는 육하원칙 기반 아키텍처 질문이다.

**Q5. FEA 기준 5대 참조 모델은 무엇이며 각각 어떤 질문에 답하는가?**
A. BRM(어떤 업무를 수행하는가), SRM(어떤 서비스 구성요소를 재사용할 수 있는가), DRM(데이터를 어떻게 표준화·공유하는가), TRM(어떤 기술·표준 제품을 채택할 것인가), PRM(아키텍처 성과를 무엇으로 측정할 것인가).

**Q6. 데이터 참조 모델(DRM)의 4계층 구조는?**
A. 주제영역 → 개체(데이터세트) → 속성 → 코드·도메인. 코드는 입력 가능한 값을 정의하고, 도메인은 형식·데이터 타입을 통제한다.

**Q7. 성숙도 3단계, 4단계, 5단계의 결정적인 차이는 무엇인가?**
A. 3단계는 전사 표준·프로세스의 '정의'(문서화·거버넌스 수립), 4단계는 KPI를 통한 '정량화 관리', 5단계는 피드백 기반의 자동화·지속적 '최적화'다.

## 한 줄 요약

EA는 단순한 IT 서류 작업이 아니라, 규칙·모델·계획(RMP)으로 조직의 전략과 시스템을 일치시키고, 5대 도메인 간 추적성과 거버넌스, 참조모델 기반 품질 게이트, 그리고 계획-설계-구현-운영-평가의 순환 생명주기를 통해 조직을 지속적으로 성숙시키는 거대한 내비게이션이다.

## 부록: 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| EA | Enterprise Architecture, 전사 아키텍처 |
| RMP | 규칙(Rule)·모델(Model)·계획(Plan) |
| As-Is / To-Be | 현재 상태 / 미래 목표 상태 |
| BA / DA / AA / TA / SA | 비즈니스 / 데이터 / 애플리케이션 / 기술 / 보안 아키텍처 |
| 전사 범위 4대 기준 | 지배구조·예산투자·데이터공유·IT관리 |
| 추적성(Traceability) | 도메인 간 산출물·요소의 논리적 연결 상태, 영향 분석의 기반(수직적/수평적) |
| 아키텍처 매트릭스 | 관점(행)×뷰(열)로 구성된 자원 관계 지도(Zachman Framework 유래) |
| ARB | Architecture Review Board, 아키텍처 리뷰보드(표준 예외 승인 기구) |
| 레퍼지토리(Repository) | 도메인 산출물·메타데이터·이력을 통합 관리하는 단일 진실 공급원(SSoT) |
| TOGAF / ADM | 대표적인 EA 구축·운영 방법론 |
| BRM / SRM / DRM / TRM / PRM | 업무/서비스/데이터/기술/성과 참조 모델(FEA 5대 참조모델) |
| DRM 4계층 | 주제 영역 → 개체 → 속성 → 코드 및 도메인 |
| EA 생명주기 | 계획 → 설계 → 구현 → 운영 → 평가(5단계 순환) |
| 변경관리 6단계 | 요구식별 → 영향분석 → 표준·모델변경 → 승인 → 교육·배포 → 효과측정 |
| EA 성숙도 모델 | 1.초기 → 2.반복 → 3.정의 → 4.관리 → 5.최적화 |
| CIO / EDA | 최고정보책임자 / 엔터프라이즈 데이터 아키텍트(EA 최종 책임자) |
