# [DAsP 데이터아키텍처 준전문가] 01-01 전사 아키텍처 개요


## 0. 강의 도입 — 문제 제기 (수강 신청 사례)

- 대학 수강 신청 시 대규모 접속과 시스템 마비 현상은 흔히 겪는 문제.
- IT 담당자가 "서버 용량을 늘리면 해결된다"고 답하는 것은 **잘못된 접근**일 수 있음.
- 시스템 부하의 근본 원인은 서버 성능 부족이 아니라 다음과 같은 다양한 요인일 수 있음:
  1. 수강 신청을 처리하는 **업무 프로세스의 비효율성**
  2. 학생·과목·수강 신청 등 **데이터 구조상의 문제**
  3. 부서별로 제각각 구축되어 애플리케이션 간 **시스템 병목**
  4. 취약한 **보안(보완) 정책**
- 결론: 조직의 정보와 자원을 개별 시스템 단위로 나눠서 보지 않고, **업무·데이터·애플리케이션·기술·보안** 전체를 아우르는 하나의 거대한 유기체로 통합하여 거시적 관점에서 설계·통제하는 방법론 → 이것이 **EA(전사 아키텍처, Enterprise Architecture)**.

### 이번 챕터에서 반드시 정복해야 할 4가지 핵심 질문
1. EA의 본질적인 정의와 역할은 무엇인가?
2. 조직에서 **전사(Enterprise)**의 경계와 범위를 설정하는 기준은 무엇인가?
3. 비즈니스·데이터·애플리케이션·기술·보안이라는 **5대 도메인**은 어떻게 톱니바퀴처럼 맞물려 돌아가는가?
4. 이 복잡한 청사진을 미완성이 아니라 지속적으로 관리 가능하게 해주는 체계는 무엇인가?

## 1. EA의 정의

### 1.1 교과서적 정의
- EA는 **조직의 전략과 IT를 일치**시키고, **정부(조직) 자원의 최적화**를 달성하기 위한 **전사적인 설계 동인(틀)**으로 정의된다.

### 1.2 실무적 압축 — 3대 핵심 동사
| 핵심 동사 | 의미 |
|---|---|
| 통합 설계 | 전체를 아우르는 구조 설계 |
| 관계 관리 | 요소 간 관계를 관리 |
| 일관성 통제 (거버넌스) | 표준·원칙의 일관된 통제 |

### 1.3 도시 계획 비유
- 아무리 개별 건물을 세계 최고 수준으로 지어도, 건물과 건물을 잇는 도로가 끊겨 있거나 상하수도·전력망이 유기적으로 연결되지 않으면 도시는 기능을 상실함.
- 기업/공공기관의 정보 시스템도 마찬가지.

### 1.4 As-Is / To-Be / 로드맵
- **As-Is**: 현재 아키텍처를 진단.
- **To-Be**: 조직이 지향해야 할 미래 목표 상태를 정의.
- **로드맵**: As-Is와 To-Be 사이의 격차를 메우기 위한 이행 계획을 체계적으로 수립하는 활동.
- 이 As-Is 진단 → To-Be 정의 → 로드맵 수립 활동 자체가 **EA의 본질**.

### 1.5 EA의 본질 요약
- EA는 단순한 IT 기술 문서가 아니라, **경영 전략을 실제 시스템 구현까지 연결시켜주는 전사적인 청사진**이다.

## 2. EA를 이해하는 공식 — RMP (규칙 · 모델 · 계획)

가장 체계적으로 EA를 이해·기억하는 공식은 **RMP**, 즉 **규칙(Rule), 모델(Model), 계획(Plan)**이다.

### 2.1 규칙 (Rule)
- 조직이 IT 의사결정을 내릴 때 반드시 준수해야 하는 **원칙과 기준**.
- 예: "신규 시스템은 클라우드 우선 원칙을 적용한다", "데이터 명명 규칙은 표준 용어 사전을 따른다."
- 부서별로 제각각 시스템을 구축하면 발생하는 무질서를 방지.

### 2.2 모델 (Model)
- 현재 정보와 자원, 미래의 목표 상태를 **일정한 표기법과 구조로 시각화**한 그림.
- 데이터베이스 중복, 프로세스 흐름 등을 모델을 통해 한눈에 파악 가능.

### 2.3 계획 (Plan)
- To-Be로 나아가는 **시계열적인 로드맵**.
- 어떤 순서로 데이터를 표준화하고, 어떤 시스템을 먼저 개편할 것인지 단계적으로 제시.

### 2.4 요약
- **규칙 = 기준, 모델 = 그림, 계획 = 그에 이르는 길**
- 이 세 가지 축이 결합하여 EA를 현실로 만든다.

## 3. 전사(Enterprise)의 범위

- EA에서 다루는 "전사"는 무조건 기업의 **법인 전체**를 의미하는 것이 아님.
- "전사"는 물리적인 회사 전체라기보다는, **동일한 의사 결정 권한과 통합된 자원 관리가 적용되는 비즈니스·IT의 경계**를 뜻함.

### 예시
- 대학교 전체가 동일한 정보화 편성과 단일 학사 데이터 정책을 공유한다면 → 대학 전체가 하나의 "전사"임.
- 대학 내 부속 병원이나 독립 법인 형태의 연구소가 예산·시스템·데이터를 완전히 독립적으로 운영하고 있다면 → 별도의 전사 아키텍처 영역으로 분리하여 관리하는 것이 타당함.

### 핵심 기준 (2가지)
1. **의사 결정의 경계**
2. **자원 관리의 경계**

→ 동일한 표준과 거버넌스를 강제할 수 있는 권한의 한계, 그 경계가 어디까지인지를 아는 것이 중요하며, 이것이 곧 전사의 범위가 된다.

## 4. EA의 5대 도메인

조직 분석을 위해 EA는 다섯 가지 핵심 도메인으로 나눈다. (수강 신청 사례로 확인)

| 도메인 | 약어 | 내용 |
|---|---|---|
| 비즈니스 아키텍처 | BA | 누가, 언제, 어떤 목적과 규정에 따라 수강 신청 업무를 수행하는가 — **업무 프로세스와 조직 정책**의 영역 |
| 데이터 아키텍처 | DA | 비즈니스 활동에 필요한 학생·과목·성적 등 **데이터의 정의·구조**와 데이터 간 상호 관계 설계 |
| 애플리케이션 아키텍처 | AA | 수강 신청 포탈, 학사 관리 시스템 등 실제 업무를 처리하는 **소프트웨어 응용 프로그램**과 이들 간의 인터페이스 정의 |
| 기술 아키텍처 | TA | 애플리케이션이 구동되는 서버, 데이터베이스 관리 시스템(DBMS), 네트워크, OS(운영체제), 클라우드 인프라 등 **기반**을 구축 |
| 보안 아키텍처 | SA | 앞의 BA·DA·AA·TA **모든 도메인을 관통**하여 사용자 인증, 권한 통제, 개인정보 암호화 및 재해복구 같은 체계를 수립 |

### 구조적 이해
- **BA**가 비즈니스의 방향을 정의.
- **DA와 AA**가 정보 시스템으로 이를 구체화.
- **TA**가 안정적인 물리적 기반을 제공.
- **SA**가 전체 영역을 철저히 보호.

### 도메인별 대표 산출물 (참고 — 암기보다 본질 이해 중요)
- 실무에서는 각 도메인별 산출물 목록(레퍼런스)이 존재하며, 모든 세부 문서를 암기할 필요는 없음. 각 산출물이 무엇을 설명하는지 본질을 파악하는 것이 중요함.
- 예시:
  - **API 명세** → AA(애플리케이션 아키텍처) 영역
  - **DRM(데이터 참조 모델)** → DA(데이터 아키텍처) 영역
  - **TRM(기술 참조 모델)** → TA(기술 아키텍처) 영역
- 문서의 목적을 먼저 이해하고, 어떤 도메인에 속하는지를 기억해 둘 것.

## 5. 추적성 (Traceability)

- 조직이 EA 도입 시 가장 흔히 범하는 오류: 산출물 수십 개를 만들어 문서고에 쌓아두는 것.
- EA의 진정한 가치는 **문서의 양이 아니라 추적성**에 있음.
- **추적성**: 각 도메인의 산출물과 요소들이 **논리적으로 강력하게 연결되어 있는 상태**.

### 예시 (수강 신청 처리 속도 목표)
- 경영진이 "수강 신청 평균 처리 속도를 3분 이내로 단축한다"는 전략 목표를 수립했다고 가정:
  1. 이 목표는 수강 신청 업무 프로세스, 즉 **BA**와 연결
  2. 프로세스는 수강 신청 접수 애플리케이션, 즉 **AA**와 연결
  3. 애플리케이션은 학생 정보 테이블(**DA**)과 고속 능 서버 인프라(**TA**)로 직결

- 이러한 아키텍처 간의 추적 관계가 살아있다면, 향후 DB의 특정 컬럼 하나를 수정해야 할 때 이 변경이 어떤 프로그램에 영향을 유발하고, 어떤 프로세스를 중단시키며, 최종적으로 어떤 경영 목표에 타격을 주는가를 정확하게 역추적할 수 있음.
- 이것이 바로 **영향 분석**이며, 추적성은 이를 가능하게 해주는 핵심 동력.

## 6. 아키텍처 매트릭스

- 추적성을 체계적인 격자 구조의 틀로 관리할 수 있도록 해주는 것이 **아키텍처 매트릭스**.
- 자크만 프레임워크(Zachman Framework)나 국내 범정부 표준에서도 널리 쓰이는 방식.

### 매트릭스의 두 축
1. **행(Row) 관점 — 누가 이 정보를 보는가**
   - 최고 경영자(계획자) → 시스템 설계자 → 실제 개발자
   - 상위에서 하위로 내려갈수록 정보는 점점 상세(구체)해짐.
2. **열(Column) 관점 — 무엇을 보는가**
   - 업무, 데이터, 애플리케이션, 기술 등의 관점.

### 수직/수평 연결
- **수직적 연결**: 예) 데이터 관점의 최상단 개념 모델에서 시작해 하단의 물리 스키마까지 수직으로 내려가는 흐름.
- **수평적 연결**: 특정 설계 단계에서 데이터와 애플리케이션 서버(배포 위치) 등을 횡으로 엮는 것.
- 매트릭스는 이 복잡한 자원 관계를 구조화하는 **지도**로 볼 수 있음.

## 7. 거버넌스 (Governance)

- 아무리 훌륭한 아키텍처 청사진과 매트릭스가 있어도, 이를 통제하고 강제할 수 있는 거버넌스가 없으면 **사문화**됨.
- 즉 "표준을 준수하라"는 선언만으로는 현업 프로세스에서 절대 지켜지지 않음.

### 실효성 있는 원칙에 반드시 동반되어야 할 5가지 요소
1. 원칙의 명확한 **정의**
2. 도입 **배경과 필요성**
3. **기대 효과**
4. 준수 여부를 확인할 수 있는 **정량적인 측정 지표**
5. 불가피하게 표준을 따르지 못할 때의 공식적인 **예외 심의 절차**

### 예시
- 원칙: "데이터는 전사 공유 자산이다."
  - 측정 지표: 데이터 중복률, 재사용률
  - 예외 필요 시: **ARB(아키텍처 리뷰보드, Architecture Review Board)** 같은 공식 의사결정 기구의 승인을 거쳐 이력을 남겨야 함.

## 8. 프레임워크와 레퍼지토리 (Repository)

- **프레임워크**: EA를 구축하고 운영하기 위한 문법이자 틀.
- 프레임워크의 중심에는 **레퍼지토리(Repository)**가 존재.
  - 레퍼지토리는 단순한 파일 폴더가 아니라, 모든 도메인 산출물·메타데이터·개체 간 링크 관계·버전 관리·변경 이력 등을 통합적으로 관리하는 **단일 진실 공급원(Single Source of Truth)**.
- 바깥쪽에서는 **TOGAF, ADM** 같은 방법론이 전사 원칙을 무엇을, 어떤 순서로 만들 것인지 규정.
- 사용자는 이 소(레퍼지토리)를 통해 필요한 아키텍처 정보를 조회할 수 있음.

## 9. 참조 모델 (Reference Model)

- **참조 모델**: 조직 전체가 공통으로 사용하는 **표준 분류 사전**.
- 미 연방정부 기준의 **5대 참조 모델**을 질문 형태로 기억해두면 좋음.

| 약어 | 명칭 | 핵심 질문 |
|---|---|---|
| **BRM** | 업무 참조 모델 | 우리는 어떤 업무를 수행하는가? |
| **SRM** | 서비스 참조 모델 | 어떤 서비스 구성 요소를 재사용할 수 있는가? |
| **DRM** | 데이터 참조 모델 | 데이터를 어떻게 표준화하고 공유하는가? |
| **TRM** | 기술 참조 모델 | 어떤 기술과 표준 제품을 채택할 것인가? |
| **PRM** | 성과 참조 모델 | 이 아키텍처의 성과를 무엇으로 측정할 것인가? |

- 이 참조 모델들은 단순한 문서 보관용이 아니라, 신규 아키텍처가 기획 단계에서 표준 데이터와 표준 기술을 준수하고 있는지를 검증할 수 있는 **품질 게이트**로 활용되어야 실효성을 발휘할 수 있음.

### 9.1 데이터 참조 모델(DRM)의 상세 구조 — 4개 계층
1. **주제 영역** (가장 상위)
2. **개체** (구체적인 개체)
3. **속성** (개체의 특징을 나타냄)
4. **코드 및 도메인** (값의 허용 범위)
   - **코드**: 어떤 값이 입력될 수 있는지 정의
   - **도메인**: 어떤 형식과 데이터 타입이 되어야 하는지 통제

- 이 체계가 무너지면 전사 데이터의 품질은 유지될 수 없음.

## 10. EA의 생명 주기(Lifecycle)

- EA는 한 번 구축하고 서랍에 넣어두는 정적인 것이 아님.
- **계획 → 설계 → 구현 → 운영 → 평가(성과 관리)**의 5단계를 거치며 끊임없이 순환하는 생명 주기를 가짐.
- 운영 단계에서 비즈니스 환경 변화나 시스템 개선 요구가 발생하면 반드시 **통제된 변경 관리 프로세스**를 거쳐야 함.
  - 이때 앞서 강조한 **추적성 기반의 영향 분석**이 선행되어야 함.
  - **아키텍처 위원회의 승인**을 받아 레퍼지토리에 반영됨.
- **책임 구조**:
  - 최종 책임: **CIO** 또는 **EDA(엔터프라이즈 데이터 아키텍트, Enterprise Data Architect)**
  - 실무 전담: **EA 전담 팀**

## 11. EA 성숙도 모델 (Maturity Model)

- 조직의 EA 역량이 어느 수준에 도달해 있는지를 평가하는 기준.
- **1단계 ~ 5단계**로 구성.

| 단계 | 명칭 | 특징 | 핵심 키워드 |
|---|---|---|---|
| 1단계 | 초기 | 담당자 개인의 역량에 의존, 절차가 매우 비체계적 | — |
| 2단계 | 반복 | 일부 프로젝트 단위로 EA 활동이 반복되기 시작 | — |
| 3단계 | 정의 | **전사 표준 프로세스**가 핵심, 공식 거버넌스가 문서화되어 정착 | 표준 정의 |
| 4단계 | 관리 | EA 활동과 성과가 정량적인 **KPI**를 통해 측정되고 통제됨 | 정량화 관리 |
| 5단계 | 최적화 | 측정된 피드백을 사용해 **자동화**와 지속적인 최적화가 일상화됨 | 최적화 |

- 시험이나 실무에서는 1~2단계보다 **3, 4, 5단계**가 주로 출제/언급됨.
  - 3단계 = 정의와 표준화
  - 4단계 = 정량화(수치)
  - 5단계 = 최적화

---

## 12. 챕터 1 마무리 — 핵심 확인 질문 (Self-Check)

1. **Q. EA를 규정하는 3대 관점은 무엇인가?**
   A. 규칙, 모델, 계획 (RMP)

2. **Q. 전사의 범위를 확정하는 두 가지 핵심 기준은 무엇인가?**
   A. 의사 결정의 경계와 자원 관리의 경계

3. **Q. 5대 도메인 간의 유기적인 관계를 유지하는 핵심적인 힘은 무엇인가?**
   A. 추적성

4. **Q. 성숙도 3단계, 4단계, 5단계의 결정적인 차이는 무엇인가?**
   A. 3단계는 표준 정의, 4단계는 정량화 관리, 5단계는 최적화

---

## 13. 한 줄 요약

> EA는 단순한 IT 서류 작업이 아니라, **기업의 전략과 시스템을 일치시키는 거대한 내비게이션**이다.

## 부록: 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| EA | Enterprise Architecture, 전사 아키텍처 |
| RMP | 규칙(Rule) · 모델(Model) · 계획(Plan) |
| As-Is / To-Be | 현재 상태 / 미래 목표 상태 |
| BA / DA / AA / TA / SA | 비즈니스 / 데이터 / 애플리케이션 / 기술 / 보안 아키텍처 |
| 추적성 (Traceability) | 도메인 간 산출물·요소의 논리적 연결 상태, 영향 분석의 기반 |
| 아키텍처 매트릭스 | 행(누가 보는가) × 열(무엇을 보는가)로 구성된 자원 관계 지도 (Zachman Framework 등) |
| ARB | Architecture Review Board, 아키텍처 리뷰보드 (표준 예외 승인 기구) |
| 레퍼지토리 (Repository) | 도메인 산출물·메타데이터·이력을 통합 관리하는 단일 진실 공급원(SSOT) |
| TOGAF / ADM | 대표적인 EA 구축·운영 방법론 |
| BRM / SRM / DRM / TRM / PRM | 업무/서비스/데이터/기술/성과 참조 모델 (미 연방정부 5대 참조모델) |
| DRM 4계층 | 주제 영역 → 개체 → 속성 → 코드 및 도메인 |
| EA 생명주기 | 계획 → 설계 → 구현 → 운영 → 평가 (5단계 순환) |
| EA 성숙도 모델 | 1.초기 → 2.반복 → 3.정의 → 4.관리 → 5.최적화 |
| CIO / EDA | 최고정보책임자 / 엔터프라이즈 데이터 아키텍트 (EA 최종 책임자) |
