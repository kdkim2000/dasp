# [DAsP 데이터아키텍처 준전문가] 01-02 전사 아키텍처 구축

## 0. 강의 도입

- 지난 시간(01-01)에는 EA가 무엇이고 왜 필요한지 **개념과 뼈대**를 세웠음.
- 이번 챕터에서는 이 방대한 청사진을 **실제로 어떻게 구축할 것인가**에 대한 실무 방법론을 다룸.

### 학습 목표 (강의 자료 화면 기준)
- EA 비전과 원칙을 조직 전략과 정렬하여 수립하고, 원칙을 측정 가능한 형태로 기술할 수 있다.
- 관리 가능한 범위를 한정하고 PPM 기준으로 이행 과제의 우선순위와 로드맵을 설계할 수 있다.
- 메타모델(객체-속성-관계)의 개념을 이해하고 도메인별 관리 정보를 정의할 수 있다.
- 현행·목표 아키텍처를 구축하고 Gap 분석을 통해 이행 과제를 도출할 수 있다.

### EA 구축 프로세스 — 3대 마일스톤
| 단계 | 명칭 | 내용 |
|---|---|---|
| 1단계 | **방향 수립** | 왜 이것을 하느냐 — 우리 조직의 **비전과 원칙**은 무엇인가를 정의 (환경분석 → 비전 → 원칙, 범위·우선순위·로드맵 수립) |
| 2단계 | **정보 구성 정의** | 정보를 어떤 구조와 속성으로 관리할 것인가에 대한 **메타모델(객체·속성·관계)** 설계 — 오늘 챕터의 핵심 (도메인별 관리 정보 정의) |
| 3단계 | **정보 구축 및 이행 계획** | 현재 상태를 조사하고 목표 상태를 설계한 뒤 그 격차를 메울 로드맵을 도출 (As-Is/To-Be/Gap 분석, 레퍼지토리·포탈·품질·보안) |

이 순서대로 체계적인 구축 로드맵을 살펴봄.

## 1. 1단계: 방향 수립

### 1.1 환경 분석 (EA 구축의 첫 걸음)
- EA 구축의 첫 걸음은 **기술 도입이 아니라 철저한 환경 분석과 진단**.
- 비유: 의사가 환자를 진찰하지 않고 처방을 내릴 수 없듯, 조직의 내외부 환경을 먼저 진단해야 함.
- 환경 분석 시 확인 사항:
  1. 경영 전략과 중장기 정보화 계획 검토
  2. 클라우드·인공지능 같은 **IT 기술 트렌드 변화** 파악
  3. **법·제도적 컴플라이언스** 확인
  4. 무엇보다 중요한 것: **경영진, 현업 사용자, 시스템 개발자**들의 고충과 니즈를 인터뷰
- 이 환경 분석 결과가 향후 EA 원칙과 비전 수립의 **절대적인 근거**가 됨.
- 원칙: **순서는 언제나 "진단 후 비전"**.

#### (참고) 환경분석 5요소 (SECTION 1-1 화면 기준)
| # | 구분 | 내용 |
|---|---|---|
| 01 | 비즈니스 내·외부 환경 | 중장기 비전·경영방침 등 경영이념을 이해하고 분석 방향을 도출 |
| 02 | 외부 환경 | 법·제도 변화, AI·클라우드 등 기술 트렌드, 시장 경쟁 구도 |
| 03 | 내부 환경 | 데이터 정책·현황, 기술 도입 동향, 내부 이슈 → 기회·위협 식별 |
| 04 | 이해관계자 | 경영진·현업·개발자·최종 사용자의 불만·개선요구·기대사항 수집 |
| 05 | 시사점 종합 | 경영전략을 지원할 EA의 방향성 정의 → 비전·원칙·프레임워크의 근거 |

- **경영진의 참여가 성패를 가른다**: EA 비전과 원칙은 최고경영진의 적극적인 참여와 지지 아래 수립되어야 함. 경영진 지지가 부족한 EA는 부서 이기주의와 단기 성과 압박에 밀려 좌초하기 쉬움.
- **EA팀의 커뮤니케이션 책무**: EA가 비즈니스 성과에 어떻게 기여하는지를 경영진의 언어로 설명하고 지속적으로 소통하여 지지를 확보해야 함. 초기 방향성 정립은 이해관계자 간 의견 충돌을 사전에 방지함.

### 1.2 EA 비전 수립
- 환경 분석이 끝나면 조직의 **북극성**이라 할 수 있는 EA 비전을 수립.
- 비전은 단순한 멋진 미사여구가 아니라, 다음 **3가지 요소**가 유기적으로 결합되어야 함:

| 요소 | 질문 | 예시 |
|---|---|---|
| ① 핵심 목표 | 정보화를 통해 무엇을 어느 수준까지 달성할 것인가? | 대민 서비스 처리도 50% 향상 |
| ② 핵심 가치 | 추진 과정에서 어떤 원칙을 고수할 것인가? | 데이터 무결성, 보안성 확보 |
| ③ 전략 방향 | 어떤 기술적·조직적 접근법을 취할 것인가? | 개방형 API 기반의 클라우드 통합 플랫폼 구축 |

- 이 세 가지 요소가 명확할 때 비전은 **실천 가능한 지침서**가 될 수 있음. 세 요소는 서로 분리된 것이 아니라 "무엇을(목표) · 어떤 원칙으로(가치) · 어떻게(방향)"라는 하나의 문장으로 이어져야 하며, 세 요소 중 하나라도 모호하면 하위 원칙과 로드맵 수립 단계에서 방향이 흔들림.
- **정량적 표현의 중요성**: 좋은 비전은 "고객 만족도를 높인다"처럼 추상적으로 끝나지 않고, 처리 시간 단축률·서비스 가용률·시스템 통합률 같은 **측정 가능한 목표 수치**를 함께 제시해야 실행 단계에서 성과를 검증할 수 있음.

### 1.3 원칙(Principle) 수립
- 비전이 거시적인 방향이라면, **원칙**은 매일의 실무에서 의사결정을 내릴 때 가이드가 되는 **나침반**.
- 예시: 데이터 우선 원칙, 오픈소스 및 표준 기술 우선 원칙, 보안 내재화 원칙 등.
- 좋은 원칙에는 반드시 **측정 지표**와 **예외 처리 절차**가 동반되어야 함 (01-01의 거버넌스 요건과 연결).
- 실무에서 원칙들을 체계적으로 모아둔 문서를 **원칙 카탈로그(Principle Catalog)**라고 부르며, 이는 조직의 IT 거버넌스를 지탱하는 **헌법** 역할을 함.

#### 좋은 원칙의 4가지 요건
1. 뜻이 분명해야 한다
2. 실제 의사결정에 도움이 되어야 한다
3. 모두가 지켜야 한다
4. 다른 원칙과 충돌하지 않아야 한다

- 예: "재사용 우선"과 "최신 기술 우선"이 동시에 있으면 어느 쪽이 우선인지 정하는 순간 현장이 혼란스러워짐.
- 그래서 원칙마다 **의미, 배경, 기대 효과, 지표, 예외 처리**를 함께 적어 모아둔 것이 **원칙 카탈로그**. 즉 EA의 헌법과 시행 규칙을 함께 적어둔 문서.

#### 핵심 EA 원칙 예시 모음 (화면 자료 재구성)
원칙 카탈로그가 실제로 어떻게 한 줄씩 채워지는지 감을 잡기 위해, 자주 쓰이는 원칙 유형을 배경·기대효과·측정지표 관점으로 정리하면 다음과 같음.

| 원칙 유형 | 핵심 의미 | 수립 배경 | 기대 효과 | 측정 지표 예시 |
|---|---|---|---|---|
| 데이터 자산화 원칙 | 데이터를 조직의 전략 자산으로 취급 | 부서별 데이터 산발 관리로 인한 중복·불일치 | 데이터 신뢰도·재사용성 향상 | 표준 준수율, 중복 테이블 수 |
| 보안 내재화 원칙 | 설계 초기 단계부터 보안 요건 반영 | 사후 보안 조치의 높은 비용과 취약점 | 컴플라이언스 리스크 감소 | 보안 점검 통과율, 사고 건수 |
| 표준·재사용 우선 원칙 | 신규 개발보다 표준 컴포넌트 재사용 우선 | 유사 기능의 중복 개발로 인한 비용 낭비 | 개발 비용·기간 절감 | 재사용률, 신규 개발 대비 비용 |
| 클라우드 네이티브 우선 원칙 | 신규 시스템은 클라우드 우선 설계 | 온프레미스 인프라의 확장성·비용 한계 | 탄력적 확장과 운영비 절감 | 클라우드 전환율, 인프라 비용 |
| 개방형 상호운용성 원칙 | 표준 API·개방형 인터페이스 채택 | 벤더 종속과 시스템 간 연계 어려움 | 시스템 간 통합 용이성 확보 | 표준 API 적용률, 연계 소요기간 |

- 이렇게 원칙별로 표를 채워두면, 실무에서 "이 신규 시스템을 왜 이 방식으로 설계해야 하는가?"라는 질문에 감이나 취향이 아니라 **문서화된 근거**로 답할 수 있게 됨.

### 1.4 관리 가능한 범위 한정과 과제 우선순위
- 모든 조직의 예산과 시간은 한정되어 있음. 처음부터 전사의 모든 시스템을 완벽하게 구축하려 들면 프로젝트는 십중팔구 실패함.

#### 범위 한정 4단계 (화면 자료 기준)
| 단계 | 내용 |
|---|---|
| 1단계 | 조직 범위 설정 — 전사 전체가 아니라 우선 적용할 사업부·부문을 선정 |
| 2단계 | 도메인 범위 설정 — BA·DA·AA·TA·SA 중 이번 단계에서 다룰 도메인을 한정 |
| 3단계 | 산출물 수준 설정 — 개념 수준·논리 수준·물리 수준 중 어디까지 상세화할지 결정 |
| 4단계 | 과제 우선순위 확정 — 아래 PPM 5대 평가 기준으로 실행 순서를 확정 |

- **과제 우선순위 객관적 평가(PPM)**: 다음을 다면적으로 평가하여 **PPM(프로젝트 포트폴리오 관리, Project Portfolio Management)** 관점에서 어떤 과제를 먼저 실행할지 결정:
  - 전략적 적합성
  - 리스크와 복잡도
  - 투자 대비 효과
  - 규제 대응
  - 시급성
- 범위를 먼저 좁히고 그 안에서 우선순위를 매기는 순서를 지켜야, 담당자가 "내가 지금 무엇부터 해야 하는가"에 대해 명확한 답을 가질 수 있음.

### 1.5 로드맵과 전환 아키텍처
- 우선순위가 정해지면 현재 상태에서 목표 상태(To-Be)로 나아가는 시간표인 **로드맵**을 작성.
- As-Is에서 To-Be로 한 번에 점프하는 것은 현실적으로 불가능하므로, 그 사이 단계마다 안정적으로 운영 가능한 중간 정거장을 정의해야 하는데, 이를 **전환 아키텍처(Transition Architecture)**라고 부름.

#### 로드맵 작성의 3가지 구성 요소 (화면 [그림 2-1] 기준)
| 구성 요소 | 설명 |
|---|---|
| ① 단계 구분 | As-Is → Phase 1 → Phase 2(Gap 해소) → Phase 3 → To-Be의 흐름으로 몇 개의 실행 단계로 나눌지 정의 |
| ② 프로그램 정의 | 각 단계에서 수행할 사업(프로그램) 단위 과제를 구체화 |
| ③ 전환 아키텍처 정의 | 각 단계 종료 시점에 조직이 어떤 안정적인 중간 상태에 있어야 하는지를 명세 |

- 예시 (4단계 로드맵):
  1. 1단계: 데이터 표준화와 인프라 클라우드 전환 완료
  2. 2단계: 핵심 업무 시스템 개편
  3. 3단계: 통합 분석 플랫폼 완성
- 로드맵을 그릴 때는 반드시 각 단계 사이의 "중간 상태"가 실제로 운영 가능해야 함 — 중간 정거장에서 시스템이 멈추거나 불안정하면 이행 프로젝트 자체가 실패로 이어지므로, 전환 아키텍처는 로드맵의 실현 가능성을 검증하는 장치로 기능함.

## 2. 2단계: 정보 구성 정의 (메타모델 구축) — 오늘 챕터의 핵심

### 2.1 메타모델이란?
- **메타모델(Meta-model)**: 모델을 설명하기 위한 상위 모델, 즉 **데이터를 담기 위한 틀**.
- 메타모델은 다음 **3가지 핵심 요소(OAR)**로 구성됨:

| 요소 | 영문 | 의미 | 예시 |
|---|---|---|---|
| **객체 (Object)** | Object | 관리할 대상 | 업무 프로세스, 애플리케이션, 데이터 엔티티, 서버 장비 |
| **속성 (Attribute)** | Attribute | 객체가 갖고 있는 고유의 특성 | 서버의 IP 주소, 시스템의 소유 부서, 담당자 연락처 |
| **관계 (Relationship)** | Relationship | 객체와 객체 간을 연결하는 고리 | "이 애플리케이션은 저 서버 위에서 구성된다" |

- 이 **OAR 구조**가 정교하게 정의되어야만, 앞서(01-01) 강조한 **추적성과 영향 분석**이 시스템적으로 작동할 수 있음.

### 2.2 메타모델 속성의 4가지 범주 (예: 애플리케이션 객체)
애플리케이션이라는 객체 하나를 관리할 때 부여하는 속성들은 크게 4가지 범주로 나뉨:

| 범주 | 질문 | 예시 |
|---|---|---|
| ① 기본 정보 | 이게 무엇인가? | 시스템 ID, 명칭, 버전, 운영 상태 |
| ② 거버넌스 정보 | 누가 책임을 지는가? | 소유 부서, 관리 책임자, 보안 등급 |
| ③ 기술 정보 | 어떤 기술로 만들어졌는가? | 개발 언어, 프레임워크, 연동 DBMS |
| ④ 관계 정보 | 어디에 연결되는가? | 지원하는 비즈니스 프로세스, 입출력 데이터, 연계 인터페이스 |

- 특히 **관계 정보 속성**은 데이터베이스의 **외래키(FK)** 역할을 하여, 전사 아키텍처의 연결성을 지원하는 핵심적인 기능을 부여함.
- 화면 자료의 속성 정의 예시를 보면, 실제 관리 카드에는 위 4범주마다 "속성명 — 정의 — 값의 예시 — 관리 주체"가 함께 기록되어, 단순히 항목명만 나열하는 것이 아니라 **누가 그 값을 최신으로 유지할 책임이 있는지**까지 명시하는 것이 특징. 이렇게 관리 주체를 못 박아두어야 시간이 지나도 정보가 방치되지 않고 실제로 갱신됨.

### 2.3 데이터 원칙 8가지와 데이터 표준 절차
- 데이터 원칙은 8개로 다소 부담스러워 보이지만 흐름은 단순함:
  > 데이터는 **자산**이므로 → **주인을 정하고** → **데이터 표준을 따르며** → **재사용하기 좋은 구조**를 만들고 → **중복을 줄이고** → **안전하게 공유**하고 → **품질을 지키자**

#### 데이터 원칙 8가지 (화면 자료 재구성)
| # | 원칙 | 한 줄 의미 |
|---|---|---|
| 1 | 데이터 자산성 | 데이터는 조직의 전략적 자산으로 관리한다 |
| 2 | 데이터 주체자 정의 | 모든 데이터에는 책임지는 소유자(Data Owner)가 있다 |
| 3 | 표준 준수 | 정의된 데이터 표준과 명명 규칙을 따른다 |
| 4 | 원자성 | 데이터는 더 이상 쪼갤 수 없는 최소 단위로 정의한다 |
| 5 | 중복 최소화 | 동일 데이터를 여러 곳에 중복 저장하지 않는다 |
| 6 | 보안 | 민감도에 따라 접근을 통제하고 안전하게 보호한다 |
| 7 | 통합 | 부서 간 데이터를 상호 연계·통합할 수 있도록 설계한다 |
| 8 | 품질 | 완전성·정확성 등 품질 기준을 지속적으로 관리한다 |

- 8가지 원칙만 선언하고 끝나는 것이 아니라, 이를 실행에 옮기기 위해 **함께 정의해야 할 데이터 표준 및 관리 절차**가 뒤따라야 함:
  - 데이터 명명 규칙(표준 단어·용어·도메인 사전)
  - 접근 권한 부여·회수 절차
  - 참조 데이터(코드값) 관리 절차
  - 데이터 정제·병합(클렌징) 절차
  - 비정형 데이터 관리 방안
  - BI·분석 활용을 위한 데이터 제공 절차

#### 데이터 품질 6요소 (일상어로 이해)
| 요소 | 의미 |
|---|---|
| 완전성 | 빠짐없이 있어야 함 |
| 유일성 | 하나만 있어야 함 |
| 유효성 | 허용 규칙에 맞아야 함 |
| 일관성 | 서로 모순이 없어야 함 |
| 정확성 | 실제와 맞아야 함 |
| 적시성 | 필요할 때 있어야 함 |

- 이 원칙 아래에 접근 권한, 참조 데이터, 정제·병합, BI, 비정형 데이터 같은 구체적인 절차들이 붙어서 실제 운영이 만들어짐.

### 2.4 데이터 모델 변경 관리 — 6단계 절차
데이터 모델은 한 번 만들고 방치하면 금방 낡아버리기 때문에, 엄격한 6단계 절차를 따름:

1. **요청** — 현업/개발팀이 변경 요청
2. **검토** — 데이터 아키텍트(DA)가 준수 여부를 검토
3. **승인** — 거버넌스 기구의 승인
4. **배포** — 레퍼지토리에 배포
5. **이행** — DBA가 실제 DB에 반영
6. **검증** — DA가 승인된 모델과 실제 구축된 DB가 정확히 일치하는지 검증

- 마지막 **검증 단계가 생략되면 문서와 현실이 완전히 갈라지는 문제**가 발생함.

### 2.5 AA / TA / SA 도메인별 구축 포인트
| 도메인 | 구축 핵심 포인트 |
|---|---|
| **AA (애플리케이션 아키텍처)** | 전사 응용 프로그램의 **중복성 제거**, 시스템 간 인터페이스(API) 현황을 빠짐없이 관리하는 **포트폴리오 구축**이 핵심 |
| **TA (기술 아키텍처)** | 하드웨어, 시스템 소프트웨어, DBMS의 표준 스펙을 정의한 기술 스택(**TRM**)을 관리하여 **유지보수 비용 절감** |
| **SA (보안 아키텍처)** | 정보자산 식별 → 위협 분석 → 보안 통제 항목 매핑을 통해 **컴플라이언스 리스크 원천 차단** |

#### 도메인별 정보 구성 상세 (화면 자료 기준)
MSA와 클라우드 네이티브 전환이 확산될수록 AA·TA·SA 세 정보의 중요성은 더욱 커짐. 각 도메인이 실제로 어떤 정보를 관리하는지 구체화하면 다음과 같음.

| 구분 | AA 정보 | TA 정보 | SA 정보 |
|---|---|---|---|
| 관리 범위 | 애플리케이션 포트폴리오 전체 목록(중요도·기술상태·TCO) | 기술 스택(서비스를 구축한 기술 조합, 예: OS·WAS·DB·언어) | 보안 기준(인증 기준, 개인정보보호 법규 등 준수 규정) |
| 세부 요소 | 애플리케이션 컴포넌트(기능 모듈·서비스 단위, MSA에서는 마이크로서비스가 독립 컴포넌트) | 표준 제품(영역별 표준 하드웨어·소프트웨어 목록 → 벤더 종속 방지) | 보안 통제(기술적·관리적·물리적 통제 항목: 접근통제·암호화·백업) |
| 연계 관점 | 인터페이스(API·EAI·ETL 연계 방식과 명세) | 호환성 정보(제품 간 버전 호환성·상호운용성) | 자산-위협-통제 매핑(SABSA 개념과 연결되는 자산·위협·통제의 관계) |

- **도메인별 핵심 객체와 관리 속성 예시**: SRM(서비스 참조모델) 관점의 서비스 컴포넌트는 서비스ID·SLA·API 명세로, AA 애플리케이션은 중요도·기술 건전성·운영비용으로, TA 기술 제품은 벤더·버전·도입 상태·EoS/EoL(단종·지원종료) 일자로, SA 보안 통제는 통제 유형·관련 정책·적용 자산으로 각각 관리 속성을 구성함. 이처럼 도메인마다 관리 속성의 성격이 다르므로 메타모델 설계 시 도메인 특성에 맞는 속성 체계를 별도로 정의해야 함.

## 3. 3단계: 정보 구축 및 이행 계획

### 3.1 핵심 방법론적 격언: "현행은 상향식, 목표는 하향식"
> **현행(As-Is) 아키텍처는 상향식(Bottom-up)으로 복원하고, 목표(To-Be) 아키텍처는 하향식(Top-down)으로 설계한다.**

- **현행(As-Is) — 상향식**: 지금 조직에 실제로 존재하는 IT 자산이 무엇인지 알아내는 **조사 및 복원 작업**이기 때문. 실제 운영 중인 DB 스키마, 소스 코드, 서버 장비, 로그 같은 아주 구체적이고 미시적인 물리적 실체로부터 출발하여 상위의 논리적 모델과 개념으로 거슬러 올라가야 빠짐없이 진단할 수 있음.
- **목표(To-Be) — 하향식**: 조직이 앞으로 무엇을 지향해야 하는가를 정하는 전략에서 출발하는 설계 작업. 경영 비전, 성숙도 목표, 신기술 도입 트렌드라는 최상위 거시적 관점에서 시작하여, 그에 부합하는 데이터 표준, 업무 프로세스, 구체적인 시스템 구조로 아래를 향해 내려가면서 그려내야 하는 과정.
- 이 **상향식/하향식 원칙을 혼동하면 구축 프로젝트는 대실패**로 끝남.

#### 현행(As-Is) 아키텍처 구축 — 상향식 5단계 (화면 자료 기준)
| 순서 | 단계 | 내용 |
|---|---|---|
| 1 | 자료 수집·분석 | 모델·테이블 정의서·인터페이스 명세 수집, DB 실제 현황의 완전성·정합성·유효성, 표준화 현황 분석 |
| 2 | 현행 물리 데이터모델 | 운영 DB 개체정보로부터 역공학(Reverse Engineering)으로 생성. 한글 논리명 확보와 관계 정보 복원 |
| 3 | 현행 논리 데이터모델 | 물리 모델을 비즈니스 관점으로 한글화하고 엔터티·속성·관계의 논리 형태로 전환 |
| 4 | 현행 개념·주제영역 | 유사 엔터티를 그룹핑해 추상화 수준을 높이고, 고객·상품·계약 등 최상위 집합으로 분류 |
| 5 | 문제점·개선방향 도출 | 데이터 중복·비일관성·비표준 등 구조상 문제와 원인 분석 → 개선 방향 수립 |

#### 목표(To-Be) 아키텍처 구축 — 하향식 5단계 (화면 자료 기준)
| 순서 | 단계 | 내용 |
|---|---|---|
| 1 | 설계 3대 고려요소 | 전략 정렬 · 성숙도 목표 · 표준 및 보안 요구 반영 |
| 2 | 목표 데이터 표준·프로세스 | 개선된 용어·도메인·코드 표준 구축, 모델/품질/요구사항 관리 프로세스 정의 |
| 3 | 목표 주제영역·개념모델 | 미래 비즈니스를 포괄하는 통합 분류체계와 목표 데이터 구조의 골격 정의 |
| 4 | 목표 논리·물리 모델 | 비즈니스 규칙을 구체화한 논리 모델과 특정 DBMS에 맞춘 물리 모델 정의 |
| 5 | 목표 데이터 흐름 | 시스템 간 데이터 교환의 미래 모습을 통합 구조도·흐름도로 정의 |

- 두 흐름을 나란히 놓고 보면, 현행은 "물리(구체) → 논리 → 개념(추상)"으로 **올라가는** 방향이고, 목표는 "전략(추상) → 표준 → 개념 → 논리·물리(구체)"로 **내려가는** 방향임이 시각적으로 대비됨. As-Is는 있는 그대로 문서화하고, To-Be는 전략에서 출발해 설계한다는 것이 이 대비의 핵심 메시지.

### 3.2 갭 분석 (Gap Analysis)
- 상향식으로 복원된 현행(As-Is)과 하향식으로 설계된 목표(To-Be)가 준비되면, 두 상태의 차이를 비교하는 **갭 분석**을 수행.
- 갭 분석의 목적은 단순히 차이점을 나열하는 것이 아니라, 현재와 미래의 격차를 메우기 위해:
  - 어떤 시스템을 **신규 개발**할 것인가
  - 어떤 시스템을 **통합**할 것인가
  - 어떤 레거시를 **폐기**할 것인가
  
  등을 결정하여 구체적인 **이행 과제**로 전환하는 것.
- 각 이행 과제에는 **목표, 수행 기간, 소요 예산, 기대 효과**가 명시되어야 비로소 실천 가능한 로드맵이 완성됨.

#### 갭 분석 → 이행 과제 도출의 3단계 (화면 자료 기준)
| 단계 | 내용 |
|---|---|
| ① 차이 식별 | 두 아키텍처 상태 간 차이를 목록화 — 신규로 추가되어야 할 시스템, 통합되어야 할 중복 시스템, 폐기되어야 할 노후 시스템, 변경되어야 할 기술 표준 |
| ② 과제(프로젝트) 정의 | 각 차이를 해결할 실행 단위를 정의 — 목표·범위·예상 기간, 필요 자원·기대 효과 |
| ③ 우선순위·이행계획 | 평가 기준에 따라 점수화하여 순서를 결정하고 장기 로드맵으로 편성 (5점 척도 평가 후 종합 점수 산정, 프로그램 단위로 묶어 단계 배치) |

- 이때 갭은 "의도적 생략"과 "누락/미정의"를 구분해서 분류해야 함 — 의도적으로 범위에서 뺀 항목까지 이행 과제로 잘못 등록하면 우선순위 산정이 왜곡됨.

#### Gap → 프로젝트 평가 매트릭스 예시 (화면 자료 재구성)
실제로는 차이 항목을 나열한 뒤, 여러 평가 기준에 점수를 매겨 우선순위를 정량적으로 산출함. 아래는 그 구조를 보여주는 예시.

| 과제명 | 비즈니스 영향 | 기술적 난이도 | 타 시스템 파급 | 규제 시급성 | 기대 가치 | 종합 점수 | 우선순위 |
|---|---|---|---|---|---|---|---|
| 노후 CRM 시스템 교체 | 높음 | 높음 | 높음 | 낮음 | 높음 | 상위권 | 1순위 |
| 개인정보 암호화 강화 | 높음 | 보통 | 보통 | 높음 | 낮음 | 중상위권 | 2순위 |
| 그룹웨어 모바일 기능 추가 | 보통 | 낮음 | 낮음 | 낮음 | 보통 | 하위권 | 3순위 |

- 이러한 매트릭스는 담당자의 주관적 판단이 아니라, 사전에 합의된 평가 기준과 배점 체계에 따라 우선순위를 산출함으로써 **의사결정의 객관성과 투명성**을 확보하는 도구로 사용됨.

## 4. EAMS (전사 아키텍처 관리 시스템)

- 이 모든 방대한 아키텍처 작업을 수작업으로 관리할 수는 없음. 이를 뒷받침하는 시스템이 바로 **EAMS (Enterprise Architecture Management System, 전사 아키텍처 관리 시스템)**.
- EAMS는 3가지 영역으로 구성됨:

| 영역 | 내용 |
|---|---|
| **정의 영역** | 모델링 도구를 통해 아키텍처 산출물들을 직접 그리고 생성 |
| **관리 영역** | 중앙 레퍼지토리에서 버전 제어, 권한 관리, 메타데이터 및 개체 간 링크 관계를 일관성 있게 통제 |
| **활용 영역** | 포탈 시스템을 통해 전사 임직원과 개발자가 아키텍처 카탈로그를 조회하고 분석하여 활용 |

#### 정의·관리·활용 3대 영역 상세 (화면 [그림 2-3] 기준)
세 영역은 서로 단절된 것이 아니라 **API로 유기적으로 연동**되어야 정보의 생성-관리-활용이 끊기지 않음.

| 영역 | 구성 요소 | 세부 내용 |
|---|---|---|
| 정의 (Definition) | EA/데이터 모델링 도구 | EA 모델링 도구(ArchiMate·UML·BPMN 등), 데이터 모델링 도구(ERD 등) — 아키텍처 정보를 "생성"하여 레퍼지토리와 실시간 연동 |
| 관리 (Management) | EA 레퍼지토리 | 형상관리(버전·이력), 접근제어(역할 기반 권한), 추적성 관리(링크와 영향분석), 메타데이터 관리, 외부 연동 API(모델링 도구·PMS 등) |
| 활용 (Utilization) | EA 포털 | 맞춤형 뷰·대시보드(경영진·현업·개발자 역할별 화면), 카탈로그 및 검색(애플리케이션 카탈로그, 데이터 사전), 통계 및 리포팅(현황·표준 준수율·활용 통계) |

- 즉 정의 영역에서 만든 산출물이 API를 통해 관리 영역(레퍼지토리)에 실시간 반영되고, 관리 영역의 정보가 다시 API를 통해 활용 영역(포털)으로 흘러가는 **끊김 없는 순환 구조**가 EAMS의 핵심 설계 목표.

## 5. 데이터 품질 사이클과 보안 정책

- 품질과 보안은 마지막에 붙는 부가 기능이 아님.
- **품질**: 핵심 데이터를 정하고 → 지표를 정의하고 → 측정하고 → 원인을 찾아 개선하고 → 다시 측정하는 **순환 구조**. 즉 한 번 정지하고 끝나는 일이 아님.
- **보안**: 데이터 등급, 최소권한, 데이터 보호(암호화·마스킹), 감사이력, 교육을 **설계 단계부터** 포함.

#### 데이터 품질 관리 사이클 6단계 (화면 자료 기준)
| 단계 | 명칭 | 내용 |
|---|---|---|
| 01 | 핵심 데이터 선정 | 고객·제품 마스터 등 관리 우선순위가 높은 데이터를 선정 |
| 02 | 품질 지표 정의 | 완전·유일·정확·적시성 등 측정할 지표를 정의 |
| 03 | 품질 측정 | 프로파일링·대시보드를 통해 실제 데이터 품질을 측정 |
| 04 | 원인 분석 | 유효성 검증 미비 등 품질 저하의 근본 원인을 분석 |
| 05 | 개선 | 앱 수정·정제 등 실제 개선 작업을 수행 |
| 06 | 재평가 | 향상 여부를 재측정하여 사이클을 다시 회전 |

#### 데이터 보안 정책 6요소 (화면 자료 기준)
| 요소 | 내용 |
|---|---|
| 데이터 자산 분류 | 중요도·민감도 등급(대외비·개인정보·일반)별 보호대책 차등 적용 |
| 접근 권한 관리 | Need-to-Know·최소 권한 원칙, 역할 기반 부여 및 정기 검토 |
| 개인식별정보(PII) | 수집·이용·제공·파기 전 과정 법규 준수, 가명·익명처리 적용 |
| 암호화 및 마스킹 | 저장·전송 시 암호화, 개발·테스트 환경은 마스킹 적용 |
| 감사 및 이력 관리 | 모든 접근·변경 이력 기록, 이상행위 탐지 모니터링 |
| 보안 교육 | 전 임직원 정기 교육으로 보안 인식 제고 |

> **핵심 한 문장**: 품질은 계속 측정해서 개선하는 일을 반복하고, 보안은 처음부터 내재화한다.

## 6. 챕터 2 마무리 — 핵심 확인 질문 (Self-Check)

1. **Q. EA 구축의 3대 마일스톤 단계는 무엇인가?**
   A. 방향 수립, 정보 구성 정의(메타모델), 정보 구축 및 이행 계획

2. **Q. 메타모델의 뼈대를 이루는 OAR은 각각 무엇인가?**
   A. 오브젝트(객체), 어트리뷰트(속성), 릴레이션십(관계)

3. **Q. 현행과 목표 아키텍처를 구성하는 접근 방식의 차이는 무엇인가?**
   A. 현행은 상향식 조사, 목표는 하향식 설계가 원칙이다.

4. **Q. 범위 한정 4단계는 무엇인가?**
   A. 조직 범위 설정 → 도메인 범위 설정 → 산출물 수준 설정 → 과제 우선순위 확정(PPM)

5. **Q. EAMS의 3대 영역과 그 연결 방식은?**
   A. 정의(모델링 도구)-관리(레퍼지토리)-활용(포털) 3영역이 API로 유기적으로 연동되어 정보의 생성-관리-활용이 끊기지 않도록 구성된다.

### CHAPTER 2 SUMMARY (화면 자료 기준)

| 구분 | 핵심 요약 |
|---|---|
| 방향 수립 | 환경분석 → 비전(목표·가치·방향) → 원칙 → 범위·우선순위 → 로드맵 |
| 전환 아키텍처 | 단계마다 안정적 중간 상태를 정의해야 변화가 예측 가능해진다 |
| 메타모델 우선 | 객체-속성-관계를 먼저 합의해야 지속 가능한 정보체계가 만들어진다 |
| As-Is 상향식 / To-Be 하향식 | 역공학으로 현행을 복원하고, 전략에서 목표를 설계한다 |
| Gap → 과제 → 로드맵 | 차이를 프로젝트로 정의하고 다기준 평가로 순서를 정한다 |

#### 프로젝트 게이트 체크리스트 (Go/No-Go)
- 분석·설계·개발·테스트·이행 단계마다 EA/DA 표준·모델·보안 체크리스트 제출을 의무화
- 통과하지 못하면 다음 단계로 진행 불가
- 메타모델 없이 문서만 축적하지 않았는가?

#### 자주 하는 실수 TOP 3
1. **범위를 좁히지 않고 전사 전체를 한 번에 구축하려는 실수** — 예산·기간이 초과되며 프로젝트가 표류함
2. **전환 아키텍처(중간 정거장) 없이 로드맵을 설계하는 실수** — 이행 도중 시스템이 불안정한 상태로 방치됨
3. **품질·보안을 이행 계획의 마지막 단계로 미루는 실수** — 설계 단계에 내재화하지 않으면 사후 비용이 급증함

| 로드맵 3요소 | 단계 구분, 프로그램 정의, 전환 아키텍처 정의 |
| 메타모델 (Meta-model) | 모델을 설명하는 상위 모델, 데이터를 담는 틀 |
| OAR | Object(객체) · Attribute(속성) · Relationship(관계) — 메타모델의 3대 구성요소 |
| 애플리케이션 속성 4범주 | 기본 정보, 거버넌스 정보, 기술 정보, 관계 정보 |
| 데이터 원칙 8가지 | 자산성, 주체자 정의, 표준 준수, 원자성, 중복 최소화, 보안, 통합, 품질 |
| 데이터 품질 6요소 | 완전성, 유일성, 유효성, 일관성, 정확성, 적시성 |
| 데이터 모델 변경관리 6단계 | 요청 → 검토 → 승인 → 배포 → 이행 → 검증 |
| AA/TA/SA 구축 포인트 | AA: 중복 제거·인터페이스 관리, TA: TRM 관리로 비용 절감, SA: 정보자산 식별→위협분석→통제 매핑 |
| 현행 구축 5단계(상향식) | 자료 수집·분석 → 물리모델 → 논리모델 → 개념·주제영역 → 문제점·개선방향 |
| 목표 구축 5단계(하향식) | 설계 고려요소 → 표준·프로세스 → 주제영역·개념모델 → 논리·물리모델 → 데이터 흐름 |
| 갭 분석 (Gap Analysis) | As-Is와 To-Be의 차이를 신규개발/통합/폐기 등 구체적 이행 과제로 전환, 다기준 평가 매트릭스로 우선순위 산정 |
| EAMS | Enterprise Architecture Management System — 정의(모델링 도구)·관리(레퍼지토리)·활용(포털) 3영역이 API로 연동되는 EA 관리 시스템 |
| 데이터 품질 사이클 | 핵심데이터 선정→지표정의→측정→원인분석→개선→재평가의 순환 구조 |
| 데이터 보안 정책 6요소 | 자산 분류, 접근 권한 관리, PII 보호, 암호화·마스킹, 감사·이력 관리, 보안 교육 |
| 보안 내재화 | 데이터 등급, 최소권한, 암호화·마스킹, 감사이력, 교육을 설계 단계부터 포함 |
