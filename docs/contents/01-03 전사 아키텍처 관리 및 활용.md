# SECTION 1. 관리 체계

## 1. EA 거버넌스란 무엇인가

> **EA가 특정 개인의 역량이 아닌, 조직의 제도화된 시스템으로 작동하게 만드는 메커니즘**

거버넌스는 특정 전문가 개인의 우수한 역량에 의존하던 업무 방식을, 조직의 표준화된 제도로 정착시키기 위한 장치임.

### 거버넌스를 구성하는 4대 요소

| # | 요소 | 설명 |
|---|---|---|
| 1 | **조직 (Organization)** | EA를 관리할 위원회와 전담팀을 구성한다 (= EA 의사 결정을 내릴 공식 기구) |
| 2 | **역할과 책임 (RACI)** | 각 조직·구성원의 권한과 책임을 명확히 한다 |
| 3 | **프로세스 (Process)** | EA 활동을 수행할 표준 절차를 정한다 (= 정기적이고 반복 가능한 운영 절차) |
| 4 | **인력 역량 (People)** | 수행 인력의 전문 역량을 지속적으로 강화한다 (= 담당 아키텍트들의 전문성 육성) |

조직의 규모가 작다면 기존 위원회가 역할을 겸유할 수도 있지만, 규모가 크다면 **전담 조직(EA 전담팀, EA Office)을 반드시 두어야** 함.

### 조직 설계 시 고려요소 3가지

| 구분 | 내용 |
|---|---|
| **IT 조직의 규모** | 중소 규모 → 기존 정보화 위원회가 EA 위원회를 겸하고 내부 전문가를 양성. 대규모 → 독립 EA 전담조직 신설 + 전사 운영위원회 구성 |
| **EA 구축의 목적** | IT 표준화·아키텍처 관리 목적 → IT 표준 조직과 통합형이 유리. 차세대 등 대형 프로젝트 지원 목적 → PMO가 EA 관리 기능 수행 가능 |
| **현업과 IT의 관계** | 현업 소통이 핵심 과제라면 비즈니스 요구를 분석·중재하는 **BA(Business Architect)**의 역할과 조직 내 위상을 강화해야 한다 |

### (참고) 전문가 육성 3단계 — 조직과 인력 배치만으로는 부족하다
1. **역량 정의**: EA 관리 직무에 필요한 리더십·기술·활용 역량을 정의하고 직급별 기술 수준을 명확히 한다.
2. **수준 평가**: 내부 아키텍트의 보유 기술 수준을 객관적으로 평가해 부족한 부분을 파악한다.
3. **육성 계획**: 개인별 경력개발경로(CDP)와 교육·멘토링 프로그램으로 역량을 강화한다.

## 2. EA 거버넌스 조직 4계층 [표 3-1]

> 전략적 의사결정을 담당하는 위원회 + 실무를 총괄하는 전담팀 구조

| 조직 구분 | 조직명 | 구성 | 주요 역할 및 책임 (RACI) |
|---|---|---|---|
| **위원회** | EA 운영위원회 (Steering Committee) | 위원장 CIO, 주요 현업·IT 부서장 | EA 비전 및 주요 정책 승인(**A**), 대규모 IT 투자 의사결정, 부서 간 이슈 조정, EA 성과 평가 및 방향 제시 |
| **전담 조직** | EA팀 (EA Office) | EA/DA 총괄 | EA 프레임워크·표준 개발 및 관리(**R**), 아키텍처 검토·컨설팅, 변경관리 프로세스 운영, EA 시스템 관리, 전사 교육·홍보 |
| **실무 그룹** | 도메인별 아키텍트 그룹 (BA/DA/AA/TA/SA) | 도메인 전문가 (모델러, DBA 등) | 도메인별 아키텍처 모델링 및 표준 적용(**R**), 현업 요구 분석·기술 검토, EA팀과 협업, 신기술 동향 분석·도입 제안 |
| **참여자** | 현업 부서 및 IT 개발·운영팀 | 모든 임직원 | EA 표준 준수, 데이터 활용 및 요구사항 제기, 변경관리 프로세스 참여(**C, I**), EA 정보의 정확성·최신성 유지 협조 |

- 구조: 최상단의 **운영위원회**가 방향을 승인하고, 중간의 **EA 전담 조직과 도메인 아키텍트**들이 실제 표준을 만들고 관리하며, 일선의 **현업과 개발자**들이 준수하고 피드백을 제공하는 수직적인 협력 체계.

## 3. 핵심 역할 5종과 책임 범위

> 역할이 명확하지 않으면 표준은 방치되고 변경은 통제되지 않는다.

| # | 역할 | 주요 내용 | RACI |
|---|---|---|---|
| 1 | **CIO / EA 담당임원** | 전사 정보화 전략의 최고 책임자. EA 비전·방향성 제시, 주요 EA 정책 승인, 부서 간 중대 이슈 조정 | **A** (Accountable, 최종 승인자) |
| 2 | **EDA / EA 전담조직** | EA·DA 실무 총괄. 정책·표준 초안 수립, 변경관리 프로세스 운영, 전사 통합모델 개발·유지, 프로젝트 아키텍처 컨설팅 | (총괄) |
| 3 | **DA (데이터 아키텍트)** | 데이터 아키텍처 실무 전문가. 전사 데이터 표준 개발·관리, 신규 모델의 표준 준수 검토, 데이터 통합·품질 관리 주도 | **R** (Responsible) |
| 4 | **모델러 / DBA** | 모델러: 도메인별 모델링, 현업 요구 분석, EA 표준 적용 — 현업과 개발팀의 가교. DBA: 물리 DB 설계·구축·운영, 성능·보안·백업·복구 관리 | — |
| 5 | **사용자 (User)** | 현업 실무자·데이터 분석가. 시스템·데이터를 업무에 활용, 품질 문제 제기, 신규 기능·데이터 요구 제기 | **C, I** (Consulted, Informed) |

- CIO는 라시(RACI)차트 기준 **어카운터블(A)**, EA 전담(EDA)은 **프레임워크와 변경 관리 프로세스를 직접 운영**.
- 역할 분담이 모호해지면 책임 소재가 사라지므로 RACI 매트릭스를 통한 명확한 정의가 필수적.

## 4. 6대 관리 프로세스와 선순환 구조 [그림 3-1]

> 중앙의 EA 레포지터리·포털이 모든 프로세스의 정보 허브 역할을 한다.

EA 관리 프로세스는 **1년 단위의 시계열적 흐름**으로 이해하면 쉬움. 총 6개 프로세스는 다음과 같이 시기별로 묶임:

| 시기 | 프로세스 | 내용 |
|---|---|---|
| **연초** | ① 기획 | 방향 재점검, 연간 운영계획과 KPI 수립, 중점 추진과제 설정 |
| **연중** | ② 변경관리 | 환경 변화에 따라 통제된 절차로 아키텍처를 갱신 — 검토·승인·이행·교육·평가 |
| **연중** | ③ 준수통제 | 프로젝트·운영 시스템의 표준 준수 정기 점검, 기술 지원, 예외 심의·관리 |
| **연중** | ④ 활용지원 | 표준 공지·홍보, 정기 교육, 활용 사례 발굴·전파, 아키텍처 관점 컨설팅 |
| **연중** | ⑤ 시스템 운영 | 레포·포털의 권한 관리, 백업·복구, 보안 점검, 가용성 모니터링 |
| **연말** | ⑥ 평가 | KPI 달성도 측정, 성숙도 진단, 투자·운영 성과 분석 → 차기 기획에 환류 |

**연간 선순환**: 기획 → 준수통제·활용지원·변경관리 → 평가 → 다시 기획

- 연말의 평가 결과는 다시 다음 연도의 기획 프로세스로 피드백되어 들어감. 이 선순환 구조가 작동해야 EA가 살아 움직일 수 있음.
- 중앙의 **EA 레포지터리 & 포털(정보 허브)**이 6개 프로세스 전체를 관통하는 정보 기반.

## 5. 변경관리 RACI 매트릭스

> 누가 무엇을 해야 하는지에 대한 혼란을 방지하고 투명성을 확보한다.

아키텍처의 변경이 발생했을 때 혼란을 방지하는 도구가 바로 라시(RACI) 매트릭스.

| 활동 (Activity) | CIO/EDA | DA (EA팀) | 모델러 | DBA | 사용자 |
|---|---|---|---|---|---|
| 변경 요구사항 접수 및 분석 | I | R | C | C | C |
| 변경 영향 분석 | I | R | C | C | I |
| 표준/모델 변경안 수립 | I | R | R | C | C |
| 변경안 검토 및 승인 | **A** | R | I | I | C |
| 변경 내용 시스템 반영 | I | I | I | R | I |

### RACI 정의
- **R — Responsible (실행 책임)**: DA·EA팀이 변경 요청 접수, 영향 분석, 표준·모델 변경 조율, 과정 감독을 담당한다.
- **A — Accountable (최종 책임)**: CIO/EDA가 원칙·표준 변경의 최종 승인 권한을 갖고 승인 사항을 전사에 공표한다.
- **C / I — Consulted / Informed (협의·통보 대상)**: 사용자는 요구 제기, 변경안 검토 의견 제시, 교육 참여, 업무 적용을 담당한다.

> **핵심 원칙**: 모든 변경 작업에서 A와 R은 단 하나씩만 명확하게 지정되어 있어야 의사 결정의 지연을 막을 수 있다.

# SECTION 2. 관리 시스템 (EAMS)

## 6. EAMS의 4대 구성요소

> EA 정보의 단일 진실 공급원(SSoT)이자 거버넌스 프로세스를 자동화·효율화하는 통합 플랫폼

| # | 구성요소 | 핵심 동사 | 설명 |
|---|---|---|---|
| 1 | **모델링 도구** | 만든다 | 아키텍트·모델러가 산출물을 작성하는 소프트웨어. ArchiMate·UML·BPMN 지원 EA 도구, ERD 작성용 데이터 모델링 도구. ▶ 레포지터리와 실시간 연동되어 결과가 즉시 반영되어야 한다. |
| 2 | **레포지터리** | 저장·연결한다 | EAMS의 심장부. 모든 아키텍처 정보를 메타모델에 따라 구조화하여 저장하는 중앙 DB. 객체 간 관계 관리, 버전 통제, 접근 제어. ▶ 단순 파일 저장소가 아니다. |
| 3 | **포털** | 찾아보고 활용한다 | 웹 브라우저로 레포지터리 정보에 접근하는 인터페이스. 검색·조회·시각화. ▶ 기술 지식이 없는 현업 사용자도 아키텍처 정보를 활용할 수 있게 한다. |
| 4 | **분석·의사결정 지원 도구** | 수행한다 | 레포지터리 데이터 기반의 복잡한 분석 수행. 영향 분석, 현행-목표 비교 분석, 포트폴리오 분석, 시나리오 시뮬레이션. ▶ EA의 가치를 실증하는 핵심. |

> 네 구성요소는 개방형 API로 연결되어 아키텍처 정보의 **생성 → 관리 → 활용 → 분석**의 전 생애주기를 끊김 없이 지원해야 한다.

## 7. EAMS 핵심 기능 8가지 [표 3-2]

> 기능 요구사항은 레포지터리·포털·분석도구·연동의 4개 구분으로 정리한다.

| # | 기능 | 설명 |
|---|---|---|
| ① | **버전·형상 관리** | 변경 이력 추적, 특정 시점 베이스라인 저장·비교 |
| ② | **역할 기반 접근제어** | 역할별 조회·수정·삭제 권한의 세밀한 제어(RBAC) |
| ③ | **활용 통계·대시보드** | 자주 활용되는 정보와 참여 사용자 통계로 활용도 측정 |
| ④ | **현행-목표 비교 분석** | As-Is와 To-Be를 시각적으로 비교해 Gap과 이행과제 도출 지원 |
| ⑤ | **참조모델 연계** | 산출물을 BRM·DRM·TRM에 매핑해 일관성 검증 및 기준 분석 |
| ⑥ | **사용자 맞춤형 뷰** | 경영진·현업·개발자 관심사에 맞춘 뷰와 대시보드 제공 |
| ⑦ | **영향 분석** | 특정 구성요소 변경의 파급효과를 자동 추적·시각화하여 리스크 사전 평가 |
| ⑧ | **개방형 API** | CMDB·PPM·ITSM 등과 연동해 EA 정보가 고립되지 않게 한다 |

### 8가지 세부 기능을 4가지 핵심 행위로 재분류

| 핵심 행위 | 해당 기능 | 실무적 의미 |
|---|---|---|
| **지킨다** | 버전·형상 관리, 역할 기반 접근제어 | 정보의 무결성 보장 및 무단 변경 방지 |
| **비교한다** | 현행-목표 비교, 영향 분석 | 변경 리스크를 사전에 식별하고 대응 |
| **보여준다** | 활용 통계 뷰, 사용자 맞춤형 대시보드, 참조 모델 연계 | 직관적인 정보 탐색 및 의사결정 지원 |
| **연결한다** | 개방형 API, CMDB·PPM·ITMS 연동 | 타 시스템과의 실시간 데이터 동기화 지원 |

- 특히 IT 자산 관리(CMDB)나 프로젝트 관리(PPM) 등을 API로 연계했을 때, EAMS는 진정한 **전사 정보의 허브**로 거듭날 수 있음.

## 8. EAMS 도입이 만드는 4가지 효과

> IT 효율성을 넘어 비즈니스 민첩성과 전략적 의사결정을 지원한다.

| # | 효과 | 설명 |
|---|---|---|
| 1 | **공통분류·표준 준수 강화** | 참조모델과 표준 라이브러리가 모든 프로젝트를 공통 분류체계·표준 기술로 유도 → 전사 일관성과 상호운용성 제고 |
| 2 | **산출물 공유·소통 개선** | 중앙 레포지터리와 포털로 모든 이해관계자가 동일한 최신 정보에 접근 → 부서 간 장벽 해소, 오해·재작업 감소 |
| 3 | **투자중복 방지** | 애플리케이션 포트폴리오 관리(APM)로 유사·중복 기능 앱을 식별·통폐합 → 라이선스·유지보수 비용 절감 |
| 4 | **변경·감사 대응력 향상** | 추적성 기반으로 변경 파급효과를 신속 분석하고, 감사 시 요구 정보(구성·데이터 효율)를 정확·신속하게 제출 |

### (참고) 자주 하는 실수 — 도입 후 운영 규정·교육 없이 방치 → 운영조직·SOP·지표까지 함께 설계할 것
- 고가의 EAMS를 도입하고도 활용하지 못하는 이유는 시스템 도입 자체에만 집중하기 때문이다.
- 도입 기획 단계부터 전담 운영조직의 역할과 책임을 명확히 정의한다.
- 아키텍처 정보의 등록·변경·폐기 절차를 담은 표준 운영절차(SOP)를 수립한다.
- 활용도를 측정할 KPI(정보 현행화율, 포털 접속자 수 등)를 설정해 모니터링한다.
- ▶ 시스템은 도구일 뿐이며, 그 가치는 조직·프로세스·성과관리가 함께 갖춰질 때 발현된다.

# SECTION 3. 활용과 성과

## 9. 활용① 목표 아키텍처 이행 지원 (대규모 IT 프로젝트 생애주기)

> 차세대 구축·클라우드 전환 같은 대규모 혁신 프로젝트의 핵심 기준서 역할

| # | 단계 | 내용 |
|---|---|---|
| 01 | **요구사항 분석** | 프로젝트 요구사항이 전사 BA와 목표에 부합하는지 검토하고 요구를 명확화하는 기준 |
| 02 | **설계** | 설계 산출물이 목표 아키텍처(DA·AA·TA·SA) 원칙·표준을 준수하는지 검토 — 설계 검토(Architecture Review) |
| 03 | **테스트 및 이행** | 설계대로 구현되었는지 검증하고, 운영 전환 계획이 타 시스템에 미치는 영향을 분석 |
| 04 | **프로젝트 관리 게이트** | 착수·분석·설계·종료 단계별 Go/No-Go 의사결정 시 EA 준수 여부를 핵심 검토 항목으로 포함 |

### (참고) 개별 프로젝트가 전사 방향성과 어긋나는 것을 방지하는 장치
- EA는 프로젝트를 통제하기 위한 규제가 아니라, 중복 설계와 재작업을 줄여주는 **'기준서'**로 제시되어야 한다.
- 설계 검토는 지적이 아닌 컨설팅 형태로 운영할 때 수용성이 높아진다 — EA팀의 역할은 감독과 기술 가이드를 겸한다.
- 게이트 통과 조건을 문서화해 두면 프로젝트팀이 착수 시점부터 EA 요건을 설계에 반영한다.

핵심 포인트: **EA팀이 프로젝트의 발목을 잡는 규제 기관이 아니라, 중복 투자와 아키텍처 오류를 미리 막아주는 전문 컨설턴트 역할로 인식되어야 한다.**

## 10. 활용② 상시 IT업무 지원 (평상시 일상 업무)

> 대규모 프로젝트뿐 아니라 일상의 기획·개발·운영 품질을 높이는 데 지속적으로 활용된다.

| # | 요소 | 설명 |
|---|---|---|
| 1 | **표준 확산** | 개발자가 EA 포털에서 표준 기술(TRM), 표준 데이터모델(DRM), 표준 API 목록을 조회·재사용. ▶ 개발 생산성 향상과 일관성 확보 |
| 2 | **품질·보안 내재화** | 시스템 변경 시 데이터 품질·보안 영향을 사전 분석하고, EA에 정의된 품질 기준과 보안 통제를 설계에 반영하도록 강제. ▶ 사후 대응 비용 절감 |
| 3 | **데이터 거버넌스 실행** | 생성부터 폐기까지 소유권·품질·보안·접근제어를 EA 원칙과 절차에 따라 관리. 이슈 발생 시 데이터 흐름도·모델로 원인 규명. ▶ 신속한 문제 해결 |
| 4 | **IT 투자·성과 관리** | 신규 투자 기획 시 기존 시스템과의 기능 중복 여부와 목표 아키텍처 부합성을 검토, 포트폴리오 주기 평가로 저가치 시스템 퇴출 근거 확보. ▶ 투자 의사결정의 합리성 |

- 개발자는 포탈에서 표준 API와 데이터 용어를 조회해서 재사용, 기획자는 신규 사업 구상 시 기존 시스템과의 중복 여부를 즉시 비교.

### Tip — 현업 KPI에 EA 활용지표를 연동하라
- IT 개발팀 KPI에 "표준 컴포넌트 재사용률", "EA 설계 표준 준수율"을 포함하고, 현업 데이터 관리 부서 KPI에 "데이터 품질 목표 달성률", "표준 용어 정의율"을 반영한다.
- EA 지표가 개인·부서 성과에 직접 영향을 미치면, 구성원은 EA 표준을 지켜야 할 규제가 아니라 목표 달성을 위해 관리할 대상으로 인식하게 된다.
- (스크립트 보충) 이런 상황을 정착시키는 가장 강력한 장치가 바로 **KPI 연계**이다. 설계 표준 준수율, 데이터 표준 재사용률 같은 지표를 부서 및 담당자의 성과 지표에 반영하는 순간, EA는 강제 규정이 아니라 달성해야 할 실무 목표로 활용된다.

## 11. 활용 시나리오 5종 [표 3-3]

> 누가 · 무엇을 · 어떤 EA 정보로 · 어떤 효과를 얻는가

| 시나리오 | 담당자 | 주요 활동 | 활용 EA 정보 | 기대 효과 |
|---|---|---|---|---|
| **신규 사업 기획** | IT 기획자 | 지원해야 할 비즈니스 기능·프로세스를 식별하고 기존 시스템과의 연관성·중복 가능성 검토 | BA(기능모델·프로세스모델), 애플리케이션 포트폴리오 | 전략적 정렬 강화, 중복 투자 방지 |
| **시스템 설계 검토** | 아키텍트 | 설계 산출물이 전사 표준·목표 아키텍처를 준수하는지 검토하고 개선 의견 제시 | 목표 아키텍처, TRM, DRM, 표준 패턴 | 설계 품질 향상, 상호운용성 확보 |
| **정보보호 승인** | 보안 담당자 | 처리 데이터의 보안 등급을 식별하고 관련 정책·통제 항목의 적절한 적용 여부 심의 | SA(보안정책·통제목록), 데이터 등급 | 보안 규제 준수, 정보보호 리스크 감소 |
| **데이터 표준 적용** | 모델러·개발자 | 신규 테이블·컬럼 정의 시 표준 용어사전을 조회해 표준 용어·도메인·코드 준수 | DRM, 표준 용어사전, 표준 코드 | 데이터 일관성 및 통합 용이성 확보 |
| **데이터 품질 개선** | 데이터 관리자 | 품질 측정 결과의 오류 원인을 데이터 흐름도·모델로 추적하고 개선 방안 수립 | 데이터 흐름도, 데이터 모델, 품질 측정 결과 | 신뢰성 있는 데이터 기반 의사결정 |

- IT자는 애플리케이션 포트폴리오를 조회해 중복 투자를 방지하고, 데이터 아키텍트는 DRM과 표준 용어 사전을 통해 신규 테이블을 정제하며, 보안 관리자는 보안 통제 매트릭스를 통해 취약점을 점검함.
- (강의 코멘트) 챕터 1에서 배운 수많은 산출물들이 드디어 현장에서 주인공으로 활력하는 장면을 이 표를 통해 확인할 수 있음.

## 12. EA 성과 측정 KPI 4관점

> 성숙도와 전략 목표에 따라 적절한 지표를 선정한다 — 지지 확보의 근거가 된다.

| # | 관점 | 세부 지표 |
|---|---|---|
| 1 | **효율성 관점** | 표준 준수율(신규 프로젝트 중 전사 기술·데이터 표준을 준수한 비율), 재사용률(개발 서비스·컴포넌트 중 재사용된 비율), 변경처리 리드타임(변경 요청 접수~완료 평균 시간) |
| 2 | **품질 관점** | 모델 최신성(레포지터리 정보 중 정기적으로 갱신되는 정보의 비율), 데이터 품질지표 충족률(핵심 데이터의 정확성·완전성 등 품질 목표 달성률) |
| 3 | **활용도 관점** | 활용 활성도(EA 포털 월간 순 방문자(MAU), 페이지뷰, 다운로드 수), 의사결정 지원 만족도(EA 정보가 IT 투자 의사결정에 도움이 되었는지 설문 점수) |
| 4 | **비즈니스 가치 관점** | IT 비용 절감액(앱 합리화·중복투자 방지로 절감된 비용), 신규 서비스 출시 기간 단축률(표준화·재사용을 통해 단축된 개발기간, TTM) |

- 경영진 보고용 **KPI 대시보드 [그림 3-2]**: 종합 현황(신호등 형태의 목표 대비 달성) + 주요 KPI 추이(월별·분기별 꺾은선) + 영역별 상세 분석(애플리케이션 포트폴리오 4분면, 표준/비표준 기술 사용 비율)
- 단순히 포탈 클릭수가 늘었다는 수준에 머무르지 않고, 그 활용이 최종적으로 **비용 절감과 비즈니스 속도 향상에 어떻게 기여할 수 있는지를 증명하는 것**이 궁극적인 목표.

## 13. 환류 체계: 평가-개선-실행-재평가 (PDCA)

> 성과 측정은 그 자체로 끝나지 않고 반드시 개선 활동으로 이어져야 한다.

| # | 단계 | 내용 |
|---|---|---|
| 01 | **평가 및 분석** | 분기·반기별 KPI 실적 측정, 목표 대비 달성도 분석, 미달 지표의 근본 원인 심층 분석 |
| 02 | **개선 계획 수립** | 구체적 개선과제 도출, 담당자·완료기한 포함 실행계획 수립 (예: 준수율 저조 시 초기 EA 검토 절차 강화) |
| 03 | **정책·표준·모델 갱신** | 개선 계획에 따라 EA 정책·표준·참조모델을 개정하고 EA 시스템에 반영 |
| 04 | **교육 및 공지** | 변경 내용을 모든 이해관계자에게 명확히 공지하고, 필요 시 별도 교육 세션 운영 |
| 05 | **재평가** | 일정 기간 후 개선 활동이 실제 KPI 향상으로 이어졌는지 재측정·평가 |

> 성과 측정의 목적은 직원들을 점수로 줄세우기 위한 것이 아니라, 환류를 통해 다음 행동을 개선하기 위한 것이다.

### (예시 흐름 — 스크립트 보충)
설계 표준 준수율이 목표치보다 낮게 나왔다면 → 원인을 분석 → 초기 설계 단계의 의무 검토 게이트를 통과하도록 프로세스를 개정 → 관련 규정을 갱신 → EAMS에 반영해 교육 실시 → 다음 분기에 준수율이 실제로 향상되었는지 재측정.

### 성숙도 관점의 선순환 — 사업 생애주기와의 연계
- 사업 기획 시 EA 관점의 사전검토를 의무화한다.
- 사업 추진 과정에서 EA 표준 준수 여부를 주기적으로 이행점검한다.
- 사업 완료 후 사후평가로 성과를 측정하고, 그 결과를 다음 EA 계획에 환류한다.
- '평가-개선-실행-재평가'의 순환 고리를 통해 EA 관리 체계는 점진적으로 성숙해 나간다.

이러한 PDCA(Plan-Do-Check-Act) 순환 체계가 돌아갈 수 있을 때, EA는 비로소 살아 있는 조직의 지능으로서 동작하게 됨.

|---|---|---|
| 규칙·모델·계획의 3대 관점 | 환경분석·비전·원칙 | 거버넌스 조직과 RACI |
| 5대 도메인과 추적성 | 범위·우선순위·로드맵 | 6대 관리 프로세스 |
| 프레임워크·참조모델 | 메타모델(객체-속성-관계) | EAMS 구성·기능 |
| 수명주기·성숙도 | As-Is / To-Be / Gap | 활용 시나리오와 KPI 환류 |

### 세 챕터를 잇는 한 문장
> EA는 규칙·모델·계획으로 조직을 설명하고(CH1), 비전과 메타모델을 세워 현행에서 목표로 가는 경로를 설계하며(CH2), 거버넌스와 시스템으로 그 경로를 실제 의사결정에 작동시킨다(CH3).

▶ CH3의 평가·환류 결과는 다시 CH2의 계획 단계로 입력되어, 전사아키텍처는 살아 있는 자산으로 유지된다.

## 16. 챕터 3 마무리 — 핵심 확인 질문 (Self-Check)

1. **Q. EA 거버넌스를 지탱하는 4대 요소는 무엇인가?**
   A. 조직, 역할과 책임, 프로세스, 인력 역량

2. **Q. 6대 관리 프로세스를 시간의 흐름으로 묶으면 어떻게 되는가?**
   A. 연초에는 기획, 연중에는 운영(변경·준수·지원·시스템)이 들어가고, 연말에는 평가 및 환류

3. **Q. EAMS의 4대 구성 요소를 수행하는 동사 네 가지는 무엇인가?**
   A. 만든다, 저장·연결한다, 보여준다(찾아보고 활용한다), 분석한다(수행한다)

4. **Q. 성과 관리의 궁극적인 완성은 무엇으로 이루어지는가?**
   A. 평가 결과를 바탕으로 프로세스를 고치는 환류 체계

## 17. 과목 1 전체 마무리 한 문장

> **전사 아키텍처(EA)는 책상 위에 쌓아두는 정적이고 거창한 청사진을 만드는 일이 아니라, 그 청사진을 조직의 실시간 의사결정 속에 끊임없이 갱신하고 살아 숨 쉬게 만드는 거버넌스 체계이다.**

| RACI | Responsible(실행) · Accountable(최종 승인) · Consulted(자문) · Informed(통보) — A와 R은 활동별로 단 하나씩만 지정 |
| 6대 관리 프로세스 | 기획 → 변경관리 → 준수통제 → 활용지원 → 시스템운영 → 평가 (연간 선순환) |
| EAMS | Enterprise Architecture Management System — 전사 아키텍처 관리 시스템 |
| EAMS 4대 구성요소 | 모델링 도구(만든다) · 레포지터리(저장·연결한다) · 포털(찾아보고 활용한다) · 분석/의사결정 지원 도구(수행한다) |
| EAMS 8대 핵심기능 | 버전관리, 접근제어, 통계·대시보드, 현행-목표 비교, 참조모델 연계, 맞춤형 뷰, 영향분석, 개방형 API — "지킨다·비교한다·보여준다·연결한다"로 재분류 |
| EAMS 도입 4대 효과 | 표준 준수 강화, 소통 개선, 투자중복 방지, 변경·감사 대응력 향상 |
| 활용① | 대규모 IT 프로젝트 생애주기(요구분석-설계-테스트/이행-게이트) 지원 |
| 활용② | 상시 IT업무 지원(표준 확산, 품질·보안 내재화, 데이터 거버넌스, IT 투자관리) |
| 활용 시나리오 5종 | 신규사업기획, 시스템설계검토, 정보보호승인, 데이터표준적용, 데이터품질개선 |
| KPI 4관점 | 효율성, 품질, 활용도, 비즈니스 가치 |
| 환류 체계(PDCA) | 평가 및 분석 → 개선 계획 수립 → 정책·표준·모델 갱신 → 교육 및 공지 → 재평가 |
| BA (Business Architect) | 비즈니스 요구를 분석·중재하는 아키텍트, 현업-IT 가교 역할 |
| APM | Application Portfolio Management, 애플리케이션 포트폴리오 관리 (중복 앱 식별·통폐합) |
| TTM | Time To Market, 신규 서비스 출시 기간 |
| CDP | Career Development Path, 경력개발경로 (EA 인력 육성 계획에 활용) |
