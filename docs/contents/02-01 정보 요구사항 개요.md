# [DAsP 데이터아키텍처 준전문가] 02-01 정보 요구사항 개요

## 0. 강의 도입 — 핵심 명제

> **실제 IT 현장에서 가장 빈번하게 발생하는 비극**: 수십억 원의 예산과 수개월의 시간을 들여 시스템 개발을 완벽히 끝냈는데, 정작 시스템을 받은 사용자가 "이건 제가 원하는 모습이 아닙니다"라고 말하는 상황.

이런 참사는 코딩 실력 부족 때문이 아니라, 대부분 코딩이 시작되기도 훨씬 전에 **요구 사항 정의 단계에서 단추를 잘못 끼웠기 때문**임.

> **오늘의 핵심 명제**: 요구 사항은 단순한 기능의 목록이 아니라, 사용자의 비즈니스 문제를 해결하기 위한 **고도의 합의 과정**이다.

### 강의 흐름과 학습 목표 (Lecture Roadmap 슬라이드)

| # | 구분 | 핵심 내용 |
|---|---|---|
| 1 | **정의와 본질** | 사용자 필요에서 출발, 동사(기능) vs 명사(데이터), 이해관계자 간 합의 |
| 2 | **중요성** | CHAOS 보고서, 실패의 연쇄반응 6단계, 거버넌스·의사소통 기반 |
| 3 | **생명주기와 유형** | 수집-분석-상세화-검증, 기능/비기능 요구사항, 결합에 따른 아키텍처 변화 |
| 4 | **요구사항 관리** | 기준선과 CCB, 추적성과 RTM, 요구사항 정의서 |

### 학습 목표 (강의 자료 화면 기준) — 본 장을 마치면 다음을 할 수 있다
- 정보 요구사항의 개념을 데이터 관점에서 정의하고, 기능 요구사항과의 관계를 설명할 수 있다.
- 요구사항 부실이 프로젝트 실패로 이어지는 연쇄 반응을 단계별로 설명할 수 있다.
- 요구사항 생명주기 4단계와 기능·비기능 요구사항의 유형을 구분하여 적용할 수 있다.
- 기준선·CCB·추적성 매트릭스(RTM)를 활용한 요구사항 관리 체계를 설계할 수 있다.

### 오늘 강의의 4대 핵심 질문
1. 요구 사항은 누구의 필요에서 출발하는가? (요구 사항의 주체)
2. 기능과 데이터는 어떻게 유기적으로 연결되는가? (데이터 중심 설계의 기초)
3. 요구 사항은 어떤 생명 주기를 거쳐 구현되는가? (프로세스 이해)
4. 필연적으로 발생하는 변경을 어떻게 통제하고 관리하는가?

# SECTION 1. 데이터 관점의 요구사항

## 1. 정보 요구사항의 정의 — 사용자와 필요

정보 요구사항을 정의할 때 가장 핵심적인 키워드는 **사용자와 필요**임.

### 예시: 쇼핑몰 주문 취소 사례
- 쇼핑몰 운영자가 "주문 취소 과정이 너무 복잡해서 고객이 불편하다"고 문제 제기.
- **초보 분석가(잘못된 접근)**: "취소 버튼을 크게 만들고 빨간색으로 바꾸자"라는 식으로 **해결책부터** 제시.
- **올바른 접근**: 사용자가 주문을 쉽고 정확하게 취소하여 불편을 해소해야 한다는 **근본적인 필요**를 정의하는 것부터 시작. 버튼의 디자인은 그다음 설계의 영역.

> 정보 시스템은 그 자체로 목적이 아니라, **비즈니스 목표를 달성하기 위한 수단이자 도구**이다.

데이터 아키텍처 관점에서는 한 걸음 더 나아가, 단순히 기능을 묻는 데 그치지 않고 그 기능을 수행하기 위해 **어떤 데이터가 생성되고, 어떻게 흐르며, 어떤 보안 및 품질 수준으로 관리되다가, 언제 폐기되어야 하는지** 전 생명주기를 아우르는 질문을 던져야 함.

> 좋은 분석의 첫걸음은 "어떤 최신 기술을 도입할까"가 아니라 **사용자가 해결하고자 하는 비즈니스 본질이 무엇인지를 꿰뚫어 보는 것**이다.

## 2. 기능은 '동사', 데이터는 '명사'이다

> What to do 를 넘어 What data to manage and how 로

기능과 데이터를 구분하는 가장 직관적인 방법은 문장 구조의 **동사와 명사를 매칭**하는 것.
- "고객을 **등록한다**" → 등록한다(행위) = **기능**, 고객(대상) = **데이터**
- "주문을 **처리한다**" → 처리한다 = 기능, 주문 = 데이터

| 구분 | 기능 요구사항 = 동사(Verb) | 데이터 요구사항 = 명사(Noun) |
|---|---|---|
| 정의 | 시스템의 '행위'를 기술한다 | 행위의 대상이 되는 '데이터'를 규정한다 |
| 내용 | "고객을 등록한다", "주문을 처리한다" | '고객' 데이터, '주문' 데이터 |
| 세부 | 입력 → 처리 → 출력의 주요 활동과 프로세스 | 구조·다른 데이터와의 관계·고유 제약조건, 데이터 표준/품질/성능/보안/생명주기 |
| 특징 | 행위에는 반드시 그 대상이 필요하다 | 데이터 모델은 애플리케이션의 부속물이 아닌 독립적 핵심 설계자산 |

많은 학생들이 "기능이 정해지면 데이터는 자동으로 결정되는 것 아닌가요?"라고 묻지만 이는 큰 오산임. '고객'이라는 단어 뒤에는 고객 체계, 성명식별 규칙, 연락처 포맷, 개인정보 보호등급, 보관기간 등 수많은 데이터 거버넌스 규칙이 숨어 있음.

> **핵심 명제**: 데이터 요구사항의 부실은 곧바로 기능 요구사항의 불완전한 구현으로 이어진다. → 견고하고 유연한 데이터 아키텍처는 기능 뒤에 숨은 데이터의 본질(구조·관계·제약)을 먼저 정의하는 데서 나온다.

> **비유**: 기능은 데이터 위에서 춤을 추는 무용수와 같다. 데이터의 정의가 부실해지면 기능이라는 무용은 결국 무너질 수밖에 없다.

## 3. 요구사항 분석은 '합의점'을 찾아가는 협상 과정이다

> 각 이해관계자는 서로 다른 우선순위로 같은 시스템을 바라본다.

요구사항 분석이 어려운 근본적인 이유는 이해관계자가 다양하고 그들의 요구가 상충하기 때문임. "주문 조회"라는 하나의 기능을 놓고도 입장이 극명하게 갈림:

| 이해관계자 | 관심사·입장 |
|---|---|
| ① **최종 사용자** | 당장의 업무 편의성, 다양한 기능의 제공 ("검색 조건을 수십 개 넣어서 자유롭게 조회하고 싶다") |
| ② **경영진** | 비용 대비 효과(ROI), 장기 비즈니스 전략 부합도 ("개발 비용 대비 실제 매출 증대 효과가 있는가?") |
| ③ **DBA** | 대용량 처리 응답 속도, 안정성·백업/복구 용이성 ("조회 조건이 너무 복잡하면 인덱스 효율이 떨어지고 시스템 수용도가 저하된다") |
| ④ **데이터 아키텍트(DA)** | 전사 데이터 표준 준수, 중복 방지·장기 일관성 ("부서마다 다른 코드를 쓰면 데이터 통합이 불가능하니 표준 코드를 써야 한다") |

> **요구는 자주 상충한다 — 분석가의 핵심 역량은 '수집'이 아니라 '조정'**
> - 사용자가 원하는 복잡·유연한 조회 기능 ↔ DBA가 지켜야 할 시스템 성능
> - 특정 부서의 비표준 용어를 그대로 반영하려는 요구 ↔ DA가 추구하는 전사 데이터 표준화 원칙
> - → 상충하는 요구를 객관적 기준으로 평가하고, 소통과 협상을 통해 최적의 균형점을 찾아내는 것이 분석가의 역할

따라서 분석가의 진정한 역량은 요구상을 단순히 받아쓰는 것이 아니라, 각 요구의 비용 대비 효과와 리스크를 분석하고 프로젝트 전체 관점에서 최적의 합의점을 도출하는 **협상력**에 있음. 즉 **요구사항 분석은 수집이 아니라 조정과 합의를 통해서 하는 과정**임.

> 협상과 합의에 실패하면 프로젝트는 초기부터 특정 이해관계자에 치우쳐 전사적 비즈니스 가치를 상실한다.

## 4. 숫자로 확인하는 요구사항의 무게 — CHAOS 보고서

> 스탠디시 그룹(Standish Group) CHAOS 보고서

| 수치 | 내용 |
|---|---|
| **16.2%** | 1994년 IT 프로젝트 성공률 (성공 요인 3대 요소 중 하나로 '명확한 요구사항 정의'를 지목) |
| **31.1%** | 완료되지 못하고 중도 취소된 비율 (요구사항 단계의 부실과 프로젝트 실패의 직접적 인과관계) |
| **TOP 2** | 2004년 실패의 주요 원인 — ① 불완전한 요구사항, ② 사용자 참여 부족 |

1990년대 중반의 통계이지만 오늘날에도 시사하는 바가 큼. **요구 사항의 품질이 프로젝트의 운명을 결정하는 선행 지표**라는 점이 핵심. 요구 사항은 설계, 구현, 테스트, 운영으로 이어지는 모든 후속 공정의 절대 기준이 되며, 이 기준이 흔들리면 아무리 뛰어난 개발자가 투입되어도 결국 잘못된 결과를 완벽하게 만들어 낼 뿐임.

### 왜 요구사항이 프로젝트의 성패를 가르는가
- 요구사항의 명확성은 후속 설계·개발·테스트 전 단계의 기준이 되며, 초기 오류는 뒤로 갈수록 증폭된다.
- 부실한 요구사항은 '기능 몇 개 누락'이 아니라 예산 초과·일정 지연·사용자 외면이라는 총체적 실패로 귀결된다.

## 5. 불명확한 요구사항이 부르는 6단계 연쇄 반응

부실한 요구 사항이 어떻게 프로젝트를 파멸로 이끄는지 그 연쇄 반응:

| # | 단계 | 내용 |
|---|---|---|
| 1 | **불명확한 요구사항** | "사용자 친화적", "빠른 응답" 등 측정 불가능한 정의 |
| 2 | **잦은 변경·범위 만연** | Scope Creep — 변경 통제 프로세스 부재 |
| 3 | **재작업 증가** | 설계·코드 반복 수정 / 생산성·사기 저하 |
| 4 | **일정 지연·예산 초과** | 1차 증상: 추가 인력과 시간 투입 |
| 5 | **품질 저하** | 2차 증상: 신규 버그 유발, 테스트 부족 |
| 6 | **프로젝트 실패** | 취소·예산 초과·Challenged 프로젝트 |

> **차단 지점은 ②번이다.** 변경 자체는 막을 수 없다. 그러나 ②단계에 체계적인 변경 관리 프로세스를 두면 연쇄 반응은 여기서 끊긴다. → 그 장치가 SECTION 2에서 다룰 '기준선(Baseline) + 변경통제위원회(CCB) + 추적성(RTM)'이다.

(스크립트 보충) 변경을 100% 막을 수는 없지만, 변경이 발생하는 즉시 영향도를 분석하고 공식적인 절차를 통해서만 통제된 변경을 한다면 이 파멸적인 연쇄 반응을 막을 수 있음 — 이것이 요구 사항 관리를 배우는 이유.

## 6. 요구사항의 역할 — 데이터 거버넌스의 출발점이자 비즈니스-IT의 공용어

요구 사항은 프로젝트 내에서 두 가지 결정적인 역할을 수행함.

### ① 데이터 품질·아키텍처 일관성의 기반
표준 용어·도메인·코드·명명 규칙 — 데이터 표준화의 모든 요소는 요구사항 단계에서 식별된 데이터를 기반으로 정의됨.

거버넌스가 작동하기 위한 논리 흐름:
1. 거버넌스의 목적은 데이터를 '관리'하는 것이다.
2. 관리하려면 관리의 '대상'이 먼저 정의되어야 한다.
3. 그 대상은 '데이터'와 데이터를 둘러싼 '규칙'이다.
4. "주민등록번호는 수집 후 3년 경과 시 파기, 저장 시 암호화" — 이런 규칙이 바로 정보 요구사항의 구체적 예시다.

### ② 비즈니스-IT 간극 해소 (유일한 공용어)
- 현업은 업무 프로세스 용어로, 개발자는 기술·구조 용어로 시스템을 이해함.
- **청사진(Blueprint)**: 요구사항 정의서와 데이터 모델은 모든 관계자가 같은 그림을 보게 하는 공용어.
- **공식 계약서**: 프로젝트의 목표와 범위에 대한 이해관계자 전원의 공식적 합의 문서.

### 결론
중요도·보안 등급·법적 보관 주기·접근 권한을 요구사항 단계에서 정의하지 않으면, 후속 거버넌스 활동은 관리 대상을 잃고 공허한 구호에 그친다.

(스크립트 보충) 즉 요구 사항은 단순한 문서가 아니라 "우리가 무엇을 만들기로 약속했는가"에 대한 전사적인 합의 기록임.

# SECTION 1 (계속). 요구사항 생명주기와 유형

## 7. 정보 요구사항 생명주기 — 모호한 아이디어가 검증 가능한 명세로 발전하는 과정

> 폭포수형 단방향이 아니라, 피드백을 통해 반복(iterative)되는 순환 구조

| # | 단계 | 내용 |
|---|---|---|
| 1 | **수집 (Elicitation)** | 암묵적 지식·기대를 형식적 요구사항으로 이끌어냄. 인터뷰·설문·워크숍, 현행 시스템/문서 분석 |
| 2 | **분석·정의 (Analysis)** | 타당성 검토, 중복 통합, 상충 요구사항 식별·해결, 우선순위 결정, 기능/비기능 분류 |
| 3 | **상세화 (Specification)** | 명확·완전·일관된 형태로 공식 문서화, 고유 식별자 부여, 산출물: 요구사항 정의서 |
| 4 | **검증 (Validation)** | "올바른 제품을 만들고 있는가?" 동료 검토·프로토타입 시연, 상관분석 매트릭스 활용 |

> **생명주기가 시사하는 것 — 요구사항 개발은 본질적으로 '불확실성을 다루는 활동'**
> 초기 요구사항은 불완전하고 모호할 수밖에 없다. 각 단계를 거치며 모호함이 제거되고 정교해진다. 검증 단계에서 오류를 발견하면 막대한 재작업 비용을 절감할 수 있다 — 뒤로 갈수록 수정 비용은 기하급수적으로 증가한다.

(스크립트 보충) 요구 사항은 한 번에 완성되는 것이 아니라 깎고 다듬는 과정을 반복해서 점진적으로 정교해지는 조각품과 같다.

---

## 8. 기능 요구사항 vs 비기능 요구사항

> What(무엇을 하는가) 과 How(어떻게 동작하는가)

| 구분 | 기능 요구사항 (Functional) | 비기능 요구사항 (Non-Functional) |
|---|---|---|
| 정의 | 시스템이 제공할 구체적 기능·서비스 | 기능 수행 시의 품질·성능·제약 조건 |
| 예시 | "사용자는 키워드를 입력하여 상품을 검색할 수 있어야 한다", "시스템은 선택한 상품을 장바구니에 담는 기능을 제공해야 한다", "사용자는 신용카드 정보를 입력하여 결제를 완료할 수 있어야 한다" | 성능(응답시간·처리량·동시 사용자 수), 외부 인터페이스(프로토콜·데이터 포맷 XML/JSON·API 규격), 보안(기밀성·무결성·가용성/인증·암호화·접근통제), 기타 품질(사용성·신뢰성(MTBF)·확장성·유지보수성) |
| 도출 유형 | 기능 개선 요건 / 신규 개발 요건 | — |

> **성능 요구사항은 반드시 '측정 가능(measurable)'하게**
> ✗ "시스템 응답이 빨라야 한다" → ○ "상품 검색 결과는 평균 15초에서 3초 이내로 개선되어야 한다"

(스크립트 보충) 측정할 수 없는 요구 사항은 검증할 수도 없고 관리할 수도 없기 때문.

### 같은 기능도 비기능 요건에 따라 아키텍처가 달라진다
예시: "사용자는 자신의 주문 내역을 조회할 수 있다"

| # | 단계 | 내용 |
|---|---|---|
| 1 | 기능 요구사항만 존재 | DB에서 해당 사용자의 주문 데이터를 조회해 화면에 표시하는 단순 구현 |
| 2 | + 성능 요건(1초 이내) | DB 인덱스 최적화, 자주 조회되는 데이터의 캐싱(Caching) 전략 도입 |
| 3 | + 보안 요건(본인만 조회) | 강력한 사용자 인증 체계 + 데이터 접근 제어 로직 필수 |

> **비기능 요구사항을 초기에 간과하면**: '어떤 자동차를 만들지'는 정했지만 엔진 성능·제동력·에어백 안전등급 같은 핵심 사양을 정하지 않은 것과 같다. → 프로젝트 후반부에 성능·보안 문제에 직면해 전체 시스템 구조를 재설계해야 하는 심각한 위험에 빠진다.

# SECTION 2. 정보 요구사항 관리

## 9. 변경은 예외가 아니라 필연이다

> 요구사항 관리 = 불확실성 관리 + 이해관계자 간 합의 유지

### 요구사항 관리의 개념
프로젝트 전 생명주기에 걸쳐 발생하는 요구사항의 변경을 체계적으로 식별·조직화·통제·추적하는 동적인 활동. 관리 대상은 명세서 문서안이 아니라 — 설계 문서·소스 코드·테스트 케이스·사용자 매뉴얼 등 모든 파생 산출물 간의 일관성 유지를 포함함.

### 왜 변경은 필연인가
비즈니스 환경은 끊임없이 변하고, 사용자도 프로젝트가 진행될수록 이해도가 깊어져 새로운 요구를 제기함.

### 관리의 궁극적 목적
사용자 요건에 완벽히 부합하는 시스템 개발과 고객 만족도 극대화.

### 기준선(Baseline)의 보호
무분별한 변경으로부터 범위를 지키고, 불가피한 변경 시 새 기준선에 합의하도록 만드는 통제탑.

> **통제 없는 변경 = 앞서 본 '프로젝트 실패의 연쇄 반응'의 시작.** 모든 변경 요청을 공식 프로세스로 접수 → 일정·비용·품질·타 요구사항에 미치는 영향을 객관적으로 분석 → 수용 여부와 자원·일정 조정에 전원 합의.

(스크립트 보충) 기준선은 특정 시점에 모든 이해관계자가 합의한 요구 사항의 상태를 사진을 찍듯이 고정시켜 두는 것. 기준선이 설정된 이후 모든 변경은 공식적인 절차를 밟아야 하며, 기준선은 변경을 거부하는 벽이 아니라 변경의 전과 후를 비교해서 영향도를 파악하기 위해 변하지 않는 척도임.

## 10. 변경 요청은 반드시 하나의 창구를 거친다

변경 요청이 들어오면 다음의 5단계를 거침:

| # | 단계 | 내용 |
|---|---|---|
| 1 | **변경 요청** | 표준 양식(정보 요구사항 정의서 / 변경 요청서)으로 공식 접수 |
| 2 | **접수 및 검토** | 기술 명확성·중복·상충 1차 검토 후 담당자 지정·이관 |
| 3 | **영향도 분석** ★가장 핵심 단계 | 데이터 모델·화면·로직·인터페이스·공수·비용 파급효과 |
| 4 | **공식화·결정** | 수용/거부/연기 — 객관적 데이터와 비즈니스 우선순위에 근거 |
| 5 | **반영 계획 수립** | 표준·설계서 변경, DB·AP 수정, 테스트, 이관 일정과 담당자 명시 |

### 변경통제위원회(CCB, Change Control Board)의 3가지 역할
- **단일 통제 창구** — 개별 개발자·분석가의 임의 수용을 차단하고 모든 변경을 공식 접수·논의하도록 강제
- **객관적 의사결정** — 개인·부서 이해를 넘어 일정·예산·품질 관점에서 판단, **'골드 플레이팅(Gold Plating)' 방지** (요청받지 않은 과잉 기능 개발을 막음)
- **공식적 기록과 소통** — 승인·반려·보류와 그 근거를 회의록·변경관리대장에 남겨 전원에게 투명하게 공유

(스크립트 보충) CCB는 "가장 큰 원인은 불명확한 요구 사항과..."가 아니라, 프로젝트에 제한된 자원을 고려해서 어떤 변경이 프로젝트 성공에 가장 기여하는지를 판단하는 전략적인 의사 결정 기구임. 단순히 "안 된다"고 말하는 사람들이 아님.

## 11. 요구사항 관리는 조직 전체의 협업으로 완성된다 [표 1.1]

> 각 역할이 명확한 R&R(Role & Responsibility)을 갖고 유기적으로 협력할 때 비로소 관리가 작동한다.

| 역할 | 주요 책임 | 관련 산출물 |
|---|---|---|
| **사용자** | 업무 요건·개선사항을 구체적으로 제시, 요구사항 검증 및 최종 확인 | 정보 요구사항 정의서, 인수 테스트 결과서 |
| **현업 분석가** | 사용자 요구 수렴 및 비즈니스 관점 분석, IT-현업 간 의사소통 중재 | 업무 프로세스 흐름도, 요구사항 목록 |
| **데이터 아키텍트(DA)** | 전사 데이터 표준·아키텍처 원칙 부합 검토, 데이터 모델 영향도 분석 | 개념/논리 데이터 모델, 데이터 표준 정의서 |
| **애플리케이션 아키텍트(AA)** | AP 컴포넌트·인터페이스 영향도 분석, 비기능 요건의 기술적 구현 방안 검토 | AP 아키텍처 설계서, 인터페이스 정의서 |
| **데이터베이스 관리자(DBA)** | 성능·안정성 영향 분석, 물리 데이터 모델 변경 및 적용 | 물리 데이터 모델, 테이블/인덱스 명세서 |
| **프로젝트 관리자(PM)** | 관리 프로세스 총괄, CCB 운영, 일정·자원 조정 및 의사소통 조율 | 프로젝트 계획서, 변경관리대장, CCB 회의록 |
| **품질 보증(QA)** | 요구사항의 명확성·검증 가능성 검토, 추적성 관리, 테스트 케이스 작성 | 요구사항 추적성 매트릭스(RTM), 테스트 계획서 |

(스크립트 보충) 사용자는 필요를 제공하고 최종 결과물을 승인, 분석가는 사용자의 말을 요구사항 명세서로 변환, DA·DBA는 데이터 표준과 정합성을 검토, PM은 일정·자원 관점에서 변경의 우선순위를 조정, QA는 요구 사항이 테스트 가능한지를 확인함.

## 12. 추적성 — 품질 보증과 위험 관리의 강력한 도구

> 행정 업무가 아니라, 완전성 보증과 영향 분석의 핵심 수단이다.

요구사항 추적성은 두 가지 방향으로 작동함:

| 방향 | 흐름 | 목적 |
|---|---|---|
| **정방향 추적성 (Forward)** | 요구사항 → 설계 → 코드 → 테스트 | "이 요구사항은 어떤 설계·코드로 구현·검증되는가?" — 요구사항이 누락 없이 반영되었는지 확인. '테스트되지 않은 요구사항' = 잠재 결함의 사전 차단 |
| **역방향 추적성 (Backward)** | 테스트 ← 코드 ← 설계 ← 요구사항 | "이 소스 코드 모듈은 어떤 요구사항을 위해 존재하는가?" — 불필요한 기능(Gold Plating) 포함 여부 확인. 운영 중 장애 시 본래 구현 의도 파악의 단서 |

### RTM(요구사항 추적성 매트릭스) 예시

| 요구사항 ID | 요구사항 설명 | 설계 문서 | 소스코드 모듈 | 테스트 케이스 | 결과 |
|---|---|---|---|---|---|
| REQ-001 | 사용자는 키워드로 상품을 검색할 수 있다 | DES-PROD-01 | ProductSearch.java | TC-SEARCH-001, 002 | Pass |
| REQ-002 | 검색 결과는 가격순으로 정렬되어야 한다 | DES-PROD-01 | ProductSearch.java | TC-SEARCH-003 | Pass |
| REQ-003 | 비회원은 상품 검색을 할 수 없다 | DES-SEC-05 | AccessControl.java | TC-SEC-010 | Fail |

→ REQ-002를 변경하려면 DES-PROD-01·ProductSearch.java·TC-SEARCH-003을 함께 수정해야 함을 즉시 알 수 있다. REQ-003의 Fail은 AccessControl.java의 결함을 시사한다.

(스크립트 보충) RTM은 프로젝트의 처음과 끝을 잇는 거대한 지도이며, 프로젝트 종료 시 "우리는 요구한 것을 모두 완벽하게 만들었다"는 것을 입증할 수 있는 유일한 증거 자료임.

## 13. 좋은 요구사항이 갖추어야 할 8가지 특성

> 정의서는 의사소통 기준·공식 계약·설계 개발의 기반·변경 관리의 기준선

| # | 특성(영문) | 설명 |
|---|---|---|
| 1 | **명확성 Unambiguous** | 단 하나의 의미로만 해석. "빠른 응답" ✗ → "평균 3초 이내" ○ |
| 2 | **완전성 Complete** | 정상 시나리오 + 예외 처리 오류 상황 대응 방안까지 명시 |
| 3 | **검증 가능성 Verifiable** | 테스트·검사로 객관적 확인 가능. 측정 불가 = 검증 불가 |
| 4 | **일관성 Consistent** | 타 요구사항·상위 문서와 모순 없음 |
| 5 | **수정 용이성 Modifiable** | 독립적 기술로 변경 영향 최소화 |
| 6 | **추적 가능성 Traceable** | 고유 ID 부여, 출처-구현까지 추적 |
| 7 | **원자성 Atomic** | 하나의 요구사항에 하나의 내용만 |
| 8 | **'What' not 'How'** | 구현 방법은 설계 단계의 몫 |

### 정의서의 핵심 구성 요소
고유 식별자(ID) · 요구사항 명칭 · 상세 설명 · 출처/근거 · 유형(기능/비기능) · 중요도/우선순위 · 상태 · 제약 조건
예) `DA-CMS-001-03 「DB 표준화 지침 준수」 / 비기능 / 중요도 상 / 근거: 제안요청서 DAR-001, 제안서 68쪽 / 수용`

### (참고) 세부 예시 — 명확성
- 나쁜 예: "시스템 속도가 빨라야 한다" (빠르다는 기준이 사람마다 다름)
- 좋은 예: "사용자가 로그인 버튼을 누르면 1.5초 안에 메인 화면이 열려야 한다"

### (참고) 세부 예시 — 원자성
하나의 요구사항에는 오직 하나의 기능이나 조건만 담아야 함. 여러 내용이 섞이면 하나만 고치거나 테스트하기 어렵기 때문.
- 나쁜 예: "사용자는 프로필 사진을 바꿀 수 있고 탈퇴 버튼을 누르면 팝업이 뜬다" (사진 변경 + 회원 탈퇴 두 기능이 섞임)
- 분리된 좋은 예: ① "사용자는 프로필 사진을 업로드할 수 있다" ② "사용자는 회원 탈퇴 버튼을 누를 때 확인 팝업창을 봐야 한다"

### (참고) 세부 예시 — What not How
어떤 기술로 구현할지가 아니라 사용자에게 제공할 기능에만 초점을 맞춰 기술하는 특성. 구현 방법을 미리 정하면 개발자의 창의성과 기술 선택을 방해하기 때문.
- 나쁜 예: "오라클 데이터베이스를 사용해서 사용자 정보를 저장한다" (구현 방법=기술 이름이 먼저 나옴)
- 좋은 예: "사용자가 입력한 가입 정보를 안전하게 저장할 수 있어야 한다" (기능으로만 구성)

## 14. CHAPTER 1 SUMMARY — 핵심 정리 & 자주 하는 실수

| 구분 | 핵심 내용 |
|---|---|
| **요구사항의 본질** | 기능 목록이 아니라 이해관계자들의 '비즈니스 문제 해결 계약서' |
| **기능 = 동사, 데이터 = 명사** | What to do 를 넘어 What data to manage and how 까지 파고들 것 |
| **생명주기 4단계** | 수집 → 분석·정의 → 상세화 → 검증 / 피드백을 통한 반복적 정제 |
| **기능 vs 비기능** | 비기능 요건이 기능의 '구현 방식'과 아키텍처를 결정한다 |
| **변경은 필수 관리 대상** | 기준선(Baseline) 설정 → CCB를 통한 통제 → 추적성(RTM) 확보 |

### 자주 하는 실수 TOP 3
- 측정 불가능한 표현을 그대로 승인 → 모든 성능·품질 요건에 수치와 조건을 붙일 것
- 비기능 요구사항을 후반으로 미룸 → 전체 아키텍처 재설계 위험
- 변경을 개별 담당자가 임의 수용 → 반드시 CCB 단일 창구로 접수

## 15. 챕터 마무리 요약 (스크립트 기준)

오늘 우리는 정보 요구사항의 본질에 대해 학습했다:
- 요구 사항은 비즈니스 문제 해결을 위한 도구이며, 기능 뒤에 숨겨진 데이터의 구조를 파악하는 것이 핵심이다.
- 변경을 피할 수 없으므로 기준선과 공식적인 절차를 통해 관리해야만 프로젝트를 성공으로 이끌 수 있다.
- 요구사항 정의가 잘된 프로젝트는 이미 절반은 성공한 것이나 다름없다.

## 부록: 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| 정보 요구사항 | 사용자의 비즈니스 문제 해결을 위한 고도의 합의 과정 (단순 기능 목록 아님) |
| 기능 요구사항(Functional) | 시스템이 무엇을 수행해야 하는가(What) — 동사로 표현 |
| 비기능 요구사항(Non-Functional) | 기능을 어떤 수준으로 수행해야 하는가(How) — 성능·보안·가용성·유지보수성 등 품질 속성. 반드시 측정 가능(measurable)해야 함 |
| CHAOS 보고서 | 스탠디시 그룹의 IT 프로젝트 성공률 조사 보고서 (1994년 성공률 16.2%, 31.1% 중도 취소, 2004년 TOP2 실패원인: 불완전한 요구사항·사용자 참여 부족) |
| 6단계 연쇄반응 | 불명확한 요구사항 → 잦은 변경(Scope Creep) → 재작업 증가 → 일정지연·예산초과 → 품질저하 → 프로젝트 실패 (차단지점: 2단계) |
| 요구사항 생명주기 4단계 | 수집(Elicitation) → 분석·정의(Analysis) → 상세화(Specification) → 검증(Validation), 반복(iterative) 순환 구조 |
| 기준선(Baseline) | 특정 시점에 이해관계자가 합의한 요구사항 상태를 고정한 것. 변경 전후 비교의 척도 |
| CCB (Change Control Board) | 변경통제위원회 — 단일 통제 창구, 객관적 의사결정, 공식 기록·소통 담당. 골드 플레이팅 방지 |
| 변경 요청 5단계 | 변경요청 → 접수및검토 → 영향도분석(핵심) → 공식화·결정 → 반영계획수립 |
| 골드 플레이팅(Gold Plating) | 요청받지 않은 과잉 기능을 개발자가 임의로 추가하는 것 (지양 대상) |
| 추적성(Traceability) | 정방향(요구사항→설계→코드→테스트, 누락 방지) / 역방향(테스트←코드←설계←요구사항, 과잉개발 방지) |
| RTM (Requirements Traceability Matrix) | 요구사항 추적성 매트릭스 — 요구사항ID·설계문서·소스코드·테스트케이스·결과를 연결한 표. 프로젝트 완결성의 유일한 증거자료 |
| 좋은 요구사항 8대 특성 | 명확성(Unambiguous), 완전성(Complete), 검증가능성(Verifiable), 일관성(Consistent), 수정용이성(Modifiable), 추적가능성(Traceable), 원자성(Atomic), What not How |
| R&R (표 1.1) | 사용자·현업분석가·DA·AA·DBA·PM·QA 7개 역할의 책임과 산출물 정의 |
| Scope Creep | 범위 만연 — 통제되지 않은 변경 요청이 쌓여 프로젝트 범위가 지속적으로 확대되는 현상 |
