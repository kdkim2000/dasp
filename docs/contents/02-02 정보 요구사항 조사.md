# 02-02 정보 요구사항 조사

## 도입부 — 강의의 관점

- 데이터 아키텍처를 짓는 과정은 **건축**에 비유할 수 있다. 건물을 지을 때 설계도(요구사항)가 부실하면 아무리 좋은 자재(기술)를 써도 부실 건축이 되듯, 데이터 아키텍처도 "정보 요구사항 조사"라는 기초 작업이 부실하면 이후 설계·구축 전체가 흔들린다.
- 이번 챕터(CHAPTER 2)는 크게 3개 절로 구성된다.
  - 제1절: 수집(Collection)
  - 제2절: 정리(Organizing)
  - 제3절: 통합(Integration)

### ① 조사의 위치 — 정보요구사항 생명주기 안에서

정보요구사항 생명주기는 4단계로 구성된다 (※ 이 슬라이드에서는 4단계 중 마지막 단계를 "Verification(검증)"으로 표기하고 있으며, 02-01 강의에서는 "Validation"으로 표기했다 — 두 용어가 실무·교재에 따라 혼용될 수 있음에 유의).

| 단계 | 영문 | 설명 |
|---|---|---|
| ① 수집 | Collection | 현장의 목소리를 모으는 단계 (본 챕터의 핵심) |
| ② 분석 및 정의 | Analysis & Definition | 수집된 내용을 분석하고 정의 |
| ③ 상세화 | Specification | 상세 명세로 구체화 |
| ④ 검증 | Verification | 요구사항이 맞는지 검증 |

- 흐름: **경영환경·정보환경 분석 → CSF(핵심성공요소, Critical Success Factor) → CIR(핵심정보요구, Critical Information Requirement)** 로 구체화되어 내려온다.
- "조사"는 이 CIR(전략에서 도출된 핵심정보요구)과 **현장의 목소리를 잇는 다리** 역할을 한다. 즉, 경영진의 전략적 방향(CIR)을 실무자의 실제 업무 현실과 연결하는 작업이다.
- **전략적 활동**: 조사는 단순한 기능 목록 작성이 아니라 **프로젝트의 성패를 좌우하는 전략적 활동**이다.

#### 반복적(iterative)·비선형적 특성

수집 → 정리 → 통합의 순서는 실제 프로젝트에서 **엄격하게 선형적으로 진행되지 않는다**. 슬라이드에 제시된 반복 사례:

1. "통합" 단계에서 부서 간 상충을 발견 → 다시 "수집" 단계로 되돌아가 조정 워크숍을 재실시
2. "정리" 단계에서 최우선 요구사항의 내용이 모호함을 발견 → 재수집을 통해 명확화

즉, 뒤 단계에서 문제가 발견되면 언제든 앞 단계로 돌아가 보완하는 순환적 구조다.

### 학습 목표 (LECTURE ROADMAP 슬라이드 기준)

1. 조사의 위치: 생명주기 4단계 중 수집의 위치, CSF→CIR 구체화 흐름, 순환적(iterative) 특성 이해
2. 제1절 수집: 하향식·상향식·혼합형 접근법, 문서분석/면담/워크숍 등 핵심 기법과 보조 기법 비교
3. 제2절 정리: ID 부여와 구조화, 아키텍처 계층 매핑, 우선순위 분석 기법(MoSCoW·Kano·RICE)
4. 제3절 통합: 중복 식별과 통합·분할, 상충 해결 협상 절차, 기준선(Baseline) 수립

## SECTION 1. 수집(Collection)의 기본 원칙

### 1. 3대 수집 접근법 — 하향식 · 상향식 · 혼합형

> 전략적 일관성과 현실적 실현 가능성 사이의 균형

| 구분 | 하향식 (Top-Down) | 상향식 (Bottom-Up) | 혼합형 (Hybrid) |
|---|---|---|---|
| 방법 | 비전·중장기 전략·사업 목표에서 구체적 데이터 요건으로 분해 | 현행 시스템의 산출물에서 상위 데이터 요건·업무 규칙을 역으로 도출 | 하향식으로 방향성을 설정하고, 동시에 상향식으로 현황·제약을 상세 분석 |
| 장점 | 전사 관점의 일관성 확보, 비즈니스 전략과 직접 연계 ("왜 이 데이터가 필요한가?"에 답할 수 있음) | 현실적 데이터 구조 반영, 문서화되지 않은 암묵적 업무 규칙 발견 | 두 결과를 상호 비교·검증하여 전략적 방향성과 현실 기반 구체성을 동시에 확보 |
| 단점 | 목표가 추상적이면 현실성·구체성 부족 | 현재 방식에 매몰되어 혁신적 미래 요건 도출이 어려움 | (양쪽에서 빠뜨리지 못한 누락 요건을 찾아내어 완전성 극대화) |
| 대표 활동 | 경영진 인터뷰, 전략기획 문서 분석, BPM | 스키마 분석(리버스 엔지니어링), 화면·보고서 분석 | — |
| 비고 | — | — | → **가장 이상적인 전략**으로 제시됨 |

※ 프로젝트의 성격과 상황에 따라 적절한 접근법을 선택하거나 조합하여 사용한다.

- 실무 요약(스크립트): 하향식은 안목적인 업무 발견 규칙을 발견해 내는데 탁월하지만, 현재 시스템 프레임에 매몰돼 급변하는 비즈니스 환경에 대응하는 혁신적이고 미래지향적인 요구 사항을 도출하기는 어렵다는 치명적인 약점이 있음. **셋째는 혼합형 접근법**이며, 실무에서는 가장 권장되는 방식. 하향식으로 전사적인 방향성과 비즈니스 전략을 설정하는 동시에, 상향식으로 현황과 제약사항을 상세히 분석하여, 두 결과를 상호 비교·검증함으로써 전략적 방향성과 현실 기반의 구체성을 동시에 확보하는 방법.

### 2. 핵심 수집 기법 ① — 문서 분석 (모든 조사의 출발점)

> 다른 수집 활동을 시작하기 전 프로젝트의 배경·범위·제약을 파악하는 기본 활동

**4대 문서 범주**

| 범주 | 예시 |
|---|---|
| 전략 / 기획 문서 | 중장기 경영 전략, 연간 사업 계획서, 제안요청서(RFP) |
| 업무 관련 문서 | 업무 매뉴얼·흐름도, 직무 기술서, 신입사원 교육 자료 |
| 시스템 관련 문서 | ERD·테이블 명세서, 인터페이스 정의서, 설계서·운영 지침서 |
| 규제 / 법규 문서 | 개인정보보호법·정보통신망법, 사내 데이터 표준 지침, 정보 보안 규정 |

**4단계 절차**

1. 자료 수집 목록 작성 — 분석에 필요한 문서 목록 사전 정의
2. 자료 수집 — 관련 부서에 공식 요청
3. 내용 분석·요약 — 업무 규칙·데이터 항목·제약 추출 후 요약 표 정리
4. 보안 관리 — 문서 관리자 지정, 접근 권한 통제

**단점**: 문서가 최신이 아니거나 부정확할 수 있고, 문서화되지 않은 암묵적 지식은 파악할 수 없다. → 반드시 면담·관찰로 교차 검증한다. 별도의 문서 관리자를 지정하고 접근을 권한화 철저히 통제하는 보안 대책이 수반되어야 할 것입니다. 또한 문서는 시성이 떨어져서 실제 현혹과 다를 수 있으므로 반드시 후속 면담과 관찰 기법을 통해서 문서의 그 현행 여부를 교차 검증해 나가야 합니다.

### 3. 핵심 수집 기법 ② — 사용자 면담 (준비가 성패의 8할)

> 문서로는 알 수 없는 상세 절차·예외 상황·암묵적 지식을 얻는 기법. 두 번째 기법은 가장 전통적이면서도 흔하고 그리고 강력한 사용자 면담, 즉 유저 인터뷰입니다. 문서만으로는 부족했을 실제 현장의 세부 절차와 예외 상황, 그리고 암묵적 지식을 얻으려면 반드시 이 기법을 통해서 문서의 그 현행 여부를 교차 검증해 나가야 합니다.

**3단계 절차**

1. 계획 및 준비 — 주제·목표 설정, 핵심 실무자 선정, '면담 요지'를 최소 1주일 전 전달
2. 수행 — 2인 1조(진행자 + 기록자), 동의를 얻어 녹음, 기록 누락 방지
3. 결과 분석·정리 — 직후 면담록 작성 → 대상자에게 재송부하여 사실 관계 확인(피드백)

**질문 유형**

- 폐쇄형: "이 업무는 하루 몇 건 처리되나요?" — 사실 관계 확인
- 개방형: "가장 어려운 점은 무엇인가요?" — 심층 정보·근본 원인
- 유도형: "이 기능이 추가되면 효율이 오를까요?" — 의견·동의 확인

**성공을 위한 5가지 고려사항**

- 시간 준수·비밀보장으로 신뢰 관계 형성
- 기대수준 설정 — 지금은 '파악' 단계, 전부 반영되는 것은 아님
- 범위 준수·실질적 권한과 책임을 가진 실무 전문가 선정
- (기타 2가지는 슬라이드 상단 4개 항목과 함께 5가지로 제시되며, 시간 준수/비밀보장, 기대수준 설정, 범위 준수·실무 전문가 선정이 핵심 3가지로 강조됨)

### 4. 핵심 수집 기법 ③ — 워크숍 / JAD (단기간에 합의를 만드는 기법)

> JAD(Joint Application Development): 명확한 역할과 절차를 갖춘 고도로 구조화된 워크숍

**3단계 절차**

1. 계획 — 목표 설정, 핵심 이해관계자 선정, 중립적 촉진자·기록자 지정, 자료 사전 배포
2. 수행 — 의제에 따라 진행, 브레인스토밍·아이디어 보드·다이어그램, 실시간 정리와 공유
3. 종료 및 정리 — 결과물(도출 요구사항·미해결 과제·결정 사항)을 보고서화, 회람·확인 후 공식 산출물 확정

**장점**

- 여러 이해관계자 의견을 단기간에 집중 수렴 → 빠른 의사결정과 합의
- 서로 다른 관점이 한자리에 모여 충돌·모호성을 조기에 발견·해결
- 참여자들의 주인의식과 공감대 형성

**단점**

- 핵심 인력의 장시간 참여 → 일정 조율 어려움, 장소·촉진자 비용
- 촉진자 역량에 따라 성패가 크게 좌우
- 일부 참석자의 의견 독점 가능성

### 5. 상황에 따라 조합하는 보조 기법 4가지

| 기법 | 설명 | 단점 |
|---|---|---|
| ① 설문조사 (Surveys) | 지리적으로 분산되거나 수가 많은 사용자 그룹 대상. 정량 데이터(기능 사용 빈도) + 정성 데이터(개선 의견) 신속 수집 | 심층 정보 한계, 질문 설계에 따라 응답 질이 좌우, 낮은 응답률 |
| ② 관찰 (Observations) | 실제 업무 환경에서 사용자의 처리 과정을 직접 관찰. 사용자 스스로 인지하지 못하는 비효율 프로세스·암묵적 요구 발견 | 호손 효과, 시간 소모, 비정기적 업무 파악 어려움 |
| ③ 프로토타이핑 | 시제품을 만들어 직접 사용하게 하고 피드백으로 요구사항 구체화. 복잡한 인터페이스·신규 기능의 이해를 돕고 문제점 조기 발견 | 초기 비용 증가, 시제품을 최종 제품으로 오인, 범위 만연 위험 |
| ④ 벤치마킹 | 경쟁사·동종 업계의 선진 사례 분석. 타사가 제공하는 기능·데이터 관리 방식을 참조하여 요구사항 도출. 시장 표준 준수 또는 경쟁 우위 확보를 위한 요건 정의에 유용 | — |

※ 기법 선택 기준 — 초기 현황 파악은 문서 분석, 심층 지식은 면담, 합의 도출은 워크숍, 대규모 의견 수렴은 설문, UI/UX 요건은 프로토타이핑.

### 6. 요구사항의 체계적 분류 — 데이터 관점에서 본 기능 · 비기능 요구사항

> 기능은 CRUD 행위와 직결되고, 비기능은 논리·물리 설계와 인프라를 결정한다

**기능 요구사항 — 무엇을(What)**: 데이터의 생성·조회·수정·삭제 행위와 직접 연결

- (C) "신규 고객 정보를 등록할 수 있어야 한다"
- (R) "주문 번호로 주문 상세 내역을 조회할 수 있어야 한다"
- (U) "고객의 배송지 주소를 변경할 수 있어야 한다"
- (D) "탈회한 회원의 개인정보를 삭제할 수 있어야 한다"
- → 향후 엔티티·속성·데이터 처리 프로세스 설계의 직접적 근거

**비기능 요구사항 — 어떻게(How)**: 데이터 아키텍처 설계 시 특히 중요한 4가지

- **표준**: 표준 용어 사전 기반 영문 약어 명명, 전사 표준 코드(M/F)
- **품질**: 완전성·유일성·유효성·일관성·정확성
- **성능**: "일일 매출 통계는 10초 이내 생성", "피크 시 동시 1,000명 지연 없이 조회"
- **보안**: "비밀번호는 복호화 불가능한 방식으로 해싱 저장", 접근 권한 최소화

**데이터 품질 5대 기준 — 요구사항 문장으로 표현하기**

- 완전성: "고객 등록 시 이름과 연락처는 필수 입력"
- 유일성: "동일 주민등록번호 고객 중복 등록 금지"
- 유효성: "이메일은 @를 포함한 유효 형식"
- 일관성: "주문 시스템과 배송 시스템의 고객 주소는 항상 동일"
- 정확성: "상품 재고 수량은 실제 창고 재고와 일치"

## SECTION 2. 정보 요구사항 정리(Organizing)

> 원석을 제련하는 단계 — 구조화와 우선순위화. 비정형·산재된 요구사항을 일관된 형식의 목록으로 변환하고 가치를 평가한다.

### 1. 정리의 5대 목표

| # | 목표 | 설명 |
|---|---|---|
| 1 | 명확성 확보 | 모호·다의적 표현 제거, 전원이 동일한 의미로 이해 |
| 2 | 완전성 검토 | 필요한 정보를 모두 담았는지, 빠진 부분 1차 검토 |
| 3 | 일관성 유지 | 동일한 용어·형식으로 표준화 |
| 4 | 구조화 | 체계적 분류 + 고유 ID 부여, 관리·추적 용이성 확보 |
| 5 | 우선순위화 | 제한된 자원의 효율적 배분, 중요도·시급성 평가 |

### 2. 2단계 절차 — ID 부여와 분류 세분화

**1단계: 수집 결과물 정리 및 식별자 부여**

- 인터뷰 결과 → '면담 기록서', 워크숍 결과 → '워크숍 결과 보고서' 등 표준 양식으로 정리
- 개별 요구사항마다 프로젝트 전반에서 유일하게 유지되는 고유 ID를 부여
  - 예) REQ-FUN-001 (기능 요구사항 1번), REQ-NF-PER-002 (비기능-성능 요구사항 2번)
- 이 고유 ID는 이후 추적·변경 이력 관리에 핵심 역할을 한다.

**2단계: 분류 기준 심화**

- 기능/비기능 구분 후, 비기능은 성능·보안·품질·표준·제약으로 세분화
- **왜 세분화하는가**: 성능 전문가에게는 성능 요건을, 보안 전문가에게는 보안 요건을 검토 의뢰할 수 있기 때문
- **다음 단계**: 데이터 아키텍처 계층에 매핑하여 추적성을 극대화한다

### 3. 아키텍처 계층 매핑

정리된 요구사항은 **개념 계층 → 논리 계층 → 물리 계층**으로 이어지는 데이터 아키텍처 계층에 매핑되어, 이후 설계 단계와의 추적성을 확보한다. (CHAPTER 2 SUMMARY 슬라이드 요약: "비즈니스 요구 → 개념, 기능 요구 → 논리, 성능 요구 → 물리 데이터 모델")

### 4. 우선순위 분석 기법 — "우선순위 기법은 계산기가 아니라 '협상 테이블'이다"

> 모든 요구사항을 주어진 시간·예산 내에 구현하는 것은 현실적으로 불가능하다

| 기법 | 핵심 내용 |
|---|---|
| **MoSCoW** | Must-have: 없으면 출시 불가(결제 기능) / Should-have: 없으면 큰 불편(상품 검색) / Could-have: 있으면 좋은 부가 기능(다크 모드) / Won't-have: 이번 범위에서 명확히 제외(VR 피팅) → 애자일·MVP 범위 정의에 적합 |
| **Kano 모델** | 기본적 품질: 없으면 매우 불만, 있어도 당연(로그인 보안) / 성과적 품질: 충족될수록 만족 선형 증가(다운로드 속도) / 매력적 품질: 기대 안 했으나 큰 기쁨(초기 앱스토어) → 신제품 기획·차별화 포인트 발굴 |
| **RICE 점수** | Reach 도달 범위(예: 월 10,000명) · Impact 영향력(3/2/1/0.5) · Confidence 확신도(100%/80%/50%) · Effort 노력(Person-Months) → 점수 = R×I×C ÷ E, 높을수록 우선 |
| **화폐가치 · 상대적 중요도** | 화폐가치: 기업·시스템 차원 중요도 점수 → 가치 비율(%) → 기대 이익 배분 / 상대적 중요도: 평가 기준별 가중치(업무 기여도 50%, 연관성 20%, 충족도 30%) 가중 평균 → ROI 관점의 대규모 투자 의사결정 |

※ 기법은 정답을 알려주지 않는다. 서로 다른 관점을 객관적 데이터와 공통 언어로 테이블 위에 올려 '프로젝트에 가장 큰 가치를 더하는 것'에 합의하도록 돕는 도구다.

## SECTION 3. 정보 요구사항 통합(Integration)

### 1. 이음동의어를 찾아 하나의 표준 요구사항으로

> 흩어진 퍼즐 조각을 맞추어 전사적 관점의 일관된 청사진을 완성한다

**부서 간 중복·유사 검토 — 실제 사례**

- 영업팀: '거래처 정보 관리'
- 구매팀: '공급사 정보 관리'
- 재무팀: '지급처 정보 관리'
- → 각 부서 관점에서 표현되었지만, 데이터 아키텍처 관점에서는 모두 '비즈니스 파트너'라는 동일한 대상을 다루고 있다.
- → 전사 데이터 표준 용어에 기반해 '파트너 정보 관리' 단일 요구사항으로 통합

| 구분 | 설명 |
|---|---|
| 동일 부서 내 중복 | 같은 담당자가 다른 시점에, 또는 같은 팀의 다른 담당자가 같은 문제를 다른 표현으로 요청한 경우 |
| 분할 (Decomposition) | "영업 활동 지원 시스템 구축" → '고객 정보 관리', '일일 활동 보고', '실적 통계 조회'로 분할 |
| 통합 (Composition) | 여러 세부 요구사항이 하나의 상위 비즈니스 목표를 위한 것임이 명확해질 때 묶어서 관리 |

**통합 단계의 4가지 목표**: 전사 데이터 일관성 확보 · 중복 개발 방지 · 이해관계자 최종 합의 도출 · 요구사항 기준선(Baseline) 수립

### 2. 상충 요구사항 해결 — "상충은 기술 문제가 아니라 소통과 협상의 문제다"

**5단계 절차**

| # | 단계 | 설명 |
|---|---|---|
| 1 | 갈등 식별·문서화 | 어떤 요구사항이 상충하는지, 각 요구사항의 '소유자'가 누구인지 공식 문서화 |
| 2 | 근본 원인 분석 | 심층 인터뷰로 "왜" 필요한지 파악 — 표면 뒤의 진짜 비즈니스 목표 이해 |
| 3 | 우선순위 재조정 | RICE·화폐가치 등으로 비즈니스 가치·긴급성·위험도 재평가 |
| 4 | 대안 탐색·타협안 도출 | 양측 목표를 모두 만족시킬 제3의 창의적 대안 모색 |
| 5 | 이해관계자 워크숍 | 조정 워크숍에서 대안 공유, 촉진자 주도로 합리적 최종 합의 |

**상충 발생 원인 (예시)**

- 이해관계자 목표 불일치 — 보안팀 "모든 개인정보 필드 복잡한 암호화" ↔ 분석팀 "대용량 집계 쿼리 성능 보장"
- 자원·기술적 제약 — "실시간 전 세계 매장 재고 확인" ↔ 현재 네트워크 인프라·예산의 한계

**타협안 예시**

- 부분 완화: "자주 조회되는 일부 필드는 암호화를 완화하고, 민감한 핵심 정보만 강력하게 암호화"
- 단계적 충족: "이번 릴리스는 기본 기능 우선, 성능 최적화는 다음 릴리스에서 진행"

### 3. 최종 확정 및 관리 — "최종 산출물은 '완벽한 목록'이 아니라 '합의된 기준선'이다"

> 기준선 = 특정 시점에서 공식적으로 합의되고 검토된 명세 또는 산출물

**기준선(Baseline) 예시 테이블**

| 요구사항 ID | 요구사항명 | 유형 | 출처 | 우선순위 | 상태 | 비고 |
|---|---|---|---|---|---|---|
| REQ-FUN-021 | 고객 등급별 할인율 자동 적용 | 기능 | 마케팅팀 워크숍 | Must-have | 수용 | 할인율 정책은 관리자 화면에서 변경 가능 |
| REQ-NF-SEC-007 | 개인정보 조회 이력 기록 | 비기능(보안) | 개인정보보호법 | Must-have | 수용 | 로그 데이터는 최소 2년간 보관 |
| REQ-NF-PER-005 | 결제 처리 시간(평균 3초, 최대 5초) | 비기능(성능) | 사용자(UX)팀 인터뷰 | Should-have | 수용 | 외부 PG사 연동 시간 포함 |
| REQ-FUN-088 | 상품 추천 알고리즘 고도화 | 기능 | 데이터분석팀 제안 | Could-have | 보류 | 로직은 2단계 사업에서 검토 |

**기준선 수립 이후 — 요구사항 추적 매트릭스(RTM)로 양방향 추적성 확보**

- 정방향(Forward): 요구사항 → 설계 → 코드 → 테스트 / 누락 없이 반영되었는지 확인
- 역방향(Backward): 테스트 ← 코드 ← 설계 ← 요구사항 / 모든 기능이 타당한 요구사항에 근거하는지 확인

2. 부서별 용어를 그대로 등록 → 이음동의어 검토 없이는 데이터 모델이 중복된다.
3. 상충을 '둘 중 하나 선택'으로 처리 → 근본 원인을 파고들어 제3의 대안을 찾을 것.

## 자기 점검 Q&A

**Q1. 정보요구사항 생명주기 4단계 중 '조사'는 어느 단계에 해당하며, 무엇과 무엇을 잇는 다리 역할을 하는가?**
> A. 생명주기의 1단계인 '수집(Collection)'에 해당한다. 전략에서 도출된 CIR(핵심정보요구)과 현장의 실제 목소리(현업의 업무 현실)를 잇는 다리 역할을 한다.

**Q2. 하향식·상향식 접근법의 각 장단점을 한 문장씩 설명하고, 왜 혼합형이 실무에서 가장 권장되는가?**
> A. 하향식은 전략과의 일관성은 확보하지만 목표가 추상적이면 구체성이 부족하고, 상향식은 현실 반영은 뛰어나지만 혁신적 미래 요건 발굴이 어렵다. 혼합형은 두 결과를 상호 검증하여 전략적 방향성과 현실적 구체성을 동시에 확보하고 양쪽에서 놓친 요건까지 찾아낼 수 있기 때문에 가장 권장된다.

**Q3. 문서 분석, 사용자 면담, 워크숍/JAD 중 '단기간에 다수 이해관계자의 합의'를 끌어내기에 가장 적합한 기법은 무엇이며 그 이유는?**
> A. 워크숍/JAD. 명확한 역할과 절차를 갖춘 구조화된 회의 방식으로, 여러 이해관계자의 의견을 한자리에서 단기간에 수렴하여 충돌·모호성을 조기에 발견하고 해결할 수 있기 때문이다.

**Q4. MoSCoW, Kano, RICE 기법의 목적상 차이를 설명하라.**
> A. MoSCoW는 출시 범위(MVP)를 4단계 우선순위로 나누는 데 적합하고, Kano는 어떤 요건이 고객 만족에 어떻게 기여하는지(기본/성과/매력적 품질)를 분석해 차별화 포인트를 찾는 데 적합하며, RICE는 도달범위·영향력·확신도·노력을 정량 점수화하여 여러 요구사항을 객관적으로 비교하는 데 적합하다.

**Q5. 요구사항 기준선(Baseline)이란 무엇이며, RTM은 이를 어떻게 관리하는가?**
> A. 기준선은 특정 시점에서 공식적으로 합의되고 검토된 요구사항 명세다. RTM(요구사항 추적 매트릭스)은 정방향(요구사항→설계→코드→테스트)과 역방향(테스트→코드→설계→요구사항) 양방향 추적을 통해 누락과 근거 없는 기능을 방지한다.

## 부록: 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| CSF (Critical Success Factor) | 핵심성공요소 — 경영환경·정보환경 분석에서 도출되는 전략적 성공 조건 |
| CIR (Critical Information Requirement) | 핵심정보요구 — CSF를 정보 관점에서 구체화한 것, 조사 단계가 연결하는 대상 |
| 하향식 / 상향식 / 혼합형 접근 | 요구사항 수집 시 전략 기반(Top-Down) / 현행 시스템 기반(Bottom-Up) / 두 방식을 조합(Hybrid)하는 접근법 |
| JAD (Joint Application Development) | 명확한 역할과 절차를 갖춘 고도로 구조화된 요구사항 도출 워크숍 |
| 호손 효과 (Hawthorne Effect) | 관찰되고 있다는 사실 자체가 관찰 대상의 행동을 변화시키는 현상 (관찰 기법의 단점) |
| 기능 요구사항 | 데이터의 CRUD(생성·조회·수정·삭제)와 직접 연결되는 '무엇을(What)'에 대한 요구 |
| 비기능 요구사항 | 표준·품질·성능·보안 등 '어떻게(How)'에 대한 요구, 논리·물리 설계와 인프라를 결정 |
| MoSCoW | Must/Should/Could/Won't-have로 우선순위를 나누는 기법 |
| Kano 모델 | 기본적·성과적·매력적 품질로 요구사항이 만족에 미치는 영향을 분석하는 기법 |
| RICE 점수 | Reach × Impact × Confidence ÷ Effort로 산출하는 우선순위 정량화 기법 |
| 이음동의어 통합 | 부서마다 다른 이름으로 부르는 동일 대상(예: 거래처/공급사/지급처=비즈니스 파트너)을 표준 용어로 통합 |
| 기준선 (Baseline) | 특정 시점에 공식적으로 합의·검토된 요구사항 명세 또는 산출물 |
| RTM (Requirements Traceability Matrix) | 요구사항 추적 매트릭스 — 정방향·역방향으로 요구사항의 추적성을 관리하는 도구 |
