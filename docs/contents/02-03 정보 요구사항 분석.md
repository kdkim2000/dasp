# 02-03 정보 요구사항 분석

## 도입부 — 강의의 관점

현장에서 수집한 요구사항을 체계적으로 분석하여 비즈니스 전략과 데이터를 연결하는 논리적 설계로 구체화하는 것이 이번 챕터의 핵심 과정이다.

### LECTURE ROADMAP — 강의 흐름과 학습 목표

| # | 절 | 핵심 내용 |
|---|---|---|
| 1 | 분석 대상 정의 | 현행 업무 분석(As-Is), SWOT·가치사슬 분석, 현행 시스템 분석·Gap 발견 |
| 2 | 요구 사항 상세화 | 프로세스 관점: DFD / 객체지향 관점: 유스케이스 / 비기능 요구사항 정량화 |
| 3 | 요구 사항 확인 | 검토 기법 3종 비교, CRUD 상관분석, SRS와 기준선 설정 |
| 4 | 핵심 통찰 | 검증(Verification) vs 확인(Validation), 두 개의 관문 |

**학습 목표**: 본 장을 마치면 다음을 할 수 있다.
- SWOT·가치사슬 분석과 리버스 모델링으로 As-Is를 진단하고 비즈니스-시스템 간 Gap을 도출할 수 있다.
- DFD를 레벨링하여 작성하고 블랙홀·미라클 등 논리적 오류를 식별할 수 있다.
- 유스케이스 다이어그램과 시나리오(정상·대안·예외 흐름)를 작성하고 클래스 후보를 도출할 수 있다.
- FURPS+로 비기능 요구사항을 분류·정량화하고, 검토·상관분석을 거쳐 기준선을 설정할 수 있다.

### 4대 핵심 산출물 (분석 단계 완료 시 도출)

| 산출물 | 설명 |
|---|---|
| ① 요구사항 명세서 | 도출된 모든 요구사항을 공식 기록한 문서. 개발팀과 현업 간 법적·기술적 구속력을 지닌 계약서이자, 향후 모든 설계와 테스트의 절대적 기준점 |
| ② 업무 영역 및 현행 시스템 매트릭스 | 전사 비즈니스 프로세스가 어떤 레거시 시스템에 의해 지원되는지 조망 → 아키텍처의 사각지대 제거 |
| ③ CRUD 매트릭스 | 프로세스와 데이터의 상호작용을 행렬로 규명 → 데이터 모델의 논리적 완전성을 검증하는 필수 통제 도구 |
| ④ 분석 모델(DFD·유스케이스) | 추상적 요건을 시각화하여 모델링의 직접적 기반 제공 |

→ 이 산출물들은 개념·논리·물리 데이터 모델링으로 직결된다. 명세서의 비즈니스 규칙은 엔티티 간 관계와 속성 제약 조건으로 투영되며, CRUD 분석 결과는 데이터 구조의 누락 여부를 판별한다. **"분석의 정밀도가 아키텍처의 수명을 결정한다."**

## SECTION 1. 분석 대상 정의

### 1. 현행 업무 분석 — 데이터 관점의 SWOT

> 비즈니스 프로세스·업무 규칙·전략적 목표를 데이터 관점에서 이해하는 것이 목표. 분석가는 단순한 기록자가 아니라 재무적·전략적 탐정의 시각을 지녀야 하며, 공식 문서뿐 아니라 현업 인터뷰 이면의 암묵적 지식을 발굴해야 한다.

| 구분 | 예시 |
|---|---|
| 강점(S) | 경쟁사 대비 정확성·최신성이 높은 고객 데이터, 잘 구축된 데이터 표준 체계 |
| 약점(W) | 부서 간 데이터 단절로 전사 분석이 어려운 데이터 사일로(Silo), 데이터 품질 관리 조직의 부재 |
| 기회(O) | 빅데이터·인공지능 등 신기술 기반 신규 서비스, 데이터 기반 마케팅을 통한 점유율 확대 |
| 위협(T) | 강화되는 개인정보보호 규제(GDPR·개인정보보호법), 경쟁사의 데이터 기반 신규 비즈니스 모델 |

**SWOT → 구체적 정보 요구사항으로 전환하는 예**: '데이터 사일로'라는 약점(W)을 극복하고 '빅데이터 분석'이라는 기회(O)를 활용하기 위해 → "전사 데이터 통합 플랫폼 구축"이라는 구체적인 정보 요구사항을 도출할 수 있다. (SWOT을 도식화하는 데 그치지 않고, 이렇게 구체적·전략적 정보 요구로 연계해서 도출하는 것이 분석의 실질적 목표다.)

**분석의 원천 자료**: 공식 문서(중장기 경영 전략, 사업 계획서, 업무 분장 기술서, 업무 매뉴얼, 규정 및 지침서) + 비공식 정보(현업 담당자 인터뷰, 워크숍에서 얻는 암묵적 지식) — 분석가는 '탐정'이 되어 단서를 모아야 한다.

### 2. 현행 업무 분석 — 가치사슬(Value Chain) 분석

> 기업의 모든 활동을 고객 가치 창출 관점에서 본원적 활동과 지원 활동으로 세분화해서 분석한다. 데이터 관점에서 가치사슬을 추적하면 각 단계별 데이터의 생성과 소비 구조가 투명해진다.

| 본원적 활동 | 관련 데이터 |
|---|---|
| 입고 물류 | 공급업체 정보, 원자재 입고 데이터, 재고량 데이터 |
| 운영 / 생산 | 생산 계획 데이터, 공정·품질 검사 데이터, 생산 실적 데이터 |
| 출고 물류 | 주문 데이터, 창고 관리 데이터, 배송 추적 데이터 |
| 마케팅 / 영업 | 고객 정보, 프로모션 반응 데이터, 영업 활동·계약 데이터 |
| 서비스 | 고객 문의(VOC) 데이터, A/S 처리 이력, 고객 만족도 데이터 |

지원 활동: 인사 관리(임직원 정보·급여 데이터·성과 평가 데이터), 재무/회계(재무제표 데이터·예산 및 실적 데이터)

**데이터 흐름의 '단절' 발견**: 예) '서비스' 단계에서 수집된 고객 불만(VOC) 데이터가 '운영/생산' 단계의 품질 개선 활동에 활용되지 않고 있다면 → 이 단절을 개선하기 위한 실시간 연계 요구사항을 도출할 수 있다. 가치사슬 분석은 아키텍처의 단절 구간을 찾아내기 위한 정밀 지도라고 볼 수 있다.

### 3. 현행 시스템 분석 — 산출물 분석과 리버스 모델링

> 업무가 '무엇을(What)'이라면, 시스템은 '어떻게 구현하고 있는가(How)'를 보여준다. 목표는 기존 시스템의 데이터 구조·흐름·인터페이스·기술적 제약을 정확히 식별하는 것이다.

| 기법 | 설명 |
|---|---|
| ① 산출물 분석 (Documentation Review) | 현행 시스템의 분석·설계·개발 보고서, 사용자 및 운영자 지침서를 면밀히 검토. 그러나 문서는 오래되거나 관리되지 않아 실제 시스템과 다를 수 있음 → 반드시 다음 4가지 기준(유용성·완전성·정확성·유효성)으로 문서의 신뢰도를 평가 |
| ② 리버스 모델링 | DDL·카탈로그 정보를 분석 도구로 역분석하여 물리(PDM)·논리(LDM) 데이터 모델을 역생성. 산출물 문서가 부실하거나 존재하지 않을 때, 실제 운영 데이터 구조를 가장 정확히 파악하는 방법. 비정규화·데이터 타입 불일치·잘못된 관계 설정 등 현행 구조의 문제점을 진단 |

**산출물**: 현행 시스템 수집 문서 목록(문서별 4기준 평가 결과 기록), 업무 영역/현행 시스템 매트릭스 — 기능 중복과 지원 공백을 시각적으로 파악

### 4. Gap 발견 — 4단계 프로세스

> 업무 분석(Why)과 시스템 분석(How)의 교차점에서 진짜 문제가 드러난다. 사례: "최근 이탈하는 고객의 원인을 분석하고 싶다"

| # | 단계 | 사례 적용 |
|---|---|---|
| 1 | 업무 분석 | SWOT — '높은 고객 이탈률'을 위협(T), '고객 데이터 분석 역량 부족'을 약점(W)으로 정의. 분석 대상 업무 목표에 최우선 과제로 포함 |
| 2 | 시스템 분석 | 업무 영역/현행 시스템 매트릭스로 '고객관리시스템'과 '성과관리시스템'이 관련됨을 파악 |
| 3 | Gap 발견 | ERD·테이블 정의서 분석 결과 — 등급·구매 이력은 관리되나 해지 사유·시점·이탈 징후를 기록할 항목이 없음 |
| 4 | 요구사항 도출 | "이탈일·이탈사유코드·이탈징후를 관리할 데이터 구조 설계 및 관련 기능 개발" |

**사용자 뷰(View)를 놓치지 마라**: 화면·보고서·수작업 양식은 사용자가 어떤 데이터를 어떤 형태로 조합해 보는지를 보여주는 가장 직접적인 증거다. 한 보고서에 '고객 정보' + '최근 3개월 주문 내역' + 'A/S 접수 이력'이 함께 나온다면 → 엔티티 간 중요한 연관 관계의 단서. 보고서에 수기로 계산해 기입하는 항목이 있다면 → 시스템이 제공하지 못하는 잠재적 요구사항(추출 속성)일 가능성이 높다.

## SECTION 2. 정보 요구사항 상세화

### 1. 프로세스 분해와 계층도 — 기본 프로세스까지 내려간다

> 기본 프로세스: 하나의 사건으로 시작되어 중단 없이 수행되고 측정 가능한 결과를 산출하는 업무 단위

| 단계 | 설명 |
|---|---|
| ① 단위 업무 기능 | 예) '주문 관리' |
| ② 기본 프로세스로 분해 | '신규 주문 접수' · '주문 내역 변경' · '주문 취소' |
| ③ 프로세스 계층도 작성 | 높은 응집도(Cohesion), 낮은 결합도(Coupling) |
| ④ 정보 항목 도출 | 각 프로세스의 입력·출력 정보를 명사형으로 식별·목록화 |

**모듈성의 원칙**: 응집도 높음 — 하나의 상위 프로세스에 속한 하위 프로세스들이 기능적으로 밀접하게 연관 / 결합도 낮음 — 서로 다른 프로세스 그룹 간의 의존성이 낮음 / 상위 1개 → 하위 7개 내외로 분해하는 것이 인지적으로 가장 효과적.

**정보 항목 도출 → 표준화 연계**: '신규 주문 접수' 입력(고객ID·상품코드·주문수량·배송지주소), 출력(주문번호·주문일시·결제예정금액) → 도출 즉시 표준 단어·용어·도메인과 대조하여 명칭·타입·길이를 일관되게 정의.

### 2. 데이터 흐름도(DFD) — 4가지 기호와 레벨링(Leveling)

> 데이터가 어떻게 입력되어 변환·저장되고 출력되는지를 시각화하는 핵심 분석 도구

| 기호 | 명칭 | 설명 |
|---|---|---|
| ○ | 프로세스 | 입력 데이터를 가공하여 새 데이터를 출력하는 활동. 원 또는 둥근 사각형, '동사+명사'로 표기(예: 고객 정보 등록) |
| → | 데이터 흐름 | 데이터의 이동 경로와 방향. 화살표, 이동 데이터명 기입(예: 신규 고객 정보) |
| ▤ | 데이터 저장소 | 데이터가 저장되는 장소(파일·테이블). 두 개의 평행선, 저장 데이터명 기입(예: 고객 마스터) |
| □ | 외부 엔티티 | 시스템과 데이터를 주고받는 외부 주체. 사각형(예: 고객, 세무 시스템) |

**레벨링**

| 레벨 | 설명 |
|---|---|
| 레벨 0 — 배경도(Context) | 전체 시스템을 단 하나의 프로세스로 보고, 외부 엔티티와의 주요 입출력만 표현 → 시스템의 범위와 외부 인터페이스 정의 |
| 레벨 1 | 레벨 0의 단일 프로세스를 주요 기능으로 분해하고, 데이터 흐름과 주요 저장소를 식별 → 시스템의 핵심 내부 구조 |
| 레벨 2 이상 | 각 프로세스를 더 상세한 하위 프로세스로 분해하여 구체적인 처리 로직 표현 → 충분히 상세화될 때까지 반복 |

### 3. DFD 작성 규칙과 검증 — 블랙홀과 미라클

> 데이터가 사라지거나 창조되는 오류를 잡아내는 것이 핵심. **데이터 보존의 원칙**: 프로세스는 입력 데이터 없이 출력 데이터를 생성할 수 없다. 모든 출력 데이터 흐름은 반드시 입력 데이터 흐름이 변환된 결과여야 한다.

| 오류 유형 | 설명 |
|---|---|
| 블랙홀 (Blackhole) | 입력 데이터 흐름은 있으나 출력 데이터 흐름이 없는 프로세스 → 데이터가 소멸되는 논리적 오류 |
| 미라클 (Miracle) | 입력 데이터 흐름 없이 출력 데이터 흐름만 생성하는 프로세스 → 데이터가 무(無)에서 창조되는 논리적 오류 |
| 직접 연결 금지 | 데이터 저장소 ↔ 데이터 저장소, 외부 엔티티 ↔ 외부 엔티티 간 직접 흐름 불가 → 모든 흐름은 반드시 프로세스를 거쳐야 함 |

**DFD가 보증하는 것**: DFD는 데이터의 흐름과 변환 과정의 '완전성'을 보증한다. 반면 사용자의 목표 달성 시나리오와 상호작용의 완전성은 유스케이스가 보증한다. → 두 관점을 교차 검증할 때 비로소 숨겨진 요구사항이 드러난다.

### 4. 유스케이스 모델링 — "사용자가 시스템으로 무엇을 할 수 있는가"

> 액터·유스케이스·시스템 경계·관계(포함·확장·일반화)

**구성 요소**
- 액터(Actor) — 시스템과 상호작용하는 사람·외부 시스템·시간 등 외부 주체
- 유스케이스(Use Case) — 액터가 목표를 달성하기 위한 일련의 상호작용, '동사+명사'(예: 회원 가입하기)
- 시스템 경계 — 개발 대상 시스템의 범위를 나타내는 사각형

**관계(Relationship)**
- 포함(Include) — 반드시 포함하여 수행. 예) '게시글 작성'과 '게시글 수정'은 모두 '사용자 인증'을 포함
- 확장(Extend) — 조건 만족 시 선택적으로 수행. 예) '상품 결제'가 '쿠폰 사용'으로 확장
- 일반화(Generalization) — 공통 특징을 상위 유스케이스로 추상화하고 하위가 상속

**시나리오 흐름 3종**: ① 정상 흐름(Basic Flow) — 예외 없이 성공적으로 완료되는 주된 경로를 단계별로 기술 / ② 대안 흐름(Alternative) — 분기될 수 있는 또 다른 정상 경로(예: 소셜 계정 로그인, 생체 인증 로그인) / ③ 예외 흐름(Exception) — 오류·비정상 상황으로 목표 달성에 실패하는 경우(예: 비밀번호 5회 오류, 인증 서버 연결 불가)

### 5. 클래스 다이어그램 도출 — 명사는 엔티티, 형용사는 속성, 동사는 관계

> 유스케이스 명세서는 개념 데이터 모델링의 기초 입력 자료가 된다.

| # | 변환 규칙 | 예시 |
|---|---|---|
| 1 | 명사 → 엔티티 클래스 | "고객이 상품을 주문한다" → '고객', '상품', '주문'이 엔티티 클래스 후보 |
| 2 | 형용사·소유격 → 속성 | "고객'의 '이름', '주소'" → 해당 클래스의 속성(Attribute) 후보 |
| 3 | 동사 → 관계 | "'고객'과 '주문' 사이의 '주문하다'" → 클래스 간 관계(Association) 도출의 단서 |

**비기능적 요구사항(NFR)은 반드시 정량화한다**: ✕ "시스템 응답 속도가 빨라야 한다" → 사용자와 개발자 간의 동상이몽만 유발 / ○ "핵심 기능인 '실시간 재고 조회'는 동시 사용자 1,000명 접속 환경에서 95%의 경우 2초 이내에 응답해야 한다" → 데이터 아키텍처 영향: 데이터의 양·처리 속도·보안 수준·백업 복구 정책이 물리 데이터 모델(인덱싱·파티셔닝·반정규화)을 결정한다. 기능을 완벽히 구현해도 느리거나 취약하거나 복잡하면 시스템은 결국 외면받는다.

### 6. 비기능 요구사항 분류 — FURPS+ 프레임워크

> 누락 없이 도출하기 위한 분류 프레임워크

| 구분 | 항목 | 세부 내용 |
|---|---|---|
| F | Functionality (기능성) | 시스템이 제공해야 할 기능의 범위·정확성·상호운용성(기능 요구사항으로 분류하기도 함) |
| U | Usability (사용성) | 얼마나 쉽게 배우고 사용할 수 있는가 — 심미성·일관성·도움말 및 문서화 |
| R | Reliability (신뢰성) | 얼마나 안정적으로 고장 없이 동작하는가 — 평균 무고장 시간(MTBF)·가용성·장애 복구 능력 |
| P | Performance (성능) | 응답 속도·처리량·자원 사용 효율 — 응답 시간·초당 트랜잭션 수(TPS)·CPU/메모리 점유율 |
| S | Supportability (지원성) | 유지보수성·이식성·확장성·테스트 용이성 |
| + | Constraints (제약) | 설계 제약(언어·프레임워크)·구현 제약(코딩 가이드)·인터페이스 제약(프로토콜)·물리적 제약(HW·대역폭) |

### 7. 핵심 통찰 — DFD와 유스케이스는 경쟁이 아니라 상호 보완 관계다

> 온라인 서점 '주문 처리' 기능을 두 관점으로 교차 검증하는 예

| 관점 | 내용 |
|---|---|
| ① 프로세스 관점(DFD) | 데이터의 정적 구조와 흐름의 논리적 무결성에 집중. '주문 처리' → '재고 확인'·'결제 처리'·'배송 요청'으로 분해. '주문 정보'가 '고객'(외부 엔티티) → '주문' 저장소 → '재고' 저장소 → '배송 시스템'으로 흐르는 파이프라인 시각화 |
| ② 객체지향 관점(유스케이스) | 사용자의 동적 행위와 시스템의 반응에 집중. '고객' 액터가 '도서를 주문한다' 목표를 달성하는 과정을 시나리오로 작성: 1) 장바구니 담기 → 2) 배송지 입력 → 3) 결제 수단 선택·결제 정보 입력 → 4) 결제 승인·주문 완료 표시 |
| ③ 상호 검증을 통한 통찰 발견 | 유스케이스 시나리오: "3. 고객이 결제 수단으로 포인트를 선택한다" — DFD '결제 처리' 프로세스에는 '회원' 저장소로부터 '포인트 정보'가 입력되는 경로가 없음 → 요구사항의 불일치 또는 누락. 한쪽 모델만 보았다면 발견할 수 없었을 것 |

DFD의 강점: 데이터의 흐름과 변환 과정의 완전성 보증 / 유스케이스의 강점: 사용자 목표 달성 시나리오와 상호작용의 완전성 보증. **두 가지를 결합했을 때 비로소 견고하고 완전한 요구사항 모델이 완성된다.**

| 단점 | 검토 깊이가 얕고 감정 개입 가능 | 작성자 발표 능력에 의존, 해결보다 발견에 집중 | 준비·수행에 많은 시간과 비용 소요 |
| 적합한 상황 | 초기 아이디어·초안 검토 | 팀 내부 중간 산출물 검토 | 안정성·품질이 매우 중요한 핵심 산출물(최종 SRS) |

※ 검토 기준(체크리스트): 완전성·정확성·일관성·명확성·검증 가능성·추적성 — 즉흥적 회의는 시간 낭비다. 목표·대상·참석자·일정·기준을 사전에 정의하고 공유한다.

### 2. CRUD 매트릭스로 요구사항의 완전성을 논리적으로 검증한다

> 행 = 업무 기능/프로세스, 열 = 데이터 집합(엔티티)

| 업무 기능 ↓ / 정보 항목 → | 고객 | 상품 | 주문 | 재고 |
|---|---|---|---|---|
| 회원 가입 | C | | | |
| 상품 정보 조회 | | R | | |
| 주문 접수 | R | R | C | U |
| 결제 처리 | | | U | |
| 배송 처리 | | | U | |
| 회원 탈퇴 | D | | | |

**검증 규칙 4가지**
1. 생성 규칙 — 모든 엔티티는 최소 하나 이상의 'C'(생성)를 가져야 한다.
2. 활용 규칙 — 'C'된 엔티티는 R·U·D 중 하나 이상과 연결되어 활용되어야 한다.
3. 프로세스 수행 규칙 — 모든 프로세스는 CRUD 중 하나 이상을 수행해야 한다.
4. 소멸 규칙 — 연구·보관이 불필요한 데이터에는 반드시 삭제(D) 프로세스가 존재해야 한다.

**분석 결과 → 도출된 요구사항 예시**: 위 표에서 '상품' 엔티티에 C·U·D가 없음(활용 규칙 위반 가능성) → "상품 등록/수정/삭제 프로세스" 신규 요구사항 도출.

### 3. 검증(Verification)과 확인(Validation) — 두 개의 관문

- **검증(Verification)**: 명세서 자체의 논리적 정확성 확인 — "제품을 올바르게(right) 만들고 있는가?" (인스펙션, CRUD 매트릭스 등으로 수행)
- **확인(Validation)**: 사용자의 실제 의도 충족 여부 확인 — "올바른(right) 제품을 만들고 있는가?"
- 두 관문을 모두 통과해야 흔들림 없는 요구사항 기준선(Baseline)이 완성된다.

2. DFD 또는 유스케이스 한쪽만 작성 → 누락된 데이터 흐름을 끝내 발견하지 못함.
3. 검증만 하고 확인을 생략 → 논리적으로 완벽하지만 현장에서 쓸 수 없는 명세서가 된다.

## 자기 점검 Q&A

**Q1. SWOT 분석 결과에서 '약점'과 '기회'를 어떻게 조합해야 구체적인 정보 요구사항이 되는가?**
> A. 약점(예: 데이터 사일로)을 극복하고 기회(예: 빅데이터 분석)를 활용하는 방향으로 결합하여, "전사 데이터 통합 플랫폼 구축"과 같은 구체적·전략적 요구사항으로 전환한다.

**Q2. Gap 발견 4단계 프로세스를 순서대로 설명하라.**
> A. ① 현행 업무 정의(SWOT 등으로 이상적 업무·데이터 요건 정의) → ② 현행 시스템 역추적(매트릭스로 현재 지원 기능·구조 매핑) → ③ Gap 식별(이상과 현실의 괴리 진단) → ④ 개선 요구사항 도출(신규 기능·데이터 구조 변경 요건 정의).

**Q3. DFD에서 블랙홀과 미라클의 차이는 무엇이며, 공통적으로 위반하는 원칙은?**
> A. 블랙홀은 입력은 있으나 출력이 없는 오류(데이터 소멸), 미라클은 입력 없이 출력만 있는 오류(데이터 무에서 창조)다. 둘 다 "프로세스는 입력 데이터 없이 출력 데이터를 생성할 수 없다"는 데이터 보존의 원칙을 위반한다.

**Q4. DFD와 유스케이스가 상호 보완적이라는 것을 CRUD 매트릭스 예시로 설명한다면?**
> A. 유스케이스 시나리오에는 있지만 DFD의 해당 프로세스에 대응하는 데이터 흐름이 없는 경우(예: 포인트 결제 시나리오는 있으나 DFD에 포인트 정보 입력 경로가 없는 경우) 요구사항의 불일치·누락이 드러난다. 이는 한쪽 모델만으로는 발견할 수 없고, 두 모델을 교차 검증해야만 발견된다.

**Q5. 검증(Verification)과 확인(Validation)의 차이를 한 문장씩 설명하라.**
> A. 검증은 "제품을 올바르게 만들고 있는가"를 묻는, 명세서 자체의 논리적 정확성 확인이다(인스펙션, CRUD 매트릭스). 확인은 "올바른 제품을 만들고 있는가"를 묻는, 사용자의 실제 의도 충족 여부 확인이다.

## 한 줄 요약

정보 요구사항 분석은 **As-Is(현행 업무·시스템)를 SWOT·가치사슬·리버스 모델링으로 해부해 Gap을 찾고(분석 대상 정의) → DFD(프로세스 관점)와 유스케이스(객체지향 관점)를 교차 검증하며 FURPS+로 비기능 요구사항을 정량화하고(상세화) → 검토 기법과 CRUD 매트릭스로 논리적 완전성을 검증(Verification)하고 사용자 의도와의 일치를 확인(Validation)하는(확인)** 3단계 과정이며, 이 전 과정의 정밀도가 이후 데이터 아키텍처의 수명을 결정한다.

## 부록: 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| SWOT 분석 | 강점(S)·약점(W)·기회(O)·위협(T)을 데이터 관점에서 분석해 구체적 정보 요구사항을 도출하는 기법 |
| 가치사슬(Value Chain) 분석 | 기업 활동을 본원적·지원 활동으로 나누어 데이터 생성·소비 흐름과 단절 구간을 찾는 기법 |
| 리버스 모델링 (Reverse Engineering) | DDL·카탈로그를 역분석하여 물리(PDM)·논리(LDM) 데이터 모델을 역생성하는 기법 |
| Gap 분석 | 이상적 요건(현행 업무)과 현실(현행 시스템) 간의 괴리를 식별해 개선 요구사항을 도출하는 4단계 프로세스 |
| DFD (Data Flow Diagram) | 프로세스·데이터 흐름·데이터 저장소·외부 엔티티 4요소로 데이터의 흐름을 시각화하는 도구 |
| 블랙홀 (Blackhole) / 미라클 (Miracle) | DFD의 대표적 논리 오류 — 출력 없는 프로세스(블랙홀) / 입력 없는 프로세스(미라클) |
| 유스케이스 다이어그램 | 액터와 유스케이스 간의 상호작용(포함·확장·일반화)을 통해 사용자 관점의 시스템 행위를 정의하는 도구 |
| FURPS+ | 기능성·사용성·신뢰성·성능·지원성·제약의 6가지 관점으로 비기능 요구사항을 빠짐없이 분류하는 프레임워크 |
| 동료 검토 / 워크스루 / 인스펙션 | 공식성 수준이 점차 높아지는 3단계 요구사항 검토 기법 |
| CRUD 매트릭스 | 업무 기능(행)과 데이터 엔티티(열)의 교차점에 생성·조회·수정·삭제를 매핑해 논리적 완전성을 검증하는 도구 |
| 검증 (Verification) | 명세서 자체의 논리적 정확성을 확인 — "올바르게 만들고 있는가" |
| 확인 (Validation) | 사용자의 실제 의도 충족 여부를 확인 — "올바른 것을 만들고 있는가" |
