# 02-04 정보 요구 검증

## 도입부 — 검증의 경제학: 결함 수용 비용 곡선

지난 챕터(조사→분석)에서 도출된 요구사항 명세서가 비즈니스 목적을 정확하고 완전하게 반영했는지 최종 검증·확정하는 단계가 이번 챕터다.

**요구사항 분석 단계에서의 수정 비용을 1이라 할 때, 단계가 늦어질수록 결함 수정 비용은 기하급수적으로 증가한다.**

| 단계 | 상대 비용 |
|---|---|
| 요구사항 분석 | 1 |
| 설계 | 3~6배 |
| 코딩 | 10배 |
| 테스트 | 20~50배 |
| 운영(상용 이후) | 100~200배 |

**정보 요구 검증의 6가지 목적**: 완전성(Completeness, 누락 없는 포함) · 정확성(Correctness, 의도와 규칙의 올바른 기술) · 일관성(Consistency, 상충·모순 제거) · 명확성(Clarity, 모호한 표현 제거) · 검증 가능성(Verifiability, 테스트로 확인 가능) · 실현 가능성(Feasibility, 예산·기술·일정 내 구현 가능)

→ 정보 요구 검증은 단순한 오류 색출이 아니라, 프로젝트의 예산·일정·품질을 담보하는 최고 수준의 경제적 활동이다.

### 검증의 의의 — 개별 시스템을 넘어 전사 아키텍처와 거버넌스를 지키는 활동

| 관점 | 설명 |
|---|---|
| 데이터 아키텍처 관점 | 새롭게 정의된 요구사항이 기존 전사 데이터 모델·표준·데이터 흐름과 정합성을 유지하는지 확인. 예) 신규 요구로 '고객 신용등급' 데이터가 필요할 때 기존 '고객' 엔티티를 재사용할지, 새 엔티티를 정의할지 판단 — 생략 시 데이터 중복·불일치·관리비용 증가로 아키텍처 근간이 흔들림 |
| 데이터 거버넌스 관점 | 데이터 정책과 원칙이 실제 요구사항에 반영되었는지 통제 — 오너십 충돌의 사전 식별(한 데이터의 생성 요구가 여러 부서에서 동시에 제기되면 오너십 원칙 위배 신호), 거버넌스 협의체 연계 |

검증이 제거하는 것은 프로젝트 최대의 위험 요소인 '요구사항의 불확실성'이다. 개발팀에게는 안정적인 개발 기준점을, 사용자에게는 기대 부응 신뢰를, 프로젝트 관리자에게는 범위 확산(Scope Creep) 통제 근거를 제공한다.

### 강의 흐름

1. 제1절: 상관분석 기법 — CRUD 매트릭스의 6대 검증 규칙, 조직·기능 간 상관분석으로 데이터 오너십 확립
2. 제2절: 이상 징후를 실행 가능한 조치로 전환하여 추가·삭제 요건 도출
3. 제3절: 인스펙션을 통한 공식 검토, 이해관계자의 최종 합의(Sign-off), 요구사항 기준선과 변경 통제 프로세스

## SECTION 1. 상관분석(Correlation Analysis)

### 1. 상관분석의 개요 — 데이터 중심으로 특화된 추적성 확보 도구

> 정보 요구사항을 프로세스·업무 기능·조직 구조와 2차원 매트릭스로 교차 분석한다

| 목표 | 설명 |
|---|---|
| ① 완전성 검증 | 업무 기능·프로세스를 지원하는 데 필요한 정보가 누락되지 않았는가. 생성은 되지만 아무 곳에서도 활용되지 않는 불필요한 정보는 없는가 |
| ② 일관성 검증 | 동일한 정보를 여러 프로세스·조직에서 중복으로 생성하려는 시도는 없는가. 요구사항 간 잠재적 충돌이나 모순 발견 |
| ③ 추적성 확보 | 모든 정보 요구사항이 어떤 비즈니스 활동에 근거해 도출되었는가. 변경될 경우 어떤 영역에 영향을 미치는가에 대한 명확한 연결고리 |

**RTM과 상관분석의 관계** (혼동 주의)

- RTM(요구사항 추적성 매트릭스): 요구사항-설계-테스트 케이스 등 개발 산출물 전반의 연결성을 추적하는 포괄적 도구
- 상관분석: 데이터(정보 요구)와 비즈니스 컨텍스트(업무·조직) 간의 논리적 정합성 보장에 집중하는, 데이터 아키텍처 분야의 특화 도구

### 2. 분석 주체별 전략 — 누가 분석하느냐에 따라 결과가 달라진다

| 분석 주체 | 장점 | 단점 |
|---|---|---|
| 요구사항 분석가 | 높은 업무 이해도(직접 도출했기에 비즈니스 맥락 이해가 깊음), 신속성(추가 인력 없이 이해관계자와 원활히 소통) | 객관성 저하 — 자신이 도출한 요구를 스스로 검증하므로 무의식적 편향·실수를 간과할 수 있음 |
| 품질보증(QA)팀 | 시스템 관점의 검증(시스템 간 인터페이스·데이터 흐름의 일관성), 객관성 일부 확보(분석가와 독립된 조직) | 낮은 업무 이해도 — 표면적 논리 오류는 잡아내나 복잡한 비즈니스 규칙의 타당성 검증에는 한계 |
| 외부 감리 | 최고 수준의 객관성(제3자 시각, 정치적 이슈에 얽매이지 않음), 규제 준수 검증에 효과적 | 업무 파악의 한계 — 단기간 이해가 어려워 형식에 그칠 위험, 높은 비용 및 내부 자원 소모 |

**전략적 선택 — 분석 주체 결정은 자원 배정이 아니라 위험 관리 전략이다.**

- 고위험(금융·의료): 외부 감리 / Agile·신속 개발: 분석가가 수행 + 동료 검토 / 대규모·복합 시스템: QA팀 중심의 인터페이스 정합성 검증
- ★ 하이브리드가 최선: ① 분석가가 초안 작성 → ② QA팀이 시스템 관점 보완 → ③ 중대 이슈·규제 사항만 외부 감리 자문

### 3. CRUD 매트릭스 — 매트릭스 작성 3단계와 표기 규칙

> 모든 정보 항목이 데이터 생명주기 전체에 걸쳐 완전하고 일관되게 관리되는지 검증한다

| # | 단계 | 설명 |
|---|---|---|
| 1 | 행(Row) 정의 | 정보 요구 분석으로 도출된 정보 항목, 즉 데이터 모델의 핵심 엔티티 목록을 행에 나열 |
| 2 | 열(Column) 정의 | 애플리케이션 아키텍처에서 정의된 단위 업무 기능(기본 프로세스) 목록을 열에 나열 |
| 3 | 셀(Cell) 값 정의 | 교차 지점에 해당 프로세스가 정보 항목에 수행하는 작업을 C·R·U·D로 표기 |

| 표기 | 의미 | 예시 |
|---|---|---|
| C (Create) | 정보 항목의 새로운 인스턴스를 생성 | '회원 가입' 프로세스는 '고객' 엔티티를 생성 |
| R (Read) | 데이터를 조회하지만 변경하지 않음 | '주문 내역 조회' 프로세스는 '주문' 엔티티를 조회 |
| U (Update) | 기존 인스턴스의 내용을 수정 | '회원 정보 수정' 프로세스는 '고객' 엔티티를 수정 |
| D (Delete) | 인스턴스를 논리적 또는 물리적으로 삭제 | '회원 탈퇴' 프로세스는 '고객' 엔티티를 삭제 |

※ 한 프로세스가 한 정보 항목에 여러 작업을 수행하는 경우(예: 주문하면서 재고를 조회하고 수정), 영향이 가장 큰 하나만 표기하거나 모두 표기 — 우선순위는 C→D→U→R 순.

### 4. CRUD 검증 체크리스트 — 6가지 검증 규칙으로 이상 징후를 식별한다

| 규칙 | 검증 항목 | 설명 및 판단 기준 |
|---|---|---|
| 규칙1 | 생성(C)의 존재 여부 | 모든 정보 항목(행)은 반드시 하나 이상의 'C'를 가져야 한다. 없으면 생성 프로세스 누락이거나 정보 항목 자체가 불필요 |
| 규칙2 | 활용(R/U)의 존재 여부 | 'C'로 생성된 항목은 최소 한 번 이상 조회·수정되어야 한다. 생성만 되고 쓰이지 않는 데이터는 목적에 기여하지 않는다 |
| 규칙3 | 소멸(D)의 존재 여부 | 비즈니스 규칙상 소멸·비활성화가 필요한 항목은 'D' 프로세스를 가져야 한다(거래 이력 등 영구 보존 데이터는 예외) |
| 규칙4 | 프로세스의 역할 존재 | 모든 기본 프로세스(열)는 하나 이상의 C·R·U·D를 수행해야 한다. 아무 작업도 없는 프로세스는 존재 목적이 불분명 |
| 규칙5 | 생성(C)의 유일성 | ★ 'C'를 수행하는 프로세스가 둘 이상이면 면밀한 검토 필요 — 업무 역할 중복·생성 경로 이원화로 정합성 문제를 유발할 위험 신호 |
| 규칙6 | 과도한 CRUD 집중 | 생성/수정/삭제 프로세스의 합이 비정상적으로 많으면(예: 7개 초과) 엔티티 역할이 과대하거나 프로세스 설계가 미세분화될 것 |

### 5. 업무 기능 · 조직 기능 상관분석 — 데이터를 비즈니스와 조직에 연결한다

> 셀 값: C(주도적 생성·변경) / U(단순 참조·활용)

| 구분 | 목적 | 핵심 점검 포인트 |
|---|---|---|
| 정보 요구 / 업무 기능 상관분석 | 데이터와 비즈니스의 전략적 정렬(Strategic Alignment). 열 = 비즈니스 아키텍처(BA)에서 정의된 최하위 업무 기능(예: 고객 관리, 주문 처리, 재고 관리) | 열 전체가 비어 있다 → 순수 오프라인 활동이거나 정보 항목 누락 신호 / 행 전체가 비어 있다 → 어떤 업무 기능도 지원하지 않는 데이터 → 삭제 대상 / 'C'는 있으나 'U'가 전혀 없다 → 데이터 존재 가치 자체를 재검토 |
| 정보 요구 / 조직 기능 상관분석 | 데이터 오너십(Ownership)과 스튜어드십 정의. 열 = 조직도상의 모든 조직 단위(본부·팀·부서) | 'C'가 표시된 조직은 해당 데이터 생성·품질에 일차적 책임을 지는 데이터 오너 후보 / ★ 'C'가 여러 조직에 나타나면 오너십 충돌 — 데이터 불일치와 품질 저하의 주된 원인 / 'U'가 다수 조직에 넓게 분포 → 전사 공유 기준 정보(Master Data), 고가용성·성능 특별 고려 |

**오너십 충돌이 발견되면 — 반드시 공식 의사결정 절차를 거친다.** 데이터 거버넌스 협의체를 통해 해당 데이터의 유일한 생성·관리 주체(Single Source of Truth)를 결정해야 한다. 이 과정을 생략하면 데이터는 여러 경로로 중복 생성되고, 어느 값이 맞는지 아무도 답할 수 없는 상태가 된다.

## SECTION 2. 요구사항 도출 프레임워크 — 이상 징후(Anomaly) → 실행 가능한 조치(Action)

> 상관분석의 진정한 가치는 매트릭스 작성이 아니라 해석과 조치에 있다

| # | 점검 내용 (Anomaly) | 분석 결과 | 조치 사항 (Action) |
|---|---|---|---|
| 1 | 정보 항목을 생성(C)하는 프로세스가 없음 | 데이터 생성 로직 누락 | 생성 프로세스 요구사항 도출 / 또는 불필요 시 정보 항목 삭제 |
| 2 | 생성만 되고 활용(R·U)되지 않음 | 불필요 데이터 또는 활용 로직 누락 | 활용 프로세스·리포트 요구사항 도출 / 또는 정보 항목 삭제 |
| 3 | 생성(C) 주체가 둘 이상(프로세스·조직) | 업무 역할 중복 또는 오너십 충돌 | 중복 프로세스 통합·역할 재정의 / 거버넌스 협의를 통한 단일 오너 지정 |
| 4 | 업무 기능·조직이 사용하는 정보 항목이 전혀 없음 | 기능 정의의 오류 또는 데이터 누락 | 업무 기능의 역할·목적 재점검 / 신규 정보 요구사항 도출 |
| 5 | 삭제(D) 프로세스가 없음(영구 보존 제외) | 데이터 생명주기 관리 로직 누락 | 보관 정책 확인 후 삭제 또는 비활성화 프로세스 요구사항 도출 |
| 6 | 기본 프로세스가 조회(R)만 함 | 상태를 변경하는 기본 프로세스가 아닐 수 있음 | 단순 리포트·화면 조회인지, 비즈니스 상태를 바꾸는 단위 프로세스인지 재검토 |
| 7 | 너무 많은 프로세스에서 사용됨(7개 이상) | 책임과 역할이 과대 — 응집도 낮음 | 더 작은 단위로 세분화 검토(예: '계약' → '계약기본' + '계약담보') |

※ 발견된 이상 징후를 기계적으로 조치해서는 안 된다. 비즈니스 특성상 생성 주체가 둘 이상이어야 하는 경우(예: '영업사원 등록'은 인사팀, '파트너사 직원 등록'은 사업개발팀)도 있으므로, 반드시 담당자와 협의하여 비즈니스 맥락 안에서 타당성을 검토받고 진행해야 한다 — 이 경우 통합이 아니라 데이터 정합성을 유지하기 위한 별도 통제 장치를 마련하는 방향으로 조치를 조정한다.

### 사례 연구 — 온라인 서점 주문 관리 시스템

## SECTION 3. 정보 보완 및 공식 확정

### 1. 형상 관리 3원칙 — 변경을 투명하게 관리한다

> 도출된 모든 추가·수정·삭제 사항은 공식 산출물에 체계적으로 반영되어야 한다

| # | 원칙 | 설명 |
|---|---|---|
| 1 | 고유 식별자(ID) 부여 | 모든 요구사항(신규 포함)은 전사 규칙에 따라 고유 ID를 부여받는다(예: DAR-016) → 명확한 식별과 추적의 기본 |
| 2 | 버전 관리 | 요구사항 목록은 변경될 때마다 버전 번호를 부여하여 관리 → 언제, 어떤 내용이 변경되었는지 이력 추적 가능 |
| 3 | 변경 이력 기록 | 각 변경 사항(추가·수정·삭제)을 변경 일자·변경자·변경 사유·승인자와 함께 상세히 기록 → 변경 과정의 투명한 관리 |

→ 이 공식화는 요구사항의 변경 과정을 투명하게 관리하고, 모든 이해관계자가 항상 최신 버전의 요구사항을 공유하도록 보장한다. "나는 그렇게 들은 적 없다"는 분쟁을 원천적으로 차단하는 장치다.

### 2. 사용자 재검토 및 최종 확정 — '통보'가 아니라 '합의와 승인(Sign-off)'의 자리

**재검토 세션(Review Session)의 목적**: 참여 대상(현업 담당자·비즈니스 분석가·시스템 설계자 등 핵심 이해관계자 전원)이 ① 보완된 요구사항이 비즈니스 의도를 정확히 반영했는가 ② 기술적으로 실현 가능한가를 확인 → 최종적인 합의(Consensus)를 도출하고 공식적인 승인(Sign-off)을 받는 과정.

★ 핵심 원칙: 제기된 모든 이슈와 질문이 완전히 해결되고 모든 참석자가 동의하기 전까지는 다음 단계로 진행해서는 안 된다.

| 검토 방식 | 설명 |
|---|---|
| 워크스루 (Walkthrough) | 작성자가 문서를 설명하고 참석자가 질문·의견을 제시하는 비공식적 검토 방식 |
| 인스펙션 (Inspection) | 사회자·기록자·검토자의 역할과 체크리스트에 따라 공식 절차로 오류를 찾는 가장 엄격한 방식 |

**선택 기준**: 프로젝트의 공식도(formality) 수준에 따라 선택 — 중간 산출물은 워크스루, 최종 요구사항 명세서처럼 품질이 결정적인 산출물은 인스펙션.

최종 확정의 의미: 프로젝트 성공을 위한 '공동의 책임'을 함께 확인하는 과정이다.

### 3. 기준선(Baseline)과 변경 통제 — 프로젝트의 '헌법'

> 특정 시점에서 공식적으로 합의되고 동결된 요구사항의 집합

| 구분 | 설명 |
|---|---|
| ① 공식적인 계약 | 비즈니스 요구 부서와 IT 개발 부서 간의 공식 '계약'. "우리는 앞으로 이 명세에 따라 시스템을 만들기로 합의했습니다"라는 선언. 이후 모든 설계·개발·테스트 활동은 이 기준선을 근거로 수행 |
| ② 범위 통제의 기준 | 기준선 설정 이후, 합의되지 않은 신규 요구나 변경은 반드시 공식 변경 통제 프로세스를 거쳐야 한다. 프로젝트 최대의 적인 '범위 만연(Scope Creep)'을 막는 유일하고 효과적인 방법이자, 개발팀을 무분별한 변경으로부터 보호하는 방패이자 전원이 목표를 공유하게 하는 등대 |

**변경 통제 프로세스 (4단계)**

| # | 단계 | 설명 |
|---|---|---|
| 1 | 변경 요청서 제출 | 변경 내용·사유·기대 효과를 공식 문서(CR)로 작성하여 제출 |
| 2 | 영향도 분석 | 다른 요구사항·설계·일정·비용·리소스에 미치는 영향 분석 |
| 3 | CCB 심의 | PM·핵심 이해관계자로 구성된 위원회(변경통제위원회, CCB)가 승인·기각·보류 결정 |
| 4 | 기준선 업데이트 | 승인 시 새 버전의 기준선 설정, 관련 문서·계획 전면 갱신 |

### 4. 총합 — 검증(Verification)과 확인(Validation)은 서로 다른 관문이다

> 두 활동이 상호 보완적으로 작용할 때 비로소 오류가 최소화된다

| 구분 | 검증 (Verification) | 확인 (Validation) |
|---|---|---|
| 핵심 질문 | "우리가 제품을 올바르게(right) 만들고 있는가?" | "우리가 올바른(right) 제품을 만들고 있는가?" |
| 초점 | 산출물 자체가 정해진 표준과 규칙에 따라 잘 만들어졌는지 — 내부적 품질. 명세서의 모든 요구사항이 명확·일관·완전·테스트 가능한가를 인스펙션으로 검토. CRUD 매트릭스로 데이터와 프로세스 간 논리적 모순이 없는지 확인 | 명세된 요구사항이 사용자의 실제 필요와 비즈니스 목표를 충족하는지 최종 사용자 관점에서 확인. 산출물이 외부 세계(사용자의 의도)와 일치하는지 따지는 활동 |
| 대표 활동 | 인스펙션, CRUD 매트릭스 검증 | 프로토타입을 제작해 최종 사용자에게 직접 시연하고 피드백 수렴. 사용자가 직접 조작하며 "이것이 정말 우리가 원했던 기능인가?"를 평가 |

**검증만으로는 결코 발견할 수 없는 것**: "기능은 맞는데, 화면의 입력 항목 순서가 실제 업무 흐름과 정반대라서 매우 불편하다" → 논리적으로 완벽하게 검증된 명세서에서도 이런 피드백은 나온다. 이 피드백으로 명세서를 수정하고, 다시 검증과 확인을 거쳐 최종 기준선을 설정한다.

## 자기 점검 Q&A

**Q1. 결함 수용 비용 곡선에 따르면, 요구사항 분석 단계에서 발견하지 못한 결함이 운영 단계까지 넘어갔을 때 수정 비용은 몇 배가 되는가?**
> A. 약 100~200배. 설계 단계는 3~6배, 코딩 단계는 10배, 테스트 단계는 20~50배로, 단계가 늦어질수록 기하급수적으로 증가한다.

**Q2. RTM과 상관분석의 차이는 무엇인가?**
> A. RTM(요구사항 추적성 매트릭스)은 요구사항-설계-테스트 등 개발 산출물 전반의 연결성을 추적하는 포괄적 도구이고, 상관분석은 데이터(정보 요구)와 비즈니스 컨텍스트(업무·조직) 간의 논리적 정합성 보장에 집중하는 데이터 아키텍처 분야의 특화 도구다.

**Q3. CRUD 매트릭스에서 한 정보 항목에 '조회(R)'만 있고 생성(C)이 없다면 어떤 문제를 의심해야 하는가?**
> A. 생성 규칙(규칙1) 위반이다. 해당 정보 항목이 어떻게 시스템에 등록되는지에 대한 생성 프로세스가 누락된 것이므로, 등록·관리 프로세스에 대한 신규 요구사항을 도출해야 한다.

**Q4. 조직 기능 상관분석에서 한 정보 항목의 '생성(C)'이 두 개 이상의 조직에 나타난다면 무엇을 의미하며 어떻게 해결해야 하는가?**
> A. 데이터 오너십 충돌을 의미하며, 데이터 불일치와 품질 저하의 주된 원인이 된다. 데이터 거버넌스 협의체를 통해 유일한 생성·관리 주체(Single Source of Truth)를 공식적으로 결정해야 한다. 단, 비즈니스 특성상 복수 생성 주체가 타당한 경우도 있으므로 기계적으로 통합하지 말고 담당자와 협의해야 한다.

**Q5. 검증(Verification)과 확인(Validation)의 차이를 한 문장씩 설명하라.**
> A. 검증은 "제품을 올바르게 만들고 있는가"를 묻는 내부적 품질 확인(인스펙션, CRUD 매트릭스)이고, 확인은 "올바른 제품을 만들고 있는가"를 묻는 사용자 관점의 외부적 타당성 확인(프로토타입 시연 등)이다.

**Q6. 요구사항 기준선(Baseline)이 설정된 이후, 새로운 요구사항이 발생하면 어떤 절차를 거쳐야 하는가?**
> A. ① 변경 요청서(CR) 제출 → ② 영향도 분석 → ③ 변경통제위원회(CCB) 심의(승인/기각/보류) → ④ 승인 시 기준선 업데이트의 4단계 변경 통제 프로세스를 거쳐야 한다.

## 한 줄 요약

정보 요구 검증은 **CRUD 매트릭스와 업무·조직 기능 상관분석으로 요구사항의 완전성·일관성·오너십을 논리적으로 검증하고(제1절), 발견된 이상 징후를 실행 가능한 추가·삭제 요구사항으로 전환하며(제2절), 형상관리·사용자 승인(Sign-off)·기준선(Baseline) 설정과 변경 통제(CCB)로 요구사항을 공식 확정하는(제3절)** 과정이다. 검증(Verification, 올바르게 만들었는가)과 확인(Validation, 올바른 것을 만들었는가)이 상호 보완적으로 작동할 때 비로소 프로젝트의 헌법인 기준선이 완성되며, 이는 이후 모든 데이터 모델링 활동의 유일한 근거가 된다.

| 상관분석 (Correlation Analysis) | 정보 요구사항을 프로세스·업무 기능·조직 구조와 2차원 매트릭스로 교차 분석하는 기법 |
| CRUD 매트릭스 | 정보 항목(행)과 기본 프로세스(열)의 교차점에 생성(C)·조회(R)·수정(U)·삭제(D)를 매핑하는 도구 |
| 오너십 충돌 | 하나의 데이터에 대해 둘 이상의 조직이 동시에 생성(C) 권한을 주장하는 상태 — 데이터 거버넌스 협의체를 통해 해결 |
| 이상 징후(Anomaly) → 조치(Action) | CRUD 매트릭스에서 발견된 빈칸·중복 등을 실행 가능한 요구사항 추가/삭제로 전환하는 프레임워크 |
| 형상 관리 (Configuration Management) | 고유 식별자 부여, 버전 관리, 변경 이력 기록의 3원칙으로 요구사항 변경을 투명하게 관리하는 활동 |
| 사인오프 (Sign-off) | 이해관계자 전원이 요구사항 명세에 대해 내리는 공식적·구속력 있는 최종 승인 |
| 기준선 (Baseline) | 특정 시점에서 공식적으로 합의되고 동결된 요구사항의 집합 — '프로젝트의 헌법' |
| 변경통제위원회 (CCB) | PM과 핵심 이해관계자로 구성되어 기준선 설정 이후의 변경 요청을 승인·기각·보류하는 심의 기구 |
| 범위 만연 (Scope Creep) | 공식 통제 없이 요구사항이 점점 늘어나 프로젝트 범위가 통제 불능으로 확장되는 현상 |
| 검증 (Verification) | "제품을 올바르게 만들고 있는가" — 명세서 자체의 논리적 정확성을 확인하는 내부적 품질 검토 |
| 확인 (Validation) | "올바른 제품을 만들고 있는가" — 사용자의 실제 의도 충족 여부를 확인하는 외부적 타당성 검토 |
