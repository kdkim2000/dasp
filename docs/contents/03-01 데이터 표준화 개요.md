# 03-01 데이터 표준화 개요

## 도입부 — 왜 데이터 표준화인가

데이터 표준화는 이름을 예쁘게 짓는 기술이 아니라, 조직 전체의 데이터 자산 가치를 지켜내는 경영 전략이다. 이 관점을 유지하며 이번 챕터를 학습한다.

### LECTURE ROADMAP — 강의 흐름과 학습 목표

| # | 블록 | 핵심 내용 |
|---|---|---|
| 1 | 표준화의 필요성 | 정보의 홍수 속 정보 빈곤, 비표준화 4대 문제점, 근본 원인 3가지 |
| 2 | 데이터 표준의 개념 | 표준화의 정의, 명칭·정의·형식·규칙, 명칭 3원칙 |
| 3 | 표준화 프로그램 | 단어·용어·도메인·코드, DA와 DBA의 역할, 표준화 4단계 절차 |
| 4 | 표준 관리 도구 | 도구의 3대 기능군, 메타데이터 관리 시스템, 도입 시 고려사항 |

**학습 목표**
- 표준화되지 않은 데이터가 기술·의사결정·비즈니스 성과로 이어지는 연쇄 효과를 설명할 수 있다.
- 데이터 표준의 4대 핵심 구성요소(명칭·정의·형식·규칙)와 데이터 명칭의 3원칙을 구분하여 적용할 수 있다.
- 표준 체계(단어·용어·도메인·코드), 관리 조직(DA·DBA), 표준화 절차의 관계를 도식으로 설명할 수 있다.
- 데이터 표준 관리 도구의 핵심 기능과 도입 시 평가 기준을 제시할 수 있다.

※ 4대 구성요소는 시험 출제 빈도가 가장 높은 부분이므로 특히 잘 기억해 둘 것.

## SECTION 1. 데이터 표준화의 필요성

### 1. 정보의 홍수 속, 정보의 빈곤

> 데이터의 양적 팽창이 곧 비즈니스 가치는 아니다 — 표준 없는 데이터는 자산이 아니라 부채다

"데이터는 폭발적으로 늘어나지만, 그 데이터가 서로 다른 이름과 형식으로 제각각 저장되고 관리된다면 이는 자산이 아닌 부채가 될 수 있다."

| 단계 | 설명 |
|---|---|
| 양적 팽창 | 빅데이터·IoT·클라우드로 전례 없는 축적 |
| 질적 저하 | 신뢰할 데이터를 적시에 확보하지 못함 |
| 경쟁력 약화 | 분석 역량 저하와 잘못된 의사결정 |

데이터 표준화는 방대하고 혼란스러운 데이터를 통찰력 있는 정보 자산으로 전환하는 첫걸음이며, 데이터 아키텍처 구축과 데이터 거버넌스 확립의 가장 기초적이면서 필수적인 **선결 과제**다. (시험에 자주 나오는 표현이므로 기억할 것)

### 2. 데이터 비표준화의 4대 문제점

> 각 문제는 독립적이지 않고 서로를 증폭시키며 IT 운영 전반의 비용을 끌어올린다

| # | 문제 | 설명 |
|---|---|---|
| ① | 중복 및 불일치 | 동일 의미 데이터가 '고객번호'(숫자)와 '회원ID'(문자)로 중복 저장되는 등. 주소 변경이 한쪽에만 반영되면 청구서는 신주소, 배송은 구주소로 나가는 사고 발생 |
| ② | 의미 파악 지연 | '신규 고객'이 가입 기준인지 첫 구매 기준인지 매번 확인 필요 → 의미를 찾는 동안 경쟁사는 실시간 분석 → 골든타임 상실 |
| ③ | 데이터 통합의 어려움 | 시스템 A는 성별을 '1/2'로, 시스템 B는 'M/F'로 관리 → 코드 변환 규칙 필요, 데이터웨어하우스·BI 구축 시 ETL 비용이 기하급수적으로 증가 |
| ④ | 변경·유지보수 곤란 | 기존 데이터 의미·구조 파악에 개발 시간의 상당 부분 소모, 작은 변경의 영향 범위를 예측할 수 없어 경직된 IT 시스템화 |

**기술적 현상 → 비즈니스 영향으로 전이되는 경로**
- 중복·불일치 → 부서 간 책임 공방, 고객 불만 증가, 재고·물류 오류로 인한 비용 손실
- 의미 파악 지연 → 시장 대응 지연, 경쟁사에 뒤처지는 전략, 신규 비즈니스 기회 상실
- 통합 어려움 → 전사 인사이트 도출 실패, 데이터 사일로 심화 / 유지보수 복잡성 → IT 비용의 지속 증가

### 3. 문제의 근본 원인 진단

> 기술적 결함이 아니라 조직의 구조적·문화적·역사적 요인에 뿌리를 두고 있다

| # | 원인 | 설명 |
|---|---|---|
| ① | 분절된 시스템 개발 | 전사 통합 아키텍처·장기 데이터 전략 없이 부서별 시급한 요구 중심으로 동시다발 개발 — '사일로(Silo)' 환경에서 각 시스템이 자신만의 비표준을 보유 |
| ② | 관리 마인드·거버넌스 부재 | 데이터를 애플리케이션의 부속물로 취급, 품질·표준의 책임 주체가 불분명, 소유권·품질 기준·준수 절차가 없으면 표준화는 일회성 구호로 끝남 |
| ③ | 전문 인력·도구의 부재 | DA(데이터 관리자)가 없거나 실질적 권한과 책임이 부족, 엑셀 수작업 관리 → 이력 추적·자동 검증·전사 공유가 사실상 불가능 |

**진단의 함의**: 처방은 조직과 도구에 있다 — 원인이 기술이 아니라 조직에 있으므로, 명명 규칙만 새로 만들어서는 같은 문제가 재발한다. 따라서 처방은 ① 전사 데이터 거버넌스 체계 ② 전담 조직(DA) ③ 자동화된 표준 관리 도구의 3종 세트여야 한다.

### 4. 데이터 표준화의 전략적 가치

> 문제를 없애는 수동적 활동이 아니라, 데이터 자산 가치를 극대화하는 적극적 투자 활동

| # | 효과 | 설명 |
|---|---|---|
| ① | 명확한 의사소통 증대 | 모든 구성원이 동일한 명칭·의미를 사용 — '고객 등급'이 전 부서에서 같은 기준 → 오해·커뮤니케이션 비용 감소 |
| ② | 품질 및 신뢰도 향상 | 형식(YYYY-MM-DD)·규칙(M/F) 통일로 입력 단계에서 오류를 원천 차단 → 데이터 클렌징 비용·시간 절감 |
| ③ | 활용성·접근성 증대 | 필요한 데이터 탐색 시간 획기적 단축, 데이터 카탈로그·표준 용어 사전 활용 → '데이터 민주화' 촉진 |
| ④ | IT 비용 절감 | 인터페이스·통합 시 변환 과정 최소화, 영향 분석 단순화로 유지보수 용이 → 장기적 IT 총소유비용(TCO) 절감 |

**심층 분석 — 비표준화가 비즈니스 실패로 이어지는 3단계 연쇄 효과**
- 1차(기술·운영): 불일치·의미 파악 지연 → 통합 난이도 상승, 유지보수 곤란 → 시스템 불안정, IT 비용 증가
- 2차(분석·의사결정): 분석가는 정제에 시간 소모, 경영진은 왜곡된 보고서 수령 → 잘못된 전략적 판단
- 3차(비즈니스 성과): 고객 경험 저하·캠페인 실패·재고 관리 오류 → 매출 감소, 고객 이탈, 브랜드 손상

→ 데이터 표준화는 IT 부서만의 문제가 아니라 전사적 위험을 관리하는 경영 과제다.

## SECTION 2. 데이터 표준의 개념

### 1. 데이터 표준화란 무엇인가

> 기술적 규칙 제정을 넘어, 조직 구성원 모두가 공유하는 '공통의 언어'를 만드는 과정

**정의**: "조직 내 여러 정보 시스템에 산재해 있는 데이터 정보 요소에 대하여 명칭·정의·형식·규칙에 대한 공통의 원칙을 수립하고, 이를 전사적으로 일관되게 적용하는 모든 활동"

이 정의는 세 덩어리로 나누어 기억하면 좋다: ① 명칭·정의·형식·규칙 ② 공통의 원칙 ③ 전사적 일관 적용

| 목표 | 설명 |
|---|---|
| 의미 통일 | 누구나 데이터 의미를 동일하게 파악 |
| 시각 조정 | 부서 간·개인 간 상반된 시각 조율 |
| 공유·재사용 | 데이터 공유와 재사용성 극대화 |

**표준화 프로그램의 3대 구성요소** (이후 전개 순서)
1. 데이터 표준 체계: 표준 단어 → 표준 용어 → 표준 도메인 → 표준 코드의 계층 구조
2. 데이터 관리 조직: 전사·전략 관점의 DA와 기술·운영 관점의 DBA로 역할 분리
3. 데이터 표준화 절차: 요구사항 수집 → 표준 정의 → 표준 확정 → 표준 관리의 생명주기

### 2. 데이터 표준의 4대 핵심 구성요소

> 하나의 데이터 항목을 완전하게 설명하는 최소한의 집합 — 시험에서 가장 중요하게 다뤄지는 개념

| # | 구성요소 | 설명 |
|---|---|---|
| ① | 데이터 명칭 | 조직 내에서 유일하게 식별·지칭하는 이름. 유일성·업무적 보편성·의미 전달의 충분성 3원칙 준수 |
| ② | 데이터 정의 | 그 명칭이 의미하는 비즈니스상의 범위·자격 요건·생성 규칙을 서술. 제3자 관점으로 서술하고, 코드값이 있다면 예시도 함께 기술 |
| ③ | 데이터 형식 | 시스템 내에서 표현·저장되는 물리적 형태 — 데이터 타입, 길이·소수점 자릿수. 상품 설명처럼 길이 예측이 어려운 항목은 향후 증가를 고려해 여유 있게 설정하고, CLOB·BLOB처럼 특정 DBMS 전용 특수 타입은 이관·통합 시 호환성 문제를 일으킬 수 있어 신중히 적용 |
| ④ | 데이터 규칙 | 값에 대한 업무적 제약으로 정합성·완전성을 보장. 기본값(Default, 미입력 시 자동 부여값) · 허용값(Permissible, 가질 수 있는 값의 목록) · 허용범위(Range, 상한·하한) 3유형 |

**잘못된 예 / 올바른 예 비교**

| 구성요소 | 잘못된 예 | 올바른 예 |
|---|---|---|
| 명칭 | 일자, 금액, 번호 (지나치게 포괄적) | 주문 접수 일자, 월 납입 보험료 금액, 송장 상세 일련번호 |
| 정의 | "고객번호는 고객의 번호를 의미한다" | "01: 주문접수, 02: 결제완료, 03: 상품준비중"처럼 코드값과 의미를 함께 기술 |
| 규칙 | 허용값 미정의로 임의 값 입력 허용 | 성별코드는 '남'/'여'만 허용 / 평가점수는 1~10 범위로 제한 |

### 3. 데이터 명칭의 3대 원칙

> 명칭이 무너지면 정의·형식·규칙이 아무리 정교해도 데이터는 통합되지 않는다

| # | 원칙 | 설명 |
|---|---|---|
| ① | 유일성 (Uniqueness) | 하나의 개념은 반드시 하나의 이름만 가져야 함. 이음동의어(같은 개념, 다른 이름 — 예: 고객 계좌번호/고객 구좌번호)와 동음이의어(같은 이름, 다른 의미) 모두 철저히 배제 |
| ② | 업무적 보편성 | 개발자 중심의 기술 약어보다 현업이 일상에서 쓰는 용어를 채택 — 직관적 이해를 돕고 현업의 표준화 참여를 유도 |
| ③ | 의미 전달의 충분성 | 명칭만으로 데이터의 의미와 범위가 전달되어야 함 — '금액', '번호' 같은 지나치게 포괄적인 이름 대신 수식어를 충분히 붙여 모호성 제거 |

**실무 팁**: 명칭 후보가 둘 이상 경합할 때는 사용 빈도와 업무적 보편성을 기준으로 하나를 선정하고, 나머지는 금칙어(비표준어)로 등록해 재발을 막는다.

### 4. 데이터 표준 체계 — 단어·용어·도메인·코드

> 가장 작은 '단어'에서 시작해 '명칭'을 만들고, '형식'과 '규칙'을 부여하는 계층적 과정

| STEP | 구성요소 | 설명 |
|---|---|---|
| 1 | 표준 단어 | 명칭을 구성하는 최소 의미 단위. 한글명·영문명·영문 약어를 정의(예: 고객→CUST, 번호→NO) |
| 2 | 표준 용어 | 표준 단어의 조합으로 만든 실제 항목명 — 엔티티명·속성명(예: 고객번호 → CUST_NO). 반드시 승인된 표준 단어로만 조합해야 중복 생성을 막을 수 있음 |
| 3 | 표준 도메인 | 여러 항목이 공통으로 갖는 형식·규칙을 묶은 템플릿(예: 일자 도메인 = DATE 형식 → 주문·입사·배송일자에 일괄 적용) |
| 4 | 표준 코드 | 도메인에 속하는 허용값의 사전 정의(예: 직급코드 SA=사원, DR=대리, GW=과장) |

**구성요소 간의 유기적 관계**: '주문' + '금액' → 표준 용어 '주문금액' 생성(단어가 명칭을 만든다) → 데이터 정의가 의미를 부여 → '금액 도메인'으로 형식(NUMBER(18,2) 등)을 강제 → 표준 코드가 규칙을 완성. 즉 표준 체계의 4단계가 표준의 4대 구성요소(명칭·정의·형식·규칙)를 구현하는 수단이라는 대응 관계를 기억해 둔다.

### 5. 데이터 관리 조직 — DA와 DBA의 역할 구분

> 거버넌스 체계에서 가장 혼동하기 쉬운 두 역할의 R&R 정립

| 구분 | 데이터 관리자 (DA) | 데이터베이스 관리자 (DBA) |
|---|---|---|
| 관점 | 전사적·전략적·비즈니스 중심 | 기술적·운영적·시스템 중심 |
| 주요 관리 대상 | 데이터 모델, 데이터 표준, 메타데이터 | 물리적 데이터베이스, DBMS 인스턴스 |
| 주요 업무 | 요구사항 분석, 표준·정책 수립, 데이터 모델링, 품질 관리 | DB 설계·구축, 성능 튜닝, 백업·복구, 보안 관리 |
| 핵심 역량 | 업무 지식, 데이터 모델링 전문성, 커뮤니케이션 능력 | 특정 DBMS에 대한 깊은 기술 지식, 시스템 관리 능력 |
| 관심사 | 데이터의 의미·일관성·정합성 (What) | 데이터의 저장·성능·가용성 (How) |

**한 문장 정리**: DA는 '데이터가 무엇을 의미하는가(What)'를, DBA는 '데이터를 어떻게 저장·운영하는가(How)'를 책임진다. (성능 튜닝·백업복구를 DA의 업무로 제시하는 것은 시험의 단골 오답이므로 주의)

### 6. 데이터 표준화 절차 — 4단계 생명주기

> 일회성 프로젝트가 아니라 데이터 환경 변화에 따라 지속 수행되는 순환 활동

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 요구사항 수집 | 현업·개발자 인터뷰, 기존 시스템 분석, 표준화 대상 식별 |
| 2 | 데이터 표준 정의 | 표준화 원칙 수립, 단어·용어·도메인·코드 정의, 명명 규칙 적용 |
| 3 | 데이터 표준 확정 | 이해관계자 검토와 합의, 최종 표준 확정, 전사 공표 |
| 4 | 데이터 표준 관리 | 신규 개발·유지보수에 이행, 준수 여부 점검, 변경 요구사항 관리 |

(수집→정의→확정→관리, 동사 4개로 암기. 순서를 묻는 배열형 문제가 자주 출제된다.)

**절차 운영 시 유의사항**
- 정의 단계에서 원칙 없이 개별 항목부터 만들면, 확정 단계에서 부서 간 이견을 조정할 근거가 사라진다.
- 확정은 '공표'로 끝나지 않는다. 관리 단계에서 준수 점검과 변경 관리가 이어져야 표준이 살아있는 자산이 된다.
- 4단계는 순차가 아니라 순환이다. 관리 단계에서 수집된 변경 요구가 다시 1단계 요구사항으로 환류된다.

## SECTION 3. 데이터 표준 관리 도구

### 1. 표준 관리 도구의 3대 기능군

> 전사 표준 항목은 수천~수만 개 — 스프레드시트 수작업으로는 관리 자체가 불가능하다

| # | 기능 | 설명 |
|---|---|---|
| ① | 데이터 표준 관리 | 표준 사전 관리(단어·용어·도메인·코드의 등록·조회·수정·삭제), 이음동의어·동음이의어·금칙어 정의로 명칭 유일성 확보, 과도기에는 여러 표준을 병행 관리(멀티 표준 관리)하며 점진적으로 통합 |
| ② | 데이터 구조 관리 | 모델링 도구(ERwin·ER-Studio 등) 산출물 또는 DBMS 카탈로그 Import, 명명 규칙·타입·길이 자동 검사 및 리포트, 모델 버전 간 차이를 시각적으로 비교 |
| ③ | 프로세스 관리 (거버넌스) | 표준 신청/승인 워크플로우(전자 결재 형태), 표준 변경 시 영향받는 모델·테이블·컬럼·프로그램까지 식별하는 변경 영향도 분석 |

**확장된 관점 — 메타데이터 관리 시스템(MMS)과의 관계**: 최근 도구는 독립 시스템을 넘어 메타데이터 관리 시스템·데이터 카탈로그의 핵심 구성요소로 진화하고 있으며, 표준 정보뿐 아니라 데이터 구조, 데이터 계보(Lineage), 소유자·품질 규칙, 접근 애플리케이션까지 포괄한다.

### 2. 도구의 역할 — '경찰'이 아닌 '내비게이션'

> 표준을 지키는 것이 지키지 않는 것보다 쉬울 때, 비로소 표준은 문화로 정착한다

| 모델 | 설명 |
|---|---|
| 경찰(Police) 모델 | 표준 위반을 감시하고 적발하는 데 초점 — 사용자에게 '번거로운 규제'로 인식되어 도구 사용에 대한 저항감 증가 → 시스템 활용도 저하, 표준 형해화 |
| 내비게이션(Navigation) 모델 | 올바른 표준을 더 쉽고 빠르게 찾아 쓰도록 안내 — 모델링 도구 플러그인이 '고객 성명/CUST_NM'을 즉시 추천, 검색·승인 대기 없이 표준 준수가 곧 업무 효율 → 자발적 준수, 표준의 문화적 정착 |

**도입 시 고려사항 3가지**
- 확장성: 이기종 DBMS·모델링 도구·BI 도구의 메타데이터를 폭넓게 수집·연동할 수 있는가
- 유연성: 복수 표준 관리 지원, 고유한 명명 규칙·승인 프로세스의 커스터마이징이 가능한가
- 편의성: 한글명→영문명 자동 변환, 준수 검사 예약 실행 등 직관적 UI를 제공하는가

Tip. 도구 평가 시 '얼마나 정교하게 통제하는가'보다 '얼마나 업무를 편리하게 만드는가'를 최우선 기준으로 삼을 것.

## 자기 점검 Q&A

**Q1. 데이터 표준화가 "선결 과제"로 불리는 이유는 무엇인가?**
> A. 데이터 표준화는 혼란스러운 데이터를 통찰력 있는 정보 자산으로 전환하는 첫걸음이며, 데이터 아키텍처 구축과 데이터 거버넌스 확립의 가장 기초적이면서 필수적인 전제 조건이기 때문이다.

**Q2. 비표준화의 4대 문제점을 각각 한 문장으로 설명하라.**
> A. ① 중복 및 불일치: 같은 의미의 데이터가 여러 이름·형식으로 중복 저장되어 갱신 시 불일치 발생 ② 의미 파악 지연: 용어의 정확한 의미를 확인하느라 분석·의사결정이 늦어짐 ③ 데이터 통합의 어려움: 시스템마다 다른 코드 체계로 인해 통합 시 변환 비용이 급증 ④ 변경·유지보수 곤란: 데이터 구조 파악에 시간이 소모되어 변경 영향 범위를 예측하기 어려움.

**Q3. 데이터 표준의 4대 구성요소와 각각의 핵심 내용을 말하라.**
> A. 명칭(유일하게 식별하는 이름), 정의(비즈니스상의 범위와 생성 규칙 서술), 형식(데이터 타입·길이 등 물리적 형태), 규칙(기본값·허용값·허용범위 등 업무적 제약).

**Q4. 데이터 명칭의 3원칙과 그 위반 사례(이음동의어/동음이의어)를 설명하라.**
> A. 유일성(하나의 개념에는 하나의 이름만 — 위반 시 이음동의어), 업무적 보편성(현업 용어 채택), 의미 전달의 충분성(수식어로 모호함 제거). 이음동의어는 같은 개념에 다른 이름이 붙는 것(예: 고객 계좌번호/고객 구좌번호), 동음이의어는 같은 이름에 다른 의미가 담기는 것이다.

**Q5. 표준 체계의 4단계(단어→용어→도메인→코드)와 표준의 4대 구성요소는 어떻게 대응되는가?**
> A. 표준 단어가 조합되어 표준 용어(명칭)를 만들고, 데이터 정의가 그 용어에 의미를 부여하며, 표준 도메인이 형식을 강제하고, 표준 코드가 규칙을 완성한다. 즉 표준 체계는 표준의 4대 구성요소를 구현하는 수단이다.

**Q6. DA와 DBA의 역할 차이를 한 문장으로 요약하라.**
> A. DA는 데이터가 무엇을 의미하는가(What)를, DBA는 데이터를 어떻게 저장·운영하는가(How)를 책임진다.

**Q7. 데이터 표준 관리 도구를 '경찰' 모델이 아닌 '내비게이션' 모델로 설계해야 하는 이유는?**
> A. 경찰 모델은 위반을 감시·적발하는 데 초점을 두어 사용자에게 규제로 인식되고 저항감을 키워 시스템 활용도를 떨어뜨리지만, 내비게이션 모델은 올바른 표준을 쉽고 빠르게 찾아 쓰도록 안내하여 표준 준수가 곧 업무 효율이 되도록 하므로 자발적 준수와 표준의 문화적 정착을 이끌어낸다.

## 한 줄 요약

데이터 표준화는 **비표준화가 낳는 4대 문제(중복·의미지연·통합난·유지보수곤란)와 그 조직적 근본 원인을 진단하는 데서 출발해, 명칭·정의·형식·규칙이라는 4대 구성요소와 명칭 3원칙을 토대로 단어→용어→도메인→코드의 표준 체계를 세우고, DA(전사·전략)와 DBA(기술·운영)의 역할을 분리한 조직 아래, 수집→정의→확정→관리의 4단계 절차를 순환적으로 운영하며, '경찰'이 아닌 '내비게이션' 역할을 하는 관리 도구로 정착시키는** 경영 전략이다.
