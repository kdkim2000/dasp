## SECTION 1. 데이터 표준화 원칙

### 1. 데이터 혼돈에서 비즈니스 명확성으로

> 비표준화의 진정한 비용은 낭비된 IT 자원이 아니라 '비즈니스 민첩성의 상실'이다

| # | 문제 | 설명 |
|---|---|---|
| ① | 중복 및 불일치 | '고객번호' vs '회원ID', 같은 '판매금액'이 한쪽은 부가세 포함, 다른 쪽은 미포함 |
| ② | 의미 파악 지연 | 보고서·분석마다 담당자 문의 반복 — 정보 제공의 적시성 저하 |
| ③ | 통합 비용 증가 | DW·빅데이터 플랫폼 구축 시 변환·정제에 공수 집중 — 기간 지연과 비용 폭증 |
| ④ | 유지보수 복잡성 | 기존 데이터 활용 가능 여부 판단 곤란 → 불필요한 중복 생성 → 복잡성 가중 |

**사례 — 고객 맞춤형 마케팅 캠페인이 실패하는 이유**: 영업 시스템의 '고객', 마케팅 시스템의 '잠재고객', 서비스 시스템의 '사용자'가 표준화되어 있지 않으면 단일 고객 뷰(Single Customer View) 구성부터 난관에 부딪히고, 캠페인은 부정확한 데이터로 실행된다. → 결론: 표준화의 ROI는 IT 비용 절감이 아니라 캠페인 전환율 증가·고객 이탈 감소로 측정되어야 한다.

### 2. 데이터 표준의 3대 핵심 원칙

> 모든 데이터 명칭과 정의에 예외 없이 일관되게 적용되어야 하는 판단 기준

| # | 원칙 | 설명 |
|---|---|---|
| ① | 유일성 (Uniqueness) | 하나의 개념 = 하나의 표준 명칭. '고객 계좌번호'와 '고객 구좌번호'가 혼용되면 합의를 통해 하나만 표준으로 지정 — 의미적 모호성 제거의 출발점 |
| ② | 업무적 보편성 | 현업 사용자가 직관적으로 이해할 수 있을 것 — 기술 약어·시스템 중심 용어보다 업무 영역의 보편적 용어를 채택해 데이터와 비즈니스의 간극을 축소 |
| ③ | 의미 전달의 충분성 | 명칭만으로 의미와 범위가 파악될 것 — '금액'은 세전·세후·할인 후로 해석이 갈릴 수 있으므로 '주문세후할인후금액'처럼 수식어로 구체화 |

| 원칙 | 위반 사례 | 적용 결과 |
|---|---|---|
| 유일성 | 고객 계좌번호 / 고객 구좌번호 혼용 | '고객 계좌번호' 단일 표준, 나머지는 금칙어 등록 |
| 의미 전달의 충분성 | '금액' — 세전인지 세후인지 불명확 | '주문세후할인후금액'으로 해석 여지 제거 |

### 3. 데이터 표준화 정책 문서화 6요소

> 정책은 표준화 활동의 방향을 제시하고 이해관계자의 참여와 준수를 이끌어내는 최상위 지침

| # | 요소 | 설명 |
|---|---|---|
| ① | 목적 및 목표 | 달성할 비즈니스 목표를 수치로 명시(예: 통합 효율성 30% 향상) |
| ② | 적용 범위 | 대상 시스템·데이터·조직 정의 — '신규 개발 + 핵심 마스터 데이터'부터 단계적 확대 |
| ③ | 데이터 표준의 정의 | 관리할 표준의 종류와 정의 명시 — 단어·용어·도메인·코드 |
| ④ | 표준화 원칙 | 유일성·보편성·충분성 + 조직 특성에 맞는 명명 규칙·정의 규칙·형식 규칙 |
| ⑤ | 조직 및 R&R | 데이터 관리자·데이터 스튜어드, 표준화 협의체 구성과 책임 정의 |
| ⑥ | 프로세스 | 신청 → 심의 → 확정 → 변경 → 폐기의 전체 관리 프로세스 정의 |

**Tip — 정책 수립은 '기술'이 아니라 '협상'과 '변화 관리'의 장이다**: 영업 부서가 수십 년 써온 'Client'를 전사 표준 'Customer'로 바꾸는 일은 그 부서의 업무 관행과 정체성에 대한 도전으로 받아들여질 수 있다. 따라서 최고경영진의 후원을 받는 공식 정책이 저항을 극복할 권한을 부여하며, 정책 수립 과정 자체가 합의를 도출하는 변화 관리 활동이자 프로젝트 성공을 담보하는 정치적 자산이 된다.

## SECTION 2. 데이터 표준 구성요소 정의

### 1. 표준을 구성하는 4대 빌딩 블록

> 의미의 최소 단위인 '단어'에서 시작해 '용어'를 구성하고, '도메인'과 '코드'로 구체화되는 계층 구조

| STEP | 구성요소 | 설명 | 산출물 |
|---|---|---|---|
| 1 | 표준 단어 | 의미의 원자 단위, 통제된 어휘 집합 구축 | 표준 단어 사전 |
| 2 | 표준 용어 | 비즈니스 어휘의 구성 — 엔티티명·속성명 | 표준 용어 사전 |
| 3 | 표준 도메인 | 구조적 무결성 강제 — 타입·길이·형식 템플릿 | 표준 도메인 사전 |
| 4 | 표준 코드 | 허용 값 관리 — 유한 집합으로 값 제한 | 표준 코드북 |

**계층 구조를 관통하는 원칙**: 모든 표준 용어는 반드시 사전에 승인된 표준 단어들로만 구성되어야 한다 — 예외를 허용하는 순간 사전 체계는 무너진다. 표준 단어가 '어휘의 재료'라면, 표준 용어는 그 재료를 명명 규칙(문법)에 맞게 조합한 '의미 있는 문장'이다. 도메인은 용어에 기술적 속성을, 코드는 도메인에 허용 값을 부여한다 — 아래로 갈수록 구체화된다.

### 2. 표준 단어 정의 프로세스

> 조직 내 모든 단어에 유일한 한글명·영문 전체명·영문 약어명을 부여하는 통제된 어휘 구축

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 현행 용어 수집 | 데이터 모델·테이블 정의서 분석, 한글명·영문명 전수 수집 |
| 2 | 단어 분할 | 최소 의미 단위로 분할(고객주문일자 → 고객·주문·일자, CUST_ORD_DT → CUST·ORD·DT) |
| 3 | 정제 및 표준화 | 이음동의어 통합, 동음이의어 분리, 영문 전체명·약어 표준화 |
| 4 | 사전 등록 | 한글명·영문명·약어 등록, 상세 의미 기술, 공식 표준 단어 사전 확정 |

- 이음동의어 통합: '고객'과 '손님', '계좌'와 '구좌' → 빈도·보편성 기준으로 '고객', '계좌' 선정, 나머지는 금칙어
- 동음이의어 분리: '주소'가 거주지와 IP를 함께 가리키면 '거주지주소', 'IP주소'로 분리해 별도 표준어로 정의
- 영문명 표준화: 고객 → Customer → CUST / 번호 → Number → NO처럼 전체명과 약어를 함께 통일

**사례 연구 — '고객번호' 관련 단어 표준화**

| 단계 | 수행 내용 | 결과 |
|---|---|---|
| ① 수집 | 고객번호(CUST_NO), 고객ID(CUST_ID), 손님번호(CLIENT_NO) | 현행 용어 3건 확보 |
| ② 분할 | '고객'·'손님'·'번호'·'ID' / 'CUST'·'CLIENT'·'NO'·'ID' | 단어·약어 후보 도출 |
| ③ 정제 | '고객'과 '손님'은 이음동의어 → '고객' 선정, 약어 'CUST' 통일 / '번호'와 'ID'도 이음동의어 → '번호' 선정, 약어 'NO' 통일 | 표준어 2건 확정 |
| ④ 등록 | 표준 단어 '고객'(CUST), 표준 단어 '번호'(NO)를 사전에 공식 등록 | 표준 단어 사전 반영 |

→ 사전 구축의 진짜 효과는 수동 검토에서 자동화된 시스템 통제로 이어진다는 데 있다. 모델러가 '고객주문번호'를 입력하면 시스템이 CUST·ORD·NO를 조합해 CUST_ORD_NO를 자동 생성한다 — 개발자의 자의적 명명을 원천 차단하고, 모든 데이터 자산이 생성 순간부터 비즈니스 어휘와 정렬되도록 보장한다.

### 3. 표준 용어 정의 프로세스

> 표준 단어를 명명 규칙에 맞게 조합해 엔티티·속성 수준의 비즈니스 개념을 표현한다

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 현행 용어 수집 | 기존 시스템의 엔티티명·속성명 전수 수집 |
| 2 | 표준 용어 정의 | 표준 단어 매핑, 명명 규칙 적용, 영문명 자동 생성 |
| 3 | 용어 정의서 작성 | 명확한 비즈니스 정의 기술, 적용 규칙과 허용 값 서술 |
| 4 | 용어 사전 등록 | 한글명·영문명·상세 정의, 관련 표준 도메인 연결 |

- 일반적 속성 명명 규칙: 수식어 + 객체 + 분류어 구조(예: '고객주문번호' → '고객' + '주문' + '번호'로 매핑, 약어 조합 CUST+ORDR+NO → CUST_ORDR_NO)
- 표준 용어가 갖는 힘: 동일 개념의 용어가 중복 생성되는 것을 방지하고, 잘 정의된 용어 하나가 그 자체로 하나의 명확한 비즈니스 규칙을 담아 시스템 간 불일치와 보고서 해석 오류를 원천 차단한다.

**사례 연구 — '주문금액'에서 '주문총금액'으로**

> 표준 정의는 이름표를 붙이는 일이 아니라, 암묵적 비즈니스 규칙을 발굴해 공식화하는 분석 활동

| # | 단계 | 내용 |
|---|---|---|
| ① | 개념 명확화 | DA가 영업·재무·물류 담당자를 인터뷰 — 부가세 포함? 배송비 포함? 할인 적용 전인가 후인가? |
| ② | 비즈니스 규칙 합의 | "모든 할인이 적용된 후, 부가세와 배송비를 모두 포함한 고객의 최종 결제 금액"으로 전사 합의 |
| ③ | 표준 용어 생성 | '주문최종결제금액', '주문총금액' 후보 검토 — 최종적으로 '주문총금액' 확정 |
| ④ | 단어 조합 및 등록 | '주문'+'총'+'금액' 조합, 영문명 ORD_TOT_AMT, 정의서 작성 후 사전 등록 |

Tip — 표준 정의의 과정을 '비즈니스 규칙 발견의 기회'로 삼을 것: '주문금액'을 표준화하는 과정은 이름을 정하는 일이 아니라, 영업·재무·물류가 각기 다르게 생각하던 규칙을 하나로 합의하는 과정이다. 잘 정의된 표준 용어 하나가 수십 페이지의 업무 프로세스 정의서보다 더 명확한 비즈니스 규칙이 될 수 있다.

### 4. 표준 도메인 — 구조적 무결성 강제

> 속성의 데이터 타입·길이·형식을 정의한 '템플릿' — 유사한 속성을 묶어 기술적 일관성을 강제한다

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 현행 컬럼 분석 | 타입·길이·제약 조건 수집 |
| 2 | 도메인 그룹화 | 비즈니스 의미·성격별로 분류 — 고객명·직원명·상품명 → '명칭' |
| 3 | 표준 도메인 정의 | 대표 타입과 길이 확정, 호환성·확장성 고려해 여유 설정 |
| 4 | 도메인 사전 등록 | 이름·타입·길이·허용값·형식 규칙 |

| 표준 도메인 | 정의 | 적용 대상 예시 |
|---|---|---|
| 명칭 도메인 | VARCHAR2(200) | 고객명·직원명·상품명·부서명 등 이름 성격의 모든 속성 |
| 금액_KRW 도메인 | NUMBER(18, 2) | 주문금액·결제금액·할인금액·제품단가 등 금액 성격의 속성 |
| 일자 도메인 | DATE 또는 CHAR(8) | 주문일자·입사일자·배송일자(YYYYMMDD 형식으로 통일) |

**표준 도메인의 가치 — 아키텍처 민첩성**: 원화 금액 컬럼 500개의 소수점 자릿수를 2자리에서 4자리로 바꿔야 한다면? 도메인이 없으면 DBA·개발자가 500개 컬럼을 일일이 탐색해 각각 스크립트를 작성·실행해야 하며(며칠이 걸리는 위험한 작업), 도메인이 있으면 DA가 중앙 도메인 사전에서 '금액_KRW'의 정의를 단 한 번만 수정하면 상속받는 500개 컬럼 전체에 자동·일관 전파된다(단 몇 분 만에 안전하게 완료). → 표준 도메인의 진정한 가치는 타입 통일이 아니라 데이터 아키텍처에 추상화(abstraction) 계층을 제공하는 데 있으며, 이 추상화가 유지보수성과 확장성을 극적으로 높이고 급변하는 비즈니스 환경에 대응할 민첩성(agility)을 확보해 준다.

### 5. 표준 코드 — 허용 값 관리

> 도메인의 특별한 형태로, 입력 가능한 값이 미리 정해진 유한 집합으로 제한되는 경우

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 코드성 데이터 수집 | 성별·직급·주문상태·지역구분 등, 소스에 하드코딩된 값까지 발굴 |
| 2 | 통합 및 표준화 | 표현 방식 통일('1','M','남'→'M'), 확장 고려한 코드 값 체계 수립, 행정표준코드·ISO 코드 재사용 |
| 3 | 코드 오너십 정의 | 직급코드 오너=인사팀, 상품분류코드 오너=상품기획팀 — 현행성·정확성 유지의 핵심 |
| 4 | 코드 사전 등록 | 분류명·코드값·코드명·설명·데이터 오너 등록 |

| 표준 코드가 없으면 | 표준 코드가 있으면 |
|---|---|
| A는 'M/F', B는 '1/2'로 성별을 저장 | '성별코드'='M'(남성), 'F'(여성)로 전 시스템이 준수 |
| 통합 분석을 위해 CASE WHEN 변환 로직 작성 필요 | 별도 변환 로직 없이 GROUP BY GENDER_CD만으로 전사 분석 가능 |
| 시스템 추가·코드 값 변경 시마다 수정이 필요한 취약한 구조 | 분석 시간 단축 + 데이터 준비 과정의 오류 제거로 결과 품질이 보장됨 |

## SECTION 3. 데이터 표준 확정

### 검토·승인 5단계

> 정의하는 기술적 활동만큼 중요한 것이, 정의된 표준을 조직의 공식 자산으로 인정받는 거버넌스 절차

| # | 단계 | 설명 |
|---|---|---|
| 1 | 검토 계획 수립 | 데이터 관리자가 검토 대상 범위(신규 표준 단어 30건, 표준 용어 50건 등)와 기준을 정하고 이해관계자 선정 |
| 2 | 검토 자료 준비 및 배포 | 표준안과 체크리스트를 사전에 배포해 참석자가 충분히 숙지 |
| 3 | 검토 회의 진행 | 각 안이 사전 기준을 충족하는지 체계적으로 검증. 이견은 즉시 결론짓지 말고 별도 이슈 목록으로 관리 |
| 4 | 검토 결과 정리 및 보완 | 의견·결정 사항을 검토 결과서로 정리, 보완 목록 작성 및 수정. 표준 단어·도메인·코드의 변경은 이를 사용하는 표준 용어에 연쇄적으로 영향을 미치므로 파급 효과를 함께 기록·반영 |
| 5 | 최종 승인 | 재검토 또는 서면 합의로 동의를 얻고, 최고데이터책임자(CDO)나 거버넌스 협의체에 상정해 공식 승인 |

**검토 체크리스트 (검토 품질을 개인 역량이 아니라 프로세스로 보장하는 장치)**: 단어·용어에 대한 유일성·범용성·명확성·정의의 완전성, 도메인·코드에 대한 타당성과 오너 지정 여부.

### 공식 공표 및 전파 전략

> 표준을 만들어 서랍에 넣어두는 것은 아무 의미가 없다 — 공표의 성공이 표준화의 성패를 좌우한다

| # | 전략 | 설명 |
|---|---|---|
| ① | 중앙 저장소 등록·공개 | 확정 표준을 즉시 메타데이터 시스템에 등록 — '단일 진실 공급원(Single Source of Truth)' 역할, 웹 포털로 누구나 최신 표준 검색·조회 |
| ② | 공식적인 커뮤니케이션 | 전사 공지·이메일·사내 게시판 활용, 변경 요약+비즈니스 배경+시스템 링크 포함, 중요 변경은 반드시 별도 고지 |
| ③ | 사용자 교육 및 훈련 | 모델러·개발자·분석가·현업 대상 정기 교육 — 표준화의 가치·정책·지침의 이해, 검색·활용 방법과 신청·변경 프로세스 안내 |
| ④ | 개발 환경으로의 통합 | 모델링 도구 플러그인으로 용어 사전 즉시 적용, IDE에서 표준 컬럼 조회 지원, 일상 업무 흐름 속에 표준을 내장 |

**Tip — 표준을 '제품'으로 생각하고 '마케팅'하라**: 개발자와 분석가는 '고객'이고, 이 제품의 성공은 기술적 완벽성이 아니라 '채택률'로 측정된다. 쉬운 포털(제품)을 만들고, 정기 교육(설명회)을 열고, 개발 도구에 통합(유통 채널)하라 — 표준 준수가 더 편할 때 문화가 바뀐다.

## 자기 점검 Q&A

**Q1. 데이터 표준화의 진정한 비용은 무엇으로 측정되어야 하는가?**
> A. IT 자원 낭비가 아니라 '비즈니스 민첩성의 상실'로 측정되어야 한다. 따라서 표준화의 투자 효과도 캠페인 전환율 증가, 고객 이탈 감소 같은 비즈니스 지표로 평가해야 한다.

**Q2. 데이터 표준의 3대 원칙을 각각 한 문장으로 설명하라.**
> A. 유일성(하나의 개념에는 하나의 표준 명칭만 존재), 업무적 보편성(현업이 직관적으로 이해할 수 있는 용어 채택), 의미 전달의 충분성(명칭만으로 의미와 범위가 파악되도록 수식어로 구체화).

**Q3. 표준 단어 정의 프로세스에서 '이음동의어 통합'과 '동음이의어 분리'의 차이는 무엇인가?**
> A. 이음동의어 통합은 같은 개념에 다른 이름이 붙은 경우(고객/손님) 하나를 표준으로 선정하고 나머지를 금칙어로 관리하는 것이고, 동음이의어 분리는 같은 이름이 다른 의미로 쓰이는 경우(주소=거주지/IP) 각각을 별도 표준어로 분리해 정의하는 것이다.

**Q4. '주문금액' 사례에서 표준 용어 정의 과정이 단순한 이름짓기가 아니라 무엇이라고 설명되는가?**
> A. 영업·재무·물류가 각기 다르게 해석하던 암묵적 비즈니스 규칙(부가세·배송비·할인 포함 여부)을 수면 위로 끌어올려 전사 합의로 공식화하는 분석 활동이다.

**Q5. 표준 도메인이 데이터 아키텍처에 제공하는 진정한 가치는 무엇인가?**
> A. 단순한 데이터 타입 통일이 아니라 데이터 아키텍처에 추상화(abstraction) 계층을 제공하는 것이다. 이 추상화 덕분에 중앙에서 도메인 정의 하나만 수정하면 그 도메인을 상속받는 모든 컬럼에 변경이 자동·일관되게 전파되어 유지보수성과 확장성, 비즈니스 환경 변화에 대응하는 민첩성이 높아진다.

**Q6. 데이터 표준 확정의 검토·승인 5단계를 순서대로 나열하라.**
> A. ① 검토 계획 수립 → ② 검토 자료 준비 및 배포 → ③ 검토 회의 진행 → ④ 검토 결과 정리 및 보완 → ⑤ 최종 승인.

**Q7. 표준을 '제품'으로 생각해야 하는 이유는 무엇인가?**
> A. 개발자와 분석가가 표준의 '고객'이며, 표준의 성공은 기술적 완벽성이 아니라 실제 사용되는 '채택률'로 측정되기 때문이다. 쉬운 검색 포털, 정기 교육, 개발 도구와의 통합을 통해 표준을 지키는 것이 지키지 않는 것보다 쉬워야 자발적 준수가 일어난다.

## 한 줄 요약

데이터 표준 수립은 **비표준화의 비즈니스 비용을 공감하고 유일성·업무적 보편성·의미 전달의 충분성 3원칙과 정책 문서화 6요소로 공식 기반을 다진 뒤(제1절), 표준 단어→용어→도메인→코드의 4대 빌딩 블록을 4단계 프로세스로 실제 정의하며(제2절), 검토·승인 5단계를 거쳐 확정하고 중앙 저장소 등록·공식 커뮤니케이션·교육·개발환경 통합의 4전략으로 전사에 공표·정착시키는(제3절)** 과정이며, 이 전 과정은 기술 작업이 아니라 조직 간 합의를 이끌어내는 협상과 변화 관리의 활동이다.
