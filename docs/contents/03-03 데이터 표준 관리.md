# 03-03 데이터 표준 관리

## 도입부 — 표준을 수립한 이후의 진짜 도전

표준을 수립하고 공표하는 것은 긴 여정의 시작일 뿐이다. 진짜 도전은 환경이 끊임없이 변화하는 가운데 표준의 가치를 유지하는 **관리** 단계에 있다. 이번 챕터의 질문은 하나: **변경을 어떻게 통제할 것인가.**

### LECTURE ROADMAP — 강의 흐름과 학습 목표

| # | 블록 | 핵심 내용 |
|---|---|---|
| 1 | 관리 프레임워크 | 거버넌스 조직 4대 역할, RACI 매트릭스, 등록·변경·폐기 프로세스 |
| 2 | 준수 감사 | 점검 5단계, 준수율 보고서, 미준수 유형 3종 |
| 3 | 변경 영향도 분석 | 식별-분석-계획 3단계, 영향 대상 자산 6종, '상품코드' 사례 |
| 4 | 기술과 성숙도 | 관리 시스템 5대 기능, 도입 고려사항, 성숙도 1~5단계 |

**학습 목표**
- 데이터 거버넌스 조직의 4대 역할과 RACI 기반 책임 배분을 설명할 수 있다.
- 표준의 신규 등록·변경·폐기 프로세스를 단계별로 구분하고 각 단계의 산출물을 제시할 수 있다.
- 표준 준수 감사 절차와 변경 영향도 분석 3단계를 실제 사례에 적용할 수 있다.
- 데이터 표준 관리 시스템의 핵심 기능과 성숙도 모델 5단계를 활용해 개선 과제를 도출할 수 있다.

## SECTION 1. 데이터 표준화 관리 프레임워크

### 1. 거버넌스 조직의 4대 역할 — '누가'를 정의한다

> 효과적인 표준 관리는 즉흥적 대응이 아니라 '누가(조직)'와 '무엇을(프로세스)'을 책임지고 수행할 것인지를 명확히 정의하는 데서 시작된다

| # | 역할 | 설명 |
|---|---|---|
| ① | 데이터 거버넌스 협의체 | 최고데이터책임자(CDO)와 주요 비즈니스·IT 리더로 구성된 최상위 의사결정 기구 — 표준화 정책 최종 승인, 부서 간 중대 분쟁 조정, 방향성 제시 |
| ② | 전사 데이터 관리자 (DA) | 표준 관리 실무를 총괄하는 핵심 역할 — 원칙·절차 수립, 신규/변경 표준안 검토, 스튜어드와 협의해 표준 정의, 관리 시스템 운영 |
| ③ | 데이터 스튜어드 | 고객·상품·재무 등 특정 데이터 영역을 위임받은 현업 전문가 — 담당 영역의 표준 용어와 비즈니스 규칙 정의, '데이터 콘텐츠'의 전문가 |
| ④ | 데이터베이스 관리자 (DBA) | 데이터의 물리적 저장을 책임지는 기술 전문가 — DA가 정의한 논리 표준을 물리 객체로 구현, 성능·백업·보안의 안정적 운영 |

**역할 구분의 한 문장 정리**: DA는 '표준화 프로세스'의 전문가이고, 데이터 스튜어드는 '데이터 콘텐츠'의 전문가다. 협의체는 '결정'하고, DA는 '조정'하며, 스튜어드는 '정의'하고, DBA는 '구현'한다.

### 2. 역할과 책임 매트릭스 (RACI)

> R(실무 책임자)·A(최종 책임자)·C(협의 대상)·I(통보 대상) — 업무 중복과 책임 공백을 막는 거버넌스 도구

| 주요 활동 | 거버넌스 협의체 | 전사 DA | 데이터 스튜어드 | DBA | 현업 사용자 |
|---|---|---|---|---|---|
| 전사 데이터 표준 정책 승인 | A | R | C | I | I |
| 신규 비즈니스 용어 정의 | I | C | A, R | I | C |
| 표준 도메인(논리적 형식) 정의 | I | A, R | C | C | I |
| 데이터베이스 물리적 성능 튜닝 | I | C | I | A, R | I |
| 표준 변경 요청에 대한 영향도 분석 | I | A, R | C | C | C |
| 표준 관련 부서 간 분쟁 조정 | A | R | I | I | I |

핵심 원칙: A(최종 책임)는 반드시 한 역할에만 부여되어야 한다. 이 표만으로 조직에서 가장 흔한 DA·DBA 역할 충돌이 명확히 정리된다 — 표준 도메인 정의의 A는 DA, 물리적 성능 튜닝의 A는 DBA다. (특정 활동의 A 또는 R 주체를 묻는 문제가 시험에 자주 출제됨)

### 3. 표준 신규 등록 프로세스 — '무엇을'을 정의한다

> 요청부터 공표까지, 모든 표준은 동일한 통제 경로를 통과해야 한다

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 요청 | 현업·개발자가 신규 개념 필요 시 시스템으로 등록 요청서 제출 |
| 2 | 검토 | DA가 접수해 기존 표준과의 중복 여부, 표준화 필요성을 1차 검토 |
| 3 | 정의 | 담당 데이터 스튜어드에게 표준안 요청 — 비즈니스 관점의 명확한 정의 작성 |
| 4 | 심의·승인 | DA가 전사 원칙에 맞게 완성해 거버넌스 협의체에 공식 심의·승인 |
| 5 | 공표 | 표준 관리 시스템에 등록, 관련자에게 공식 공표 |

**단계별 주체 확인**: 요청은 현업·개발자, 검토와 완성은 DA, 비즈니스 정의는 데이터 스튜어드, 최종 승인은 거버넌스 협의체가 담당한다. DA가 정의를 직접 쓰지 않는다는 점이 중요하다 — 의미의 주인은 현업(스튜어드)이기 때문이다. 공표까지 완료되어야 비로소 신규 개발과 유지보수에 적용할 수 있는 '살아있는 표준'이 된다.

### 4. 표준 변경 관리·폐기 프로세스

> 변경은 신규 등록보다 더 엄격한 심의를, 폐기는 참조 여부의 시스템적 검증을 요구한다

| 표준 변경 관리 프로세스 | 표준 폐기 프로세스 |
|---|---|
| ① 요청: 정의·도메인 길이 확장 등 변경 요청서 제출 | ① 요청 및 분석: 단종 상품 코드 등 미사용 표준의 폐기 요청 접수 → 데이터·프로그램·보고서에서 참조 여부를 시스템적으로 검증 |
| ② 영향도 분석: 접수 즉시 파급 효과 분석을 '의무적으로' 수행 | ② 심의 및 승인: 어떤 자산에도 영향이 없음이 확인되면 공식 승인 |
| ③ 심의·승인: 타당성·시급성·소요 비용을 종합 검토, 신규 등록보다 엄격 | ③ 폐기 처리: '사용 중지' 또는 '폐기' 상태로 변경(물리 삭제 대신 이력 보존) |
| ④ 변경 실행·공표: 시스템 변경 계획 수립 → 작업 완료 → 공표 | |

**심층 분석 — 성숙도가 낮은 조직에서 벌어지는 일**: 개발자가 긴급 버그 수정을 이유로 DBA에게 요청해 컬럼 길이를 즉시 변경한다. 이 변경은 중앙 표준 관리 시스템이나 데이터 모델에 반영되지 않아 문서와 실제의 불일치(메타데이터 드리프트)를 낳는다. 성숙한 조직은 아무리 긴급해도 공식 변경 관리 프로세스를 강제한다 — 이것이 유일한 방어책이다.

## SECTION 2. 데이터 표준 준수 감사

> 표준을 수립하는 것만으로는 충분하지 않다. 준수 감사는 물리적으로 구현된 데이터베이스나 모델이 중앙에 정의된 표준과 일치하는지 주기적으로 점검하는 활동이다.

### 표준 준수 감사 5단계

| STEP | 단계 | 설명 |
|---|---|---|
| 1 | 점검 대상 선정 | 대상 스키마·모델 범위 확정(예: 신규 구축된 CRM 전체 테이블) |
| 2 | 자동 스캔 | 메타데이터 시스템으로 테이블명·컬럼명·타입·길이 자동 추출 |
| 3 | 표준과 비교 | 중앙 저장소의 표준과 대조해 불일치 항목 자동 식별 |
| 4 | 보고서 생성 | 전체 준수율 산출, 미준수 유형별 통계·상세 목록 |
| 5 | 개선·추적 | 담당자와 개선 계획 수립, 신규 등록 또는 시스템 수정 결정 |

**준수율 보고서의 구성**
- 전체 준수율 = (준수 항목 수 ÷ 전체 점검 항목 수) × 100
- 미준수 유형별 통계와 발생 건수
- 오류가 발생한 테이블명·컬럼명·오류 내용의 상세 목록

**미준수 3대 유형**
1. 미등록 용어 사용 — 표준 용어 사전에 없는 용어를 사용
2. 도메인 불일치 — 표준 도메인과 타입·길이가 상이
3. 명명 규칙 위반 — 표준 영문 약어 미사용, 조합 규칙 위반

→ 감사는 처벌이 아니라 현 주소를 파악하고 문제를 조기 발견하는 활동이며, 미준수 항목에 대해 표준을 새로 등록하거나 기존 표준에 맞게 시스템을 수정하는 두 선택지가 있다.

## SECTION 3. 변경 영향도 분석

> 표준 관리에서 가장 중요하고 복잡한 활동. 사소해 보이는 변경 하나가 연쇄 반응을 일으켜 시스템 전체에 장애를 유발할 수 있다.

### 변경 영향도 분석 3단계

| # | 단계 | 설명 |
|---|---|---|
| ① | 영향 대상 식별 (Identification) | 메타데이터 시스템에서 'Where-Used' 질의로 해당 표준을 사용하는 모든 데이터 자산을 목록화 |
| ② | 영향 내용 분석 (Analysis) | 기술적 영향(비정상 종료? ETL 실패? 데이터 잘림?)과 비즈니스적 영향(보고서 수치 오류? 법규 준수 문제?)을 함께 분석 |
| ③ | 대응 계획 수립 (Planning) | 수정 대상 프로그램·담당자·일정, 테스트 방안과 변경 작업 배포 순서까지 상세 실행 계획 수립 |

**영향 대상 자산 6종**: 데이터 모델(논리·물리) / 데이터베이스 객체(테이블·컬럼·뷰·프로시저) / ETL 스크립트 및 데이터 변환 로직 / 애플리케이션 소스 코드(UI 필드·백엔드 변수·쿼리문) / 보고서 및 BI 대시보드 / 데이터 인터페이스 전문

### 사례 연구 — '상품코드' 길이 변경

> CHAR(10) → VARCHAR2(12), 단순해 보이는 이 한 줄이 165개 자산을 흔든다

| 영향 자산 | 규모 | 예상되는 영향 |
|---|---|---|
| 데이터베이스 | 25개 테이블 | 데이터 잘림 위험은 없으나, 고정 길이→가변 길이 전환에 따른 미세한 성능 변화 가능성 |
| 애플리케이션 | 80개 화면 | 입력 필드가 10자로 고정되면 12자리 입력 불가 / 백엔드 변수 10자 선언 시 잘림·오류 |
| ETL 작업 | 15개 작업 | 타겟 시스템의 컬럼이 여전히 10자라면 데이터 적재 자체가 실패 |
| 보고서·BI | 45개 보고서 | 조회 조건·출력 레이아웃이 10자리 기준이면 UI 깨짐 또는 조회 오동작 |

→ 대응 계획: 80개 화면·백엔드 로직·15개 ETL·45개 보고서에 개발자를 할당하고, 통합 테스트 시나리오를 작성하며, 일괄 배포 일정을 수립한다. 만약 정밀한 분석 없이 DB 컬럼만 고쳤다면 원인 모를 장애와 데이터 불일치로 조직 전체가 혼란에 빠졌을 것이다.

### 표준 변경 요청 및 영향도 분석서 (3단 템플릿)

| 파트 | 내용 |
|---|---|
| A. 변경 요청 | 요청자/요청일, 변경 대상 표준(예: 표준 용어 '상품코드'), 현재 정의(예: CHAR(10)), 변경 요청 내용(예: VARCHAR2(12)), 변경 사유(비즈니스 정당성) |
| B. 변경 영향도 분석 (DA 작성) | 영향 받는 자산 유형별 정리 — 데이터 모델/데이터베이스, ETL 작업/애플리케이션, 보고서 — 각 유형별 건수와 예상 영향 기술 |
| C. 검토 및 승인 | DA 종합 검토 의견(예: 총 25개 자산 수정 필요, 예상 공수 15 M/D), 타당성 인정·전사 동시 배포 필요 등 메모, 거버넌스 협의체 결정(승인/반려/보류), 승인자·승인일 |

Tip — 변경 영향도 분석 역량을 거버넌스 팀의 핵심 가치로 삼을 것: 거버넌스 팀의 가장 중요한 역할은 표준을 '만드는' 것이 아니라 표준의 '변경'을 관리하는 것이다. 데이터 계보(Lineage) 기술에 투자해 이 역량을 확보하는 것이 거버넌스 활동의 ROI를 가장 명확히 증명하는 방법이다.

## SECTION 4. 활성화 기술과 지속적 개선

### 1. 데이터 표준 관리 시스템의 5대 핵심 기능

> 수천~수만 개의 표준을 엑셀·워드로 관리하는 것은 사실상 불가능하다

| # | 기능 | 설명 |
|---|---|---|
| ① | 중앙 리포지토리 | 단어·용어·도메인·코드의 단일 저장소, '단일 진실 공급원(SSoT)' 역할 |
| ② | 워크플로우 엔진 | 등록·변경·폐기의 신청·검토·승인 자동화, 단계별 태스크 할당, 처리 이력 투명 관리 |
| ③ | 모델링 도구 통합 | ERwin·ER-Studio와 연동 — 모델링 중 실시간 표준 조회·적용, 개발 초기 단계부터 준수 내재화 |
| ④ | 변경 영향도 분석 엔진 | 자산 간 연관 관계(Lineage) 자동 분석, 영향 객체 목록을 신속·정확하게 제공 |
| ⑤ | 준수율 점검 및 리포팅 | 물리 스키마를 주기적 추출·비교, 준수율 현황과 미준수 내역을 대시보드로 시각화 |

**도입 시 3대 고려사항**: 확장성(이기종 DBMS·BI·ETL의 메타데이터 수집), 유연성(명명 규칙 커스터마이징, 복수 표준 관리), 사용 편의성(직관적 UI, 한글→영문 약어 자동 변환). 효과적인 도구 없이는 표준 관리가 곧 관리 부하에 직면해 형식적 활동으로 전락한다 — 도구 투자는 지속 가능성을 위한 필수 투자다.

### 2. 데이터 표준화 성숙도 모델 5단계

> 현재 수준을 객관적으로 진단하고 다음 단계로 가는 로드맵을 제시하는 나침반

| 단계 | 상태 | 특징 |
|---|---|---|
| 1단계 초기 (Initial) | 공식 표준이 전혀 없음. 명칭은 프로젝트·개발자 개인 판단으로 임의 부여 | 중복·불일치 만연, 의미 파악은 항상 구두 확인 |
| 2단계 관리 (Managed) | 부서·프로젝트별 비공식 표준(엑셀 용어집) 존재 | 일부 영역만 일관성, 통합 시 변환 작업 다수, 수동·비정기 관리 |
| 3단계 정의 (Defined) | 전사 표준이 공식 정의·문서화, 조직(DA·스튜어드)과 프로세스 수립, 중앙 시스템 도입 | 신규 개발 시 표준 준수 의무화 |
| 4단계 정량적 관리 | 준수율을 정기 측정해 KPI로 활용, 변경 영향도 분석 의무 수행 | 준수 여부가 객관적 데이터로 관리, 품질이 눈에 띄게 향상 |
| 5단계 최적화 | 정량 분석 결과가 프로세스 개선에 지속 피드백, 표준이 비즈니스 민첩성의 전략 자산 | 거버넌스가 조직 문화로 정착 |

**활용법**: 매년 자체 평가로 현 수준을 진단하고, 3단계 달성을 위해 관리 시스템을 도입하며, 4단계 달성을 위해 준수율 KPI를 정의하는 식으로 구체적 개선 과제를 도출한다. (특정 상태 서술을 주고 몇 단계인지 묻는 문제가 시험에 자주 출제됨)

**자가진단 체크리스트 (6문항, Yes/No)**
1. 표준의 최종 승인권자가 문서로 지정되어 있는가?
2. DA와 DBA의 책임이 RACI로 정의되어 있는가?
3. 긴급 상황에서도 공식 변경 관리 프로세스를 우회하지 않는가?
4. 준수율을 정기 측정하고 KPI로 관리하는가?
5. 변경 영향도 분석이 의무로 규정되어 있는가?
6. 메타데이터 시스템으로 데이터 계보를 자동 추적할 수 있는가?

→ 4개 이상 'Yes'면 4단계(정량적 관리) 수준, 3개 이하면 3단계 정착을 우선 과제로 삼아야 한다(전사 표준화가 아직 도달되지 않은 상태). 이 체크리스트는 성숙도 모델과 1:1로 대응한다.

## CHAPTER 3 REVIEW — 관리 단계 전체 지도

> 조직 → 프로세스 → 감사 → 변경 통제 → 기술 → 성숙도로 이어지는 거버넌스 순환

| 관리 영역 | 핵심 내용 | 출제 포인트 |
|---|---|---|
| 거버넌스 조직 | 협의체(결정)·DA(조정)·스튜어드(정의)·DBA(구현) | 역할 매칭형 |
| RACI | 도메인 정의의 A는 DA / 성능 튜닝의 A는 DBA | A·R 주체 확인 |
| 생명주기 프로세스 | 신규 등록 5단계 / 변경 4단계 / 폐기 3단계 | 단계 수와 순서 |
| 준수 감사 | 대상 선정 → 스캔 → 비교 → 보고서 → 개선 추적 | 준수율 산식 |
| 변경 영향도 분석 | 식별(Where-Used) → 분석(기술·비즈니스) → 대응 계획 | 영향 자산 6종 |
| 기술·성숙도 | 관리 시스템 5대 기능 / 성숙도 1~5단계 | 단계별 상태 판별 |

**자주 하는 실수 TOP 3**
1. 긴급하다는 이유로 변경 프로세스를 우회한다 → 메타데이터 드리프트가 쌓인다.
2. 영향도 분석을 데이터베이스 컬럼 범위로만 한정한다 → ETL과 화면·보고서에서 장애가 발생한다.
3. 폐기할 때 물리적으로 삭제한다 → 이력 추적이 아예 불가능해진다.

## 자기 점검 Q&A

**Q1. 데이터 거버넌스 조직 4대 역할의 관계를 동사 하나씩으로 요약하라.**
> A. 협의체는 '결정'하고, 전사 DA는 '조정'하며, 데이터 스튜어드는 '정의'하고, DBA는 '구현'한다.

**Q2. RACI 매트릭스에서 '표준 도메인 정의'와 '데이터베이스 물리적 성능 튜닝'의 최종 책임자(A)는 각각 누구인가?**
> A. 표준 도메인 정의의 A는 전사 DA, 데이터베이스 물리적 성능 튜닝의 A는 DBA다. 이 두 줄이 조직에서 가장 흔한 DA-DBA 역할 충돌을 명확히 정리한다.

**Q3. 표준 신규 등록 프로세스에서 DA가 표준의 정의를 직접 작성하지 않고 데이터 스튜어드에게 요청하는 이유는?**
> A. 데이터의 의미상의 주인은 IT(DA)가 아니라 현업(스튜어드)이기 때문이다.

**Q4. 표준 준수율은 어떻게 계산하며, 미준수의 3대 유형은 무엇인가?**
> A. 준수율 = (준수 항목 수 ÷ 전체 점검 항목 수) × 100. 미준수 3대 유형은 미등록 용어 사용, 도메인 불일치, 명명 규칙 위반이다.

**Q5. 변경 영향도 분석 3단계를 순서대로 설명하라.**
> A. ① 영향 대상 식별(Where-Used 질의로 관련 자산 전수 목록화) → ② 영향 내용 분석(기술적·비즈니스적 관점) → ③ 대응 계획 수립(수정 대상·담당자·일정·테스트·배포 순서).

**Q6. 표준을 폐기할 때 물리적으로 즉시 삭제하지 않고 '사용 중지' 상태로 두는 이유는 무엇인가?**
> A. 물리적으로 삭제하면 이력 추적이 불가능해지기 때문이다. 상태 변경으로 처리해 향후 감사·추적이 가능하도록 유지한다.

**Q7. 데이터 표준화 성숙도 모델의 3단계와 4단계를 가르는 결정적 분기점은 무엇인가?**
> A. '측정'이다. 3단계는 표준이 공식 정의·문서화되고 조직·프로세스·시스템이 갖춰진 상태이지만, 4단계는 준수율을 정기적으로 측정해 KPI로 활용하고 변경 영향도 분석이 의무적으로 수행되는 단계다.

## 한 줄 요약

데이터 표준 관리는 **거버넌스 협의체·DA·스튜어드·DBA의 4대 역할과 RACI로 '누가'를 정의하고 신규 등록·변경·폐기의 생명주기 프로세스로 '무엇을' 통제할지 정한 뒤(제1절), 준수 감사 5단계로 물리적 구현이 표준과 일치하는지 주기적으로 점검하며(제2절), 변경 영향도 분석 3단계로 사소한 변경이 일으킬 연쇄 반응을 사전에 통제하고(제3절), 관리 시스템의 5대 기능과 성숙도 모델 5단계를 활용해 지속적으로 개선하는(제4절)** 순환적 거버넌스 활동이며, 이를 통해 과목 3 「데이터 표준화」(왜→어떻게 만드는가→어떻게 지키고 바꾸는가)의 전 과정이 완성된다.

|---|---|
| 데이터 거버넌스 협의체 | 표준화 정책을 최종 승인하고 부서 간 중대 분쟁을 조정하는 최상위 의사결정 기구 |
| 전사 데이터 관리자 (DA) | 표준 관리 프로세스를 총괄·조정하는 전문가 |
| 데이터 스튜어드 | 특정 데이터 영역의 비즈니스 콘텐츠를 정의하는 현업 전문가 |
| RACI 매트릭스 | 실무 책임자(R)·최종 책임자(A)·협의 대상(C)·통보 대상(I)으로 역할과 책임을 명확히 하는 도구 |
| 표준 등록·변경·폐기 프로세스 | 표준의 생명주기 — 등록 5단계, 변경 4단계(영향도 분석 의무 포함), 폐기 3단계 |
| 메타데이터 드리프트 | 공식 프로세스를 우회한 임의 변경으로 문서(표준)와 실제 시스템이 불일치하게 되는 현상 |
| 준수 감사 | 물리적으로 구현된 데이터베이스·모델이 중앙 표준과 일치하는지 주기적으로 점검하는 활동 |
| 준수율 | (준수 항목 수 ÷ 전체 점검 항목 수) × 100으로 산출하는 표준 준수 정도의 지표 |
| 변경 영향도 분석 (Impact Analysis) | 표준 변경이 미치는 영향을 식별·분석·계획하는 3단계 활동, Where-Used 질의로 시작 |
| 데이터 계보 (Lineage) | 데이터 자산 간의 연관 관계를 추적해 변경 영향 범위를 파악하는 메타데이터 기술 |
| 데이터 표준화 성숙도 모델 | 초기(1)→관리(2)→정의(3)→정량적 관리(4)→최적화(5)의 5단계로 조직의 표준화 수준을 진단하는 모델 |
