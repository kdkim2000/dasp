## SECTION 1. 전사 데이터 모델링 개요

### 1) 모델이란 무엇인가 — "단순화하여 표현하는 행위"

모델은 복잡한 현실을 특정 목적에 맞게 형상화하는 과정이며, 데이터 모델링은 그 원칙을 데이터에 적용한 것이다. 모델은 크게 두 갈래로 나뉜다.

| 구분 | 정의 | 예시 |
|---|---|---|
| 물리적 모델(Physical Model) | 실재하는 대상을 구체적 형태로 모방·표현한 것 | 자동차 축소 모형, 건축 설계도(모델하우스) |
| 개념적 모델(Conceptual Model) | 눈에 보이지 않는 현상·법칙을 논리적·추상적으로 표현한 것 | 기상 예측 수식, 경제 모형 |

데이터 모델은 **개념적 모델**에 속하며, 특정 기술이나 구현 방식에 얽매이지 않는 독립적 관점에서 데이터의 실체를 표현한다. 핵심은 데이터를 단순히 나열하는 것이 아니라, 비즈니스 논리를 데이터 구조라는 형식으로 체계화하는 지적 설계 활동이라는 점이다.

**모델링의 3원칙**

| 원칙 | 설명 |
|---|---|
| 추상화(Abstraction) | 중요한 특징에 집중하고 불필요한 세부는 제거 |
| 단순화(Simplification) | 제한된 규칙·표기법으로 누구나 이해 가능하게 |
| 명확화(Clarity) | 애매모호함을 제거하여 단 하나의 의미로만 해석되게 |

이 세 원칙에 기반해 데이터 모델링의 정의를 세 키워드로 분해하면 다음과 같다: **① 정보와 관계, ② 업무 규칙의 식별, ③ 컴퓨터가 처리할 수 있는 형태로의 변환.** 정의 문장을 통째로 외우기보다 이 세 키워드로 기억하는 편이 실전에 유리하며, 특히 "업무 규칙 식별"이 빠지면 서술형에서 오답으로 처리되는 경우가 많다.

### 2) 왜 프로세스 중심에서 데이터 중심으로 옮겨갔나

초창기 정보 시스템은 파일 시스템에 의존하는 배치 프로그램 위주였고, 설계의 중심에는 항상 프로세스가 있었다. 인사 시스템은 인사 데이터를, 회계 시스템은 회계 데이터를 각각 별도로 관리했으며, 각 기능이 독립된 굴뚝처럼 서 있다고 하여 **난로 연통(Stovepipe) 시스템**이라고도 불렸다. 이 구조는 세 가지 문제를 낳았다.

| 문제 | 내용 |
|---|---|
| ① 정보의 고립화(Information Silos) | 각 시스템 데이터가 단절되어 전사적 통합·공유가 사실상 불가능 |
| ② 데이터 중복(Data Redundancy) | 동일 정보(예: 사원 정보)가 인사·급여·영업 시스템에 각기 다른 형태로 중복 존재 |
| ③ 무결성 훼손(Data Integrity) | 한 곳의 주소 변경이 다른 곳에 반영되지 않아 정확성·일관성 유지 불가 |

이 결과 유지보수 비용이 기하급수적으로 증가하고 데이터 신뢰도가 하락하여 기업 경쟁력이 약화되었다. 이에 대한 해법은 두 갈래로 나타났다.

- **기술적 혁신 — DBMS의 등장**: 1960년대 GE의 찰스 바크만(Charles Bachman)이 개발한 IDS(Integrated Data Store)가 최초의 상용 DBMS로 평가받는다.
- **방법론적 혁신 — 관계형 모델**: 1970년 IBM의 에드거 F. 커드(E. F. Codd)가 집합 이론에 기반한 관계형 모델을 발표하며 논리적 구조(사용자 인식)와 물리적 저장 구조를 완전히 분리했다.

> **암기 포인트**: 바크만은 IDS, 커드는 1970년 관계형 모델 — 시험 단골 매칭 문제.

### 3) 모델링을 왜 반드시 해야 하는가

| 근거 | 내용 |
|---|---|
| ① 파급 효과 | 개발 후반·운영 단계에서 데이터 구조를 바꾸면 스키마 변경은 물론 관련 응용 프로그램 수정, 테스트, 데이터 이관까지 연쇄적으로 이어짐 → 초기의 정확한 설계가 프로젝트 성공의 전제 |
| ② 간결한 표현 | 수백 페이지의 문서보다 잘 그린 ERD 한 장이 명확 — 개발자·설계자·현업이 같은 그림으로 소통하는 공통 언어가 됨 |
| ③ 데이터 품질 | 구조 결함이 있으면 오래 쌓인 데이터가 신뢰할 수 없는 자산이 됨. 초기에는 알기 어렵지만 활용하려는 시점엔 치유가 어려움 |

> **암기법**: "파·간·품"(파급효과·간결한표현·품질)으로 외운다. 서술형에서 자주 출제된다.

모델링은 세 가지 고질병 — **중복, 비유연성, 비일관성**을 예방한다. 이를 소홀히 했을 때의 대표 실패 사례로 생산 라인이 멈춘 자동차 산업 사례, 고객 데이터 불일치로 배송 오류가 발생한 유통 사례가 언급된다.

### 4) 개념 → 논리 → 물리, 추상화 수준에 따른 3단계

이 표 한 장에 앞으로 배울 챕터 2·3·4의 모델링 과정 전체가 들어 있다. 행 단위가 아니라 **"추상화 수준"** 행부터 읽는 것이 핵심이다 — 개념은 가장 높고 기술과 무관, 논리는 중간이며 특정 DBMS와 무관, 물리는 가장 낮고 DBMS에 종속적이다. 이 세로축이 잡히면 나머지는 따라온다.

| 구분 | 개념 데이터 모델링(Conceptual) | 논리 데이터 모델링(Logical) | 물리 데이터 모델링(Physical) |
|---|---|---|---|
| 주요 목표 | 전사적 관점의 핵심 데이터와 관계 정의, 업무 범위·대상·산출물 파악 | 비즈니스 정보의 논리 구조·규칙 표현, 중복 배제와 정합성 확보 | 특정 DBMS에 최적화된 물리 구조로 변환, 성능·저장·보안 고려 |
| 주요 대상 | 경영진, 현업 최고책임자, 비즈니스 분석가 | 현업 실무자, 데이터 분석가, 데이터 아키텍트 | 데이터베이스 관리자(DBA), 개발자 |
| 추상화 수준 | 가장 높음(기술과 무관) | 중간(특정 DBMS와 무관) | 가장 낮음(DBMS 종속적) |
| 주요 활동 | 주제 영역 정의, 핵심 엔티티 도출, 핵심 관계 정의 | 속성 상세화, 식별자 확정, 정규화, M:N 관계 해소 | 테이블·컬럼 변환, 데이터 타입 정의, 인덱스 설계, 반정규화, 파티셔닝 |
| 주요 산출물 | 개념 ERD | 논리 ERD, 개체 정의서, 속성 정의서 | 물리 ERD, 테이블 정의서, DDL 스크립트 |

> **핵심 포인트**: 정규화는 논리, 반정규화는 물리, 주제 영역은 개념 — 매칭 문제로 자주 출제된다.

**왜 3단계로 나뉘는가 (조감도 비유)**

- **개념 모델링**: 건물의 조감도를 그리는 것과 같다. 기술적 세부를 배제하고 비즈니스 핵심 개념을 표현해 경영진과 공감대를 형성하는 도구.
- **논리 모델링**: 모델링의 핵심 단계. 특정 DBMS에 종속되지 않는 순수한 데이터 구조를 설계하며, 모든 개체·속성을 도출하고 식별자를 확정, 정규화하며 M:N을 해소.
- **물리 모델링**: 실제 데이터베이스로 구현하는 단계. 테이블·컬럼으로 변환하고 데이터 타입을 지정하며, 때로는 의도적으로 정규화 원칙을 위배하는 반정규화를 수행.

> **"변환"이 아니라 "변형"이다.** 개념 모델은 비즈니스 소통을 위해 기술적 복잡성을 희생하고, 논리 모델은 정합성이라는 이론적 이상을 추구하며, 물리 모델은 성능이라는 현실적 요구를 위해 그 순수성을 의도적으로 타협(반정규화)한다. 반정규화를 "정규화 실패"로 헷갈리면 안 된다 — 이는 의도적 타협이다. "변환이 아니라 변형"이라는 표현은 서술형 키워드로 자주 출제된다.

### 5) 전사 아키텍처(EA) 안에서의 데이터 모델링

데이터 모델링을 기업 전체 자산 관리로 확장하면 전사 아키텍처(EA)와 만난다.

- **자크만 프레임워크(Zachman)**: 육하원칙(열) × 관점(행)의 6×6 매트릭스. 이 중 '데이터(What)' 열이 모델링 3단계와 정확히 대응된다.

  | 관점 | 대응 산출물 |
  |---|---|
  | 계획자(Planner) | 핵심 데이터 목록(고객·상품·계약) |
  | 소유자(Owner) | 개념 데이터 모델 / 개념 ERD |
  | 설계자(Designer) | 논리 데이터 모델 / 논리 ERD |
  | 구축자(Builder) | 물리 데이터 모델 / DDL |

  이 대응 관계는 시험 단골 문제이므로 반드시 기억해 둔다.

- **토가프(TOGAF)**: 프로세스 중심의 프레임워크로 **비즈니스, 데이터, 애플리케이션, 기술** 4대 아키텍처 도메인으로 나뉜다. 데이터 아키텍처는 논리·물리 데이터 자산과 관리 자원의 구조를 다룬다.

**결론**: 데이터 모델링은 하나의 시스템 설계를 넘어, EA라는 거시적 틀 안에서 데이터 자산을 체계화하고 비즈니스 목표와 IT를 정렬(Alignment)시키는 역할을 수행한다.

## SECTION 2. 데이터 모델링 기법 이해

### 1) 개체-관계 모델(ERM)의 4대 구성요소

1976년 피터 첸(Peter Chen)이 제안한 개체-관계 모델(ERM)은 사실상의 표준(De facto)이다. ERM을 이해하는 가장 좋은 방법은 **문법 비유**다.

| 구성요소 | 문법 비유 | 정의 |
|---|---|---|
| 개체(Entity) | 명사 | 저장할 가치가 있는 사람·사물·장소·개념·사건. 데이터의 집합(Set)으로 표현 |
| 속성(Attribute) | 형용사 | 개체의 특성·상태를 설명하는 항목. 더 이상 분리할 수 없는 최소 데이터 단위 |
| 관계(Relationship) | 동사 | 개체 간 논리적 연관성·상호작용. 두 개체 간 업무 규칙을 정의 |
| 식별자(Identifier) | 주어(주민번호) | 개체 집합 내 인스턴스를 유일하게 구별하는 속성(집합). DB의 기본키(PK) |

"학생이 과목을 수강한다"라는 한 문장이 곧 개체·관계·개체를 담고 있다. 모델링은 비즈니스를 이런 문장으로 서술하는 작업이다.

**좋은 개체가 갖추어야 할 5가지 조건**: 관리 대상일 것, 식별 가능할 것, 인스턴스의 집합일 것(2개 이상), 속성을 포함할 것, 관계를 형성할 것. 여기서 세 번째가 가장 자주 틀리는 부분으로, **"홍길동"은 개체가 아니라 인스턴스**이고 "학생"이 개체다. 개체는 두 개 이상의 인스턴스를 갖는 집합이어야 한다.

**강한 개체 vs 약한 개체**

| 구분 | 정의 | 예시 |
|---|---|---|
| 강한 개체(Strong Entity) | 다른 개체의 존재 여부와 무관하게 독립적으로 존재 가능 | 학생, 과목, 상품 |
| 약한 개체(Weak Entity) | 강한 개체가 존재해야만 의미를 갖는 종속적 개체 | 강한 개체가 있어야 존재하는 수강신청내역 |

이 개념은 챕터 3에서 식별 관계와 다시 다룬다.

### 2) 속성의 분류

속성은 "어떻게 만들어졌는가(특성)"와 "더 쪼갤 수 있는가(구성)"라는 두 기준으로 나뉜다.

| 특성에 따른 분류 | 설명 | 예 |
|---|---|---|
| 기본 속성(Basic) | 업무 분석을 통해 직접 도출된 가장 일반적인 속성 | 학생이름, 주문일자 |
| 설계 속성(Designed) | 업무에는 없지만 유일성 부여·코드화를 위해 인위적으로 생성 | 학생ID, 학과코드 |
| 파생 속성(Derived) | 다른 속성으로부터 계산·변형되어 생성 | 생년월일 → 나이 |

| 구성에 따른 분류 | 설명 | 예 |
|---|---|---|
| 단순 속성(Simple) | 더 이상 다른 의미로 분해 불가 | 성별 |
| 복합 속성(Composite) | 여러 작은 의미 단위로 분해 가능 | 주소 → 시/구/동 |
| 다중값 속성(Multi-valued) | 한 인스턴스가 여러 값을 가질 수 있음 | 한 사람의 취미 |

파생 속성은 "나중에 저장할 것인가, 계산할 것인가"를 따지는 물리 모델링 논점으로 이어지고, 복합·다중값 속성은 제1정규형(1NF)의 대상이 된다.

**식별자(Identifier) 분류 — 4가지 기준**

| 기준 | 구분 | 예 |
|---|---|---|
| 대표성 | 주 식별자 / 보조 식별자 | 사원번호(주) ↔ 주민등록번호(보조) |
| 생성 위치 | 내부 식별자 / 외부 식별자 | 사원번호(내부) ↔ 관계로 상속된 FK(외부) |
| 속성 개수 | 단일 식별자 / 복합 식별자 | 학번(단일) ↔ (학번,과목코드)(복합) |
| 업무 의미 | 본질 식별자 / 인조 식별자 | 주민번호(본질) ↔ 순차 일련번호(인조) |

인조 식별자는 복합 식별자가 너무 길고 복잡할 때 단순화를 위해 사용한다는 점을 기억해 둔다.

### 3) 관계는 차수·기수성·선택성 세 가지로 정의된다

관계를 "선 긋기"가 아니라 "업무 규칙 선언"으로 다루어야 하며, 세 가지를 명확히 해야 한다. 암기법으로 "차·기·선"이라고도 외운다.

| 요소 | 정의 | 유형/예 |
|---|---|---|
| ① 관계 차수(Degree) | 하나의 관계에 참여하는 개체의 수 | 이항 관계(Binary, 가장 일반적, 예: 학생↔과목), 순환 관계(Unary/Recursive, 하나의 개체가 자기 자신과 관계, 예: 사원 내 상사-부하), 삼항 관계(Ternary, 세 개체가 동시 참여, 예: 교수·강의실·과목) |
| ② 대응수/기수성(Cardinality) | 한 개체 인스턴스가 상대편과 몇 개까지 관계를 맺는가 | 일대일(1:1, 예: 학생-사물함), 일대다(1:N, 예: 지도교수-학생), 다대다(M:N, 예: 학생-과목) |
| ③ 참여도/선택성(Optionality) | 반드시 관계를 맺어야 하는가 | 필수 참여(Mandatory, 예: 모든 학생은 반드시 하나의 학과에 소속), 선택 참여(Optional, 예: 사원은 프로젝트에 참여할 수도 안 할 수도 있음) |

선택성은 표기법에서 각각 수직선(필수)과 원(선택)으로 구분 표현된다.

### 4) 두 가지 심화 기법 — 슈퍼타입/서브타입, M:N 관계 해소

**슈퍼타입/서브타입**: 공통 특징을 공유하면서 일부는 고유 특징을 갖는 'is-a' 계층 구조를 표현하는 기법이다. 예를 들어 "회원"은 "일반회원"과 "기업회원"으로 나뉘는데, 아이디·비밀번호·이름은 공통(슈퍼타입)이지만 기업회원만 사업자등록번호와 법인명을 추가로 갖는다(서브타입). 공통 속성을 슈퍼타입에 모아 중복을 제거하고, 각 서브타입의 고유 특징을 명확하게 표현할 수 있다.

| 구분 | 정의 | 예 |
|---|---|---|
| 배타적 관계(Exclusive) | 한 인스턴스가 여러 서브타입 중 단 하나에만 속함 | 회원은 일반회원이거나 기업회원이거나 둘 중 하나 |
| 포괄적 관계(Inclusive) | 여러 서브타입에 동시에 속할 수 있음 | 사원은 정규직이면서 동시에 관리자일 수 있음 |

**M:N 관계 해소 4단계 — 학생·과목 사례**

M:N은 개념적으로 존재하지만 관계형 DB 테이블로는 직접 구현할 수 없다. 두 개체 사이에 연관 개체(Associative Entity)를 두어 두 개의 1:N으로 분해한다.

| 단계 | 내용 |
|---|---|
| ① M:N 관계 식별 | '학생'과 '과목' 사이에 '수강한다'는 M:N 관계가 존재함을 파악 |
| ② 연관 개체 생성 | 두 개체 사이에 '수강신청'이라는 새 개체 생성 — '수강'이라는 행위 자체를 표현하는 개체 |
| ③ 1:N 관계로 분해 | 학생-수강신청(1:N), 과목-수강신청(1:N)의 두 관계로 분해 |
| ④ 식별자 상속 및 속성 추가 | 학번·과목코드를 FK로 상속받아 복합 주식별자 구성, 수강신청일자·성적처럼 관계에서만 발생하는 속성을 추가 |

M:N 관계는 숨겨진 업무 행위를 찾아내라는 신호다(수강신청, 주문상세 등이 이런 M:N 분해 과정에서 발견되는 개체들). 이 작업은 논리 모델링 과정에서 반드시 수행해야 한다.

### 5) ERM 바깥의 두 패러다임 — 객체지향과 NoSQL

관계형이 지배적이지만 유일한 방법은 아니다.

| 구분 | ERM | 객체지향 모델링(OOM) |
|---|---|---|
| 핵심 단위 | 개체(Entity) | 객체(Object) — 데이터+행위 모함 |
| 관계 | 관계(Relationship) | 연관(Association), 상속(Inheritance) |
| 핵심 개념 | 데이터 구조 중심 | 캡슐화(Encapsulation) |
| 산출물 | ERD | UML 클래스 다이어그램 |

객체지향 모델링은 데이터와 그 데이터를 처리하는 행위를 '객체'라는 하나의 단위로 묶는 캡슐화가 핵심이며, ERM이 데이터 구조에 집중하는 반면 객체지향은 속성과 메소드를 통합해 객체 관점으로 시스템을 설계한다. 이 차이 때문에 객체지향 애플리케이션 데이터를 관계형 DB에 저장할 때 **패러다임 불일치(임피던스 불일치)** 문제가 생길 수 있다 — 상속이나 다형성을 평면적인 테이블로 표현하기 까다롭기 때문이다. ORM으로 완화할 수 있지만 근본적 차이는 남는다.

시험에 자주 나오는 문장: **"RDBMS는 데이터 중심·정규화 지향인 반면, NoSQL은 쿼리 결과 지향·비정규화 지향이다."** NoSQL은 복잡한 조인을 지원하지 않으므로 조회 형태를 먼저 분석하고 그에 최적화된 형태로 저장하는 방식이다(예: 성능을 위해 의도적으로 중복 허용, 주문 문서 안에 고객 정보를 함께 포함해 1회 읽기로 처리).

## SECTION 3. 데이터 모델링 표기법 이해

표기법은 단순한 기호의 나열이 아니라 모델의 의미를 전달하는 공식적인 언어다. 모두가 자기 방식대로 그린다면 그것은 통일된 약속이 아니라 개인의 낙서가 된다.

### IE(까마귀 발) 표기법 vs 바커(Barker) 표기법

| 요소 | 정보공학(IE) 표기법 | 바커(Barker) 표기법 | 핵심 차이 |
|---|---|---|---|
| 개체 | 모서리가 각진 사각형 | 모서리가 둥근 사각형(Soft-box) | 시각적 스타일의 차이 |
| 주 식별자 | 속성 목록 상단에 두고 밑줄로 구분 | 속성명 앞에 # 기호 표시 | 표시 위치와 기호의 차이 |
| 선택성 | 관계선 끝의 기호로 표현 — 필수는 수직선(ㅣ), 선택은 원(O) | 관계선의 종류로 표현 — 필수는 실선, 선택은 점선 | IE는 끝점 기호, 바커는 선 종류 |
| 기수성 | 하나는 수직선(ㅣ), 다(多)는 까마귀 발 | 하나는 무기호 또는 수직선, 다(多)는 까마귀 발 | 다(多) 표현은 동일 |
| 서브타입 | 슈퍼타입-서브타입을 별도 사각형으로 그리고 관계로 연결 | 슈퍼타입 사각형 내부에 중첩된 상자로 표현 | IE는 명확성, 바커는 공간 효율 |

> UML 클래스 다이어그램도 데이터 모델링 도구다 — 클래스↔개체, 속성↔속성, 연관(Association)↔관계. 집합(Aggregation, 빈 마름모)과 복합(Composition, 채운 마름모)으로 ERM보다 풍부한 전체-부분 관계 표현이 가능하다.

**실전 팁**: 부서와 사원 관계를 두 표기법으로 그려 볼 때, IE 기준 정답은 부서→사원 선의 양쪽 끝이 까마귀발과 원(즉 0..N) — 신설 부서는 사원이 없을 수도 있기 때문이다. 반대로 사원→부서 방향의 선의 끝은 이중 수직선(즉 1..1)이다. 어느 표기법이 우월하다고 말하기는 어렵지만, 프로젝트나 도구에 맞게 정해진 표준을 일관되게 쓰는 것이 중요하다.

### 좋은 데이터 모델이란 무엇인가 — 6가지 조건

기술적 완벽함을 넘어 지속적인 가치를 담아내는 6가지 조건이다.

| # | 조건 | 설명 |
|---|---|---|
| 1 | 완전성(Completeness) | 업무에 필요한 모든 데이터를 빠짐없이 담아낸다 |
| 2 | 중복 배제(Non-Redundancy) | 동일한 사실은 단 한 곳에서만 관리되도록 한다 |
| 3 | 업무 규칙 표현(Business Rules) | 비즈니스의 중요한 규칙을 모델에 명시적으로 담는다 |
| 4 | 데이터 재사용성(Data Reusability) | 특정 애플리케이션에 종속되지 않고 전사적으로 재사용된다 |
| 5 | 안정성·확장성(Stability & Flexibility) | 미래의 업무 변화에 유연하게 대응하는 구조를 가진다 |
| 6 | 의사소통(Communication) | 모든 이해관계자가 모델을 통해 명확하게 소통할 수 있다 |

이 중 중복 배제와 재사용성은 챕터 3의 정규화·품질 검토에서 다시 등장한다.

> **Tip. 표기법은 '공통의 언어'이자 계약서다.** 모두가 자신만의 방식으로 그린다면 그것은 공통의 언어가 아니라 '개인의 낙서'에 불과하다. 전사적으로 약속된 표준 표기법(IE·바커)을 일관되게 사용하는 것은 모든 이해관계자가 정보 구조에 대해 동일한 이해를 공유하고 오해를 막는 장치이며, 이는 기술이 아니라 데이터 거버넌스의 필수 전제 조건이다.

1. '홍길동'을 개체로 잡는다 → 개체는 2개 이상의 인스턴스를 갖는 집합이어야 한다.
2. M:N을 그대로 두고 물리 설계로 넘어간다 → 논리 모델링에서 반드시 연관 개체로 해소해야 한다.
3. 표기법을 프로젝트 중간에 바꾼다 → 표준 표기법 1개를 정해 끝까지 일관되게 사용해야 한다.

## 자기 점검 Q&A

**Q1. 데이터 모델링의 정의를 세 키워드로 설명하면?**
A. 정보와 관계, 업무 규칙의 식별, 컴퓨터가 처리할 수 있는 형태로의 변환. 이 중 '업무 규칙 식별'이 빠지면 시험에서 오답 처리되는 경우가 많다.

**Q2. 스토브파이프(난로 연통) 시스템의 3대 문제는?**
A. 정보의 고립화, 데이터 중복, 무결성 훼손. 이로 인해 유지보수 비용이 기하급수적으로 증가하고 데이터 신뢰도가 하락했다.

**Q3. 관계형 모델을 발표한 사람과 연도는? 최초의 상용 DBMS는?**
A. 1970년 IBM의 에드거 F. 커드(E. F. Codd)가 관계형 모델을 발표했다. 최초의 상용 DBMS는 1960년대 찰스 바크만(Charles Bachman)이 개발한 IDS다.

**Q4. 개념·논리·물리 모델링 중 정규화와 반정규화는 각각 어느 단계에 해당하는가?**
A. 정규화는 논리 모델링, 반정규화는 물리 모델링, 주제 영역 정의는 개념 모델링에 해당한다.

**Q5. "논리에서 물리로 가는 것은 변환이 아니라 무엇인가?"**
A. 변형(Transformation)이다. 물리 모델은 성능이라는 현실적 요구를 위해 정규화의 순수성을 의도적으로 타협(반정규화)하기 때문이다.

**Q6. M:N 관계를 해소하는 4단계는?**
A. ① M:N 관계 식별 → ② 연관 개체 생성 → ③ 1:N 관계로 분해 → ④ 식별자 상속 및 속성 추가.

**Q7. IE 표기법과 바커 표기법에서 선택성(Optionality)을 표현하는 방식의 차이는?**
A. IE는 관계선 끝의 기호(필수=수직선, 선택=원)로 표현하고, 바커는 관계선의 종류(필수=실선, 선택=점선)로 표현한다.

## 한 줄 요약

데이터 모델링은 스토브파이프의 고질병(중복·비유연성·비일관성)을 예방하기 위해 개념→논리→물리 3단계로 비즈니스를 "변형"해 가는 지적 설계 활동이며, ERM의 개체·속성·관계·식별자를 표준 표기법(IE/바커)으로 일관되게 표현하는 것이 핵심이다.

## 부록: 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| 데이터 모델링(Data Modeling) | 비즈니스의 정보와 관계, 업무 규칙을 식별하여 컴퓨터가 처리할 수 있는 형태로 변환하는 개념적 설계 활동 |
| 스토브파이프(Stovepipe) 시스템 | 기능별로 데이터가 단절되어 고립된 초기 정보 시스템 구조 |
| 개념/논리/물리 모델링 | 추상화 수준에 따른 데이터 모델링의 3단계 |
| 반정규화(Denormalization) | 성능 향상을 위해 의도적으로 정규화 원칙을 타협하는 물리 모델링 기법 |
| 자크만 프레임워크(Zachman) | 육하원칙(열)×관점(행)의 6×6 매트릭스로 구성된 EA 프레임워크 |
| 토가프(TOGAF) | 비즈니스·데이터·애플리케이션·기술 4대 도메인의 프로세스 중심 EA 프레임워크 |
| 개체-관계 모델(ERM) | 1976년 피터 첸이 제안한, 개체·속성·관계·식별자로 구성된 데이터 모델링 표준 기법 |
| 강한 개체 / 약한 개체 | 독립적으로 존재 가능한 개체 / 강한 개체가 있어야만 의미를 갖는 종속적 개체 |
| 슈퍼타입 / 서브타입 | 공통 속성을 가진 상위 개체(슈퍼타입)와 고유 속성을 가진 하위 개체(서브타입)의 'is-a' 계층 구조 |
| 연관 개체(Associative Entity) | M:N 관계를 해소하기 위해 두 개체 사이에 생성하는 새로운 개체 |
| 임피던스 불일치(Impedance Mismatch) | 객체지향 모델과 관계형 DB 구조 간의 패러다임 차이로 발생하는 불일치 문제 |
