# 04-02 개념 데이터 모델링

이번 챕터를 한 마디로 요약하면, **개념 데이터 모델링은 코드 한 줄 쓰기 전에 비즈니스의 오해를 잡아내는 가장 값싼 품질보증 활동**이라는 것이다. 지난 시간에 배운 개념·논리·물리 3단계 중 첫 단계를 깊이 있게 다룬다.

### LECTURE ROADMAP

| 블록 | 주제 | 핵심 내용 |
|---|---|---|
| SECTION 1 | 개념 모델의 이해 | 정의와 기술 독립성, 데이터 아키텍처 4계층 내 위상, 3가지 목표(의사소통·안정성·통찰력) |
| SECTION 2 | 주제 영역 정의 | 분류 원칙과 기준, 명명 규칙, 계층적 분할 3단계, 도출 접근법(하향식/상향식/혼합형) |
| SECTION 3~4 | 후보 엔티티 선정과 핵심 엔티티 정의 | 4단계 생명주기(수집·식별·분류·검증), 좋은 엔티티의 조건, 키·메인·행위 분류, 검증 4대 기둥, 본질 식별자 |
| SECTION 5~6 | 관계 정의와 모델 작성 | 관계의 3요소(차수·선택성·관계명), 1:1·1:M·M:M과 식별/비식별 관계, 3가지 작성 방법론, CRUD 매트릭스 검증 |

### 학습목표

- 개념 데이터 모델링이 왜 "위험 관리 전략"인지 설명할 수 있다.
- 주제 영역을 정의하는 원칙(중복 최소화·확장성·관련성)과 기준(데이터 관점 분류)을 구분해 적용할 수 있다.
- 엔티티 선정의 4단계 생명주기와 후보를 걸러내는 4대 기둥(관리적 중요성·집합 무결성·동질성과 독립성·본질 순수성)을 설명할 수 있다.
- 관계의 3요소를 이용해 관계를 정의하고, M:N 관계가 개념 단계와 논리 단계에서 다르게 취급되는 이유를 설명할 수 있다.

## SECTION 1. 개념 모델의 이해

### 1) 개념 데이터 모델링이란 — 비즈니스와 기술을 잇는 청사진

개념 데이터 모델링이란 조직의 데이터 요구사항을 발견·분석하여 어떤 데이터가 중요하고 관리되어야 하는지를 결정하는 과정이다. 가장 중요한 특징은 의도적으로 **기술 독립적(Technology-Agnostic)**이라는 점이다 — 특정 DBMS·하드웨어의 제약에 얽매이지 않고 비즈니스 규칙과 요구사항을 공식화한다. 왜 중요한가? 기술 전문성이 없는 현업 이해관계자도 모델의 정확성을 직접 검증할 수 있어야 하기 때문이다. 현업이 못 믿는 모델은 개념 모델의 역할을 할 수 없다.

**데이터 아키텍처 4계층 내 위상**: 개괄(Contextual) → **개념(Conceptual)** → 논리(Logical) → 물리(Physical). 개념 모델은 '책임자/분석가(Owner/Analyst)' 관점 — 개괄 모델의 전략적 도메인을 공식 구조로 변환하고, 논리 모델의 지침이 된다.

| 관점 | 개념(Conceptual) | 논리(Logical) | 물리(Physical) |
|---|---|---|---|
| 핵심 질문 | 무엇(What)이 필요한가 | 어떻게(How) 구조화되는가 | 어디에 어떻게 저장되는가 |
| 주요 구성요소 | 핵심 엔티티, 주요 관계 | 모든 엔티티·속성·관계·식별자·서브타입 | 테이블, 칼럼, 데이터타입, 제약조건, 인덱스 |
| 기술 독립성 | 완전 독립 | DBMS 독립적 | 특정 DBMS 종속적 |
| 주요 사용자 | 현업 전문가, 비즈니스 분석가, DA | 데이터 모델러, 비즈니스 분석가, DBA | DBA, 개발자 |

> 개념은 What, 논리는 비즈니스 관점의 How, 물리는 저장 관점의 How — 이 매칭이 시험에 자주 출제된다.

### 2) 개념 모델링은 최고의 "위험 관리 전략"이다

개념 모델링의 목표는 세 가지다.

| 목표 | 설명 |
|---|---|
| ① 의사소통(Communication) | 비즈니스 사용자·분석가·개발자가 데이터 요구사항을 발견·검증하는 시각적 구조화된 토론의 장 제공 |
| ② 안정성(Stability) | 데이터의 정의를 데이터의 사용 프로세스로부터 분리하여, 프로세스 변화에 흔들리지 않는 유연한 구조를 만듦 |
| ③ 통찰력(Insight) | 구축 과정에서 이해관계자가 근본적 질문을 던지게 되어, 숨겨진 가정과 명문화되지 않은 규칙이 드러남 |

> **핵심**: 오류는 발견 시점이 빠를수록 수정 비용이 기하급수적으로 감소한다. 개념 모델은 비즈니스 로직이 공식화되는 첫 단계로, 코드 한 줄 작성되기 전에, 상세 스키마가 설계되기 전에 비즈니스 로직의 오해와 논리적 불일치를 표면으로 드러낸다. 개발 후반의 데이터 구조 변경은 수많은 애플리케이션·보고서·이관 스크립트에 연쇄 수정을 유발하므로, 이 단계의 검토는 전체 개발 생명주기에서 가장 비용 효율적인 품질보증 활동이다. 완성된 모델은 모호함을 줄이고, 데이터가 특정 기능 부서 내에 고립되는 '난로 연통(Stovepipe) 시스템' 문제를 예방한다.

> 이 진술은 "개념 모델링을 위험 관리 전략으로 규정한다"는 참/거짓 판단 문제로 시험에 자주 출제된다.

## SECTION 2. 주제 영역 정의

### 1) 주제 영역은 데이터의 최상위 분류 체계다

주제 영역은 기업이 사용하는 데이터의 최상위 집합이며, 실무적으로는 업무상 친밀도가 높은 데이터 묶음을 말한다. 소프트웨어 공학의 원리(**높은 응집도, 낮은 결합도**)가 그대로 적용된다 — 하나의 영역 안의 데이터는 서로 강하게 연관되어야 하고, 서로 다른 영역 간의 상호작용은 최소화되어야 한다.

정의하는 목적은 **복잡성 관리(분할 정복, Divide and Conquer)**다. 거대 기업의 모든 데이터를 한 번에 모델링하는 것은 불가능하므로 논리적 도메인으로 그룹화해서 한 번에 하나에만 집중한다.

**주제 영역 정의의 4대 목적**: ① 전사적 데이터 조망, ② 의사소통의 기준(공통 언어), ③ 데이터 통합의 기반(데이터 웨어하우스의 주제 지향성과 연결되는 개념으로 시험 출제 빈도가 높음), ④ 데이터 거버넌스 단위(주제 영역별 데이터 오너 지정).

### 2) 원칙은 '무엇을', 기준은 '어떻게'

| 분류 원칙(The "What") | 설명 |
|---|---|
| ① 데이터 중복 최소화 | 본질적으로 동일한 데이터 집합이면 하나의 주제 영역으로 통합(영업고객·AS고객·잠재고객을 포괄하는 '고객' 단일 영역 → 단일 진실 공급원) |
| ② 데이터 확장성 보장 | '아이폰 판매·갤럭시 판매'가 아니라 '상품'으로, 미래 변화를 기존 분류 체계의 최소 변경으로 수용 |
| ③ 데이터 관련성·편의성 | 함께 쓰이고 변경 가능성이 높은 데이터는 묶고, '고객'과 '재고'처럼 관련성 낮은 것은 분리 |

| 분류 기준(The "How") | 설명 |
|---|---|
| ① 데이터 관점의 분류 | 조직도·업무 흐름이 아닌 데이터 자체의 본질에 근거 — 주제(Who)·대상(What)·행위(Action)로 분류. '영업부 데이터'가 아니라 '고객·판매 데이터' |
| ② 신규 요건에 대한 유연성 | 추상화·일반화 기법 활용. 정기예금·보통예금 → '예금상품' → '금융상품'으로 추상화하면 ELS 퇴직연금이 추가돼도 큰 틀에서 수용 |
| ③ 주제 영역 간 균형 유지 | MECE 원칙 — 상호 배제(하나의 데이터는 오직 하나의 영역에), 전체 포괄(모든 데이터가 소속될 영역 존재), 상세화 수준 균형 |

> **Tip**: 가장 근본적인 기준은 데이터 자체의 본질이다. 조직도나 업무 흐름은 자주 바뀐다. '영업부 데이터'처럼 가변적 요소를 기준으로 정의하면 조직 개편 때마다 아키텍처 전체를 수정해야 한다. 반면 '고객·상품·주문'과 같은 데이터의 본질적 개념은 조직이 변해도 쉽게 변하지 않는다.

### 3) 명명 3원칙과 계층적 분할 3단계

**주제 영역 명명 3원칙**: ① 실무 업무 용어 사용(○고객·상품·주문, ×고객마스터·상품정보), ② 유일한 단수형 명사(○고객, ×고객들), ③ 데이터 그룹명(명사·What) 부여(○고객·주문·재고·결제, ×고객관리·주문처리 — 동사·How는 프로세스를 지칭하며 자주 바뀌기 때문에 금지).

**계층적 분할 3단계 절차**

| 단계 | 내용 |
|---|---|
| 1차 분류 | 주요 데이터 집합의 유형 정의 — 주체(관계자·조직·직원), 대상(상품·자산·자재), 행위(계약·주문·결제), 자원·장소(채널·창고), 기준·공통(기준정보·회계) |
| 2차 분류 | 업무 활동에 필요한 데이터 분류 — 고객 기본, 고객 상세, 고객 관계, 고객 거래 이력, 고객 등급 같은 기능적 세분화 |
| 3차 분류 | 세부 주제 영역 — 핵심 엔티티와 거의 1:1로 대응(관계자 → 관계자기본 → 개인고객·법인고객·협력사·임직원). 다음 섹션(엔티티 선정)으로 가는 다리가 됨 |

산업별 1차 주제 영역 예시로는 금융업의 위험관리·여신, 제조업의 생산·품질·공급망 등이 있으며, 본인 업종에 해당하는 예시를 확인해 두는 것이 좋다.

### 4) 하향식·상향식·혼합형 접근법

| 접근법 | 시작점 | 장점 | 단점 |
|---|---|---|---|
| 하향식(Top-Down) | 비즈니스 전략·기업 경영 목표에서 추상적 개념 → 구체적 데이터로 진행 | 전사적 일관성·통합성, 강력한 비즈니스 연계 | 분석 기간 김, 세부 요구사항 누락 가능 |
| 상향식(Bottom-Up) | 기존 DB 스키마·업무 양식에서 구체적 데이터 → 추상적 개념으로 진행 | 현업 요구 충실 반영, 구체적·현실적, 빠름 | 전사 일관성 확보 어려움, 기존 문제 답습 위험 |
| 혼합형(Hybrid) | ① Top-Down 전략 수립(경영진·핵심 현업 인터뷰로 1~2차 주제 영역 초안 도출) → ② Bottom-Up 현실 분석(CRM·ERP·주문 시스템 스키마를 리버스 엔지니어링) → ③ 검증 및 상세화(초안에 실제 항목을 매핑해 누락·불필요한 분리 발견) | 가장 현실적·실용적인 방법론 | — |

> 주제 영역 정의는 기술 활동인 동시에 조직 내 정치적 협상 과정이다. 단일한 '고객' 영역을 정의하려면 마케팅·재무 부서가 공동 정의·소유권·거버넌스 모델에 합의해야 하며, 이 단계에서 데이터 아키텍트의 성공은 기술 전문성만큼이나 의사소통·협상 능력에 달려 있다.

## SECTION 3~4. 후보 엔티티 선정과 핵심 엔티티 정의

### 1) 후보 엔티티 선정의 4단계 생명주기

엔티티란 "업무 활동상 지속적인 관심을 가지고 관리해야 하는 대상"의 집합이며, 단순한 명사가 아니다.

| 단계 | 내용 |
|---|---|
| ① 수집(Collection) | 비즈니스 전반에 흩어진 잠재 후보를 빠짐없이 찾아내는 탐색 |
| ② 식별(Identification) | 진정한 엔티티의 자격을 갖추었는지 엄격히 검증하는 여과 |
| ③ 분류(Classification) | 중요도·업무 영역에 따라 구조화하여 모델의 뼈대 구축 |
| ④ 검증(Validation) | 업무 프로세스를 온전히 지원하는지 최종 확인(CRUD) |

**수집 방법 6가지 — As-Is(현재 기록)와 To-Be(미래 설계) 사이의 전략적 스펙트럼**

| 방법 | 성격 | 설명 |
|---|---|---|
| 기존 시스템 문서 | As-Is | 설계서·DB 스키마·정의서·사용자 매뉴얼. 가장 직접적이고 유용한 정보 |
| 현업 장표·보고서 | As-Is | 이미 가공·집계된 결과물이므로 주의 — '월매출표'이라면 그 근원인 '고객·상품·주문'을 찾아야 함 |
| 현업 사용자 인터뷰 | To-Be | "최상의 모델링 방법". 문서로는 알 수 없는 암묵적 업무 규칙과 미래 요구사항 발견 |
| 관련 전문 서적 | To-Be | 동종 업계 선진 사례 참고, 현재 업무의 상상력을 넘어 재창조하기 위한 힌트 |
| 데이터 흐름도(DFD) | As-Is | DFD의 데이터 저장소(Data Store)는 훌륭한 엔티티 후보. 데이터 사전과 함께 활용 |
| 타 시스템·현장 조사 | 혼합 | 관계사·유사 업종 자료 참조, 직접 현장 방문으로 문서·인터뷰로 못 잡는 제약 파악 |

수집 단계의 원칙은 "판단하지 말고 일단 모아라"이다.

### 2) 3단계 심사 — 순차 필터링 프레임워크

수집된 목록은 아직 후보일 뿐이며, 세 필터를 순서대로 통과시켜야 한다.

| 단계 | 내용 |
|---|---|
| ① 개념의 명확한 정립 | 후보 단어가 의미하는 진정한 집합이 무엇인지 우리 비즈니스 맥락에서 구체적으로 정의(예: '사원'은 정규직만인가, 계약직·협력사 직원까지 포함하는가) |
| ② 관리 대상 여부 판정 | 현재뿐 아니라 앞으로 관리해야 할 필요성까지 포함하는 전략적 판단 |
| ③ 집합의 요건 확인 | ⓐ 두 개 이상의 인스턴스, ⓑ 두 개 이상의 속성, ⓒ 유일한 식별자 — "가로(속성)와 세로(인스턴스)를 가진 면적"이어야 한다는 비유 |

온라인 서점 심사 결과 예시: 회원·도서·주문·리뷰·출판사·저자는 통과. 반면 장바구니는 영속 관리 대상이 아닌 임시 보관 기능으로 탈락(기능적 개념), 결제·배송은 주문에 종속된 하위 정보로 탈락(하위 엔티티), 별점은 '리뷰' 엔티티를 설명하는 하나의 속성이므로 탈락(속성).

> **본질 순수성**: 엔티티는 순수한 개체 본질(사람·상품)이거나 순수한 행위 본질(입금·계약) 중 하나여야 하며, '납입자·수강생'처럼 둘이 결합된 형태는 엔티티가 아니라 관계로 판별된다. 이 원칙은 숨겨진 M:N 관계를 찾아내는 강력한 진단 도구다.

### 3) 키·메인·행위 엔티티 — 발생 시점에 따른 분류

이는 꼬리표 붙이기가 아니라 모델의 안정성과 변경 위험도를 평가하는 아키텍처 분석이다.

| 구분 | 정의 | 특징 | 예 |
|---|---|---|---|
| 키 엔티티 | 다른 엔티티에 의존하지 않고 독립적으로 생성(Parentless) | 업무에서 원래부터 존재하는 근원적 정보 집합, 고유한 주식별자 보유 | 고객, 상품, 사원, 부서, 자재, 공급업체 |
| 메인 엔티티 | 키 엔티티들의 상호작용으로 발생하는 중심 사건·계약 | 부모 키 엔티티가 있어야 인스턴스 생성 가능, M:N 관계 해소 과정에서 자연스럽게 도출, 상속 식별자·순번/일자의 복합 식별자 | 주문, 계약, 청구, 수주, 보험계약 |
| 행위 엔티티 | 메인 엔티티를 상세화하거나 변화 이력을 기록 | 부모 엔티티 생명주기에 강하게 의존, 발생 빈도가 가장 높아 데이터량 최대 | 주문상세항목, 계약변경이력, 결제내역 |

**변경 위험 지도 — 폭발 반경(Blast Radius)**: 키 엔티티는 비즈니스의 가장 안정적·기초적 개념이다. 따라서 '고객'의 정의 변경은 주문·주문목록 등 모든 하위 엔티티에 영향을 미치는 고위험 변경이며, '주문목록'에 속성 하나를 추가하는 것은 국소적 저위험 변경이다. 모델링 순서도 키 → 메인 → 행위 순이 효과적이다.

**설계 안티패턴 3가지**: ① 프로세스 중심 모델링(화면 흐름을 따라 '주문신청/주문조회' 엔티티로 분리 → 데이터 중복·불일치), ② EAV(Entity-Attribute-Value) 모델(속성명·값을 행으로 저장 → 무결성 제약 사용 불가, 셀프 조인으로 성능 저하), ③ 갓 오브젝트(God Object, 주문·고객·결제·배송을 하나의 '거래'로 뭉쳐 모든 로직이 의존).

### 4) 진정한 엔티티를 가려내는 네 개의 기둥 (검증)

광석에서 순수한 금속을 제련하듯, 후보를 엄격하게 검증하는 프레임워크다.

| 기둥 | 질문 | 판정 포인트 |
|---|---|---|
| 제1기둥: 관리적 중요성 | 이것이 우리가 관리하고자 하는 대상인가? 비즈니스가 시간과 자원을 들여 추적·관리할 가치가 있는가 | '고객 만족도 점수'는 '고객'과 '설문조사'의 상호작용 결과값일 뿐, 관리 대상은 고객과 설문조사다 |
| 제2기둥: 집합 무결성 | 가로와 세로를 가진 면적 집합인가? | 관리자가 한 명이고 정보가 '이름'뿐이면 엔티티가 아니라 '프로젝트'의 속성이다 |
| 제3기둥: 동질성 및 독립성 | 동질성 = 모든 인스턴스가 동일한 본질·속성 집합 공유, 독립성 = 다른 엔티티와 개념적으로 명확히 구분 | '임원'이 '사원'의 완전한 부분집합이라면 독립 엔티티가 아니라 서브타입 |
| 제4기둥: 본질 순수성 | 개체 집합이거나 행위 집합이어야 하며, 이 둘이 혼합된 형태여서는 안 됨 | '납입자'는 개체(고객)+행위(납입하다)의 혼성 개념 → 엔티티가 아니라 관계 |

> 본질 순수성 원칙은 숨겨진 M:N 관계를 찾아내는 진단 도구다 — '수강생'은 '학생'과 '과목' 사이의 M:N을 암시한다.

### 5) 본질 식별자 — 엔티티의 '의미상의 주어'를 찾아라

| 구분 | 정의 | 예 |
|---|---|---|
| 본질 식별자(Essential) | 엔티티의 비즈니스적 정의에 내재된 속성 및 관계로 구성, 업무 규칙을 담고 있음 | 수강신청 = (학번, 과목코드, 수강 연도/학기) |
| 인조 식별자(Artificial) | 비즈니스 의미 없이 시스템이 생성한 값, 조인 성능·복합키 단순화 등 기술적 편의 목적 | 수강신청ID = 순차 증가 번호 |

**모델 검증 도구로서의 본질 식별자**: "이 엔티티의 인스턴스는 어떤 부모 엔티티들이 존재해야만 태어날 수 있는가?" — 예를 들어 '주문항목'의 본질 식별자가 (주문ID, 상품ID, 항목순번)임을 규명하면 두 부모(주문, 상품)에 종속됨이 증명된다. 부모를 찾을 수 없다면 엔티티 정의가 잘못되었거나 상위 엔티티가 누락된 것이다. 개념·논리 단계에서는 본질 식별자에 집중하고, 인조 식별자 사용 여부는 물리 모델링의 구현 편의에 따른 결정이다. 설계 단계에서 섣불리 인조 식별자에 의존하는 것은 구현 편의를 위해 비즈니스 명확성을 희생하는 오류다.

**엔티티 정제를 위한 고급 기법**: ① 통합(Integration) — 높은 동질성을 공유할 때 상위 엔티티로 통합(개인고객+법인고객 → '고객' 고객유형), ② 분할(Division) — 본질 식별자가 근본적으로 다르거나 핵심 속성·관계가 크게 다르면 분리 유지('내부 직원' vs '외부 파견 직원'), ③ 서브타입 활용(슈퍼타입(계약)+서브타입(대출계약·예금계약)), ④ 코드성 엔티티 판단(① 자체 속성을 가지는가 ② 다른 엔티티의 부모가 되는가 ③ 여러 엔티티와 관계를 맺는가 — 하나라도 해당하면 엔티티로 승격).

## SECTION 5. 관계 정의

### 1) 관계는 비즈니스 규칙을 데이터 구조에 새기는 일이다

관계의 정의는 선을 긋는 기술적 작업이 아니라 비즈니스 규칙을 데이터 구조에 내재화하는 선언적 행위다. 규칙이 스키마에 명시되면 모든 애플리케이션이 예외 없이 지켜야 한다.

| 요소 | 정의 | 유형 |
|---|---|---|
| ① 관계 차수 | 한 엔티티의 인스턴스가 상대방 몇 개와 연결되는가 | 단수(One): 단일 선 / 다수(Many): 까마귀 발. "단 하나라도 규칙을 깨는 예외가 있는지" 찾는 것이 핵심(반례 하나로 다수가 증명됨) |
| ② 관계 선택성 | 반드시 관계에 참여해야 하는가 | 필수(Mandatory): 실선 / 선택(Optional): 점선. 1:M에서 자식(M쪽)을 필수로 설계해 '고아 데이터' 발생을 원천 차단하는 것이 바람직 |
| ③ 관계명 | 두 엔티티 간 업무적 연관성의 이름 | 간결한 현재 시제 동사(소속된다·주문한다) 사용, '관계가 있다·관련된다' 같은 모호한 표현 금지, 순환·다항 관계에서는 필수 |

**관계 구문(Relationship Syntax)**: [엔티티1]의 임의의 한 개체는 [관계 형태]의 [엔티티2]와 [관계명] 관계를 [선택 사양] 가진다.

**사원·부서 양방향 분석 예시**: 사원 → 부서: "사원의 임의의 한 개체는 단 하나의 부서와 '소속된다' 관계를 반드시 가진다." 부서 → 사원: "부서의 임의의 한 개체는 하나 이상의 사원과 '보유한다' 관계를 가질 수도 있다(신설 부서는 사원이 없을 수 있음)." 합성 결과: **1:M 관계, 사원 쪽 필수, 부서 쪽 선택**.

관계의 두 가지 성격: **존재에 의한 관계**(한 엔티티의 존재가 다른 엔티티의 상태를 나타내는 정적 관계, 예: '사원은 부서에 소속된다'), **행위에 의한 관계**(특정 행위를 함으로써 발생하는 동적 관계, 예: '고객은 상품을 주문한다').

### 2) 1:1 · 1:M · M:M 그리고 식별/비식별의 선택

| 유형 | 특징 |
|---|---|
| 1:1 | 드물게 나타나는 형태. 필수-필수 1:1이 나왔다면 두 엔티티가 사실상 하나의 논리 집합일 가능성 의심 필요. 전략적 용도는 수직 분할(대용량/비활성 상세)과 서브타입의 물리 구현 |
| 1:M | 가장 흔한 형태, 계층 구조의 근간. 필수(M)-선택(1)이 기본형 — 사원-부서, 필수-필수는 주문-주문항목 |
| M:M | 반드시 해소되어야 하는 형태. 교차/연관 엔티티를 도입해 두 개의 1:M으로 분해 (상품-공급자 → '공급상품목록', 해소 과정에서 공급단가·최소주문수량 같은 새 속성 발견) |

특수 관계 패턴: 순환 관계(Recursive, 하나의 엔티티가 자기 자신과 관계 — 사원의 상사-부하, 조직의 상하위 부서), BOM(Bill of Materials, M:M 순환 관계, 하나의 부품이 여러 제품에, 하나의 제품이 여러 부품에), 배타적 관계(Arc, 여러 엔티티 중 단 하나와만 관계, 결제수단이 카드 또는 계좌 중 하나).

**M:M의 유효성은 단계마다 다르다.** 개념 단계에서는 M:M이 유효하고 오히려 권장된다 — 이해관계자와의 소통이 목적인데 '학생-과목'의 M:M이 가장 직관적이기 때문이다. 중간 엔티티를 보여주면 오히려 소통을 방해한다. 반면 논리와 물리 단계에서는 반드시 해소되어야 한다 — 최종 모델에 M:M이 남아 있다면 모델링이 아직 진행 중인 것이다. M:M 해소는 기술적 변환이 아니라 비즈니스 규칙을 발견하는 과정이다.

**식별 관계 vs 비식별 관계**

| 구분 | 식별 관계 | 비식별 관계 |
|---|---|---|
| 정의 | 부모 PK가 자식 PK에 포함 | 부모 PK가 자식의 일반 속성(FK) |
| 표기법 | 실선(Solid Line) | 점선(Dashed Line) |
| 자식의 존재 | 부모에 강하게 종속, 부모 없이 존재 불가 | 부모와 독립적으로 존재 가능 |
| 데이터 무결성 | DB 스키마 수준에서 강력하게 강제 | 애플리케이션 로직·추가 제약 필요 |
| 모델 유연성 | 낮음(부모 변경이 연쇄 영향) | 높음(수정·확장 용이) |
| 사용 사례 | '~의 일부이다'(주문-주문항목) | 단순 참조(사원-부서) |

식별 관계는 정합성을 최우선하는 '보수적' 전략(부모와의 관계가 존재의 본질인 경우 적합), 비식별 관계는 변화 적응성과 확장성을 중시하는 '민첩한' 전략이다. 우수한 결과는 무조건적 선택이 아니라 업무 규칙과 장기 발전 방향을 고려해 균형점을 찾는 것이다.

|---|---|---|
| 하향식(Forest to Trees) | 비즈니스 전략 → 주제 영역 → 핵심 엔티티 → 핵심 관계 | 전사 일관성·통합성 확보, 중복 방지 / 초기 분석에 많은 시간·경영진 참여 필요 / EDA 수립·차세대 시스템 구축에 적합 |
| 상향식(Trees to Forest) | 요구사항·자료 수집 → 후보 엔티티·속성 → 정제·관계 → 추상화 | 실제 업무 요건 충실 반영, 빠른 산출물 / 전사 관점 부족, 부분 최적화 위험 / 특정 부서 업무 개선·프로토타이핑에 적합 |
| 리버스 엔지니어링(Product to Blueprint) | 물리 스키마 추출 → 논리화(Logicalization) → 개념화 | 문서 없는 레거시 분석에 거의 유일한 방법 / 나쁜 설계를 답습할 위험, 물리 구조에 매몰 / 레거시 현대화·데이터 마이그레이션에 적합 |

정답은 하나가 아니며, 프로젝트 성격·가용 자원·범위에 따라 유기적으로 혼합한다. 리버스 엔지니어링의 본질은 복사하는 추출이 아니라 숨겨진 설계 의도를 역추적해서 해석하고 현재 요구에 맞게 재창조하는 과정이다.

**CRUD 매트릭스 검증 규칙**

| 규칙 | 의미 |
|---|---|
| C(Create)가 없는 엔티티 | 데이터를 생성하는 프로세스가 누락되었거나, 엔티티 자체가 불필요 |
| R(Read)이 없는 엔티티 | 생성만 되고 아무도 활용하지 않음, 저장 가치를 재검토해야 함 |
| CRUD가 전혀 없는 프로세스 | 프로세스 분석 오류 또는 관련 엔티티 누락 |

데이터 모델과 프로세스 모델 사이의 정합화된 '대화 채널'이 CRUD 매트릭스다.

**이해관계자 검토 워크숍 3단계**: ① 사전 준비(목표·범위 설정, ERD·정의서·시나리오를 2~3일 전 배포, 핵심 질문 준비), ② 워크숍 진행(배경 공유 → 주제 영역 단위 순차 설명 → 일방적 발표 금지, 실시간 기록·시각화), ③ 사후 조치(논의 결과 반영 및 모델 수정, 결정 사항 확인, 공식 합의 도출). 워크숍 성공의 핵심은 일반적인 설명이 아니라 참여를 유도하는 질문의 질이며, 모델러는 발표자가 아니라 퍼실리테이터가 되어야 한다.

## 자기 점검 Q&A

**Q1. 개념 데이터 모델링이 "위험 관리 전략"으로 불리는 이유는?**
A. 오류는 발견 시점이 빠를수록 수정 비용이 기하급수적으로 감소하기 때문이다. 개념 모델은 코드 작성 전, 상세 스키마 설계 전에 비즈니스 로직의 오해를 표면화해 개발 생명주기 전체에서 가장 비용 효율적인 품질보증 활동이 된다.

**Q2. 주제 영역 명명 원칙 중 "동사가 아닌 명사"가 중요한 이유는?**
A. 프로세스(동사, 예: 고객관리·주문처리)는 조직·업무 흐름에 따라 자주 바뀌지만, 데이터의 본질(명사, 예: 고객·주문)은 상대적으로 안정적이기 때문이다. 프로세스 기준으로 정의하면 조직 개편 시마다 아키텍처를 재정의해야 한다.

**Q3. 엔티티 선정의 4단계 생명주기는?**
A. 수집(Collection) → 식별(Identification) → 분류(Classification) → 검증(Validation).

**Q4. 좋은 엔티티가 갖추어야 할 3단계 요건 확인(집합의 요건)은?**
A. 두 개 이상의 인스턴스, 두 개 이상의 속성, 유일한 식별자 — "가로(속성)와 세로(인스턴스)를 가진 면적"이라는 비유로 정리된다.

**Q5. 키·메인·행위 엔티티 분류에서 "폭발 반경(Blast Radius)"이 의미하는 바는?**
A. 키 엔티티(예: 고객)의 정의 변경은 그에 의존하는 모든 하위 엔티티(주문, 주문목록 등)로 연쇄 영향을 미치는 고위험 변경임을 뜻한다. 반대로 행위 엔티티의 속성 변경은 국소적 저위험 변경이다.

**Q6. 본질 식별자와 인조 식별자의 차이는? 개념·논리 단계에서 어느 쪽에 집중해야 하는가?**
A. 본질 식별자는 엔티티의 비즈니스적 정의에 내재된 속성·관계로 구성되어 업무 규칙을 담고 있는 반면, 인조 식별자는 비즈니스 의미 없이 시스템이 생성한 값이다. 개념·논리 단계에서는 본질 식별자에 집중해야 하며, 인조 식별자 사용 여부는 물리 모델링의 구현 편의에 따른 결정이다.

**Q7. M:N 관계가 개념 단계와 논리·물리 단계에서 다르게 취급되는 이유는?**
A. 개념 단계에서는 M:N이 이해관계자와의 직관적 소통에 유리해 오히려 권장되지만, 논리·물리 단계에서는 관계형 DB로 직접 구현할 수 없으므로 연관 엔티티를 통해 반드시 해소되어야 한다.

## 한 줄 요약

개념 데이터 모델링은 기술 독립적인 관점에서 주제 영역을 정의하고, 4단계 생명주기와 4대 기둥으로 진짜 엔티티를 걸러내며, 관계의 3요소로 비즈니스 규칙을 명시적으로 새기는 — 코드 작성 전 오류를 가장 값싸게 잡아내는 위험 관리 활동이다.

| 본질 식별자(Essential Identifier) | 엔티티의 비즈니스적 정의에 내재된, 존재 이유를 규명하는 식별자 |
| 인조 식별자(Artificial Identifier) | 시스템이 생성한 기술적 편의 목적의 식별자(순차 번호 등) |
| 관계 차수/선택성/관계명 | 관계를 정의하는 3요소 — 참여 개체 수/필수 여부/업무적 이름 |
| 식별 관계 / 비식별 관계 | 부모 PK가 자식 PK에 포함되는 관계 / 부모 PK가 자식의 일반 속성(FK)이 되는 관계 |
| CRUD 매트릭스 | 엔티티와 프로세스 간 생성·조회·수정·삭제 관계를 검증하는 도구 |
| 리버스 엔지니어링(개념모델 작성) | 물리 스키마를 추출해 논리화·개념화하는, 레거시 분석에 쓰이는 방법론 |
| 블라스트 레이디어스(Blast Radius) | 엔티티 정의 변경이 다른 엔티티에 미치는 영향 범위(변경 위험도) |
