## SECTION 1. 논리 모델의 이해

### 1) 전산화와 독립적인 관점을 유지하는 것

논리 모델링의 가장 근본적인 철학은 **전산화의 독립적인 관점**이다. 특정 하드웨어·DBMS의 제약을 의도적으로 배제하고, 업무의 사실(Fact)과 규칙(Business Rule)에만 집중한다. 왜 중요한가? 기술은 끊임없이 변화하지만 기업의 핵심 비즈니스 프로세스와 데이터의 본질은 오랜 기간 안정성을 유지하기 때문이다. 특정 DBMS의 인덱싱 전략이나 파티셔닝 기능에 종속된 모델은 그 기술이 교체되는 순간 무용지물이 되지만, 비즈니스 논리를 정확히 포착한 논리 모델은 기반 시스템이 바뀌어도 유효성을 유지한다.

지난 시간에 배운 문법 비유가 여기서도 이어진다 — 개체(명사)·속성(형용사)·관계(동사)가 하나의 문법 체계를 이루며, "고객이 상품을 주문한다"처럼 개체와 관계를 연결하면 비즈니스 규칙을 나타내는 완전한 문장이 된다. 모델링은 도형을 그리는 행위가 아니라 비즈니스의 이야기를 작성하는 과정이다.

**논리 데이터 모델링의 4대 목적**

| 목적 | 설명 |
|---|---|
| ① 명확한 이해와 소통 | ERD가 복잡한 업무 규칙을 시각적·직관적으로 표현, 설계자·개발자·현업이 동일한 관점을 공유하는 공통 언어 |
| ② 전사 통합 데이터 체계 | 부서별 독립 개발이 낳은 '사일로' 현상 극복, 공통 데이터를 식별해 일관된 구조로 통합, 재사용성 극대화 |
| ③ 일관성·정확성 규칙 도출 | 관계값의 제약 등 업무 규칙을 모델에 명시, 물리 DB의 제약조건으로 구현되어 무결성을 시스템 차원에서 강제 |
| ④ 안정적·유연한 설계 토대 | 정규화로 중복을 최소화하고 구조적 안정성 확보, 변경 이상 현상을 예방하고 확장성 높은 DB 구조의 기초 |

특히 ③(규칙)은 여기서 정의한 것이 물리 DB의 제약 조건으로 구현되며, 무결성이 시스템 차원에서 강제된다는 점에서 중요하다.

### 2) 서브타입은 변화의 파급 효과를 국지화한다

슈퍼타입/서브타입 모델은 단순한 분류 기법이 아니라, **캡슐화 원리를 데이터 모델에 적용하는 전략**이다. 공통 속성(고객번호·연락처)은 슈퍼타입에, 고유 속성(주민등록번호 vs 사업자등록번호·법인명)은 각 서브타입에 배치한다.

예를 들어 개인 고객만 상대하던 기업이 법인 고객, 나아가 정부 고객으로 확장한다고 하자. 고객을 단일 개체로만 모델링했다면 법인의 사업자등록번호나 정부 고객을 위한 '주 계약 정보'와의 관계를 추가하기 위해 기존 '고객' 테이블의 구조 자체를 변경해야 하고, 이는 그 테이블을 사용하는 모든 애플리케이션에 영향을 미치는 위험하고 비용이 많이 드는 작업이다. 반면 슈퍼타입/서브타입 구조라면 '정부고객'이라는 서브타입 하나만 추가하면 되고, 슈퍼타입과 기존 서브타입은 전혀 변경할 필요가 없다 — 즉 변화의 영향을 국지화한다.

**올바른 개체가 갖추어야 할 6가지**: 업무적 연관성 및 관리 대상(지속적으로 관리하려는 정보의 집합), 유일한 식별 가능성(각 인스턴스가 유일 식별자로 구분), 영속적인 존재(보고서 출력 시 임시 생성되는 계산값은 개체가 아님), 업무 프로세스와의 연관성(하나 이상의 프로세스가 반드시 사용), 속성의 존재(반드시 하나 이상의 속성 보유), 관계의 존재(다른 개체와 최소 한 개 이상의 관계 형성).

시험에서는 서브타입의 목적을 "분류"가 아니라 "유연성·확장성·확복(변화 흡수)"으로 서술하는 선택지를 고르는 것이 핵심이다.

## SECTION 2. 속성 정의

### 1) 속성의 네 가지 본질적 특징

속성은 데이터를 담는 변수가 아니라, **모델의 구조와 무결성을 규정하는 요소**다.

| 특징 | 설명 |
|---|---|
| ① 귀속성 | 속성은 독립적으로 존재하지 않고 반드시 특정 엔티티에 귀속된다. 영어 'Attribute'의 어원 'attribuere'는 '할당하다·부여하다'라는 뜻으로, 모델러는 수동적 기록자가 아니라 어떤 정보를 어느 엔티티에 할당할지 결정하는 설계자라는 의미다 |
| ② 집합성 | 속성은 값을 담는 공간이 아니라 유효한 모든 값의 집합을 표현하며, 이를 **도메인**이라 부른다. '직급'의 도메인은 (사원, 대리, 과장, 부장, 이사)라는 유한 집합이며, 이 집합에 없는 값은 허용되지 않는다 |
| ③ 관계의 이중성 | 논리 모델의 추상적 관계는 물리 세계에서 외래키 속성으로 구현된다. '사원은 부서에 소속된다'(논리·What)가 '사원 테이블에 부서코드를 포함한다'(물리·How)로 전환된다 |
| ④ 독립성 | 주 식별자가 아닌 모든 일반 속성은 오직 주 식별자에만 완전히 종속되어야 하며, 일반 속성끼리 종속되면(이행적 종속) 갱신 이상이 발생한다 — 정규화(2NF·3NF)의 기본 사상 |

**독립성 원칙의 예**: 주문 엔티티에서 주문번호가 PK인데 고객명이 일반 속성인 고객아이디에도 종속되어 있다면 이것이 이행적 종속이다. 고객 A가 100건 주문했다면 이름이 100번 중복 저장되고, 그 고객이 개명하면 100개를 모두 고쳐야 하는 갱신 이상이 발생한다. 설계 결함이 운영 리스크로 직결되는 대표적 사례다.

### 2) 속성 후보 도출 6대 수집처와 선정 원칙

엔티티 수집과 비슷하지만, 항목 단위로 본다는 점이 다르다. 단일 정보원에 의존하지 않고 교차 검증하는 종합적 접근이 필수다.

| 수집처 | 설명 |
|---|---|
| 구 시스템 문서 | 테이블 정의서·화면 설계서·COBOL COPYBOOK 등의 컬럼/필드 분석, 화면 역분석 |
| 현업 장표·보고서 | 최종 결과값에 현혹되지 말고 계산에 필요한 원천 데이터를 역추적해야 함(예: 월별 총 판매액이 아니라 판매일자·판매금액을 도출) |
| 사용자 협의 | "이 정보 중 시간이 지나면서 변경될 수 있는 것은 무엇입니까?"라는 질문이 이력 관리 설계로 이어짐 |
| DFD/데이터 사전 | DFD의 데이터 저장소는 훌륭한 엔티티·속성 후보 |
| 전문 서적·표준 모델 | 산업 표준 데이터 모델(BIAN, ISO 20022 등)로 필수 속성 체크리스트 확보 |
| 타 시스템 인터페이스 | 외부 API가 요구하는 수취인명·연락처·배송지주소 등 다른 시스템의 핵심 속성 참고 |

**후보 선정 2대 원칙**

- **원시 속성을 버리지 않는다**: '나이'는 '생년월일'로부터 언제든 계산 가능한 파생 속성이다. '나이'만 저장하고 '생년월일'을 버리면 특정 생일 고객을 추린 생일 마케팅 같은 미래 요건을 충족할 수 없다. 파생 속성의 사전 계산 저장은 성능상의 최적화 이유로만 한다.
- **소그룹 후보군 → 엔티티 할당**: 1차로 의미가 유사한 속성을 '고객 신상 정보', '상품 기본 정보' 같은 후보군(Pool)으로 묶고, 2차로 후보군 전체를 가장 적합한 엔티티에 할당한다. 개별 할당의 오류를 줄이고 그 근거를 되짚기 쉽다.

**속성의 3대 기본 구성요소**: 속성명(업무 용어 사용·모호하지 않고 명확한 상태·주문상태코드 등, 복합 표현 지양, 일관된 명명 규칙 준수), 도메인(데이터 타입·길이/정밀도·허용값·기본값·NULL 허용 여부·재사용 가능한 표준 도메인 라이브러리 구축), 선택성(값이 반드시 존재해야 하는 필수(Mandatory)인지, 없어도 되는 선택(Optional)인지 명시).

### 3) 도메인 — 데이터 품질의 첫 방어선

도메인은 속성이 가질 수 있는 값의 범위와 제약을 정의한 것이다. 단순한 기술 명세가 아니라 데이터 품질의 첫 방어선이다. 많은 품질 문제가 'M/매일 1'처럼 같은 의미가 다른 값으로 입력되는 불일치에서 시작된다 — A 시스템은 주문 상태를 '접수/처리중/완료'로, B 시스템은 'P/I/C'로 쓴다면 통합 시 심각한 혼란이 생긴다.

논리 단계에서 도메인을 명확히 정의하면 이를 예방할 수 있다. 성별 코드를 캐릭터 2자리, 허용값을 '01' 또는 '02'로 명시하면 이 규칙이 물리 DB의 체크 제약 조건으로 구현되어 'N'이나 'M' 같은 입력을 원천 차단하게 되며, 이는 애플리케이션 로직에 의존하는 것보다 훨씬 강력하다. 기업에서는 개별 속성을 각자 정의하기보다 표준 도메인 라이브러리를 구축하는 것이 효과적이며, 결론적으로 도메인은 데이터 거버넌스를 실현하는 근본 도구다.

## SECTION 3. 엔티티 상세화

### 1) 식별자 확정 — 본질에서 인조까지

논리 모델링의 '식별자'와 물리 모델링의 '키(Key)'는 서로 다른 단계에서 다른 목적을 수행한다는 점을 먼저 기억해야 한다.

| 유형 | 정의 | 설명 |
|---|---|---|
| 본질 식별자(Essential) | 엔티티가 생성되기 위해 근본적으로 필요한 '의미상의 주어' | 키 엔티티는 자체 생성, 행위 엔티티는 절대·직접 종속의 부모로부터 상속받은 식별자 조합. 목적함수로도 명확화할 수 없으면 찾기 어려움 |
| 후보 식별자(Candidate) | ① 유일성 ② 최소성(직접적 속성 식별) ③ NULL 불허 ④ 개념적 유일성(향후 데이터까지 보장) ⑤ 변경 가능성 최소 — 다섯 조건 모두 만족해야 함 | 뒤의 두 조건(개념적 유일성·변경 가능성 최소)이 자주 누락됨 |
| 대체/보조 식별자(Alternate) | 후보 중 주 식별자로 선정되지 않은 것 | 사원번호가 주 식별자일 때 주민등록번호가 대체 식별자. 물리 단계에서 Unique Constraint/Unique Index로 구현 |
| 인조 식별자(Artificial) | 본질·후보 식별자가 부적합할 때 임의 값을 부여해 새로 만든 식별자 | 주로 일련번호 형태, 범용값 활용·유일값 확보·편의성 등의 사유로 도입 |

**개념적 유일성 예시**: 동명이인이 있을 수 있다면 '부서명+사원명'은 후보 식별자가 될 수 없다.

**종속 관계의 두 축**: 절대 종속(부모 없이 자식이 논리적으로 생성될 수 없음, 예: 주문 없는 주문항목은 불가), 상대 종속(부모와 관계를 맺지만 부모 없이도 생성 가능, 예: 사원은 부서 배정 전에도 생성 가능), 직접 종속(부모와의 1촌 관계) vs 간접 종속(조부모 등 1촌 이상을 통한 종속).

**UID BAR와 상속-단절의 원리**: UID BAR는 식별자 역할(유일 식별 기여)과 정보 역할(부모 정보 내포)을 동시에 수행한다. 식별 관계는 부 식별자를 계속 상속시키고, 비식별 관계는 신규 식별자 도입으로 상속 흐름을 단절시킨다. 확정 절차는 하향식 — 키 엔티티 → 메인 엔티티 → 행위 엔티티 순으로 확정·상속한다.

### 2) 제1정규형에서 제5정규형까지

각 단계는 이전 정규형을 만족해야 하며, 일반적으로 3NF까지 수행하는 것을 목표로 한다.

| 단계 | 명칭 | 조건 | 예 |
|---|---|---|---|
| 1NF | 원자값(Atomic Value) | 모든 속성값이 원자값이어야 함. 다중값 속성이나 반복 속성 그룹이 존재해서는 안 됨 | 반복 그룹(자녀1이름·자녀2이름)이나 다중값(취미='등산·낚시')을 별도 엔티티로 분리하고 1:M 관계 설정 |
| 2NF | 완전 함수 종속 | 1NF를 만족하고, 기본키가 아닌 모든 속성이 기본키 전체에 완전 함수 종속되어야 함(부분 함수 종속이 없어야 함) — 기본키가 복합키일 때만 발생 가능 | 수강신청의 PK가 (학번, 과목코드)인데 '과목명·담당교수'가 과목코드에만 종속 → '과목' 엔티티로 분리 |
| 3NF | 이행적 종속 제거 | 2NF를 만족하고, 기본키가 아닌 속성 간에 이행적 함수 종속이 존재하지 않아야 함 | 주문의 '고객명'이 PK인 주문번호가 아니라 일반 속성인 고객ID에 종속 → '고객' 엔티티로 분리 |
| BCNF | 모든 결정자가 후보키 | 3NF의 강화형. 릴레이션의 모든 결정자(determinant)가 후보키여야 함 | 후보키가 중복되거나 복합 후보키가 겹치는 특수한 경우에 3NF를 만족해도 이상 현상이 남을 때 적용 |
| 4NF | 다가 종속 제거 | BCNF를 만족하고, 자명하지 않은 다가 종속(MVD)이 존재하지 않아야 함 | X→Y가 존재하면 (X,Y)와 (X,Z)를 속성으로 갖는 두 릴레이션으로 무손실 분해 |
| 5NF | 조인 종속 = 후보키 | 4NF를 만족하고, 모든 조인 종속이 후보키를 통해서만 성립해야 함(위반 사례가 매우 드묾) | 후보키가 아닌 조인 종속이 있으면 해당 조인 종속을 만족하는 최소 릴레이션으로 분해 |

> **시험 포인트**: 1NF는 원자값, 2NF는 부분 종속 제거, 3NF는 이행적 종속 제거, BCNF는 모든 결정자가 후보키. 이 네 문장은 반드시 기억한다.

정규화는 데이터의 중복성을 제거하고 구조적 안정성을 확보하기 위해 논리 모델을 개선하는 절차이며 함수 종속성 이론에 기반한다. 잘못 설계된 모델에서는 변경 이상(Anomaly)이 발생한다 — 삽입 이상(특정 데이터를 넣기 위해 불필요한 값을 함께 넣어야 함), 삭제 이상(특정 정보를 지울 때 유지되어야 할 다른 정보까지 함께 사라짐, 예: 마지막 수강생을 지웠더니 과목 정보까지 없어짐), 갱신 이상(위의 고객 개명 사례). 정규화의 다섯 가지 장점은 중복 감소(핵심 목표), 널값 감소, 무결성 강화 등이며, 특히 네 번째 장점인 **"요구사항 발견 및 업무 규칙 명확화"**가 의외로 자주 출제된다 — 함수 종속 관계를 분석하다 보면 인지하지 못했던 업무 규칙을 발견하게 되므로, 정규화는 기술적 절차이면서 동시에 분석 활동에 해당한다. 성능상의 이유로 의도적으로 정규화 수준을 낮추는 반정규화(Denormalization)는 물리 데이터 모델링 단계(CHAPTER 4)의 활동이다.

### 3) M:N 해소와 참조 무결성 규칙 정의

**최종 논리 모델에 M:N 관계가 남아 있다면 모델링이 완료되지 않은 것이다.** M:N을 반드시 해소해야 하는 이유는 세 가지다 — ① 관계형 모델 구현 불가(표준 RDBMS는 M:N을 직접 표현하는 구조를 지원하지 않음), ② 업무 규칙·속성 표현의 한계(수강신청일자·성적 같은 관계 고유 정보를 담을 곳이 없음), ③ 모델의 불완전성·불일치성(아직 정규화되지 않았을 가능성이 높고 누락 정보를 파악하기 어려움).

**해소 절차 — 관계/교차/연관 엔티티 생성**: ① 두 엔티티 사이에 새로운 관계 엔티티를 생성, ② 관계 엔티티는 두 부모와 각각 1:M **식별** 관계를 맺음(단순 관계가 아님), ③ 주 식별자는 두 부모로부터 상속받은 식별자의 조합(복합 식별자), ④ 관계에서만 발생하는 속성(신청일자·성적)을 관계 엔티티의 속성으로 추가, ⑤ 원래 M:N의 선택 사양·기수성을 분석해 새 1:M 관계에 정확히 반영.

**참조 무결성 규칙 — 기술적 편의가 아니라 업무 규칙(Business Rule)에 근거해 결정한다.**

| 입력 규칙(자식 엔티티 기준) | 설명 |
|---|---|
| Dependent(기본 규칙) | FK값이 부모 PK에 반드시 존재해야 허용 |
| Automatic | 존재하지 않아도 허용하고 부모를 자동 생성(거의 미사용) |
| Nullify | 존재하지 않으면 FK를 NULL로 설정(선택 관계 전환) |
| Default | 존재하지 않으면 사전 정의된 기본값으로 설정 |

| 삭제/수정 규칙(부모 엔티티 기준) | 설명 |
|---|---|
| Restrict(기본 규칙) | 참조하는 자식이 하나라도 있으면 삭제·수정 불허 |
| Cascade | 부모 삭제 시 자식도 함께 삭제, PK 수정 시 FK도 함께 수정(의도치 않은 데이터 손실에 주의) |
| Nullify | 부모 삭제·수정 시 자식의 FK를 NULL로 설정 |
| Default | 부모 삭제·수정 시 자식의 FK를 기본값으로 설정 |

기본 대비로는 기본값인 Dependent(입력)와 Restrict(삭제/수정)를 확실히 기억해 둔다.

## SECTION 4. 이력 데이터 모델링

### 이력 관리는 아키텍처적 트레이드오프다

이력 관리는 단순한 기능 추가가 아니라 시스템 전반에 영향을 미치는 아키텍처적 트레이드오프다. 모든 데이터에 일괄 적용하는 것이 아니라 비용-편익 분석으로 **선별 적용**해야 한다.

| 비용 | 편익 |
|---|---|
| 저장 공간 증가(원본 대비 수십~수백 배 필요할 수 있음) | 의사결정 지원 강화(시계열 추이 분석으로 비즈니스 예측 정확도 향상) |
| 설계·구현 복잡성(시작일자·종료일자 설계와 변경 시 일관성 처리 로직 추가) | 완벽한 감사 추적(Audit Trail, 규제 준수 증측과 데이터 포렌식 지원) |
| 성능 저하 가능성(쓰기 작업 시 이력 생성 오버헤드가 트랜잭션 성능에 영향) | 신뢰도·복구 능력 향상(과거 시점 복원과 잘못된 수정의 원본 확인 가능) |

이력 관리 대상 선정을 위한 5대 요구사항 질문: "이전 값은 무엇이었고 언제 변경되었는지 추적해야 합니까?"(변경 내역 감시), "시간이 지남에 따라 이 값이 자연스럽게 변할 수 있습니까?"(데이터의 시간적 변화), "담당 영업사원이 바뀌는 것처럼 관계가 변할 수 있습니까?"(관계의 시간적 변화), "작년 말 기준으로 이 데이터의 상태를 조회해야 합니까?"(과거 데이터 조회, As-of Query), "계약서 1.2버전처럼 버전 자체를 보관·비교해야 합니까?"(과거 버전 보관).

### 이력의 3가지 유형과 시간을 표현하는 2가지 방식

**무엇을 기록하는가(성격) × 어떻게 시간을 표현하는가(형태)**

| 성격 | 설명 |
|---|---|
| 발생 이력(Occurrence) | 새로운 사건 자체가 발생할 때마다 기록. 계좌의 입출금 거래 내역 등, 이벤트 소싱과 유사하며 수정·삭제가 거의 없는 추가 전용(Append-only) 구조 |
| 변경 이력(Modification) | 기존 데이터의 속성값이 변할 때 그 사실을 기록. 하나의 개체가 시간에 따라 상태가 변하는 과정을 추적하며, 마스터 엔티티와 이력 엔티티를 1:M으로 분리 |
| 진행 이력(Progress) | 업무 프로세스가 여러 단계를 거쳐 진행되며 상태가 변하는 것을 기록. 주문접수→결제완료→배송중→배송완료. 워크플로우 상태 머신과 밀접 |

| 시간 표현 형태 | 설명 |
|---|---|
| 시점 이력(Point-in-Time) | 변경이 발생한 특정 시점(timestamp)만 기록. 입력(Write)이 단순 — 새 레코드 INSERT만 하면 됨. 조회(Read)가 복잡 — MAX() 서브쿼리로 이전 시점 중 최신을 찾아야 하며 데이터가 늘수록 성능 저하 |
| 선분 이력(Line-Segment) | 각 상태가 유효했던 기간을 시작-종료 시점의 쌍으로 관리. 조회가 매우 효율적 — BETWEEN 조건으로 인덱스를 효과적으로 활용. 입력 로직이 복잡 — 새 레코드 추가와 함께 기존 레코드의 종료 시점을 마감해야 함 |

> **정리**: 시점 이력은 쓰기가 쉽고 읽기가 어려우며, 선분 이력은 읽기가 쉽고 쓰기가 어렵다.

### 설계 패턴 선택과 Bitemporal 모델링

만병통치약은 없다 — 데이터 특성·활용 시나리오·성능·저장 제약을 종합 고려한다.

| 패턴 | 설명 | 적합 |
|---|---|---|
| 인스턴스 레벨 | 속성 하나만 바뀌어도 레코드 전체를 새 이력으로 복사 | 과거 시점 스냅샷 조회 성능 최고, 저장 공간 낭비 심함 / 컬럼 수가 적고 스냅샷 조회가 최우선일 때 |
| 주제 레벨 | 연관성 높은 속성을 그룹으로 묶어 그룹 단위로 스냅샷 저장 | 중복을 줄이면서 재구성 복잡도는 낮춤 / 실무적 절충안, 업무에 예가 많음 |
| 속성 레벨 | 변경된 속성 값만(개체ID, 속성코드, 속성값, 변경시점으로) 기록 | 저장 효율 최고, 스키마 변경 없이 유연 / 조회 로직이 복잡하고 자주 변경되는 소수 대형 테이블에 적용(SECTION 3에서 다룬 EAV 안티패턴과 유사한 구조로, 유연성의 대가로 복잡성을 애플리케이션 계층에 전가) |

**구현·성능 최적화 포인트**: 주 식별자 설계(복합키(대상식별자+시작일자) vs 인조 식별자(단순 일련번호) — 하위 상속과 조회 패턴을 함께 고려), 종료일자 처리(NULL 사용 vs 최대값(9999-12-31) 사용 — 최대값이 BETWEEN 조건과 인덱스 활용에 유리), 인덱스 전략(클러스터형 인덱스로 물리 정렬 / 분석용 Columnstore / 현재 유효 건만 대상으로 하는 필터링 인덱스), SCD 관리(Type 2(이력추적용 행 추가) · Type 4(치웁 테이블은 최신만 유지, 이력은 별도 테이블로 분리)).

**Bitemporal 모델링 — 두 개의 시간 축**

| 축 | 정의 | 예 |
|---|---|---|
| 유효 시간(Valid Time) | 현실 세계에서 특정 사실이 유효한 기간, 비즈니스 관점의 시간 | 2월 15일부로 급여 인상이 소급 확정 |
| 트랜잭션 시간(Transaction Time) | 그 사실이 DB에 기록되어 시스템이 인지하게 된 기간 | 3월 15일에 담당자가 시스템에 등록 |

4개 타임스탬프(ValidFrom/To, TransactionFrom/To)로 구현하며, 물리적 UPDATE·DELETE 없이 INSERT와 TransactionTo 마감만으로 모든 변경을 불변의 기록으로 남긴다. 핵심은 물리적 삭제 없이 인서트와 마감만으로 모든 변경을 불변의 기록(Immutable Log)으로 남긴다는 점이다.

## SECTION 5. 논리 데이터 모델 품질검토

### 1) 품질 검토는 감사가 아니라 사전 예방적 위험 관리다

품질 검토는 결함을 찾아 책임을 묻는 감사가 아니라, 모두가 협력해서 완성도를 높이는 건설적인 활동이다. 궁극적인 목표는 이론적으로 완벽한 모델(Perfect Model)이 아니라 조직에 가장 적합한 모델(Suitable Model)을 만드는 것이다.

**검토 시점 4가지**: ① 주제 영역별 초안 작성 후(초기 방향성과 주요 구조의 타당성 검증), ② 상세화 완료 후(모든 엔티티·속성·관계 정의와 정규화 완료 시 — 사실상 가장 중요한 검토 시점), ③ 중요 변경 발생 시(요구사항 변경·중요 설계 결정 변경 시 모델 전체 영향 평가), ④ 물리 모델링 전환 직전(최종 확정 전 모든 이슈 해결 여부를 확인하는 최종 검토).

**단계별 검토 관점의 차이**: 개념 모델 검토는 핵심 주제 영역과 핵심 엔티티가 올바르게 식별되었는지, 거시적 관계가 비즈니스 전략과 일치하는지를 본다. 논리 모델 검토는 물리적 제약에서 벗어나 요구사항과 업무 규칙이 데이터 구조에 정확·완전하게 표현되었는지를 본다. 물리 모델 검토는 테이블·인덱스가 최적 설계되었는지를 본다. 논리는 What(화슬)을, 물리는 How(하우)를 다룬다는 매칭이 여기서도 이어진다.

**검토 참여자와 각자의 관점**: 데이터 모델러/아키텍트(모델의 작성자로서 설계 의도와 결정 사항을 설명·제기된 이슈에 대해 방어하며 토론을 주도, 모델의 기술적 무결성을 책임), 현업 전문가/최종 사용자(모델이 실제 업무의 현실과 규칙을 정확히 반영하는지 판단하는 최종 결정권자, 이들 없이는 '정확성'과 '완전성'을 보장할 수 없음), DBA/개발자(구현 가능성과 성능 관점의 조기 피드백을 제공하여 물리 모델링 단계의 재작업을 예방).

### 2) 논리 데이터 모델 품질의 6대 기준

정확성·완전성·준거성·최신성·일관성·활용성 — 앞자만 따서 "정완준 최일활"로 외우기도 한다.

| # | 기준 | 설명 |
|---|---|---|
| 1 | 정확성(Correctness) | 업무 규칙과 요구사항이 데이터 구조에 오류 없이 반영되었는가, 관계의 기수성·선택성이 실제 업무와 일치하는가 |
| 2 | 완전성(Completeness) | 관리해야 할 데이터가 누락 없이 포함되었는가. **동시에** 현재 사용하지 않는 불필요한 요소가 없는가도 확인해야 함(복잡성 증가·유지비용·오해 유발) |
| 3 | 준거성(Compliance) | 표준 단어·용어, 도메인 표준, 명명 규칙을 준수하는가. 개인정보보호법의 고유식별정보 암호화, 법정 데이터 보관 주기 등 규제 요건 반영 — 실무 감사에서 가장 먼저 지적되는 항목 |
| 4 | 최신성(Up-to-dateness) | '살아있는 문서'로서 현재 시점의 비즈니스 환경을 정확히 반영하는가. 결려되면 폐지된 규칙으로 개발되는 요구사항 불일치·의사소통 혼란·유지보수 곤란 발생 |
| 5 | 일관성(Consistency) | 동일한 개념이 모델 전반에서 동일하게 표현되는가. 제각기면 데이터 중복·불일치, 업무 로직 복잡, 통합 분석 곤란으로 이어짐 |
| 6 | 활용성(Usability & Flexibility) | 의사소통 도구로 충분한 설명과 업무 규칙이 기술되어 있는가, 작은 변화에 대규모 구조 변경이 불필요한 안정성과 신규 요건을 수용하는 확장성을 갖췄는가 |

**완전성의 함정에 유의**: 누락이 없는가만 보는 것이 아니라, 동시에 현재 쓰이지 않는 불필요한 요소가 없는가도 확인해야 한다. 불필요한 요소는 구조를 복잡하게 만들고 개발자가 지금 구현해야 할 기능으로 오해하게 만든다.

### 3) 구성 요소별 상세 품질 검토 체크리스트

엔티티·속성·식별자·관계·모델 전반의 5개 영역을 순차적으로 점검한다. 실무 검토 형식으로 그대로 쓸 수 있다.

| 영역 | 점검 항목 |
|---|---|
| 엔티티 | 엔티티명이 집합의 성격을 잘 나타내는가, 정의가 포함/제외 기준까지 명확히 기술되었는가(예: '고객'이라면 상품 구매·서비스 가입 이력이 있는 개인/법인처럼 경계 명확), 통합 수준이 적절한가(과도한 통합·과도한 분할 여부), 서브타입의 분류 기준이 명확하고 배타적인가 |
| 속성 | 속성명이 데이터의 의미를 정확히 설명하는가('상태X' → '주문상태코드O'), 도메인(타입·길이·허용값)이 정의되었는가, 필수/선택 여부와 기본값이 명시되었는가, 정규화가 수행되어 중복과 종속성이 제거되었는가 |
| 식별자 | 주식별자가 유일성과 최소성을 만족하는가, 값이 가급적 변하지 않는 안정성을 갖는가, 인조 식별자 사용이 적절한가(자연키가 있는데 불필요하게 도입하지 않았는가) |
| 관계 | 관계명이 업무 규칙을 서술하는 동사로 표현되었는가, 기수성과 선택성이 실제 업무 규칙과 일치하는가, 참조 무결성 규칙이 업무 규칙에 근거해 정의되었는가 |
| 모델 전반 | 주제 영역 배치가 적절하여 복잡성이 관리되는가, M:N 관계가 모두 해소되었는가, 이력 관리가 필요한 데이터에 대한 설계가 반영되었는가 |

> **품질이 왜 결정적인가**: 논리 모델의 결함은 물리 모델·애플리케이션 코드·데이터 전환 프로세스로 전파된다. 뒤늦게 발견될수록 수정 비용과 파급 효과가 막대해지므로, 이 단계의 검증이 가장 경제적이고 효율적인 방법이다. 고품질 논리 모델은 TCO를 절감하고 비즈니스 민첩성을 확보한다.

## CHAPTER 3 SUMMARY — 핵심 정리 & 자주 하는 실수

| 핵심 정리 | 내용 |
|---|---|
| 논리 모델 = 전산화 독립적 관점 | 기술은 변해도 비즈니스 본질은 안정적 / 소통·통합·규칙·토대의 4대 목적 |
| 속성 = 귀속·집합·이중·독립 | 도메인은 데이터 품질의 첫 방어선이자 강제성 있는 비즈니스 규칙 |
| 식별자 = 본질 → 후보 → 대체 → 인조 | 후보 5조건: 유일성·최소성·NULL불허·개념적 유일성·변경 최소 |
| 정규화 = 1NF 원자값 → 2NF 부분종속 → 3NF 이행종속 | 삽입·삭제·갱신 이상을 제거 / 최종 논리 모델에 M:N은 없어야 함 |
| 이력 = 발생·변경·진행 × 시점·선분 | 시점은 쓰기가 쉽고, 선분은 읽기가 쉽다 / 품질 6기준: 정완준 최일활 |

**자주 하는 실수 TOP 3**

1. 파생 속성만 저장하고 원시 속성은 버린다 → '나이'만 남기면 생일 마케팅 요건을 영영 충족할 수 없다.
2. 2NF를 단일 PK 엔티티에서 따진다 → 부분 함수 종속은 복합키일 때만 발생한다.
3. 이력 관리를 모든 테이블에 일괄 적용한다 → 저장·성능 비용 대비 편익을 따져 선별 적용해야 한다.

## 자기 점검 Q&A

**Q1. 논리 모델링이 "전산화 독립적 관점"을 유지해야 하는 이유는?**
A. 기술(하드웨어·DBMS)은 끊임없이 변하지만 기업의 핵심 비즈니스 프로세스와 데이터의 본질은 오랜 기간 안정적이기 때문이다. 특정 기술에 종속된 모델은 그 기술이 교체되는 순간 무용지물이 되지만, 비즈니스 논리를 정확히 포착한 논리 모델은 시스템이 바뀌어도 유효하다.

**Q2. 슈퍼타입/서브타입 모델링이 캡슐화 원리로 설명되는 이유는?**
A. 공통 속성은 슈퍼타입에, 고유 속성은 서브타입에 배치함으로써 신규 유형(예: 정부 고객) 추가 시 기존 구조를 변경하지 않고 새 서브타입만 추가하면 되므로, 변화의 파급 효과를 국지화(캡슐화)하기 때문이다.

**Q3. 속성의 독립성 원칙을 위반하면 어떤 문제가 발생하는가?**
A. 일반 속성끼리 종속되는 이행적 종속이 발생하며, 이는 갱신 이상으로 이어진다. 예를 들어 주문 엔티티에 고객명이 고객아이디를 통해 종속되어 있으면, 고객이 개명할 때 모든 관련 레코드를 일일이 수정해야 한다.

**Q4. 2NF(부분 함수 종속 제거)는 어떤 조건에서만 문제가 될 수 있는가?**
A. 기본키가 복합키(2개 이상의 속성으로 구성)일 때만 부분 함수 종속이 발생할 수 있다. 단일 속성 PK는 항상 2NF를 만족한다.

**Q5. M:N 관계를 논리 단계에서 해소할 때 관계 엔티티가 부모와 맺는 관계의 성격은?**
A. 단순한 관계가 아니라 식별 관계다. 관계 엔티티의 주 식별자는 두 부모로부터 상속받은 식별자의 조합(복합 식별자)으로 구성된다.

**Q6. 시점 이력과 선분 이력의 트레이드오프는?**
A. 시점 이력은 입력(쓰기)이 단순하지만 조회(읽기)가 복잡하고(MAX() 서브쿼리 필요), 선분 이력은 조회가 매우 효율적(BETWEEN 조건)이지만 입력 로직이 복잡하다(기존 레코드의 종료 시점 마감 필요).

**Q7. 논리 데이터 모델 품질 6대 기준 중 "완전성"에서 자주 놓치는 함정은?**
A. 완전성은 누락이 없는가만 확인하는 것이 아니라, 동시에 현재 사용되지 않는 불필요한 요소가 없는가도 확인해야 한다. 불필요한 요소는 구조를 복잡하게 만들고 개발자에게 잘못된 구현 신호를 줄 수 있다.

## 한 줄 요약

논리 데이터 모델링은 전산화와 독립적인 관점에서 속성의 4대 특징과 도메인을 정의하고, 본질→후보→대체→인조 식별자를 확정하며, 정규화와 M:N 해소로 구조적 안정성을 확보하고, 이력 관리와 6대 품질 기준으로 완성도를 검증하는 — 사실상 데이터 모델링의 최종 완료 단계다.

## 부록: 핵심 용어 정리

| 용어 | 설명 |
|---|---|
| 논리 데이터 모델링 | 전산화 독립적 관점에서 비즈니스 사실과 규칙을 완전한 형태의 데이터 구조로 표현하는 과정 |
| 도메인(Domain) | 속성이 가질 수 있는 모든 유효한 값의 집합, 데이터 품질의 첫 방어선 |
| 이행적 종속(Transitive Dependency) | 기본키가 아닌 일반 속성끼리 종속되는 현상, 갱신 이상의 원인 |
| 본질/후보/대체/인조 식별자 | 엔티티 생성에 근본적으로 필요한 식별자에서 시스템이 생성한 인조 식별자까지의 확정 절차 |
| 정규화(Normalization) | 함수 종속성 이론에 기반해 데이터 중복성을 제거하고 구조적 안정성을 확보하는 절차 |
| 삽입/삭제/갱신 이상(Anomaly) | 정규화되지 않은 구조에서 데이터 조작 시 발생하는 세 가지 이상 현상 |
| 참조 무결성 규칙 | 부모-자식 엔티티 간 데이터 정합성을 유지하기 위한 입력·삭제·수정 규칙(Dependent, Restrict, Cascade 등) |
| 발생/변경/진행 이력 | 기록 대상의 성격에 따른 이력의 3가지 분류 |
| 시점/선분 이력 | 시간을 표현하는 방식에 따른 이력의 2가지 분류(입력 용이 vs 조회 용이) |
| Bitemporal 모델링 | 유효 시간과 트랜잭션 시간, 두 개의 시간 축을 동시에 관리하는 이력 설계 기법 |
| 논리 모델 품질 6대 기준 | 정확성·완전성·준거성·최신성·일관성·활용성 |
