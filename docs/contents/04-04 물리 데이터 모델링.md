## SECTION 1. 물리 모델링의 이해

### 1) '무엇을'에서 '어떻게'로 — 다차원 최적화 문제

물리 데이터 모델은 논리 모델을 특정 DBMS의 기술적 특성을 고려해 물리적 스키마로 변환한 최종 청사진이다. 이 변환은 단순한 용어 치환이 아니라 심층적인 공학 활동이다. 논리 모델이 기술 환경으로부터 독립적인 추상 구조를 지향하는 반면, 물리 모델은 특정 DBMS와 하드웨어, 성능 요구사항이라는 현실적 제약 아래에서 구현되어야 하기 때문이다.

**핵심 목표**: 시스템의 성능 향상, 개발·운영 과정의 편의성 증대와 단순화. 나아가 논리 모델에서 정의된 무결성·보안성·품질·활용성이라는 추상적 원칙을 물리적 제약조건과 접근 제어를 통해 실질적으로 통제하고 강제하는 것이다.

**상충하는 목표들 — 트레이드오프의 실제**: 성능을 위해 반정규화하면 조회는 빨라지지만 무결성·일관성이 저해될 위험이 있다. 저장 공간을 위해 타입을 작게 잡으면 향후 더 큰 값이 필요할 때 확장성 문제가 생길 수 있다. 개발 편의를 위해 정합성을 앱 코드로 넘기면 DB 자체의 보호 기능이 약해진다. 그래서 물리 모델링은 기계적 치환이 아니라, 여러 트레이드오프 관계에 있는 속성들 사이에서 우선순위를 파악해 균형점을 찾는 의사결정 활동이다.

물리 모델은 데이터 아키텍처의 '실행 증거'이자 '제약 조건의 최종 집행자'다. "고객은 여러 계좌를 가질 수 있다"는 추상적 비즈니스 규칙은, 물리 모델에서 고객 테이블과 계좌 테이블 간 관계를 1:N으로 설정하고 이를 외래키 제약조건으로 구현함으로써 비로소 시스템적 강제력을 갖는다. 따라서 모든 테이블·컬럼·제약조건은 반드시 상위 논리 모델의 엔티티·속성·관계로부터 추적 가능해야 한다.

### 2) 논리 데이터 모델과 물리 데이터 모델의 비교

이 변환은 정보를 잃는 과정이 아니라, 구현과 최적화를 위한 방대한 물리 정보를 '추가'하는 과정이다.

| 구분 항목 | 논리 데이터 모델(Logical) | 물리 데이터 모델(Physical) |
|---|---|---|
| 핵심 목표 | 비즈니스 규칙과 데이터 구조의 정확한 표현(정합성·일관성) | 데이터베이스 성능 최적화 및 실제 시스템 구현(성능·저장 효율) |
| 기본 관점 | 분석가·현업 전문가의 관점(Business-Centric) | 개발자·DBA의 관점(Technology-Centric) |
| 기술 종속성 | 기술 독립적(Platform-Independent) | 특정 DBMS 및 인프라 환경에 종속적(Platform-Dependent) |
| 주요 구성요소 | 엔티티, 속성, 관계, 주/대체 식별자 | 테이블, 칼럼, 제약조건(PK·FK·UK·Check), 인덱스, 뷰 |
| 표현 방식 | 비즈니스 용어 사용, 정규화 원칙의 엄격한 준수 | DBMS 명명 규칙 준수, 구체적 데이터 타입, 성능을 위한 반정규화 |
| 추상화 수준 | 높음(개념적·논리적 구조) | 낮음(물리적 구현 상세 명세) |
| 주요 활동 | 정규화, 관계 정의, 업무 규칙 분석, 엔티티 상세화 | 반정규화, 인덱스 설계, 파티셔닝, 데이터 타입 선정, 저장 옵션 |

인덱스의 종류와 구성, 파티셔닝 전략, 테이블스페이스와 데이터 파일의 물리적 위치, 데이터 블록 저장 옵션은 논리 모델에 존재하지 않는 순수한 물리적 정보다 — 물리 모델은 논리 모델을 '대체'하는 것이 아니라 '확장'하고 '구체화'한다.

### 3) 물리적 스키마의 구성 요소

**테이블 유형**

| 유형 | 특징 | 장/단점 |
|---|---|---|
| 힙 구성 테이블(Heap-Organized) | 데이터가 입력되는 순서대로 특별한 정렬 없이 저장되는 가장 일반적인 형태 | ○ 삽입 속도가 빠름 / × 특정 데이터를 찾으려면 테이블 전체를 스캔할 수 있음 |
| 클러스터 인덱스 테이블(Index-Organized) | PK 또는 특정 인덱스 키 값의 순서에 따라 데이터 행 자체가 물리적으로 정렬되어 저장 | ○ 특정 범위 조회 성능이 매우 뛰어남 / × DML 시 물리적 재정렬이 필요해 부하 발생 |
| 파티션 테이블(Partitioned) | 대용량 테이블을 날짜·지역·값의 범위 등 특정 기준에 따라 여러 파티션으로 나누어 저장 | ○ 관리 용이성 향상, 쿼리 성능 개선 / × 파티션 키가 WHERE 절에 없으면 전체 스캔 |

> **테이블스페이스**는 단순한 공간 할당이 아닌 전략적 구획화다. 하나 이상의 물리적 데이터 파일과 연결되어 논리적 설계와 물리적 저장을 분리한다. 테이블 데이터와 인덱스 데이터를 서로 다른 물리 디스크의 데이터 파일에 할당하면, 테이블 스캔과 인덱스 탐색이 동시에 일어날 때 서로 다른 디스크에서 I/O가 발생해 디스크 경합이 줄어든다. 또한 업무별·대용량 테이블별로 독립적인 테이블스페이스를 두면 백업·복구 작업을 해당 단위에만 국한할 수 있다.

## SECTION 2. 물리 요소 조사 및 분석

### 1) 명명 규칙은 데이터 거버넌스의 초석이다

조직의 명명 규칙 성숙도는 그 조직의 데이터 거버넌스 성숙도를 보여주는 가시적인 지표다. 어떤 시스템은 고객 테이블을 CUSTOMER로, 다른 시스템은 CUST나 CUSTM로 쓰고 컬럼명도 제각각이라면 이는 데이터 사일로와 사후 대응적 품질 문화의 신호다.

| 계층 | 정의 | 예 |
|---|---|---|
| ① 표준 단어(Standard Word) | 데이터 표준의 가장 작은 의미 단위, 업무 개념(고객)을 유일하게 승인된 영문 약어(CUST)로 매핑. 가장 중요한 역할은 동의어·동형이의어 통제 — '회사·업체·거래처'를 모두 CORP 하나로 통일 | 고객 → CUST |
| ② 표준 용어(Standard Term) | 표준 단어들을 조합해 엔티티·속성 이름을 만드는 규칙. 객체명 자체가 의미를 설명(Self-describing)하게 되어 예측 가능성과 가독성 향상 | 고객(CUST) + 번호(NO) → CUST_NO |
| ③ 도메인(Domain) | 속성이 가질 수 있는 값의 범위·타입·길이·NULL 허용 여부를 정의. 단어·용어가 '이름의 일관성'이라면 도메인은 '구조적 일관성'을 강제 — 조인 시 타입 불일치로 인한 성능 저하를 원천 방지 | 고객번호 = 어느 테이블에서 외래키로 쓰이든 항상 같은 타입과 길이 |

**물리적 객체별 명명 규칙 예**: 테이블은 [업무영역]_[주제어]_[분류어](예: SLS_ORD_HDR), 컬럼은 표준 용어를 그대로 사용(CUST_NO, ORD_DT), 기본키는 [테이블명]_PK, 외래키는 [자식]_[부모][FK번호], 인덱스는 [테이블명]_IX[번호] 또는 _UX[번호] — 이렇게 하면 스키마가 자체적으로 문서화된다.

**데이터 용어 사전 — 표준의 단일 진실 공급원**: 표준 자동 추천 생성, 표준 준수 여부 자동 검증, 영향도 분석(예: '고객번호' 길이를 10→12자리로 바꿀 때 영향받는 모든 오브젝트·테이블·앱 식별), 표준화를 수동 검토에서 자동화된 품질 보증 활동으로 전환.

### 2) 하드웨어 자원 파악 — 성능 지표와 임계값

**높은 CPU 사용률은 원인이 아니라 증상일 수 있다 — 메모리와 I/O를 먼저 확인하라.**

| 자원 | 지표 | 임계값과 의미 |
|---|---|---|
| CPU(두뇌) | 전체 사용률 | 80~85% 지속 초과 → CPU 병목 신호 |
| | 프로세서 대기열 | 코어 수의 2배 지속 초과 → CPU 모자람 |
| | I/O 대기 시간 | %iowait 20% 이상 → 디스크가 발목을 잡는 CPU 병목 |
| 메모리(가속 페달) | Pages/sec | 초당 50회 초과 → 심각한 메모리 부족 |
| | Page Life Expectancy | 300초 미만 → 캐시에 데이터가 머물지 못함 |
| | Buffer Cache Hit Ratio | OLTP는 95% 이상, 이상적으로 99% 이상 |
| | swap in/out | DB 서버에서는 어떤 경우에도 0이어야 함 |
| 디스크(저장소) | 지연 시간(Latency) | OLTP 고성능 스토리지는 10ms 미만, 20ms 초과 시 병목 |
| | 디스크 사용률(%util) | 80% 초과해 100%에 근접하면 포화 상태 |
| | 디스크 대기열 길이 | 스핀들 수의 2배 지속 초과 → 처리 지연 |

**정석적인 분석 순서와 '캐시 친화적' 설계**: 부적절한 인덱스 설계로 인한 비효율적 쿼리 계획은 수백만 개의 불필요한 페이지를 읽게 만들고, 이 데이터를 메모리로 가져와 필터링·정렬·조인하는 과정에서 막대한 CPU를 소모시킨다. 최종적으로 관찰되는 현상은 높은 CPU 사용률이지만 근본 원인은 인덱스 하나의 부재일 수 있다. 따라서 물리 모델링의 목표 중 하나는 '캐시 친화적' 구조를 만드는 것 — 테이블 폭을 좁게 설계하고(Narrow Table) 선택도 높은 인덱스를 생성해, 핵심 데이터가 한정된 메모리에 최대한 많이·오래 머물게 하는 것이다.

## SECTION 3. 논리-물리 모델 변환

### 1) 변환의 트릴레마 — 무결성·성능·확장성

기계적 치환이 아니라 상충하는 목표 사이에서 최적의 균형점을 찾는 의사결정 과정이다.

| 목표 | 설명 |
|---|---|
| ① 무결성(Integrity) — 데이터 무결성 보존 | 성능 향상을 위해 반정규화를 수행하더라도, 논리 모델의 본질적 업무 규칙이 훼손되지 않도록 한다. 계산된 값을 컬럼으로 추가했다면, 원본 변경 시 일관성 있게 갱신되는 메커니즘(트리거·애플리케이션 로직)을 반드시 함께 설계해야 한다 — 반정규화만 하고 동기화 설계를 하지 않는 것이 가장 흔한 사고 원인 |
| ② 성능(Performance) — 성능 극대화 | 데이터 접근 경로를 최소화하고 디스크 I/O를 줄이는 것이 핵심. 성능 최적화는 추측이 아니라 예상 데이터량과 트랜잭션 부하 분석에 근거해야 함 |
| ③ 확장성(Scalability) — 확장성·유연성 확보 | 오늘의 요구사항이 내일도 유효하리라는 보장은 없다. 서브타입 변경 시 향후 새 유형 추가 가능성을 고려하고, 코드성 데이터를 별도 테이블로 분리해 신규 코드 추가 시 프로그램 수정 없이 데이터 추가만으로 대응할 수 있게 설계 |

### 2) 기본 요소 변환 규칙

| 논리 요소 | 물리 요소 | 설명 |
|---|---|---|
| 엔티티(Entity) | 테이블(Table) | 1:1이 기본이나, 수량·수직 분할(1:N)이나 반정규화 통합(N:1)도 가능 |
| 속성(Attribute) | 칼럼(Column) | 데이터 타입·길이·NULL 허용·기본값 결정. 고정길이 NOT NULL 칼럼을 앞쪽에 배치 권장 |
| 주 식별자(UID) | 기본 키(PK) | 대부분 DBMS에서 클러스터형 인덱스의 후보가 되어 데이터 접근 성능에 지대한 영향 |
| 대체 식별자 | 고유 키(UK) | Unique Constraint 또는 Unique Index로 구현되어 유일성을 시스템 차원에서 보장 |
| 관계(Relationship) | 외래 키(FK) | 논리적 관계의 선택성(Optionality)이 FK 칼럼의 NULL 허용 여부를 결정. 참조 동작 옵션 지정 가능 |

### 3) 서브타입 변환 3전략 — 통합·분할·개별

| 전략 | 방식 | 적합한 상황 | 단점 |
|---|---|---|---|
| ① 슈퍼타입 기준 통합(Single Table) | 모든 서브타입을 하나의 테이블로 합치고 구분 컬럼(타입 코드)을 추가 | 전체 통합 조회가 많고 고유 속성이 적을 때 유리 | 고유 컬럼에 NULL이 많이 발생 |
| ② 서브타입 기준 분할(Table per Subtype, '롤다운') | 각 서브타입을 별도 테이블로 만들고 공통 속성을 각각 포함 | 서브타입별 접근이 빈번하고 고유 속성이 많을 때 효과적 | 전체 조회 시 UNION이 필요해 번거로움 |
| ③ 개별 타입 기준 변환(Table per Type) | 슈퍼타입과 서브타입을 모두 개별 테이블로 만들고 1:1로 연결 | 전체 처리와 개별 처리가 모두 빈번할 때 유연 | 조인이 항상 필요 |

### 4) 데이터 타입 선택

**CHAR vs VARCHAR**: CHAR는 선언된 길이만큼 고정 공간을 사용하며, 주민번호·코드값처럼 길이가 고정된 데이터에 적합하고 파편화 방지에 유리하다. VARCHAR는 실제 데이터 길이만큼만 사용하므로 주소·이름 등에는 저장 효율적이지만, 수정으로 길이가 변하면 재배치(로우 마이그레이션)가 발생해 추가 I/O를 유발한다. 선택 기준은 저장 효율만이 아니라 수정 빈도도 함께 고려해야 한다.

> **금융 데이터 주의**: 부동소수점형(FLOAT, DOUBLE)은 이진법으로 표현하므로 정확한 십진수 계산에 오차가 발생한다. 금융 데이터에서는 절대 사용해서는 안 되며 DECIMAL/NUMERIC을 사용해야 한다.

## SECTION 4. 반정규화와 품질 검토

### 1) 반정규화는 정규화의 실패가 아니라 공학적 타협이다

반정규화란 정규화된 모델이 성능 향상과 운영 단순화를 목적으로 수행하는 의도적인 정규화 원칙 위배 행위다. 중요한 구분이 있는데, 반정규화는 정규화를 전혀 하지 않은 '비정규화'와는 다르다. 반드시 잘 정립된 정규화 모델에서 출발해서, 성능 저하가 예상되는 지점에 한정해 통제된 중복을 허용하는 최적화 전략이다. 정규화 없이 무분별하게 중복시키는 것은 그냥 잘못된 설계다.

**본질**: 정규화 모델에서는 여러 테이블에 나뉜 데이터를 조합하고 계산하는 작업이 모두 조회 시점(Read Time)에 집중된다. 반정규화는 이 부하를 **조회 시점에서 입력·수정 시점으로 이전시키는 전략**이다. 조회할 때는 준비된 데이터를 읽기만 하면 되므로 빨라지고, 대신 입력·수정·삭제 시 중복 데이터의 일관성 유지를 위한 추가 작업이 필요해 쓰기 성능은 저하된다.

| 관점 | 정규화(Normalization) | 반정규화(Denormalization) |
|---|---|---|
| 주요 목표 | 데이터 일관성·무결성 확보, 중복 최소화 | 조회(Read) 성능 향상, 쿼리 단순화 |
| 데이터 중복성 | 최소화(Minimal Redundancy) | 의도적 허용(Intentional Redundancy) |
| 데이터 무결성 | 높음(High Integrity) | 저하 위험 존재(Risk of Lower Integrity) |
| 조회 성능 | 조인이 많을 경우 저하될 수 있음 | 빠름(Faster) |
| 입력/수정/삭제 | 빠름(Faster) | 중복 데이터 관리로 저하될 수 있음 |
| 주요 사용 사례 | OLTP 시스템, 입력·수정이 빈번한 시스템 | OLAP 시스템, 데이터 웨어하우스, 보고·통계 |

**반정규화가 효과적인 4가지 상황**: 과도한 조인으로 인한 성능 저하(데이터가 여러 테이블에 분산), 대용량 데이터 처리(대량 범위 조회·집계 쿼리가 빈번), 디스크 I/O 과부하(쿼리 실행 시 I/O가 과도해 응답 시간이 길어짐), 실시간 계산 부하(SUM·COUNT·AVG 등 복잡한 계산을 조회 시점에 수행할 때).

### 2) 왜 성능이 향상되는가 — I/O와 잠금의 원리

반정규화는 논리적 변경을 넘어 물리적 수준에서 데이터 지역성과 동시성을 최적화한다.

**데이터 페이지와 버퍼 캐시**: 데이터는 8KB 또는 16KB의 고정 크기 블록 단위로 저장되며, 읽고 쓰는 것은 항상 페이지 단위로 이루어진다. 버퍼 캐시는 RAM의 일부를 할애해 디스크에서 읽어온 페이지를 임시 저장하며, 재사용 시 캐시 히트가 되어 매우 빠르고, 없으면 캐시 미스로 느린 디스크 I/O가 발생한다. **성능 향상 = 물리적 디스크 I/O 최소화 + 버퍼 캐시 히트율 극대화.**

**잠금(Locking)과 잠금 에스컬레이션**: 행 수준 잠금은 동시성이 최고지만 잠금 관리 메모리 오버헤드가 크고, 페이지 수준 잠금은 해당 페이지의 모든 행이 함께 잠기며, 테이블 수준 잠금은 가장 강력하지만 동시성을 심각하게 저해한다. 대규모 UPDATE·DELETE가 수만 개의 행을 유발하면 DBMS는 메모리 부담을 줄이려고 이를 페이지·테이블 잠금으로 자동 전환하는 **잠금 에스컬레이션**이 발생하며, 이때 테이블 전체가 잠기면 관련 없는 행을 조회하려는 모든 트랜잭션까지 대기 상태에 빠져 심각한 블로킹이 발생한다.

**반정규화의 두 가지 기술적 가치**: ① 데이터 지역성(Data Locality) 최적화 — 테이블 병합·중복 컬럼 추가는 관련 데이터를 물리적으로 같은 페이지 또는 인접 페이지에 함께 위치시키려는 시도이며, 필요한 데이터를 단 한 번의 I/O로 가져오거나 최소한의 순차 I/O로 처리할 수 있게 되어 캐시 오염(Cache Pollution)도 줄어든다. ② 잠금 부작용 회피와 동시성 보장 — 자주 갱신되는 '동적(Hot)' 칼럼(재고 수량·로그인 일시)과 거의 변하지 않는 '정적(Cold)' 칼럼(사용자 프로필·가입일)이 한 테이블에 공존하면, 대량 업데이트가 잠금 에스컬레이션을 일으켜 테이블 전체를 마비시킬 수 있다. 수직 분할로 Hot 칼럼을 분리하면 업데이트가 작은 테이블에만 국한된다 — 즉 수직 분할의 동기는 조인 감소가 아니라 **동시성 보장**이다.

### 3) 관점별 반정규화 기법 총정리

테이블 관점·컬럼 관점·관계 관점 — 문제의 특성에 맞게 신중히 선택한다.

| 관점 | 기법 | 설명 |
|---|---|---|
| 테이블 | ① 테이블 병합 | 물리적으로 분리된 두 개 이상의 테이블을 하나로 합쳐 조인을 원천 제거. 1:1 관계(사용자-사용자상세)가 가장 안전, 1:N도 자식 건수가 적고 항상 함께 조회되면 고려(슈퍼/서브타입 통합도 여기 해당) |
| | ② 테이블 분할 | 수평 분할(행 기준)과 수직 분할(칼럼 기준), 논리적 분할과 물리적 파티셔닝으로 구분. 주문을 진행중/완료로 분할, 대용량 로그를 일자 기준 Range 파티셔닝. 파티션 단위 백업·삭제 등 관리가 용이해짐 |
| | ③ 테이블 추가 | 요약/집계 테이블, 이력 테이블, 부분 테이블을 새로 만들어 부하를 분산. 일별 매출 요약 테이블은 복잡한 집계 쿼리 성능을 극적으로 향상시키고 운영계(OLTP) 부하를 줄임. 단 실시간은 아님 |
| 컬럼 | ④ 중복 컬럼 추가 | 다른 테이블의 컬럼을 중복 보관해 조인을 제거. 게시글 목록에 항상 작성자명이 필요하면 게시글 테이블에 작성자명을 중복 저장. 원본 변경 시 불일치 위험이 최대 단점 |
| | ⑤ 파생/계산 컬럼 추가 | 쿼리 시점에 수행하던 계산 결과를 미리 계산해 별도 칼럼에 저장. 주문항목에 항목총액(수량×단가), 게시글에 댓글수를 추가. 원본 변경 시 파생 칼럼도 반드시 갱신되어야 함 |
| 관계 | ⑥ 중복 관계 추가 | 여러 단계를 거쳐야 도달하는 테이블 사이에 직접 관계(FK)를 추가. 조인 경로를 단축해 조회 성능을 높이지만 관계의 중복으로 무결성 관리 부담이 늘어남 |

> 여섯 가지 기법의 공통 단점은 **데이터 불일치 위험**과 **쓰기 성능 저하**다.

### 4) 반정규화 적용 절차와 5대 핵심 원칙

**반정규화는 마지막 수단이다** — 비침습적 최적화를 먼저 모두 시도하라.

| 단계 | 내용 |
|---|---|
| 1. 성능 병목 지점 식별 | 추측이 아니라 측정으로. 느린 쿼리 로그·모니터링 도구로 실제 병목 지점을 특정 |
| 2. 실행 계획 분석 | 옵티마이저의 실행 계획을 읽어 Full Scan, 비효율적 조인 순서 등 근본 원인을 파악 |
| 3. 비침습적 최적화 우선 | 인덱스 튜닝(WHERE·JOIN 조건 컬럼), 쿼리 재작성, 커버링 인덱스 활용을 먼저 시도 — 실무는 보통 이 단계에서 해결되는 경우가 대부분 |
| 4. DBMS 기능 활용 검토 | 논리적 분할 대신 물리적 파티셔닝, 조인이 빈번한 테이블의 클러스터링 등을 검토 |
| 5. 반정규화 고려 및 기법 선택 | 위 모든 대안이 부족할 때 비로소, 문제 특성에 맞는 최소한의 기법을 선택해 적용 |

**과도한 반정규화의 함정**: 유연성 저하(특정 조회 패턴에 과최적화되어 새로운 요구사항 변화에 대응하기 어려운 경직된 구조), 의미론적 무결성 훼손(중복 칼럼은 더 이상 FK 제약의 보호를 받지 못해 모델이 표현하는 업무 의미 자체가 흐려짐), 유지보수 복잡성·인지 부하(동기화 로직·트리거·배치의 시스템 복잡도를 높이고, 여기 버그가 생기면 전체 데이터 신뢰성이 무너짐).

**반정규화 5대 핵심 원칙**: ① 정규화를 먼저 하라(Normalize First), ② 측정하고 증명하라(Measure, Don't Guess), ③ 대안을 먼저 검토하라(Consider Alternatives), ④ 일관성 유지 전략을 수립하라(Always Have a Strategy), ⑤ 모든 결정을 문서화하라(Document Everything) — 왜 이 반정규화를 했는지 기록이 없으면 후임자가 설계 오류로 오해할 수 있다.

### 5) 물리 데이터 모델 품질의 6대 기준

논리 모델의 품질 기준과 같은 6개 축이지만, 검증 대상이 **물리 개체**라는 점이 다르다.

| # | 기준 | 검증 대상 |
|---|---|---|
| 1 | 정확성(Accuracy) | 비즈니스 규칙이 물리적으로 올바르게 구현되었는가 — PK·FK·CHECK 제약조건이 논리 모델의 규칙을 정확히 강제하는가 |
| 2 | 완전성(Completeness) | 필요한 물리적 객체가 누락 없이 정의되었는가 — 테이블·칼럼·인덱스·제약조건·코멘트가 모두 갖춰졌는가 |
| 3 | 준거성(Compliance) | 표준 단어·용어·도메인과 명명 규칙을 준수하는가, 개인정보 암호화 등 법적·규제적 요건이 물리 설계에 반영되었는가 |
| 4 | 최신성(Currency) | 최신 요구사항과 논리 모델의 변경이 물리 모델에 반영되었는가, 실제 운영 DB와 모델이 일치하는가 |
| 5 | 일관성(Consistency) | 동일성 있는 설계 패턴이 적용되었는가, 유사한 상황에 서로 다른 데이터 타입·인덱스 전략이 혼재하지 않는가 |
| 6 | 활용성(Utility) | 사용 편의성·유연성·성능이 적합성을 갖췄는가, 반정규화가 정당한 근거를 갖고 문서화되었는가 |

**품질 검토 프로세스와 이해관계자 역할**: 준비 단계(체크리스트·모델 산출물을 사전 배포해 검토의 효율성과 집중도를 높임), 수행 단계(체크리스트 기반 검토 → 이슈 식별 및 토의 → 상충 요구사항에 대한 의사결정 및 협의), 후속 조치(검토 결과 보고서 작성 → 이슈 추적 및 해결 → 최종 모델 확정 및 공표).

**체크리스트 기반 상세 점검** — 테이블·칼럼 / 키·제약조건 / 성능·확장성의 3개 영역을 순차적으로 검증:

| 영역 | 점검 항목 |
|---|---|
| 테이블 | 명칭이 명명 규칙과 표준 용어를 준수하는가, 테이블 설명(Comment)이 기술되어 있는가, 서브타입 변환 전략의 선택 근거가 타당한가, 저장 공간·파라미터가 데이터량에 맞게 설정되었는가 |
| 칼럼 | 명칭이 표준 용어 사전과 일치하는가, 데이터 타입·길이가 도메인 정의를 따르는가, NULL 허용 여부가 논리 모델의 선택성과 일치하는가, 기본값과 칼럼 설명이 명시되었는가 |
| 키 | PK가 유일성·최소성·안정성을 만족하는가, UK가 대체 식별자에 대해 정의되었는가, 복합 키의 칼럼 순서가 조회 패턴을 고려했는가 |
| 참조 무결성 | FK가 모든 관계에 대해 정의되었는가, 참조 행위 옵션(CASCADE·SET NULL 등)이 업무 규칙에 부합하는가, CHECK 제약조건으로 도메인 규칙이 강제되는가 |
| 성능·확장성 | 반정규화의 정당성과 트레이드오프가 분석·문서화되었는가, 인덱스가 실제 조회 패턴에 근거해 설계되었는가, 대용량 테이블의 파티셔닝 전략이 수립되었는가 |

> **검토의 궁극적 목표**: 이론적으로 완벽한 모델이 아니라, 해당 시스템의 성능 요구와 운영 환경에 가장 적합한 모델을 만드는 것, 물리 모델이 논리 모델의 의도대로 실제로 작동하는지를 증명하는 마지막 관문이다. 모든 물리 객체는 상위 논리 모델로부터 추적 가능해야 한다.

|---|---|

| 명명 규칙 = 단어 → 용어 → 도메인 | 조직의 데이터 거버넌스 성숙도를 보여주는 가시적 지표 |
| 변환 = 엔티티→테이블, 식별자→키, 관계→FK | 서브타입은 통합·분할·개별 3가지 전략 |
| 반정규화 = 부하를 조회에서 입력으로 전이 | 언제나 마지막 수단, 성능·무결성·확장성의 트레이드오프를 문서화 |
| 품질 6기준 = 정완준 최일활 | 논리와 동일한 축이지만 검증 대상이 물리 개체 |

**자주 하는 실수 TOP 3**

1. 정규화 없이 곧바로 중복을 허용한다 → 반정규화가 아니라 잘못된 설계다.
2. 높은 CPU 사용률을 보고 곧바로 CPU 증설부터 고려한다 → 근본 원인은 인덱스 부재일 수 있다.
3. 금융 데이터의 금액 컬럼에 FLOAT을 사용한다 → DECIMAL/NUMERIC을 써야 한다.

### 과목 4 종합 — 개념에서 물리까지, 4개 챕터의 흐름

비즈니스(Why) → 구조(What) → 성능(How)으로 이어지는 시스템 아키텍처의 뼈대다.

| CH 1. 데이터 모델링 이해 | CH 2. 개념 데이터 모델링 | CH 3. 논리 데이터 모델링 | CH 4. 물리 데이터 모델링 |
|---|---|---|---|
| 모델링 = 추상화·단순화·명확화 | 주제 영역 정의(MECE·데이터 본질) | 속성·도메인 정의 | 명명 규칙·하드웨어 자원 분석 |
| 3단계: 개념 → 논리 → 물리 | 엔티티 4단계 생명주기·4기둥 | 식별자 확정·정규화(1~3NF) | 논리-물리 변환(테이블·칼럼·키·FK) |
| ERM 4대 요소·IE/바커 표기법 | 관계 정의(차수·선택성·관계명) | M:N 해소·이력관리·품질검토 | 반정규화·물리 모델 품질검토 |

> **세 단계를 관통하는 하나의 문장**: 개념 모델은 기술을 배제하고 비즈니스의 핵심 개념을 정의하며(비즈니스, Why), 논리 모델은 비즈니스 정보의 모든 구조와 규칙을 명확하고 상세하게 표현하고(구조, What), 물리 모델은 이 논리 구조를 특정 DBMS에 맞춰 성능과 효율을 최적화한다(성능, How). 논리→물리는 단순 변환(Conversion)이 아니라, 이론적 이상과 현실적 제약 사이의 절충을 통해 최적의 해를 찾는 변형(Transformation)이다. 이 3단계는 비즈니스에서 시작해 구조를 거쳐 성능으로 이어지는, 시스템 전체의 안정성과 유연성을 결정하는 핵심 아키텍처 뼈대다.

## 자기 점검 Q&A

**Q1. 물리 데이터 모델링이 왜 "다차원 최적화 문제"인가?**
A. 성능·저장 공간·개발 편의성·확장성 등 여러 목표가 서로 상충하는 트레이드오프 관계에 있기 때문이다. 예를 들어 성능을 위해 반정규화하면 무결성이 저해되고, 저장 공간을 위해 타입을 작게 잡으면 확장성 문제가 생길 수 있어, 우선순위를 파악해 균형점을 찾는 의사결정이 필요하다.

**Q2. 논리 모델과 물리 모델의 핵심 목표·기술 종속성 차이는?**
A. 논리 모델의 핵심 목표는 정합성·일관성이고 기술 독립적(Platform-Independent)이다. 물리 모델의 핵심 목표는 성능·저장 효율이고 특정 DBMS·인프라에 종속적(Platform-Dependent)이다.

**Q3. 명명 규칙의 3계층은 무엇이며, 도메인이 가장 강력한 이유는?**
A. 표준 단어 → 표준 용어 → 도메인 순으로 구성된다. 도메인은 속성의 데이터 타입·길이를 표준화해, 조인 시 타입 불일치로 인한 성능 저하를 원천 방지하는 구조적 일관성을 강제하기 때문에 가장 강력하다.

**Q4. 높은 CPU 사용률을 볼 때 왜 곧바로 CPU 증설을 고려해서는 안 되는가?**
A. 높은 CPU 사용률은 원인이 아니라 증상일 수 있기 때문이다. 부적절한 인덱스로 인한 비효율적 실행 계획이 불필요한 페이지를 대량으로 읽어 필터링·정렬하는 과정에서 CPU를 과도하게 소모시키는 경우가 많으며, 근본 원인은 인덱스 부재일 수 있다.

**Q5. 서브타입 변환의 3가지 전략과 각각의 적합한 상황은?**
A. 슈퍼타입 기준 통합(전체 조회가 많고 고유 속성이 적을 때), 서브타입 기준 분할(서브타입별 접근이 빈번하고 고유 속성이 많을 때), 개별 타입 기준 변환(전체·개별 처리가 모두 빈번할 때).

**Q6. 반정규화가 성능을 향상시키는 근본 원리는?**
A. 반정규화는 계산과 조합의 부하를 조회 시점에서 입력·수정 시점으로 이전시킨다. 물리적으로는 관련 데이터를 같은 페이지에 위치시켜(데이터 지역성) 디스크 I/O를 최소화하고 버퍼 캐시 히트율을 높이며, 동적/정적 칼럼을 분리해 잠금 에스컬레이션에 의한 동시성 저하를 회피한다.

**Q7. 반정규화 적용 절차 5단계 중 4단계까지의 공통점은?**
A. 1~4단계(병목 식별 → 실행계획 분석 → 비침습적 최적화 → DBMS 기능 활용)는 모두 반정규화 없이 문제를 해결하려는 시도이며, 반정규화(5단계)는 이 모든 대안이 부족할 때 비로소 고려하는 마지막 수단이다.

## 한 줄 요약

물리 데이터 모델링은 논리 모델을 특정 DBMS·하드웨어 제약 위에서 무결성·성능·확장성의 균형점을 찾아 변형하는 과정이며, 명명 규칙과 하드웨어 지표에 근거한 설계, 신중한 논리-물리 변환, 그리고 마지막 수단으로서의 근거 있는 반정규화를 통해 완성된다.

| 데이터 지역성(Data Locality) | 관련 데이터를 물리적으로 같은 페이지에 위치시켜 I/O를 최소화하는 전략 |
